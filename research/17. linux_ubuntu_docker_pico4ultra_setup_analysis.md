# Ubuntu 24.04 + Docker 환경에서의 PICO 4 Ultra 셋업 분석

> **날짜**: 2026-03-22
> **관련 문서**: `16. quest3s_to_pico4ultra_migration_guide.md`
> **목적**: Linux 환경에서 PICO Connect/SteamVR 없이 PICO 4 Ultra + MT + UDCAP를 구동하는 방법 분석

---

## Executive Summary

| 문제 | 분석 결과 |
|------|----------|
| PICO Connect → Windows 전용 | **불요** - CloudXR 경로는 이미 Linux에서 동작 중 |
| SteamVR → Windows 중심 | **불요** - XRoboToolkit이 SteamVR 없이 직접 데이터 전달 |
| UDCAP 드라이버 → Windows 전용 | **우회 가능** - USB 동글 + OSC/VMC 프로토콜로 Linux에서 수신 |
| XRoboToolkit PC Service → Linux | **네이티브 지원** - Ubuntu 22.04/24.04 공식 .deb 패키지 |

### 핵심 결론

```
┌─────────────────────────────────────────────────────────────────┐
│ 현재 환경에서 PICO 4 Ultra 셋업은 100% 가능하다.                   │
│                                                                 │
│ 이유:                                                           │
│ 1. CloudXR Runtime은 이미 Docker에서 Linux로 동작 중               │
│ 2. XRoboToolkit PC Service는 Ubuntu 22.04/24.04 네이티브 지원     │
│ 3. PICO → PC 데이터 전송은 WiFi (JSON over TCP) → OS 무관         │
│ 4. UDCAP 글러브는 2.4GHz USB 동글 → OS 수준 HID 장치로 인식 가능   │
│                                                                 │
│ PICO Connect / SteamVR는 "VR 게임 스트리밍"용이며,                 │
│ 로봇 텔레오퍼레이션에는 전혀 필요하지 않다.                          │
└─────────────────────────────────────────────────────────────────┘
```

## 2. "PICO Connect + SteamVR 필요" 오해 분석

### 2.1 왜 이전 가이드에서 PICO Connect를 언급했나

문서 16에서 PICO Connect/SteamVR를 언급한 이유:
1. **UDCAP 글러브**: SteamVR 드라이버로 동작 → SteamVR 필요 → PICO Connect로 SteamVR 접속
2. **일반 VR 용도**: VR 게임/앱 스트리밍에는 PICO Connect 필수

그러나 **UST 프로젝트의 목적은 VR 게임이 아니라 로봇 텔레오퍼레이션**이다.

### 2.2 실제로 필요한 것 vs 필요 없는 것

| 소프트웨어 | 용도 | UST 프로젝트에서 필요? | 대안 |
|-----------|------|---------------------|------|
| **PICO Connect** | VR 게임 PC 스트리밍 | **불필요** | CloudXR.js (이미 동작 중) |
| **SteamVR (Windows)** | VR 게임 런타임 | **불필요** | XRoboToolkit (Linux 네이티브) |
| **SteamVR (Linux)** | Linux VR 런타임 | **불필요** | CloudXR Runtime (이미 동작 중) |
| **UDCAP Windows 드라이버** | SteamVR 플러그인 | **우회 가능** | UDCAP SDK 직접 통신 또는 별도 경량 Windows VM |
| **XRoboToolkit PC Service** | Body Tracking 수신 | **필요 (Linux 지원!)** | Ubuntu .deb 패키지 직접 설치 |

### 3.2 이 아키텍처의 핵심 포인트

1. **CloudXR 경로**: 이미 Linux Docker에서 동작 중 → **변경 없음**
2. **XRoboToolkit**: Ubuntu .deb 패키지로 **호스트에서** 직접 실행 → SteamVR/PICO Connect 불요
3. **UDCAP**: USB 동글은 OS 수준에서 HID/시리얼 장치로 인식 → Linux에서 접근 가능
4. **PICO Connect 완전 불필요**: CloudXR.js가 브라우저 기반이므로 PICO Connect 없이 동작

## 4. XRoboToolkit PC Service 셋업 (Ubuntu)

### 4.1 설치

```bash
# Ubuntu 호스트에서 (Docker 외부):

# 1. .deb 패키지 다운로드
# GitHub: https://github.com/XR-Robotics/XRoboToolkit-PC-Service/releases
wget https://github.com/XR-Robotics/XRoboToolkit-PC-Service/releases/download/v1.0.0/XRoboToolkit_PC_Service_1.0.0_ubuntu_22.04_amd64.deb

# 2. 설치
sudo dpkg -i XRoboToolkit_PC_Service_1.0.0_ubuntu_22.04_amd64.deb
# 의존성 문제 시:
sudo apt-get install -f

# 3. 실행 확인
xrobotoolkit-pc-service --version
```

### 4.2 Python Pybind 패키지 설치

```bash
# XRoboToolkit Pybind (Python에서 직접 트래킹 데이터 접근)
pip install xrobotoolkit-pybind  # 또는 소스 빌드

# 사용 예시:
python3 -c "
from xrobotoolkit import PCService
service = PCService()
service.start()
# PICO에서 연결되면 콜백으로 데이터 수신
"
```

### 4.3 PICO 헤드셋 ↔ PC Service 연결

```
1. Ubuntu 호스트에서 XRoboToolkit PC Service 실행
2. PICO 4 Ultra에서 XRoboToolkit App 실행
3. PC Service IP 입력 (호스트의 LAN IP, 예: 192.168.0.117)
4. 상태: "WORKING" 확인
5. Motion Tracker 데이터가 PC Service로 스트리밍 시작
```

### 4.4 Docker 컨테이너로 데이터 전달

XRoboToolkit PC Service는 **호스트**에서 실행하지만, Isaac Lab은 **Docker 컨테이너** 내에서 실행된다. 데이터를 컨테이너로 전달하는 방법:

```
방법 A: 네트워크 포워딩 (추천)
─────────────────────────────────
호스트: XRoboToolkit PC Service → localhost:PORT
Docker: --network=host 또는 포트 매핑으로 접근

현재 Docker 구성이 이미 network_mode: host를 사용하므로,
컨테이너 내에서 localhost로 PC Service에 접근 가능.

방법 B: 공유 메모리 / Unix Socket
─────────────────────────────────
호스트: PC Service → /tmp/xrobotoolkit.sock
Docker: -v /tmp/xrobotoolkit.sock:/tmp/xrobotoolkit.sock

방법 C: Pybind를 호스트에서 실행하고 TCP로 전달
─────────────────────────────────────────────────
호스트: Python 스크립트 (Pybind) → 데이터 가공 → TCP/ZeroMQ → Docker
Docker: Isaac Lab에서 TCP 수신
```

> **추천**: 방법 A (network_mode: host). 현재 Docker Compose가 이미 `network_mode: host`를 사용하고 있으므로 추가 설정 없이 동작할 가능성 높음.

## 5. UDCAP VR Gloves Linux 연동 분석

### 5.1 문제 정의

UDCAP VR Gloves의 공식 소프트웨어/드라이버는 **Windows 전용**이다:
- UDCAP Software (Windows .exe)
- SteamVR 드라이버 (Windows DLL)
- 캘리브레이션 도구 (Windows GUI)

### 5.2 해결 방안 비교

| 방안 | 복잡도 | 실용성 | 설명 |
|------|--------|--------|------|
| **A: UDCAP SDK 직접 통신** | ★★★☆☆ | ★★★★☆ | USB 동글 → Linux HID → 커스텀 파서 |
| **B: OSC/VMC 프로토콜 수신** | ★★☆☆☆ | ★★★★★ | UDCAP SW가 OSC로 출력 → Python 수신 |
| **C: 경량 Windows VM** | ★★★☆☆ | ★★★☆☆ | KVM/QEMU + USB 패스스루 |
| **D: Windows 미니PC 별도** | ★☆☆☆☆ | ★★★★★ | 별도 소형 PC에서 UDCAP 실행 → 네트워크 전달 |
| **E: XRoboToolkit 핸드 트래킹만 사용** | ★☆☆☆☆ | ★★★★★ | UDCAP 없이 PICO 카메라 핸드 트래킹 |

#### 방안 A: UDCAP SDK 직접 통신 (기술적 우회)

```
UDCAP 글러브 → 2.4GHz USB 동글 → Ubuntu 호스트
                                      │
                                      ▼
                            /dev/ttyUSBx 또는 /dev/hidraw*
                                      │
                                      ▼
                            커스텀 Python 파서
                            (UDCAP SDK가 MIT 라이선스 오픈소스)
                                      │
                                      ▼
                            21 관절각/손 → Isaac Lab
```

**실현 가능성**:
- UDCAP Driver가 [GitHub에서 MIT 라이선스로 공개](https://github.com/Udexreal/Udcap-Driver)
- USB 동글은 2.4GHz 무선 → Linux에서 시리얼/HID 장치로 인식될 가능성
- 프로토콜 리버스 엔지니어링 또는 소스 코드 참조로 Linux 포팅 가능
- **리스크**: 프로토콜 문서가 공개되어 있지 않을 수 있음

#### 방안 B: OSC/VMC 네트워크 수신 (추천)

```
┌─────── Windows 환경 (VM 또는 별도 PC) ───────┐
│  UDCAP Software (Windows)                     │
│  └── 글러브 데이터 수신                         │
│       └── OSC 프로토콜로 네트워크 전송           │
│            UDP → 192.168.x.x:9000              │
└───────────────────────────────────────────────┘
                    │ WiFi/Ethernet
                    ▼
┌─────── Ubuntu 호스트 ────────────────────────┐
│  Python OSC 수신기                            │
│  (python-osc 라이브러리)                      │
│  └── 21 관절각/손 → Isaac Lab (Docker)        │
└───────────────────────────────────────────────┘
```

UDCAP Software는 **VMC (Virtual Motion Capture)** 및 **OSC (Open Sound Control)** 프로토콜 출력을 지원한다. OSC는 UDP 기반의 간단한 프로토콜로:
- **Linux에서 수신이 매우 간단** (`python-osc` 라이브러리 사용)
- 네트워크를 통해 어디서든 수신 가능
- Windows에서 UDCAP Software만 실행하면 됨

```python
# Python OSC 수신 예시
from pythonosc import dispatcher, osc_server

def finger_handler(address, *args):
    """UDCAP 핑거 데이터 수신 콜백"""
    joint_angles = list(args)  # 21개 관절각
    print(f"Hand data: {address} -> {joint_angles}")
    # Isaac Lab으로 전달

disp = dispatcher.Dispatcher()
disp.map("/udcap/left/*", finger_handler)
disp.map("/udcap/right/*", finger_handler)

server = osc_server.ThreadingOSCUDPServer(("0.0.0.0", 9000), disp)
server.serve_forever()
```

#### 방안 C: 경량 Windows VM (KVM/QEMU)

```bash
# Ubuntu 호스트에서 KVM Windows VM 실행
# USB 패스스루로 UDCAP 동글을 VM에 전달

sudo apt install qemu-kvm virt-manager
# Windows 10/11 VM 생성
# USB 패스스루: UDCAP 2.4GHz 동글 → VM
# VM 내에서: UDCAP Software 실행 → OSC 출력 → 호스트로 네트워크 전달
```

**장점**: 완전한 UDCAP 호환성 (캘리브레이션 포함)
**단점**: VM 리소스 사용, 셋업 복잡

#### 방안 D: 별도 Windows 미니PC (가장 간단)

```
미니PC ($200~$300, Windows 11)
├── UDCAP USB 동글 연결
├── UDCAP Software 실행
├── OSC/VMC → 네트워크 전송
└── 캘리브레이션 UI 사용

Ubuntu 호스트
├── Python OSC 수신
└── Isaac Lab → 핑거 데이터 활용
```

**장점**: 가장 간단하고 안정적, 간섭 없음
**단점**: 추가 PC 비용

#### 방안 E: UDCAP 없이 XRoboToolkit 핸드 트래킹만 사용 (최소 구성)

```
PICO 4 Ultra 카메라 핸드 트래킹
├── 26 관절 포인트/손 (4 엄지 + 5x4 손가락 + 손바닥 + 손목)
├── XRoboToolkit App이 자동 전송
└── XRoboToolkit PC Service → Python → Isaac Lab
```

**장점**: 추가 하드웨어/소프트웨어 완전 불요, Linux 100% 네이티브
**단점**: 카메라 기반 → FOV 밖 손 추적 불가, 정밀도 UDCAP 대비 낮음
**적합한 경우**: 초기 프로토타이핑, 그리퍼 open/close 수준의 제어

### 5.3 UDCAP 방안 추천

```
★ Phase 1 (즉시): 방안 E - XRoboToolkit 핸드 트래킹만 사용
  → UDCAP 없이 시작, Full-Body + 기본 핸드 트래킹으로 검증
  → Linux 환경에서 추가 설정 불요

★ Phase 2 (UDCAP 도착 후): 방안 B - OSC 네트워크 수신
  → Windows 환경 필요하지만 가벼운 VM 또는 별도 PC로 해결
  → UDCAP Software에서 OSC 출력 → Ubuntu에서 Python 수신
  → 가장 안정적이고 검증 가능한 경로

★ Phase 3 (고급): 방안 A - UDCAP 오픈소스 드라이버 Linux 포팅
  → MIT 라이선스 소스코드 활용
  → 완전 Linux 네이티브 솔루션
```

## 8. PICO 핸드 트래킹 vs UDCAP 비교 (Linux 환경)

XRoboToolkit이 PICO의 카메라 기반 핸드 트래킹 데이터도 전송하므로, UDCAP 없이도 **기본적인 핸드 트래킹은 가능**하다.

| 항목 | PICO 핸드 트래킹 (XRoboToolkit) | UDCAP 글러브 |
|------|-------------------------------|-------------|
| **관절 수** | 26 포인트/손 (4+5x4+2) | 21 관절각/손 |
| **정밀도** | ★★★☆☆ (카메라 AI 추론) | ★★★★★ (elastic 센서 직접 측정) |
| **FOV 제한** | 카메라 시야 내에서만 | 제한 없음 (센서 직접 측정) |
| **occlusion** | 손이 겹치면 추적 실패 | 영향 없음 |
| **Linux 호환** | ★★★★★ (네이티브) | ★★☆☆☆ (Windows 경유 필요) |
| **추가 비용** | $0 | $559~$699 + Windows 환경 |
| **셋업 복잡도** | ★☆☆☆☆ | ★★★☆☆ |
| **Dexterous Manipulation** | 가능 (제한적) | 가능 (고정밀) |

### 권장 전략

```
Phase 1 (즉시 시작):
  PICO 핸드 트래킹 (XRoboToolkit 경유) → 26 관절 포인트/손
  → Linux 네이티브, 추가 설정 없음
  → 그리퍼 제어 + 기본 Dexterous Manipulation 테스트

Phase 2 (정밀도 필요 시):
  UDCAP 글러브 → OSC → Linux 수신
  → Windows VM 또는 미니PC 추가
  → INSPIRE 5-finger hand 정밀 텔레오퍼레이션
```

## 9. Docker 컨테이너 내부에서의 데이터 접근

### 9.1 현재 Docker 네트워크 구성

```bash
# docker-compose 확인
# 현재 CloudXR Runtime은 network_mode: host 사용
# → 컨테이너 내에서 localhost = 호스트
```

### 9.2 XRoboToolkit 데이터를 Docker로 전달

```
방법 1: network_mode: host (현재 구성)
───────────────────────────────────────
호스트: XRoboToolkit PC Service (포트 X)
Docker (host 네트워크): localhost:X로 접근 가능
→ 추가 설정 불필요

방법 2: Docker 볼륨 마운트
───────────────────────────────────────
호스트: XRoboToolkit → /tmp/xrt_data.json (파일 기반)
Docker: -v /tmp/xrt_data.json:/tmp/xrt_data.json
→ 공유 파일로 데이터 전달 (지연 주의)

방법 3: TCP/ZeroMQ 브릿지
───────────────────────────────────────
호스트: Python 브릿지 (XRoboToolkit Pybind → ZeroMQ 퍼블리셔)
Docker: ZeroMQ 서브스크라이버 → Isaac Lab
→ 가장 유연하지만 추가 코드 필요
```

### 9.3 추천 통합 코드 구조

```python
# 호스트에서 실행: xrt_bridge.py
"""XRoboToolkit → Isaac Lab 데이터 브릿지 (호스트에서 실행)"""
import zmq
from xrobotoolkit import PCService

service = PCService()
service.start()

context = zmq.Context()
publisher = context.socket(zmq.PUB)
publisher.bind("tcp://*:5555")

while True:
    data = service.get_tracking_data()
    # JSON 직렬화하여 ZeroMQ로 발행
    publisher.send_json({
        "head": data.head_pose,
        "body": data.body_joints,      # 24 스켈레톤 포인트
        "left_hand": data.left_hand,    # 26 관절/손
        "right_hand": data.right_hand,  # 26 관절/손
        "controllers": data.controllers,
    })
```

```python
# Docker 컨테이너 내에서: Isaac Lab 텔레오퍼레이션 디바이스
"""XRoboToolkit 데이터 수신기 (Docker 내 Isaac Lab)"""
import zmq

class XRoboToolkitDevice:
    """XRoboToolkit 기반 Full-Body 텔레오퍼레이션 디바이스"""

    def __init__(self, host_ip="localhost", port=5555):
        self.context = zmq.Context()
        self.subscriber = self.context.socket(zmq.SUB)
        self.subscriber.connect(f"tcp://{host_ip}:{port}")
        self.subscriber.setsockopt_string(zmq.SUBSCRIBE, "")

    def advance(self):
        data = self.subscriber.recv_json(flags=zmq.NOBLOCK)
        return data  # head, body, hands, controllers
```

## 11. FAQ

### Q: PICO Connect를 설치해야 하나?
**A: 불필요.** PICO Connect는 PC VR 게임 스트리밍용이다. UST 프로젝트에서는:
- VR 렌더링: CloudXR.js (브라우저 기반) → 이미 Linux에서 동작
- Body Tracking: XRoboToolkit (Linux 네이티브) → PICO Connect 불요
- 손가락: UDCAP (별도 경로) 또는 PICO 핸드 트래킹 (XRoboToolkit 경유)

### Q: SteamVR를 Linux에 설치해야 하나?
**A: 불필요.** SteamVR는 VR 게임 런타임이다. UST 프로젝트에서는:
- VR 런타임: CloudXR Runtime (Docker) → SteamVR 대체
- OpenXR: CloudXR가 OpenXR 세션 직접 관리

### Q: UDCAP 글러브를 쓰려면 Windows가 반드시 필요한가?
**A: 현재는 예.** UDCAP Software(캘리브레이션, 드라이버)는 Windows 전용이다. 그러나:
- OSC 프로토콜로 데이터를 네트워크 전송하면 Linux에서 수신 가능
- 가벼운 KVM VM 또는 $200 미니PC로 해결 가능
- 대안: PICO 핸드 트래킹 (XRoboToolkit)은 Windows 불요

### Q: Docker 내에서 XRoboToolkit 데이터에 접근 가능한가?
**A: 가능.** `network_mode: host`이면 호스트의 모든 포트에 접근 가능. 또는 ZeroMQ/TCP 브릿지를 사용하여 명시적으로 데이터 전달.

### Q: PICO Motion Tracker는 Linux에서 직접 페어링하나?
**A: 아니오.** Motion Tracker는 **PICO 헤드셋과 직접 페어링**한다 (2.4GHz). Linux PC와는 무관. XRoboToolkit App이 트래커 데이터를 수집하여 WiFi로 PC에 전송.
