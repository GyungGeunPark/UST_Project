## 0. 1쪽 요약 (TL;DR)

### 핵심 깨달음 — 32번 문서의 가정이 멀티태스킹 제약 하에 무너진다

직전 §32 가이드는 "PICO 핸드 트래킹을 손가락 source로 추가하고 UDCAP는 fallback 으로 유지한다" 는 비단순 **추가 통합** 시나리오로 설계됐다. 그러나 사용자가 명시한 **PICO OS 5.15.4 단일 immersive 앱 제약** 을 적용하면 다음 세 가지가 **물리적으로 동시 성립하지 않는다**:

```
┌─ Virtual Desktop App  (현재 VR 렌더링 + SteamVR 연결고리)
│
├─ XRoboToolkit App     (PICO 핸드 트래킹 + Body/MT/Head 데이터 송출)
│
└─ PICO Connect         (대안 PCVR 스트리밍)

→ 셋 중 하나만 PICO 헤드셋 포그라운드에 떠 있을 수 있음
→ 사용자가 핸드 트래킹을 켜는 순간 VD 가 죽음 → SteamVR 트래커/HMD/컨트롤러 전부 끊김
→ ust_fourier_260421의 vr_sampler.py / forearm tracker / HMD pose / waist tracker 모두 동시 손실
```

### 한 줄 결론

> **현재 UDCAP 기반 코드를 더 보강하는 쪽이 ROI 우위이며, 손가락 정밀도 ceiling 이 사용자 작업의 한계라면 UDCAP **하드웨어 자체를 MANUS Quantum 등으로 교체**하는 것이 단계적 정답이다.**
>
> PICO 핸드트래킹 전환은 **단순 손가락 source 교체가 아니라 전체 트래킹+렌더링 스택 재작성** 이다 (코드 ~3000+ 라인 + Pose 계열 모두 재플럼빙 + Isaac Sim 뷰가 모니터로 강제 됨).

### 권장 의사결정 순위

| 순위 | 경로 | 작업량 | 정밀도 ceiling | 위험 | 추천 시점 |
|---|---|---|---|---|---|
| **1순위** | 🟢 UDCAP 코드 보강 + 글러브 캘리브 / 페어링 점검 | 1 ~ 3일 | 글러브 H/W 한계 | 낮음 | **지금 즉시**, 모든 sub-cm 정밀이 필요 없는 작업 |
| 2순위 | 🟡 UDCAP H/W 단위 교체/수리 (좌측 글러브 frozen finger 고장 가능성 검증) | 0.5일 + 부품 비용 | 글러브 H/W spec | 낮음 | 이번 글러브 페어가 결함품일 가능성 진단 후 |
| 3순위 | 🟡 MANUS Quantum 등 상용 글러브로 업그레이드 ($5,000) | 2 ~ 3주 + $5K | 서브밀리미터 (mocap급) | 중 — SteamVR 통합 검증 필요 | 정밀도 ceiling 이 사용자 작업의 진짜 병목임이 입증됐을 때 |
| 4순위 | 🔴 PICO XRT 전체 스택 전환 (VD 포기 + 모니터뷰 강제) | 2 ~ 3주 | 카메라 한계 + 60Hz | 높음 — 전 파이프라인 재작성 | UDCAP+상용글러브 모두 막혔을 때 마지막 수단 |
| 5순위 | 🔴 PICO XRT 전환 + 헤드셋 비디오 스트리밍 자체 구현 | 4 ~ 6주 | 위 + 추가 인코더 | 매우 높음 | 현실적 비추천 (NVIDIA GR00T 외 검증된 사례 거의 없음) |

핵심 메시지: **9.18까지 누적된 fix는 코드의 실수가 아니라 글러브 신호의 한계와 싸운 흔적**이다. PICO 카메라로 이전한다고 해서 신호가 정확해진다는 보장이 없고, 다만 **다른 종류의 한계**(occlusion, 60Hz, 광량)와 싸우게 된다.

## 1. 멀티태스킹 제약이 질문 자체를 다시 정의한다

### 1.1 사용자 명시 제약 — 다시 강조

> **PICO 는 멀티태스킹이 안된다. 즉 XRoboToolkit 이나 Virtual Desktop 앱이나 PICO Connect 등 하나의 앱밖에 실행이 안된다.**

이 한 문장이 §32 마이그레이션 가이드의 모든 가정을 무효화한다:

| §32 가정 | 실제 (멀티태스킹 제약 적용) |
|---|---|
| "PICO 손가락은 source 추가만 하면 된다" | ❌ — PICO XRT 켜는 순간 VD 가 죽고 SteamVR 트래킹 0 |
| "UDCAP fallback 은 그대로 살아있다" | ❌ — UDCAP 의 SteamVR Skeletal/finger-curl 경로는 VD가 살아있어야 동작.  단, **VMC OSC over UDP** 채널만은 헤드셋 OS 와 무관하게 살아남음 |
| "head/waist estimator 별개" | ❌ — 두 estimator 모두 SteamVR 의 HMD/hips tracker pose 를 입력으로 받음.  VD 죽으면 둘 다 죽음 |
| "viewport HMD-follow 그대로" | ❌ — `_update_head_follow()` 가 SteamVR 의 HMD pose 를 이용 |
| "renderer/Isaac Sim 뷰는 변경 없음" | ❌ — VD 죽으면 헤드셋 안에 Isaac Sim 화면이 안 나옴.  XRT 의 자체 비디오 스트리밍을 별도 구현하거나 모니터뷰로 후퇴 |

### 1.2 헤드셋 측 제약의 구조

[research §26.2.2 그림 재인용] PICO OS 5.x 의 멀티태스킹은 "2D 패노라믹 윈도우 위에 떠 있는 앱들" 만 동시 가능하다.  Fully-immersive OpenXR PRIMARY 세션은 한 슬롯뿐이며, 다음이 모두 그 슬롯을 요구한다:

- Virtual Desktop App (PCVR 스트리밍)
- PICO Connect / Pico Link (PCVR 스트리밍 — VDXR fork)
- XRoboToolkit Unity Client (PRIMARY VR intent, Unity 2022.3.16f1 + PICO Integration SDK 3.1.2)
- CloudXR.js 브라우저 WebXR

→ **이 중 정확히 하나** 가 켜질 수 있다.

### 1.3 PICO 측 단일 슬롯의 의미를 PC 쪽에 매핑

```
[PICO 헤드셋 — 한 번에 하나]              [PC 측에서 받는 것]
─────────────────────────────────────    ──────────────────────────────────────
Virtual Desktop App 켜짐  ────────────▶  SteamVR (HMD/컨트롤러/Pico MT 5개 →
                                          oculus_virtualdesktop driver →
                                          pyopenvr 가 보는 것)
                                         + UDCAP VMC OSC (네트워크 별도 경로)
                                         + UDCAP SteamVR Skeletal/Index curl
─────────────────────────────────────    ──────────────────────────────────────
XRoboToolkit App 켜짐  ──────────────▶  XRoboToolkit-PC-Service gRPC →
                                          ConsoleDemo stdout JSON →
                                          { Head, Controller, Hand 26j×2,
                                            Body 24j, Motion (MT 독립) }
                                         + UDCAP VMC OSC (네트워크 별도 경로)
                                         (UDCAP SteamVR 경로는 끊김 —
                                          SteamVR 자체에 헤드셋이 없음)
─────────────────────────────────────    ──────────────────────────────────────
PICO Connect 켜짐  ──────────────────▶  SteamVR via PicoStreamingXR
                                          (oculus_virtualdesktop 와 비슷한
                                          OpenVR 드라이버 자리)
                                         (트래커 지원 한계 있음 — research §14)
─────────────────────────────────────    ──────────────────────────────────────
모두 꺼짐  ──────────────────────────▶  PC 가 받는 헤드셋/트래킹 데이터 0
                                         (UDCAP VMC 만 존재)
```

핵심: **사용자가 어떤 PICO 앱을 켜느냐가 PC 측에서 받을 수 있는 신호의 종류를 완전히 결정한다**.  손가락만 보고 결정할 일이 아니라 **전체 트래킹 입력 행렬** 을 보고 결정해야 한다.

## 2. UDCAP 보강 경로 분석

### 2.1 현재 시스템 (확정 사실)

```
[Pico 4 Ultra (VD App 포그라운드)]      [Windows 메인 PC]                       [Windows 미니 PC]
 ┌───────────────────────────┐           ┌─────────────────────────────────┐    ┌─────────────┐
 │ VD App                    │──VR렌더 스트림 H264◀── Isaac Sim 뷰포트       │    │ UDCAP SW    │
 │ + 5 Pico MT (VRChat 10세그)│            │   ↑                               │ ◀VMC UDP 39539─┘
 │ + HMD pose                │            │   ↓                               │
 │ + 2 컨트롤러               │           │  pyopenvr (vr_sampler.py 120Hz)   │
 └──────SteamVR over VD─────┘           │   ↓                               │
                                          │  GR1T2FourierUDCAPDevice          │
                                          │   ↓                               │
                                          │  pack_22d → 36D action → env.step│
                                          └─────────────────────────────────┘
```

이 시스템은 **이미 동작한다**.  UDCAP 글러브의 손가락 정확도만이 9.10 ~ 9.18 동안 추가 fix 의 표적이 되어 왔다.  9.18 이후 잔존 문제:

- L 손 일부 손가락 (특히 mid/ring/pinky) Δrange < 0.05 rad — 9.18 진단 메시지가 자동 보고
- 좌·우 비대칭 (L 28%/R 56% 같은 패턴 관측됨)
- thumb pitch/yaw 매칭 부족

### 2.2 UDCAP 글러브 자체 사양 (외부 자료)

| 항목 | UDCAP 공식 스펙 | 출처 |
|---|---|---|
| 센서 수 | 12 elastic 센서 (per glove) | UDEXREAL 공식 |
| 추적 관절 | 15 손가락 관절 → 21 joint angles | UDEXREAL 공식 |
| 각도 해상도 | 0.01° (claim) | UDEXREAL 공식 |
| 통신 | 2.4G USB 동글, 120Hz, <10ms 지연 | UDEXREAL 공식 |
| 무게 | 45g | UDEXREAL 공식 |
| 추적 영역 (위치) | **없음** (글러브는 손가락 굽힘만, 위치는 외부 트래커 필요) | research §14 |

→ **이론상** UDCAP 는 PICO 카메라보다 손가락 굽힘 측정이 정밀해야 한다 (서브-도 해상도 vs 카메라).  현실의 frozen finger / 비대칭은 **개별 글러브 페어의 캘리브/페어링/엘라스틱 센서 wear** 에서 비롯될 가능성이 높다.

### 2.3 이미 적용된 9.10 ~ 9.18 fix 요약 (memory.md 발췌)

| 버전 | 핵심 변화 |
|---|---|
| 9.10 | UDCAP VMC bone REST POSE 첫 N프레임 평균 zero-cal 도입 (절대값에 흡수되던 motion 회복) |
| 9.11 | finger_proximal_scale CLI 튜닝 추가 |
| 9.12 | tanh 진폭화 (좌·우 비대칭 보정 — saturation 회피) |
| 9.13 | VMC port=39539 always-on default (SteamVR Skeletal 0인 환경 자동 fallthrough) |
| 9.14 | per-bone REST POSE 캘리브 + thumb yaw midpoint 진단 |
| 9.15 | thumb yaw piecewise linear 매핑 (yaw=0 → 정확히 0) |
| 9.16 | wrist tracker 우선 (controller 우선 default 변경) + finger-scale auto-advice |
| 9.17 | 5-finger 진단 로그 / HMD camera robot head anchor |
| 9.18 | HeadEstimator + viewport camera 제거 / rest cal 30→10 frame / stuck-finger 진단 |

→ **소프트웨어 측 가능한 거의 모든 보정이 이미 들어가 있다**. 지금 더 시도할 수 있는 추가 코드 보강은 한정적이다.

### 2.4 UDCAP 추가 보강 가능성 — 코드 측

남은 코드 leverage 는 다음 범주뿐:

#### 2.4.1 페어/유닛 검사 도구 (1일)
- 새 진단 스크립트 `scripts/diagnose_udcap_glove_unit.py`:
  - VMC OSC 들어오는 11개 손가락 본의 raw quaternion magnitude 통계 (per-bone σ over 30s)
  - 좌·우 글러브 SNR 비교 → 한쪽 unit 결함 진단
  - "이 글러브 페어를 교환하시오" 권고 메시지

#### 2.4.2 Per-finger adaptive scale (0.5일)
- 현재 `finger_proximal_scale` 은 per-glove 한 값.  per-finger 별 자동 학습 스케일 추가:
  - 첫 30s 동안 사용자가 손가락별 max curl 시도 → 각 finger 별 normalize 인자 캘리브
  - 9.16 의 finger-scale-advice 메시지를 자동 적용으로 격상

#### 2.4.3 Outlier rejection / median filter (0.5일)
- VMC OSC 라인의 quaternion 점프 (>30°/frame) 검출 → 중앙값 필터로 부드럽게
- 글러브 RF 간섭/페어링 일시 끊김에 대한 강건성

#### 2.4.4 Dual-source ensemble (1일)
- VMC bone + finger-curl + skeletal 세 source 를 frame 별 신뢰도 가중 합 (현재는 우선순위 first-wins)
- 한 source 에서 frozen 인 손가락을 다른 source 가 보충

#### 2.4.5 사용자 onset 캘리브 인터페이스 (0.5일)
- 시작 시 "주먹 → 펴기 → 핀치 → V 사인" 4초 시퀀스로 per-finger 동작 범위 자동 측정
- 이 범위에서 [0, 1] 정규화 → URDF limit 매핑

→ 합산 ~3일.  **모든 보강을 적용해도 H/W 가 frozen 신호를 보내면 코드는 무력**.  근본 한계가 있다.

### 2.5 UDCAP 보강 가능성 — 하드웨어 측

#### 2.5.1 단순 점검 (0.5일, 비용 0)
- 글러브 양쪽 모두 USB 동글 새로 페어링 (UDCAP UI 의 "Repair" 메뉴)
- UDCAP UI 의 per-finger heatmap 으로 frozen finger sensor 직접 확인
- USB 동글 위치 변경 (RF 간섭 제거)
- 글러브 elastic 천 장력/주름 제거
- 캘리브 자세를 "정확히 ㄱ자 펴짐" 으로 수정

#### 2.5.2 결함 unit 교환 (3 ~ 7일, 비용 글러브 1쌍 ≈ $200)
- Udexreal 의 보증 교환 (구매 후 1년 내)
- 좌·우 글러브 모두 새 페어로 — frozen finger 가 세팅의 H/W 결함이라면 즉시 해결

#### 2.5.3 상용 mocap급 글러브로 업그레이드 (2~3주, 비용 $5,000)
- **MANUS Quantum Metagloves**: 서브밀리미터 fingertip tracking, ROS 2 + Isaac Sim 공식 지원, SteamVR 통합 (Manus Core), 25 DoF
- TeleOpBench 보고: GR1T2 평가에서 mocap (Manus 같은 모듈) 이 "highest task precision with shortest completion time" 달성
- 단점: $5,000 / 한대, Manus Core SteamVR 드라이버 + Vive Tracker 3.0 (글러브 앵커링용) 필요

### 2.6 UDCAP 경로 종합 평가

| 차원 | 현재 (9.18) | 코드 추가 보강 후 | 글러브 H/W 교환 후 | MANUS 업그레이드 후 |
|---|---|---|---|---|
| 코드 작업 | 완료 | +3일 | +0일 | +1주 (Manus Core 통합) |
| H/W 비용 | $0 | $0 | ~$200 (보증 교환은 $0) | $5,000 |
| 손가락 정밀도 | 좌·우 비대칭, frozen 패턴 | 같음 (H/W 한계) | 글러브 spec 회복 (0.01°) | 서브밀리미터 |
| 위치/팔 트래킹 | VD + Pico MT 그대로 | 동일 | 동일 | 동일 (Manus Core + Vive Tracker) |
| VR 렌더링 | VD 그대로 | 동일 | 동일 | 동일 |
| 기존 9.18 환경 보존 | ✅ | ✅ | ✅ | ✅ (글러브만 swap) |
| 회귀 위험 | — | 매우 낮음 | 0 | 중 (Manus Core <-> Isaac Lab 연결부) |
| 데이터 수집 가능 시점 | 즉시 | 3일 후 | 1일 후 | 3주 후 |

**핵심**: UDCAP 경로는 **현 시스템을 보존하면서 점진 개선** 한다.  최악의 경우(코드+H/W swap 실패)에도 데이터 수집 자체는 가능 (frozen finger 회피 작업 위주).

## 3. PICO 핸드트래킹 전환 경로 — 멀티태스킹 제약 적용 후 실제

### 3.1 §32 가이드의 실패점 — 명확히

§32 는 다음 그림을 그렸다 (잘못된 가정):

```
[Pico 4 Ultra]
 ┌─────────────────────────┐
 │ VD app (VR 스트림)     │──▶ SteamVR (HMD/MT/wrist)  ─┐
 │ XRoboToolkit App APK   │──▶ XRT (Hand 26j)          ─┼─▶ device.advance()
```

### 3.4 PICO 핸드트래킹의 정확도 — 실제 알려진 사실

#### 3.4.1 데이터 채널 (XRoboToolkit-PC-Service README 검증됨)

```

  "isActive": 0|1,         // 0=low quality, 1=high
  "count": 26,
  "scale": 1.0,

    { "p": "px,py,pz,qx,qy,qz,qw",   // 7D pose (left-handed)
      "s": <bitmask>,                  // OrientationValid|PositionValid|OrientationTracked|PositionTracked
      "r": <radius> },
    ... 26 entries
  ]
}
```

#### 3.4.2 한계 (XRoboToolkit 논문, arxiv 2508.00097v1)

XRoboToolkit 논문 자체 인용:

> Hand tracking data updates **at 60 Hz (versus 90 Hz for other pose data)** due to camera limitations, potentially affecting temporal resolution during rapid finger movements.

> The hand retargeting framework **cannot accurately retarget to robot hands with mechanical constraints that couple joint movements, such as the INSPIRE Hands**.

→ 두 번째 문장은 **Fourier 6-DoF 손에도 직접 적용**될 가능성이 높다.  Fourier 손 역시 mimic 결합 (proximal-intermediate) + thumb yaw/pitch 분리 + distal mimic 의 강한 mechanical coupling 을 가진다.  XRT 의 표준 retargeter 는 이 toll 을 직접 처리하지 못한다.

→ 단, ust_fourier_260421 의 `gr1t2_retargeter.py` + `fourier_hand_mapper.py` 는 PACK_22D_SIGNS / mimic factor 등으로 이 mechanical constraint 를 자체 처리하고 있다.  XRT 26-joint 입력만 갈아끼우면 어느 정도 회복 가능.

#### 3.4.3 카메라 핸드 트래킹의 일반적 한계 (학술 합의)

[Camera vs Glove 비교 메타분석, MDPI/arxiv 2502.07730 등]:

| 항목 | 카메라 (Pico-class) | 데이터 글러브 |
|---|---|---|
| 정확도 | 도-단위 (quat ambiguity, occlusion 시 nan) | 서브-도 (UDCAP 0.01° claim, MANUS 서브밀리미터) |
| 지연 | 30 ~ 60ms (이미지 처리) | <10ms (UDCAP), <2ms (MANUS) |
| 손가락 occlusion | 자주 발생 (양손 겹침, 물체 잡기) | 없음 |
| 광량 의존 | 강함 (저조도 / IR 간섭 시 끊김) | 없음 |
| 빠른 동작 | motion blur 시 신뢰도 ↓ | 신호 그대로 |
| 서로 닿은 손가락 구분 | 어려움 (RGB 만으로는 거의 불가) | 명확 |
| 사용자 instrumentation | 없음 (raw hand) | 글러브 착용 |
| 캘리브 | 사용자별 손 모델 자동 학습 | 글러브당 한 번 |

→ **카메라 = 캐주얼/탐사적 작업에 강함, 글러브 = 정밀 조작에 강함**.  로봇 텔레오퍼레이션에서 "정밀 손가락 제어" 가 목표라면 글러브가 우위 (단, 글러브 H/W 가 정상일 때).

#### 3.4.4 NVIDIA GR00T 의 PICO XRT 사용 사례

GR00T-WBC 공식 문서가 PICO 4/4 Pro + XRoboToolkit 사용을 명시.  주의점:
- **whole-body** 텔레오퍼레이션에 사용 (전신 + 풀바디 모션 캡처)
- 손가락 정밀도에 대한 **공식 정확도 metric 미공개**
- VD/PICO Connect 사용하지 않음 (XRT 단독 모드)

→ NVIDIA 가 GR00T 에서 한 것을 ust_fourier_260421 에 적용한다는 선택지는 **정상적**이지만, 사용자의 작업이 "정밀 손가락 제어" 가 진짜 병목이라면 GR00T 도 **글러브 사용을 별도 옵션으로** 두고 있음을 유념.

## 6. 권장 행동 계획

### 6.1 즉시 실행 (오늘 ~ 3일) — UDCAP 보강 + 진단

#### Step A — 글러브 H/W 진단 (1시간, 비용 0)

UDCAP UI 의 per-finger heatmap 으로 좌·우 글러브 모든 손가락이 굽혔다 폈을 때 의미 있게 변화하는지 확인:

- 좌측 글러브 mid/ring/pinky 가 heatmap 에서도 frozen → **글러브 H/W 결함**.  6.2 의 H/W 교환으로 진행.
- 좌·우 모두 heatmap 에서는 변동, ust_fourier_260421 로그에서만 frozen → **소프트웨어 mapper 의 누락 케이스**.  6.1.B 코드 보강.

#### Step B — 코드 보강 패치 (1 ~ 3일)

위 §2.4 의 5가지 보강 항목 (per-finger adaptive scale, outlier rejection, dual-source ensemble, onset 캘리브, glove unit 진단 도구) 적용.

신규 fix 번호 9.19 ~ 9.21 시리즈로 memory.md 에 점진 추가.

#### Step C — 측정 (1일)

다음 메트릭을 30s 텔레오퍼레이션 세션 후 기록:

| 메트릭 | 목표 | 의미 |
|---|---|---|
| 좌·우 모든 5 finger Δrange (rad) | > 0.5 | 모든 손가락 의미 있게 동작 |
| 좌·우 비대칭 (max diff) | < 0.3 rad | 균형 |
| frozen finger count (Δ < 0.05 rad) | 0 | H/W frozen 0 |
| `[stuck-finger-warn]` 메시지 | 미출력 | 9.18 진단 통과 |

→ 모두 만족이면 사용자가 원하는 작업 시도.  부족하면 6.2.

### 6.2 단계적 H/W 개입 (1주)

#### Plan A — 페어링 / 캘리브 점검 (0.5일, 비용 0)

- USB 동글 위치 변경 (RF 간섭 제거)
- 글러브 RePair 메뉴 사용 (UDCAP UI)
- 캘리브 자세 정확히 잡고 30s 정지

#### Plan B — 보증 교환 (1주, 비용 $0 ~ 200)

- 좌측 글러브만 결함 — Udexreal 보증 교환 요청
- 양쪽 모두 결함 의심 — 페어 교환

### 6.3 정밀도 ceiling 이 진짜 병목임이 입증된 경우 (2~3주)

#### Plan C — MANUS Quantum 업그레이드 ($5,000)

ust_fourier_260421 통합 절차:

1. Manus Quantum + Vive Tracker 3.0 (글러브 앵커링용) + Lighthouse 2.0 베이스 스테이션 2개 구매
2. Manus Core SteamVR 드라이버 설치 → SteamVR 가 Manus 손가락 데이터 받음
3. `ust_260418_win.teleop.vr_sampler.py` 의 Skeletal Input 2.0 경로가 자동으로 Manus 데이터 수신 (Manus 가 표준 OpenVR Skeletal Input 구현)
4. `fourier_hand_mapper.map_hand_skeletal()` 가 그대로 동작 — 단지 source 가 정밀해짐
5. UDCAP fallback 은 그대로 보존 (Manus 페어링 끊김 시)

→ **코드 변경 최소** (~50 LOC).  주된 작업은 Manus Core 캘리브.  ust_260418_win 모듈은 변경 없음.

### 6.4 PICO XRT 전환을 진지하게 고려할 시점 (2~3주, 비추천)

다음 모든 조건 만족 시:

- UDCAP 보강 + H/W 교환 + Manus 모두 검토 후 부적합
- Isaac Sim 화면을 모니터로 보는 운영 모드 수용
- NVIDIA GR00T 호환성 우선
- 사용자 손이 카메라 시야 안에 항상 있는 작업 (예: 정면 책상 위 조작)

이 경우 §32 가이드를 재작성:

1. `vr_sampler.py` 경로 deprecate
2. `xrt_sampler.py` 신규 (XRT TCP 전체 데이터 수신)
3. `xrt_to_isaaclab.py` 좌표 변환 (left-handed Y-up Z-in → right-handed Y-up Z-up + base_link offset)
4. `gr1t2_retargeter` 의 EEF source 를 XRT Body[20]/[21] 또는 Controller pose 로 재배선
5. `pico_hand_mapper.py` (§32 그대로)
6. HeadEstimator/WaistEstimator 입력을 XRT Head/Body[0] 으로 갈아끼움
7. 모니터뷰 운영 모드 명시 (`--render_mode monitor` 강제)
8. 또는 XRoboToolkit-Unity-Client 의 stereo video 채널에 Isaac Sim 카메라 H264 NVENC 송신 — 추가 ~2주

### 6.5 PICO OS 6 수급되면 (현재 불가)

→ Spatial Multitasking 으로 VD + XRT App 공존 가능 → §32 의 원래 가정이 회복.  이 시점에 §32 그대로 적용 가능.  지금 PICO XRT 전환에 시간 들이는 것은 OS6 출시 후 가치 휘발 위험.

## 7. 요약 답변 — 사용자의 본 질문

### Q: UDCAP 보강 vs PICO 핸드트래킹 전환, 어느 쪽이 유리한가?

**A: UDCAP 보강 (또는 H/W 교환) 이 유리하다.  PICO 전환은 마지막 수단으로 보류한다.**

### 결정 근거 (멀티태스킹 제약을 명확히 적용):

1. **PICO XRT 전환 = 손가락 source 교체 ≠ 손가락만의 문제**
   PICO OS 5.15.4 의 single-immersive-app 제약 때문에, XRT 를 켜면 VD 가 죽고, 그러면 SteamVR + HMD pose + Pico MT + UDCAP SteamVR 경로 + viewport HMD-follow 모두 동시에 죽는다.  ust_fourier_260421 의 9.10 ~ 9.18 보강 자산의 약 70% 가 휘발된다.

2. **UDCAP 의 잔존 정밀도 문제는 글러브 H/W 측 가능성이 크다**
   9.18까지 적용된 코드 보정 (rest cal, tanh, piecewise yaw, 3-source priority) 은 H/W 신호가 정상이라는 가정 아래 거의 한계다.  좌측 손 frozen finger 패턴이 6주 내내 잔존한다면 그 글러브 unit 의 elastic sensor 결함이 의심된다.  보증 교환 / 페어링 점검이 코드 작업보다 훨씬 단기 리턴이 크다.

3. **PICO 카메라 핸드 트래킹은 "다른 종류의 한계" 일 뿐 "더 좋은 정밀도" 가 아니다**
   - 60Hz (vs UDCAP 120Hz)
   - Camera occlusion 시 신뢰도 ↓
   - "INSPIRE 손과 같은 mechanical coupling 손에 정확히 retarget 못함" — XRoboToolkit 논문이 명시 (Fourier 6-DoF 손도 동일 패턴)
   - 손이 카메라 시야 안에서만 동작 → 책상 위 작업은 OK, 옆구리·뒤쪽은 끊김

4. **정밀도 ceiling 이 진짜 병목이라면 Manus Quantum 이 정답이지 PICO 가 아니다**
   - $5,000 부담은 있지만 서브밀리미터 + drift-free + 60ms 미만 지연 + Isaac Sim 공식 지원 + SteamVR Skeletal Input 표준
   - ust_fourier_260421 코드 변경 ~50 LOC (글러브 source 만 swap, 나머지 그대로)

5. **NVIDIA GR00T 가 PICO XRT 만 쓰는 이유는 "전신 + 일반 매니퓰레이션" 시나리오다**
   ust_fourier_260421 의 사용 사례 (정밀 손가락 제어가 핵심) 와는 강조점이 다르다.  GR00T 도 정밀 작업에는 별도 글러브 옵션을 둔다.

### 단 하나의 예외

> 사용자가 "Isaac Sim 화면을 모니터로 보고, 손은 카메라 시야 안에 항상 두고, 글러브 자체를 벗고 싶고, NVIDIA GR00T 호환을 강하게 원한다" 면 → PICO XRT 전환이 정합.

이 조건이 모두 성립하지 않으면 UDCAP 측 보강·교환이 우위.
