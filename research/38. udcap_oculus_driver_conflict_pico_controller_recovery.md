# 38. UDCAP + Oculus 드라이버 동시 활성 시 PICO 컨트롤러 입력 무력화 — 근본 원인 분석 및 복구 가이드

> 작성: 2026-05-06
> 사용자 보고: SteamVR Manage Add-Ons 에서 **oculus 드라이버와 UDCAP 드라이버 둘 다 활성화** 후 PICO VR 안에서 SteamVR 진입 시 컨트롤러가 "오큘러스 컨트롤러" 로 표시 + 트리거/버튼 일체 무반응 + 컨트롤러 바인딩 변경도 무효.
> 컨텍스트: research/37 의 SteamVR 직접 입력 path 권장 후, 사용자가 실제로 시도하다 발견한 시나리오. 이 문제는 SteamVR Skeletal Input 2.0 path (Phase X1) 진행 가능성을 막는 **선행 차단 요인**.

---

## 0. 한 줄 요약 (TL;DR)

> **결론**: 사용자 시스템의 SteamVR 설정 파일 (`steamvr.vrsettings`, `default.vrsettings`) 직접 분석 결과, 이건 SteamVR 의 알려진 **다중 컨트롤러 드라이버 충돌** 패턴이다. 핵심 증거 4 가지:
> 1. **`steamvr.vrsettings.LastKnown.ActualHMDDriver = "oculus_virtualdesktop"`** + `HMDManufacturer = "Oculus"` + `HMDModel = "Meta Quest 3"` + `HMDSerialNumber = "1PASH5D1P17365"` → **Virtual Desktop 이 PICO 4 Ultra 를 Meta Quest 3 + Oculus Touch 컨트롤러로 emulate 중**.
> 2. **`steamvr.vrsettings.driver_udcap.enable = false`** ← UDCAP 의 SteamVR-side driver enable 플래그가 **꺼져 있음**. 사용자가 Manage Add-Ons 에서 "udcap" 토글을 켰어도, 이 vrsettings 키가 Manage Add-Ons UI 와 별개로 false 면 driver가 **로드만 되고 controller 인터셉트는 비활성**.
> 3. **`UdcapDriver.dll.config`** 의 `Controller_Priority="true"` (HIGH) + `Controller_Module="False"` → UI 차원의 priority 는 HIGH 이지만 module override 는 비활성.
> 4. **`default.vrsettings.driver_UDCAP.enable = false`** + **`pose_settings.controller_override = false`** ← installer-shipped default 가 비활성.
>
> **결과 발생 메커니즘**:
> - Virtual Desktop 이 PICO 컨트롤러를 `oculus_touch` 타입으로 SteamVR 에 emulate
> - 사용자가 SteamVR Manage Add-Ons 에서 "oculus" (= SteamVR 내장 `driver_oculus`) 까지 켜면 충돌 시 raw oculus_touch 가 점유
> - UDCAP 의 SteamVR-side override 가 disabled 상태 → 컨트롤러는 oculus_touch 인 채로 남음
> - 우리 앱 (`actions.json`) 은 `controller_type: udcap` / `knuckles` 만 binding → **oculus_touch 와 매칭되는 binding 없음**
> - 결과: 모든 action 입력이 0, "버튼이 안 먹힌다" 가 SteamVR 자체 Test Controller 와 우리 앱 모두에서 발생
>
> **즉시 시행 가능한 해결 (Plan A 권장)**:
> 1. SteamVR 종료
> 2. **`driver_udcap.enable: true`** 로 `steamvr.vrsettings` 수정 (또는 SteamVR Settings → Startup/Shutdown → Manage Add-Ons 에서 udcap 한 번 더 토글 + Settings → Drivers 탭에서 활성)
> 3. **SteamVR 내장 oculus driver 비활성화** (Manage Add-Ons → "oculus" = OFF). PICO 4 Ultra 는 Virtual Desktop 의 `oculus_virtualdesktop` driver 로 충분 — SteamVR 내장 `driver_oculus` 는 **실제 Oculus/Meta Quest 헤드셋 직접 USB 연결 시에만 필요**.
> 4. UDCAP UI → Settings → Controller Priority = **HIGH** 확인 (이미 됨)
> 5. SteamVR 재시작 → Test Controller 화면에서 컨트롤러 type 이 "udcap" 또는 "knuckles" 로 표시되는지 확인
>
> 그래도 안 되면 **Plan B (PICO 네이티브 streaming 전환)** 또는 **Plan C (vrsettings 수동 재작성)** 을 단계적으로 시도. 자세한 절차는 §5–§7 에서.

## 1. 증거 — 사용자 시스템의 실제 설정 분석

### 1.1 `steamvr.vrsettings` (SteamVR 측 설정)

`C:\Program Files (x86)\Steam\config\steamvr.vrsettings` 의 핵심 부분:

| 키 | 의미 | 현재 값 | 정상 값 (UDCAP 활성화 시) |
|---|---|---|---|

| `pose_settings.controller_override` | controller override 활성 | `true` | `true` |

## 2. 근본 원인 — driver 충돌 메커니즘 도식화

### 2.1 정상 흐름 (UDCAP 가 제대로 활성화된 경우)

```
PICO 4 Ultra HMD                                    PICO Touch 컨트롤러
       │                                                 │
       ▼                                                 ▼
Virtual Desktop Streamer (PICO 측 앱)                Virtual Desktop Streamer
       │                                                 │
       ▼ (Wi-Fi 6/6E)                                    ▼
Virtual Desktop OpenVRDriver (PC 측 SteamVR plugin)
       │
       ├─ HMD: oculus_virtualdesktop (Meta Quest 3 emulation)
       │
       └─ Controllers: oculus_touch type (Oculus Touch emulation)
              │
              ▼
       UDCAP driver (driver_udcap.enable = TRUE)
              │
              ├─ pose_settings.controller_override = TRUE
              ├─ Controller_Priority = HIGH
              └─ controller_override_left/right = 3/4 (knuckles)
              │
              ▼
       UDCAP 가 oculus_touch 를 인터셉트해서 controller_type 을 "udcap" (compat: "knuckles") 으로 변환
              │
              ▼
       SteamVR 가 controller 를 "udcap" 로 인식
              │
              ▼
       우리 앱의 actions.json 이 controller_type="udcap" → bindings_udcap.json 자동 적용
              │
              ▼
       Skeletal Input 2.0 활성 (UDCAP_profile.json 에 정의된 /input/skeleton/* 경로)
       trigger/grip/finger curl 모든 액션 정상 라우팅
```

### 2.2 현재 (버그) 흐름

```
PICO Touch 컨트롤러 → VD → oculus_touch type 그대로 SteamVR 에 도달
       │
       ▼
UDCAP driver (driver_udcap.enable = FALSE) ← 핵심 문제
       │
       └─ 인터셉트 안 함 (driver 만 로드되고 controller override 비활성)
       │
       ▼
SteamVR 가 controller 를 "oculus_touch" 그대로 인식
       │
       ├─ 사용자가 추가로 SteamVR 내장 driver_oculus 까지 enable
       │  → 이중으로 controller 를 claim 시도 → 더 큰 충돌 (드라이버 lock)
       │  → SteamVR Test Controller 화면에서도 입력 0 (드라이버 conflict 결과)
       │
       ▼
우리 앱 (ust_fourier_260421) actions.json 의 default_bindings
       │
       ├─ "udcap" 매칭 ❌ (controller 가 oculus_touch 라서)
       └─ "knuckles" 매칭 ❌
       │
       ▼
**바인딩 0 매칭 → 모든 action 0 → "버튼 안 먹힘"**
```

### 2.3 사용자가 컨트롤러 바인딩을 변경해도 반영되지 않은 이유

SteamVR 의 binding editor 는 **현재 활성 controller_type 에 대한 binding** 만 편집 가능.  컨트롤러가 oculus_touch 로 인식되면:
- editor 가 `oculus_touch_*_steamvrinput` URL 만 편집
- 우리 앱의 `default_bindings` 에 oculus_touch entry 가 없으면 (ust_fourier_260421) → editor 에서 새로 만들어야 하는데 사용자가 인지 못함
- 또는 controller_type 자체가 "oculus" 로 잘못 인식 (driver_oculus 의 raw 클레임) 시 → SteamVR 의 default 매핑이 우리 액션을 받지 못함

→ binding 화면에서 변경한 게 적용되지 않은 게 아니라, **잘못된 controller_type 의 binding 을 변경하고 있었던 것**.

## 3. SteamVR 다중 드라이버 충돌의 일반 원리

### 3.1 SteamVR 의 driver 활성화 계층 (3 단계)

| 단계 | 위치 | 역할 |
|---|---|---|
| 1. Driver registration | `openvrpaths.vrpath` 의 `external_drivers` | SteamVR 가 어떤 driver 를 로드할지 결정 |
| 2. Manage Add-Ons (UI) | SteamVR → Settings → Startup/Shutdown → Manage Add-Ons | UI 에서 드라이버 ON/OFF 토글 |
| 3. driver_<name>.enable (vrsettings) | `steamvr.vrsettings` + 각 driver 의 `default.vrsettings` | 드라이버 내부의 기능 활성화 (예: controller intercept) |

**중요**: 단계 2 의 토글이 ON 이라도 단계 3 의 `enable` 이 false 면 driver 가 로드만 되고 기능은 잠긴 상태.

### 3.2 `driver_oculus` (SteamVR 내장) vs `driver_VirtualDesktop` vs `driver_udcap` 의 역할

| Driver | 위치 | 역할 | 사용자 시스템 상태 |
|---|---|---|---|
| `driver_oculus` | `<SteamVR>/drivers/oculus/` (SteamVR 번들) | **실제 Oculus/Meta Quest 헤드셋을 USB Link / AirLink 로 연결 시에만 필요** | 현재 enable 상태 (사용자 보고). 충돌 원인. |
| `driver_VirtualDesktop` | `C:\Program Files\Virtual Desktop Streamer\OpenVRDriver` | PICO 4 Ultra ↔ Wi-Fi 스트리밍, Meta Quest 3 + Oculus Touch 으로 emulate | enable. PICO 사용에 필수. |
| `driver_udcap` | `C:\Program Files\UdcapDriver\udcap` | UDCAP 글러브 + 컨트롤러 인터셉트 + skeletal/finger curl 광고 | **disable** (driver_udcap.enable=false). 핵심 문제. |
| `driver_gamepad` | `<SteamVR>/drivers/gamepad/` | Xbox 컨트롤러 등 일반 게임패드 | enable. 무관. |

### 3.3 사용자가 "오큘러스 vr 와 udcap 활성화" 라고 표현한 정확한 동작

추정:
- SteamVR 내 Settings → Startup/Shutdown → Manage Add-Ons 화면 진입
- `oculus` 항목 토글 ON ← 사용자 의도: PICO 가 Quest 3 으로 보이는데 그러면 oculus driver 를 켜야 하나? 추측
- `udcap` 항목 토글 ON ← 사용자 의도: UDCAP 글러브 사용
- **하지만 두 드라이버는 함께 쓰면 안 되는 조합**:
  - `driver_oculus` 는 USB-link 연결 또는 Oculus Runtime 직접 통신 시에만 사용
  - PICO + VD 환경에선 `driver_VirtualDesktop` 가 이미 oculus 호환 layer 를 제공
  - 둘 다 활성 → 컨트롤러 claim 충돌

### 3.4 왜 컨트롤러 type 이 "오큘러스" 로 보이는가

| 시나리오 | LastKnown.ActualHMDDriver | 컨트롤러 type | 설명 |
|---|---|---|---|
| VD 만 활성 + UDCAP enable=true | `oculus_virtualdesktop` | `udcap` (compat: knuckles) | 정상. UDCAP 가 oculus_touch 를 인터셉트 |
| VD 만 활성 + UDCAP enable=false (현재) | `oculus_virtualdesktop` | `oculus_touch` | UDCAP 인터셉트 없음 |
| VD + 내장 oculus 모두 활성 | `oculus_virtualdesktop` (또는 충돌) | `oculus_touch` 또는 driver lock | 두 driver 가 동일 controller claim |
| 내장 oculus 만 (VD off) | `oculus` (Oculus Link 시) | `oculus_touch` | PICO 환경엔 부적합 |

→ 사용자 케이스: VD + 내장 oculus + UDCAP(disable) 조합 → 가장 혼란스러운 상태.

## 4. UDCAP 공식 문서 + GitHub 정보 보강

### 4.1 UDCAP FAQ 의 controller priority 가이드 (인용)

> **UDCAP FAQ**: "If you encounter a situation where the controllers or other devices (e.g., Pico series, HTC series) are competing for control, it is recommended to set the control priority to High for the glove. Go to UDCAP → Settings and set the Controller Priority to [HIGH]. After adjusting Controller Priority, restart SteamVR for the settings to take effect."

→ **핵심 단어 "competing for control"** — 이게 정확히 사용자 시나리오. 그리고 **"restart SteamVR for the settings to take effect"** 가 자주 빠지는 step.

### 4.2 UDCAP 의 Add-On 호환성 가이드 (인용)

> **UDCAP support**: "Disable any other add-ons of the same type (e.g., other hand tracking or skeletal driver plugins)" — to avoid conflicts.

→ "of the same type" 의 의미: hand tracking driver 가 둘 이상이면 충돌.  내장 `driver_oculus` 자체는 hand tracking 이 아니지만 **controller emulation type** 이 oculus_touch 이고, UDCAP 도 controller emulation 을 하려고 함 → 같은 namespace 충돌.

### 4.3 PICO Connect 의 RVRPlugin.ini controllertype (대안 경로)

만약 사용자가 Virtual Desktop 대신 PICO Connect 를 쓴다면:
- 위치: `C:\Users\<user>\AppData\Local\PICO Link\driver\bin\win64\RVRPlugin.ini` (최신) 또는 `C:\Program Files (x86)\Pico Link\driver\bin\win64\RVRPlugin.ini`
- 키: `[PICO]` 섹션 아래 `controllertype=N`
  - 0 = PICO native controller (controller_type: pico_controller)
  - 1 = Oculus Touch emulation (controller_type: oculus_touch)
  - 2 = Vive Wands emulation
  - 3 = default (PICO 권장)

→ PICO Connect 사용 + `controllertype=0` (native PICO) + UDCAP 활성 + 내장 oculus driver OFF 가 가장 깔끔한 setup.

### 4.4 v0.1.8.x 시리즈의 실제 설치 버전 확인

`C:\Program Files\UdcapDriver\` 폴더 내 installer 잔여 파일에서 확인:
```
Udcap Driver_v0.1.8.2_setup_release_202604101523.exe
```

→ 사용자 시스템 UDCAP 버전: **v0.1.8.2 (2026-04-10)** — research/34 (2026-05-04 작성) 시점의 v0.1.3.3 보다 **5 버전 점프**.  **Skeletal Input 2.0 + finger curl action 모두 지원되는 버전** (UDCAP 공식 product 페이지 광고와 일치).

→ 즉, `driver_udcap.enable=true` 만 켜주면 research/37 의 Phase X1 (Skeletal Input primary) 시나리오로 직행 가능.

## 10. 추가 안전장치 — 향후 driver 충돌 재발 방지

### 10.1 SteamVR `Manage Add-Ons` 의 정책

PICO 4 Ultra + UDCAP 환경에서 권장 driver 토글:
| Driver | ON/OFF | 비고 |
|---|---|---|
| `udcap` | **ON** | 글러브 사용 시 항상 |
| `VirtualDesktop` | **ON** (VD 사용 시) / **OFF** (PICO Connect 사용 시) | HMD streaming path |
| `oculus` (SteamVR 내장) | **OFF** | 실제 Oculus 헤드셋 USB Link 사용 안 하면 끄기 |
| `gamepad` | (유지) | 무관 |
| 기타 vendor add-ons (lighthouse, vive, holographic, ...) | OFF | PICO 환경에 무관 |

### 10.2 vrsettings 변경 후 자동 검증 스크립트

`ust_ws/ust_fourier_260421/scripts/diagnose_steamvr_drivers.py` 신규 작성 권장 (Phase X1 진입 후 후속 작업):
- `steamvr.vrsettings` 의 `driver_udcap.enable` 검증
- `default.vrsettings` 의 `driver_UDCAP.enable` + `pose_settings.controller_override` 검증
- `openvrpaths.vrpath` 의 external_drivers 리스트 검증
- `<SteamVR>/drivers/oculus/driver.vrdrivermanifest` 존재 여부
- 결과 출력: PASS/FAIL + 권장 action

### 10.3 `actions.json` 에 oculus_touch fallback binding 추가 검토

만약 사용자가 어쩔 수 없이 oculus_touch type 을 유지해야 하는 시나리오 (예: 다른 게임용 환경 공유) 라면:
- `bindings_oculus_touch.json` (controller_type: oculus_touch) 신규 작성 — `bindings_index.json` 카피 후 path 조정
- `actions.json` 의 `default_bindings` 에 oculus_touch entry 추가

이렇게 하면 driver_udcap.enable=false 인 fallback 환경에서도 trigger/grip 만은 동작.  finger curl/skeletal 은 oculus_touch 에 없으므로 손가락은 idle.

## 11. 결론 — 사용자에게 전달할 한 줄 요약

> **사용자 시스템의 SteamVR 설정 파일을 직접 분석한 결과, 컨트롤러 무반응의 정확한 원인은 `steamvr.vrsettings.driver_udcap.enable = false` + `default.vrsettings.driver_UDCAP.enable = false` + Virtual Desktop 의 oculus_touch emulation 의 3중 조합이다. UDCAP 의 SteamVR-side 활성 플래그가 false 이기 때문에 UDCAP 가 oculus_touch 컨트롤러를 인터셉트하지 못하고, 컨트롤러는 oculus_touch 인 채로 SteamVR 에 보고된다. 우리 앱의 actions.json 은 controller_type "udcap" / "knuckles" 만 binding 하므로 oculus_touch 에 매칭되지 않아 모든 입력이 0. 사용자가 추가로 SteamVR 내장 driver_oculus 까지 enable 한 것이 driver claim 충돌을 더 악화시키고 있다. 해결은 단순: (1) `driver_udcap.enable = true` 로 두 vrsettings 파일 모두 수정, (2) SteamVR 내장 oculus driver 비활성화, (3) UDCAP UI Controller Priority HIGH 재확인, (4) SteamVR 재시작. 이 4 step (5-10분) 후 컨트롤러 type 이 udcap/knuckles 로 인식되면 research/37 의 Phase X1 (Skeletal Input primary) 즉시 진행 가능. 사용자 시스템엔 이미 UDCAP v0.1.8.2 (2026-04-10 build) 가 설치돼 있어 Skeletal Input 2.0 활성 가능성이 높다.**
