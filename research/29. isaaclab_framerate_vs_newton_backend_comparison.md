## 1. 두 옵션의 정확한 정의

### 1.1 옵션 1 — 현재 PhysX 백엔드에서 frame rate 상향
**정의**: `sim.dt` 와 `decimation` 파라미터만 조정해 환경 step rate를 20 Hz → 60~120 Hz로 끌어올림.

**현재 상태** ([kitchen_sorting_gr1t2_env_cfg.py:514-518](ust_ws/ust_fourier_260421/kitchen_sorting_gr1t2_env_cfg.py:514)):
```python
self.decimation = 6
self.sim.dt = 1 / 120          # physics 120 Hz
self.sim.render_interval = 1
# → env.step() rate = sim.dt × decimation = 1/120 × 6 = 50 ms = 20 Hz
```

**조정 후보**:
| 변형 | sim.dt | decimation | env step | sub-sampling 대 UDCAP 140 Hz |
|---|---|---|---|---|
| 현재 | 1/120 | 6 | 20 Hz | 7.0:1 |
| 보수적 | 1/120 | 3 | 40 Hz | 3.5:1 |
| 균형 | 1/120 | 2 | 60 Hz | 2.3:1 |
| 공격적 | 1/120 | 1 | 120 Hz | 1.17:1 ★ |
| 매우 공격적 | 1/240 | 1 | 240 Hz | 0.58:1 (over-sample) |

**작동 메커니즘**:
- PhysX TGS solver는 `sim.dt` 마다 1번 step 실행 (joint integration + contact resolution)
- Action Manager는 `env.step()` 호출 시 1회만 action을 articulation에 명령으로 전달
- decimation 회만큼 PhysX가 그 명령을 유지하며 step
- Pink IK `compute()`는 `env.step()` 마다 1회 호출 → step rate ↑ 시 호출 빈도 ↑

### 1.2 옵션 2 — Newton/MuJoCo Warp 백엔드로 마이그레이션
**정의**: Isaac Lab 3.0 베타에 도입된 `isaaclab_newton` extension으로 PhysX → MuJoCo Warp solver 전환.

**작동 메커니즘** ([Newton Physics Integration Docs](https://isaac-sim.github.io/IsaacLab/main/source/experimental-features/newton-physics-integration/index.html)):
- PhysX 백엔드를 떼고 Newton (NVIDIA Warp 기반) 백엔드 장착
- MuJoCo Warp solver: `implicitfast` 또는 `euler` integrator + `pyramidal` 또는 `elliptic` contact
- Articulation, rigid body, rigid object collection 지원
- CUDA-graph acceleration으로 fused GPU kernels 사용
- 데이터 파이프라인: 모든 `.data` 속성이 `wp.array` 반환 (torch.Tensor 아님)

**Newton 1.0 발표 (CoRL 2025 / GTC 2026)**:
- dexterous manipulation에서 PhysX 대비 **65% 빠름** ([NVIDIA Blog](https://developer.nvidia.com/blog/newton-adds-contact-rich-manipulation-and-locomotion-capabilities-for-industrial-robotics/))
- MuJoCo Warp는 manipulation에서 MJX 대비 **313x 빠름**, locomotion에서 152x 빠름

### 2.2 Pink IK 호환성
| | 옵션 1 | 옵션 2 |
|---|---|---|
| 현재 동작 | ✓ (osqp 0.6 + qpsolvers 4.x compat shim 적용 후) | 베타 도큐먼트 미언급 |

### 2.3 Breaking Changes (옵션 2에서 우리 코드에 영향)
[Isaac Lab 3.0 Beta Release Notes](https://github.com/isaac-sim/IsaacLab/releases/tag/v3.0.0-beta):
- **Quaternion format**: WXYZ → **XYZW**
  - 우리 retargeter는 [전부 wxyz](ust_ws/ust_fourier_260421/teleop/gr1t2_retargeter.py)
  - 영향: gr1t2_retargeter.py / fourier_hand_mapper.py / waist_estimator.py / head_estimator.py 모두 수정
- **Data properties**: `wp.array` ← `torch.Tensor`
  - 9.23 EMA fix가 numpy 기반 → wp.array 변환 layer 필요
  - Action manager interface 변경
- **Write method split**: `_index` / `_mask` 변형
- **Deprecated**: `root_physx_view` → `root_view`, `--headless` → `--visualizer`/`--viz`

옵션 1: **변경 없음**. 옵션 2: 9.23 fix 포함 모든 teleop 코드 사실상 재작성.

### 2.4 Pink IK QP 비용 정량 추정 (옵션 1의 핵심 위험)

Pink IK는 매 `env.step()`마다 한번 `compute()` 호출:
- Pinocchio FK: 54 joints articulation, ~0.5 ms (CPU C++)
- Task Jacobian (FrameTask × 2 + NullSpacePostureTask): ~1 ms
- QP build + osqp solve: 36D action space, ~2~5 ms
- Total: **~3~7 ms per step**

| env step rate | step interval | QP budget | 여유 |
|---|---|---|---|
| 20 Hz | 50 ms | 7 ms | 86% 여유 — 안전 |
| 40 Hz | 25 ms | 7 ms | 72% 여유 — 안전 |
| 60 Hz | 16.7 ms | 7 ms | 58% 여유 — 안전 |
| 120 Hz | 8.33 ms | 7 ms | **16% 여유 — 위험** |
| 240 Hz | 4.17 ms | 7 ms | **−68% — 무리** |

> **결론 (옵션 1 안전 zone)**: env step **40~60 Hz**가 안전. 120 Hz는 osqp warm-start로 QP가 1~2 ms로 떨어지면 가능, 그러나 QP 가끔 발산할 수 있음. 240 Hz는 분명히 무리.

> **권장 시작점: decimation 6 → 2 (env step 60 Hz)**. 실측 후 1로 더 낮춤.

## 3. PhysX TGS solver와 step rate 상승 안정성

### 3.1 dt 감소 vs 안정성 트레이드오프
[NVIDIA PhysX 가이드](https://docs.isaacsim.omniverse.nvidia.com/4.2.0/simulation_fundamentals.html):
> "Time steps that are too long can lead to instabilities, especially with fast-moving objects, strong forces, or complex articulated assemblies."

> "For high-performance simulations, it's important to find an appropriate tradeoff between the number of solver iterations and simulation fidelity."

**우리 케이스**:
- 현재 `sim.dt = 1/120` (8.33 ms)는 PhysX 표준 권장 범위
- `dt`를 줄이면 articulation 안정성 향상 (substepping과 같은 효과)
- 그러나 GPU 부담 증가
- TGS 기본 4 position iter / 1 velocity iter는 dexterous에 충분

### 3.2 dexterous finger jitter — 이미 9.7~9.23 fix로 mitigation 완료
- stiffness 10000 / damping 100 / effort 100 (9.7)
- thumb yaw axis Z→X (9.19)
- thumb yaw URDF clamp (9.20)
- 22D EMA low-pass (9.23)

→ PhysX 자체에서 finger jitter는 더 이상 큰 이슈 아님. step rate ↑ 만이 잔존 문제.

## 4. Newton/MuJoCo Warp 백엔드의 현재 (2026-05) 한계

### 4.1 Newton 자체 ([Linux Foundation 발표 + GitHub newton-physics/newton](https://github.com/newton-physics/newton))
- **Status**: alpha → beta (Newton 1.0 GA는 GTC 2026 발표, 그러나 Isaac Lab 통합은 별도 베타)
- **OS**: Linux 우선 (Ubuntu 22.04+), Windows 미발표
- **API stability**: "you are likely to encounter breaking changes as well as limited documentation. The developers do not expect to be able to provide official support or debugging assistance until the framework has reached an official release"

### 4.2 Isaac Lab 3.0 + Newton 통합
- 3.0 베타 발표 ([Release v3.0.0-beta](https://github.com/isaac-sim/IsaacLab/releases/tag/v3.0.0-beta))
- "Newton backend is in active development — **Not all environments have Newton presets yet**"
- "only a limited set of classic RL and **flat terrain locomotion** reinforcement learning examples are included at the moment"
- **PhysX-only 기능**: deformable objects, surface grippers, material randomization
- **manipulation 환경 지원 명시 없음** — Cartpole / Ant / Humanoid 예제만 mentioned
- GR1T2 환경 Newton preset 부재

### 4.3 mjlab — 대안 마이그레이션 경로
[mjlab GitHub](https://github.com/mujocolab/mjlab) (UC Berkeley + Tsinghua, v1.3.0 2026-04):
- Isaac Lab manager-based API + MuJoCo Warp의 lightweight 구현
- "Familiar APIs: If you know Isaac Lab or MuJoCo, you already know mjlab"
- Pure Python, minimal deps, no Isaac Sim/Kit 필요
- 검증된 task: Unitree G1 velocity tracking, motion imitation, manipulation (G1만 명시)
- **GR1T2 / Pink IK 명시적 언급 없음**

### 7.2 Step 2 — EMA alpha 재조정 (1일)
60 Hz에서 EMA time constant 비교:
- alpha=0.4 @ 60 Hz → tau ≈ 33 ms (perceptible 일관성 ↓)
- alpha=0.2 @ 60 Hz → tau ≈ 75 ms (현재 20 Hz alpha=0.4와 유사)
- alpha=0.6 @ 60 Hz → tau ≈ 17 ms (lag 거의 없음)

```powershell

python -X utf8 -m ust_ws.ust_fourier_260421.scripts.run_teleop ... --finger_lp_alpha 0.6  # responsive
```

→ 영상 비교 후 default 확정.

### 7.3 Step 3 — decimation=1 시도 (조건부, 1~2일)
Step 1/2가 만족스럽고 GPU 여유 충분 (`nvidia-smi` 50% 미만)이면 decimation=1로 추가 시도:
- env step 120 Hz, UDCAP 140 Hz와 거의 매칭 (1.17:1)
- Pink IK 8.33 ms budget — osqp warm start 활성화로 1~2 ms 달성하면 OK
- `controller.show_ik_warnings=True` 로그 모니터링 필수

## 9. 추가 고려사항

### 9.1 단순한 frame rate ↑로 풀리지 않을 수 있는 잔존 문제
- **VMC 패킷 수신측 jitter**: UDP UDCAP 패킷이 항상 정확히 ~140 Hz로 오는 게 아니라 jitter가 있음. env step rate가 매우 높을수록 이 jitter도 그대로 노출됨 → VMCHandReceiver측 EMA 추가가 보완책
- **forearm tracker dropout**: SteamVR forearm tracker는 가끔 frame을 놓침. 60 Hz step rate에선 더 두드러짐
- **HMD/controller 90 Hz vs Pico Connect**: HMD 90 Hz 한계는 그대로, env step 120 Hz로 가면 HMD 데이터는 1.3:1 sub-sample (역방향)

### 9.2 decimation 변경의 부작용
- Action recording (record_demos.py): `dt`가 파일에 저장되므로 호환됨, 그러나 timestamp 명시
- Mimic data augmentation: env step rate가 다른 dataset끼리 join 시 보간 필요
- RL training: rew/observation rate 모두 변경 → 학습 hyperparameter 재튜닝 필요

### 9.3 Render rate 별도 고려
현재 `render_interval=1` → 매 sim_step 마다 rendering (8.33 ms 마다). decimation 6→1로 줄여도 render rate는 그대로. GPU 부담 변화 없음. 단 환경 step rate 60 Hz로 바뀌면 sim/render 비율이 1:6 → 1:2 가 되어 sim per render가 줄어듦 (frame은 더 자주 나옴).
