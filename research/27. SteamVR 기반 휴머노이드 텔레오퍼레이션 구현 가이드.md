# SteamVR 기반 휴머노이드 텔레오퍼레이션 구현 가이드

**Pico 4 Ultra + 5개 모션 트래커 + UDCAP 글러브를 SteamVR로 통합하여 Isaac Lab에서 휴머노이드 로봇을 전신 텔레오퍼레이션하는 것은 기술적으로 실현 가능하지만, Linux 단독 구성보다는 Windows(SteamVR) + Linux(Isaac Lab) 듀얼 PC 아키텍처가 현실적 최적해입니다.** 핵심 이유는 SteamVR Linux 버전이 아직 개발 베타 상태이고, Pico 모션 트래커의 안정적 패스스루를 지원하는 Virtual Desktop이 Windows 전용이기 때문입니다. 이 가이드는 하드웨어 연결부터 Isaac Lab 커스텀 DeviceBase 구현까지 전체 파이프라인을 기술 깊이를 유지하며 다룹니다.

## 1. Pico 4 Ultra → SteamVR 연결 방법 완전 비교

Pico 4 Ultra를 PC의 SteamVR에 연결하는 방법은 5가지이며, **모션 트래커 패스스루 지원 여부**가 텔레오퍼레이션 용도에서 결정적 차이를 만듭니다.

### 연결 방법 비교표

| 방법 | Windows | Linux | 트래커 패스스루 | 지연시간 | 비용 | 성숙도 |
|------|---------|-------|--------------|---------|------|--------|
| **Virtual Desktop** | ✅ | ❌ | ✅ 최상 (Vive Tracker 에뮬레이션) | 최저 | $25 | 높음 |
| **Pico Connect** | ✅ | ❌ | ⚠️ 부분적 (네이티브 포맷, 호환성 이슈) | 낮음~중간 | 무료 | 중간 |
| **ALVR** | ✅ | ✅ (베타) | ✅ v20.14.0+ (바디 모드) | 중간 | 무료 | 중간 |
| **Steam Link** | ✅ | ✅ (추정) | ❌ 미지원 | 낮음~중간 | 무료 | 중간~높음 |
| **USB 유선** | ✅ | ✅ (ALVR) | SW에 의존 | 최저 | 케이블 비용 | 중간 |

**Virtual Desktop (VD)** 이 텔레오퍼레이션에 가장 적합합니다. VD는 Pico 모션 트래커 데이터를 **HTC Vive Tracker로 에뮬레이션**하여 SteamVR에 전달하므로, SteamVR 생태계의 모든 앱이 트래커를 표준 Vive Tracker로 인식합니다. Pico Connect는 네이티브 포맷으로 트래커 데이터를 전달하지만, 일부 앱에서 트래커를 인식하지 못하는 호환성 문제가 보고되어 있습니다. **ALVR은 유일하게 Linux를 지원**하며 v20.14.0부터 바디 트래킹을 지원하지만, 오브젝트 트래킹 모드에서 Vive Tracker 생성 실패 이슈(#3014)가 있고 전반적으로 베타 수준입니다.

### Pico 모션 트래커 기술 상세

Pico 모션 트래커는 **2.4GHz 독자 프로토콜**로 헤드셋에 직접 연결됩니다 (Bluetooth도 WiFi도 아님). PC 동글이 필요 없으며, 트래커 → 헤드셋 → 스트리밍 SW → SteamVR 경로로 데이터가 전달됩니다.

5개 트래커 구성 시 (Pico OS 5.14+):
- **기본 3개**: 양 발목 + 허리 → 24개 골격 관절점 추론
- **추가 2개 옵션**: 양 팔뚝(Enhanced Forearm) 또는 양 허벅지(Enhanced Thigh)
- **텔레오퍼레이션 권장**: Enhanced Forearm 모드 (허리 + 양 발목 + 양 팔뚝)

트래커 스펙은 **200Hz IMU, 12개 적외선 LED, 27g, 25시간+ 배터리, ~20ms 모션 캡처-전송-계산 지연, 평균 5cm 위치 편차, 평균 6° 각도 편차**입니다. DisplayPort Alt Mode는 **미지원**이므로 비압축 유선 PC VR은 불가능합니다.

중요한 점은, Pico의 바디 트래킹 모드에서 트래커 데이터는 **개별 6DoF 포즈가 아닌 AI 알고리즘이 추론한 24개 골격 관절 위치**로 SteamVR에 전달된다는 것입니다. 개별 트래커의 raw 6DoF 포즈가 필요하면 오브젝트 트래킹 모드를 사용해야 하지만, 이 모드는 ALVR에서 안정성 이슈가 있습니다. Virtual Desktop의 Vive Tracker 에뮬레이션이 가장 안정적인 파이프라인입니다.

## 2. UDCAP VR 글러브 통합 경로 비교

UDCAP 글러브는 중국 상하이 기반 **UDEXREAL** 사의 제품으로, 두 가지 라인업이 있습니다.

### 제품 라인업

| 구분 | UDCAP VR Glove | UDCAP Data Glove |
|------|---------------|-----------------|
| 가격 | $699 | $1,799 |
| 용도 | 게임/소셜 VR | 로봇공학/시뮬레이션 |
| 센서 | 손당 12개 초박형 탄성 플렉스 센서 (0.1mm) | 동일 |
| 관절 추적 | 손당 15관절, **21개 관절 각도** 출력 | 동일 |
| 샘플레이트 | **120Hz** | **120Hz** |
| 무선 프로토콜 | 2.4GHz 독자 프로토콜 (USB 동글) | 동일 |
| 지연 | <10ms (10m 반경) | 동일 |
| SDK | UDCAP Driver (SteamVR 드라이버) | **HandDriver** (로봇용 SDK) |
| OS 지원 | Windows (SteamVR) | **Windows + Linux (Ubuntu)** ✅ |
| 데이터 출력 | SteamVR Skeletal Input, VMC, OSC | **UDP (JSON/Protobuf)** |
| ROS2 패키지 | 없음 | 없음 (UDP 기반 커스텀 노드 필요) |

**IMU 기반이 아닌 독자적 초박형 탄성 플렉스 센서**를 사용하며, 소재 변형으로 굽힘 각도를 직접 측정합니다. 글러브 자체에 위치 추적 기능이 없으므로, 손목 위치는 별도 트래커(Pico 모션 트래커 또는 Vive Tracker)로 획득해야 합니다.

### Path A: Data Glove 직접 SDK → ROS2 (★ 권장)

```
UDCAP Data Glove → 2.4GHz → USB 동글 → PC
→ HandDriver (Linux/Windows) → UDP (JSON 또는 Protobuf)
→ 커스텀 ROS2 노드 (Python) → sensor_msgs/JointState
→ Isaac Lab
```

**HandDriver**는 웹 버전(브라우저 기반 GUI, 권장)과 Windows 독립형이 있으며, **Linux Ubuntu를 공식 지원**합니다. 120Hz로 **21개 관절 각도(Euler 또는 Quaternion)**를 UDP로 스트리밍하며, JSON과 Protobuf 포맷을 모두 지원합니다. C++과 Python SDK가 제공되므로 ROS2 노드 개발이 직관적입니다.

**지연시간 분석:**
- 센서 → HandDriver: <10ms (2.4GHz 무선)
- HandDriver → UDP: ~1ms
- UDP → ROS2 노드 → Isaac Lab: ~1-5ms
- **총 예상 지연: ~12-16ms @ 120Hz** — 텔레오퍼레이션에 우수

**ROS2 노드 구현 패턴:**
```python
import rclpy, socket, json
from rclpy.node import Node
from sensor_msgs.msg import JointState

class UDCAPBridgeNode(Node):
    def __init__(self):
        super().__init__('udcap_bridge')
        self.pub_left = self.create_publisher(JointState, '/vr/hand/left/joint_states', 10)
        self.pub_right = self.create_publisher(JointState, '/vr/hand/right/joint_states', 10)
        self.sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        self.sock.bind(('0.0.0.0', 12345))  # HandDriver가 송신하는 포트
        self.sock.setblocking(False)
        self.timer = self.create_timer(1.0/120.0, self.poll_data)
    
    def poll_data(self):
        try:
            data, _ = self.sock.recvfrom(4096)
            parsed = json.loads(data)
            msg = JointState()
            msg.header.stamp = self.get_clock().now().to_msg()
            msg.name = [f'finger_joint_{i}' for i in range(21)]
            msg.position = [float(v) for v in parsed['joint_angles']]
            self.pub_left.publish(msg)  # 좌/우 구분 로직 추가 필요
        except BlockingIOError:
            pass
```

### Path B: VR Glove → SteamVR Skeletal Input

```
UDCAP VR Glove → 2.4GHz → USB 동글 → PC (Windows)
→ UDCAP Driver → SteamVR (Valve Index 컨트롤러 에뮬레이션)
→ OpenVR Skeletal Input API → 26개 뼈 변환 / 5개 fingerCurls
→ pyopenvr → ROS2 → Isaac Lab
```

VR Glove용 UDCAP Driver는 **SteamVR Skeletal Input을 지원**하며 Valve Index 컨트롤러로 에뮬레이션됩니다. 그러나 이 경로는 SteamVR 추가 지연(5-15ms), Windows 필수, SteamVR의 보간/필터링에 의한 데이터 손실 가능성, 그리고 21개 raw 관절 각도 대신 5개 fingerCurls + 4개 fingerSplays = 9개 값으로 축소될 수 있다는 단점이 있습니다.

### 권장 사항

**Path A (Data Glove + HandDriver → UDP → ROS2)를 강력 권장합니다.** 이유:
- Linux 네이티브 지원으로 Isaac Lab과 동일 머신에서 실행 가능
- 120Hz의 21개 관절 각도 — 로봇 손의 dexterous 제어에 최적
- SteamVR 의존성 없음 — 글러브 데이터 파이프라인이 독립적
- 지연시간 최소화 (~12-16ms)

참고로, **MANUS Metagloves Pro**($5,000+)는 Isaac Lab 2.3에서 네이티브 지원(`ManusVive` 디바이스 클래스)되며 공식 ROS2 패키지도 존재합니다. 예산과 통합 복잡도를 고려한 대안입니다.

## 3. SteamVR → Isaac Lab 데이터 파이프라인 설계

### pyopenvr를 이용한 트래커 포즈 읽기

**pyopenvr**(`pip install openvr`)는 OpenVR API의 Python 바인딩으로, SteamVR의 모든 추적 디바이스 데이터를 읽을 수 있습니다.

```python
import openvr
import math

# 초기화 — VRApplication_Other로 HMD 렌더링 없이 트래커 데이터만 읽기
vr_system = openvr.init(openvr.VRApplication_Other)

# 모든 연결된 디바이스 열거
def enumerate_devices(vr_system):
    devices = {}
    for i in range(openvr.k_unMaxTrackedDeviceCount):
        device_class = vr_system.getTrackedDeviceClass(i)
        if device_class == openvr.TrackedDeviceClass_Invalid:
            continue
        serial = vr_system.getStringTrackedDeviceProperty(
            i, openvr.Prop_SerialNumber_String)
        model = vr_system.getStringTrackedDeviceProperty(
            i, openvr.Prop_ModelNumber_String)
        class_name = {
            openvr.TrackedDeviceClass_HMD: "HMD",
            openvr.TrackedDeviceClass_Controller: "Controller",
            openvr.TrackedDeviceClass_GenericTracker: "Tracker",
        }.get(device_class, "Unknown")
        devices[i] = {"class": class_name, "serial": serial, "model": model}
    return devices

# 포즈 추출 (HmdMatrix34_t → 위치 + 쿼터니언)
def extract_pose(pose_mat):
    x, y, z = pose_mat[0][3], pose_mat[1][3], pose_mat[2][3]
    m = pose_mat
    w = math.sqrt(max(0, 1 + m[0][0] + m[1][1] + m[2][2])) / 2
    qx = math.copysign(
        math.sqrt(max(0, 1 + m[0][0] - m[1][1] - m[2][2])) / 2,
        m[2][1] - m[1][2])
    qy = math.copysign(
        math.sqrt(max(0, 1 - m[0][0] + m[1][1] - m[2][2])) / 2,
        m[0][2] - m[2][0])
    qz = math.copysign(
        math.sqrt(max(0, 1 - m[0][0] - m[1][1] + m[2][2])) / 2,
        m[1][0] - m[0][1])
    return (x, y, z), (w, qx, qy, qz)
```

**`getDeviceToAbsoluteTrackingPose()`는 한 번의 호출로 HMD + 모든 트래커의 포즈를 동시에 반환**하므로, 센서 간 시간 동기화가 자연스럽게 보장됩니다. 이것이 SteamVR 기반 접근의 핵심 장점입니다.

### 트래커를 신체 부위에 매핑하기

SteamVR UI(Settings → Controllers → Manage Vive Trackers)에서 트래커 역할을 `Waist`, `Left Foot`, `Right Foot`, `Left Elbow`, `Right Elbow` 등으로 할당할 수 있습니다. 그러나 **프로그래밍적으로는 시리얼 넘버 기반 매핑이 더 안정적**입니다:

```python
# config.json으로 트래커-신체 부위 매핑 관리
TRACKER_MAP = {
    "LHR-3CD1A9DA": "waist",
    "LHR-25865D81": "left_foot",
    "LHR-4359D2B6": "right_foot",
    "LHR-AABBCCDD": "left_elbow",
    "LHR-EEFF0011": "right_elbow",
}
```

SteamVR의 역할 할당 API는 `/user/foot/left`, `/user/waist` 등의 경로를 사용하지만, 역사적으로 불안정했으므로 시리얼 넘버 기반 식별을 권장합니다.

### 좌표계 변환: SteamVR → ROS2 → Isaac Lab

세 시스템의 좌표 규약이 다릅니다:

| 시스템 | 좌표계 | 위 방향 | 앞 방향 |
|--------|--------|---------|---------|
| **SteamVR/OpenVR** | 오른손, Y-up | +Y | -Z |
| **ROS2 (REP-103)** | 오른손, Z-up | +Z | +X |
| **Isaac Lab (물리 월드)** | 오른손, Z-up | +Z | +X |

Isaac Lab의 물리 월드 좌표계는 **ROS2와 동일**(Z-up, X-forward)이므로, SteamVR → ROS2 변환만 수행하면 됩니다:

```python
import numpy as np
from scipy.spatial.transform import Rotation

def steamvr_to_ros(position_svr, quaternion_wxyz):
    """SteamVR (Y-up, Z-backward) → ROS (Z-up, X-forward)
    매핑: ROS_X = -SVR_Z, ROS_Y = -SVR_X, ROS_Z = SVR_Y"""
    sx, sy, sz = position_svr
    ros_pos = np.array([-sz, -sx, sy])
    
    R_svr_to_ros = np.array([[0, 0, -1], [-1, 0, 0], [0, 1, 0]])
    w, x, y, z = quaternion_wxyz
    r_device = Rotation.from_quat([x, y, z, w])
    r_frame = Rotation.from_matrix(R_svr_to_ros)
    r_ros = r_frame * r_device * r_frame.inv()
    return ros_pos, r_ros.as_quat()  # [x, y, z, w]
```

### CloudXR와의 공존

CloudXR와 SteamVR은 **상호 보완적**이며 동일 머신에서 공존 가능합니다:
- **SteamVR**: 로컬 VR 런타임, 트래커/글러브 입력 획득 계층
- **CloudXR**: XR 디바이스로의 원격 스트리밍 기술 (시각화 + 원격 입력)
- SteamVR이 로컬 트래커/글러브를 관리 → Python 노드 → ROS2 → Isaac Lab, CloudXR은 선택적으로 Isaac Lab 시각화를 별도 XR 헤드셋에 스트리밍
- **모니터로만 시뮬레이션을 확인할 경우 CloudXR는 불필요**

### 완전한 ROS2 퍼블리셔 노드

```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy
from geometry_msgs.msg import PoseStamped
import openvr

teleop_qos = QoSProfile(
    reliability=ReliabilityPolicy.BEST_EFFORT,
    history=HistoryPolicy.KEEP_LAST, depth=1)

class VRTrackerNode(Node):
    def __init__(self):
        super().__init__('vr_tracker_node')
        self.vr = openvr.init(openvr.VRApplication_Other)
        
        parts = ['hmd','waist','left_foot','right_foot','left_elbow','right_elbow']
        self.pubs = {p: self.create_publisher(
            PoseStamped, f'/vr/tracker/{p}/pose', teleop_qos) for p in parts}
        
        self.serial_map = {  # 실제 시리얼로 교체
            'LHR-3CD1A9DA': 'waist', 'LHR-25865D81': 'left_foot',
            'LHR-4359D2B6': 'right_foot', 'LHR-AABBCCDD': 'left_elbow',
            'LHR-EEFF0011': 'right_elbow',
        }
        self.timer = self.create_timer(1.0/90.0, self.publish_poses)
    
    def publish_poses(self):
        poses = self.vr.getDeviceToAbsoluteTrackingPose(
            openvr.TrackingUniverseStanding, 0, 
            openvr.k_unMaxTrackedDeviceCount)
        now = self.get_clock().now().to_msg()
        
        for i in range(openvr.k_unMaxTrackedDeviceCount):
            if not poses[i].bPoseIsValid:
                continue
            serial = self.vr.getStringTrackedDeviceProperty(
                i, openvr.Prop_SerialNumber_String)
            cls = self.vr.getTrackedDeviceClass(i)
            
            if cls == openvr.TrackedDeviceClass_HMD:
                part = 'hmd'
            elif serial in self.serial_map:
                part = self.serial_map[serial]
            else:
                continue
            
            pos, quat = extract_pose(poses[i].mDeviceToAbsoluteTracking)
            ros_pos, ros_quat = steamvr_to_ros(pos, quat)
            
            msg = PoseStamped()
            msg.header.stamp = now
            msg.header.frame_id = 'vr_origin'
            msg.pose.position.x = float(ros_pos[0])
            msg.pose.position.y = float(ros_pos[1])
            msg.pose.position.z = float(ros_pos[2])
            msg.pose.orientation.x = float(ros_quat[0])
            msg.pose.orientation.y = float(ros_quat[1])
            msg.pose.orientation.z = float(ros_quat[2])
            msg.pose.orientation.w = float(ros_quat[3])
            self.pubs[part].publish(msg)
```

### 권장 ROS2 토픽 구조

```
/vr/hmd/pose                    # geometry_msgs/PoseStamped (90Hz)
/vr/tracker/waist/pose          # geometry_msgs/PoseStamped
/vr/tracker/left_foot/pose
/vr/tracker/right_foot/pose
/vr/tracker/left_elbow/pose
/vr/tracker/right_elbow/pose
/vr/hand/left/joint_states      # sensor_msgs/JointState (120Hz, UDCAP)
/vr/hand/right/joint_states

```

QoS는 **BEST_EFFORT + depth=1**로 설정하여 최신 데이터만 유지하고 재전송 오버헤드를 제거합니다.

## 4. Linux vs Windows: 아키텍처 결정

### SteamVR Linux 현황 (2025-2026)

SteamVR for Linux는 공식적으로 **"development release"**이며 프로덕션 릴리스가 아닙니다. **Async reprojection이 SteamVR >1.14에서 모든 드라이버/하드웨어에서 깨져 있고**, NVIDIA GPU에서 프레임 드롭이 빈번하며, 870+개 이상의 오픈 이슈가 있습니다. 스탠드얼론 헤드셋(Pico)을 Linux SteamVR에 연결하는 것은 ALVR을 통해 가능하지만 추가적인 불안정성이 발생합니다.

### 아키텍처 옵션 비교

| 구성 | 장점 | 단점 | 권장도 |
|------|------|------|--------|
| **듀얼 PC: Windows(SteamVR) + Linux(Isaac Lab)** | VD 트래커 에뮬레이션 사용 가능, 각 시스템 최적 환경 | 네트워크 홉 추가, 두 대 관리 | ★★★★★ |
| **Linux 단일 PC: ALVR + SteamVR + Isaac Lab** | 한 대로 운영, 네트워크 지연 없음 | SteamVR Linux 베타, ALVR 트래커 이슈, 불안정 | ★★★☆☆ |
| **Windows 단일 PC: SteamVR + Isaac Sim** | 한 대, VD 사용 가능 | Isaac Lab Docker가 WSL2에서 headless만 지원, Fast-DDS만 사용 가능 | ★★★☆☆ |

### 듀얼 PC ROS2 DDS 설정

ROS2 DDS 멀티머신 설정은 간단합니다. 두 PC를 동일 LAN에 연결하고 (직결 이더넷 케이블 권장):

```bash
# 양쪽 PC에서 동일 설정
export ROS_DOMAIN_ID=42
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp

# 또는 Fast-DDS Discovery Server 사용 (멀티캐스트 불필요)
# Linux PC에서 서버 실행:
fastdds discovery -i 0 -l 192.168.1.100 -p 11811
# 양쪽 PC:
export ROS_DISCOVERY_SERVER="192.168.1.100:11811"
```

**로컬 기가비트 LAN에서 ROS2 메시지 전송 지연은 0.1-0.5ms**로, VR 스트리밍 지연(20-50ms)에 비해 무시할 수 있는 수준입니다. PoseStamped 같은 작은 메시지에서는 네트워크 홉이 실질적 병목이 되지 않습니다.

### 최종 권장: 듀얼 PC

**Windows PC**(RTX Pro 6000이 여기에 있다면): SteamVR + Virtual Desktop 스트리머 + pyopenvr ROS2 노드 + UDCAP HandDriver
**Linux PC**: Isaac Lab + ROS2 구독자 + 리타게팅 + 시뮬레이션

또는 RTX Pro 6000이 Linux에 있고 별도 Windows PC가 있다면, Windows PC는 SteamVR/VR 전용으로, Linux PC는 Isaac Lab + GPU 시뮬레이션 용도로 분리합니다.

## 5. Isaac Lab 통합: 커스텀 DeviceBase와 리타게팅

### Isaac Lab 텔레오퍼레이션 아키텍처

Isaac Lab은 `isaaclab.devices` 서브패키지에서 **`DeviceBase`** 추상 클래스를 제공하며, 모든 텔레오퍼레이션 디바이스는 이를 상속합니다. 현재 기본 제공 디바이스:
- `Se3Keyboard`, `Se3SpaceMouse`, `Se3Gamepad` — 단순 입력
- `OpenXRDevice` — Apple Vision Pro, Quest 3, Pico 4 Ultra (CloudXR 경유)
- **`ManusVive`** — Manus 글러브 + HTC Vive 트래커 (네이티브 지원)

**SteamVR용 DeviceBase는 기본 제공되지 않으므로 커스텀 구현이 필요**합니다.

### 커스텀 SteamVR DeviceBase 구현 패턴

```python
from dataclasses import dataclass
from isaaclab.devices import DeviceCfg, DeviceBase
import torch
import rclpy
from geometry_msgs.msg import PoseStamped
from sensor_msgs.msg import JointState

@dataclass
class SteamVRDeviceCfg(DeviceCfg):
    tracker_topic_prefix: str = "/vr/tracker"
    hand_topic_prefix: str = "/vr/hand"

class SteamVRDevice(DeviceBase):
    def __init__(self, cfg: SteamVRDeviceCfg):
        super().__init__()
        self.cfg = cfg
        # ROS2 구독자 초기화
        self._hmd_pose = torch.zeros(7)  # pos(3) + quat(4)
        self._tracker_poses = {part: torch.zeros(7) for part in
            ['waist','left_foot','right_foot','left_elbow','right_elbow']}
        self._left_hand_joints = torch.zeros(21)
        self._right_hand_joints = torch.zeros(21)
        # rclpy 노드 또는 Isaac Sim ROS2 브릿지로 토픽 구독
    
    def reset(self):
        self._hmd_pose.zero_()
        for v in self._tracker_poses.values():
            v.zero_()
    
    def advance(self):
        # ROS2 토픽에서 최신 데이터 읽기
        # 리타게팅 파이프라인으로 전달
        return {
            'hmd': self._hmd_pose,
            'trackers': self._tracker_poses,
            'left_hand': self._left_hand_joints,
            'right_hand': self._right_hand_joints,
        }
```

### 리타게팅 파이프라인

Isaac Lab은 **3단계 리타게팅**을 사용합니다:

1. **손목 추적 → PinkIKController → 팔 관절 위치**: VR의 손목/팔꿈치 포즈에서 IK로 팔 관절 각도를 계산합니다. **PinkIKController**는 Pinocchio + QP 솔버 기반으로 **≤1mm 위치, ≤1° 방향 정밀도**를 달성합니다.

2. **손가락 추적 → dex-retargeting(DexPilot) → 손 관절 위치**: `dex-retargeting` 라이브러리의 `DexPilotOptimizer`가 손목-손끝 벡터와 손가락 간 벡터를 정렬하여 인간 손 포즈를 로봇 손에 매핑합니다. 이 라이브러리는 Allegro Hand, Shadow Hand, LEAP Hand, Inspire Hand 등을 지원합니다.

3. **전신 → 하체 제어**: 허리 + 발 트래커 데이터로 하체 관절을 제어하며, OmniH2O 스타일의 RL 정책이나 `G1LowerBodyStandingControllerRetargeterCfg` 같은 기존 리타게터를 사용할 수 있습니다.

### Isaac Lab에서 사용 가능한 휴머노이드 모델

| 로봇 | 제조사 | 손 | 텔레오퍼레이션 지원 |
|------|--------|------|-----------------|
| **GR1T2** | Fourier | 다지 핸드 | ✅ 가장 완벽 (PinkIK + DexPilot) |
| **G1** | Unitree | TriHand(3지) / Inspire(5지) | ✅ 상하체 분리 제어 |
| **H1** | Unitree | 단순 그리퍼 | 기본적 |
| **Digit** | Agility | 단순 엔드이펙터 | 보행만 |

GR1T2가 텔레오퍼레이션 시나리오에서 가장 완성도 높은 파이프라인을 가지고 있으며, `Isaac-PickPlace-GR1T2-Abs-v0` 환경과 `GR1T2Retargeter`가 준비되어 있습니다.

### 구현 로드맵 (예상 기간: 3-4주)

**1주차: 기본 연결 확립**
- Virtual Desktop 구매 및 Pico 4 Ultra + 5 트래커 SteamVR 연결 확인
- pyopenvr로 HMD + 5개 트래커 포즈 읽기 검증

- 듀얼 PC ROS2 DDS 통신 검증

**2주차: ROS2 브릿지 노드 개발**
- VR Tracker → ROS2 퍼블리셔 노드 (좌표 변환 포함)
- UDCAP UDP → ROS2 JointState 퍼블리셔 노드
- 동기화 번들 메시지 설계 및 구현

**3주차: Isaac Lab 커스텀 디바이스 통합**
- `SteamVRDevice(DeviceBase)` 구현
- PinkIKController 설정 (대상 휴머노이드 URDF에 맞춤)
- dex-retargeting YAML 설정 (대상 로봇 손에 맞춤)
- 기본 텔레오퍼레이션 루프 동작 확인

**4주차: 튜닝 및 최적화**
- 캘리브레이션 절차 정립 (VR 원점 ↔ 로봇 원점 정렬)
- 관절 각도 매핑 미세 조정
- 지연시간 프로파일링 및 최적화
- (선택) CloudXR 시각 피드백 통합

### 알려진 함정과 팁

- **Virtual Desktop의 Vive Tracker 에뮬레이션 설정을 반드시 활성화**해야 합니다. 기본 꺼져 있을 수 있으며, 이 설정 없이는 SteamVR 앱이 트래커를 인식하지 못합니다.
- **pyopenvr 초기화 시 `VRApplication_Other` 사용**: `VRApplication_Scene`이나 `VRApplication_Overlay`는 HMD 렌더링을 요구하므로, 데이터 수집 전용이면 `Other`를 사용합니다.
- **SteamVR 설정에서 `requireHmd: false`**: HMD 없이 트래커만 사용할 때 필요합니다 (`steamvr.vrsettings` 편집).
- **UDCAP Data Glove에는 위치 추적이 없음**: 손목 6DoF 포즈는 Pico 모션 트래커(팔뚝 모드) 또는 별도 Vive Tracker로 얻어야 합니다. Enhanced Forearm 모드의 양 팔뚝 트래커가 이 역할을 할 수 있습니다.
- **dex-retargeting의 URDF 요구사항**: 로봇 손의 fingertip 링크가 실제 손끝에 위치해야 합니다. 관절 중간에 있으면 DexPilot 최적화가 부정확해집니다.
- **QoS 불일치 주의**: 퍼블리셔와 구독자의 QoS가 호환되지 않으면 메시지가 전달되지 않습니다. 양쪽 모두 BEST_EFFORT로 통일합니다.
- **네트워크는 직결 이더넷 케이블** 권장: 스위치/라우터를 거치면 추가 지연이 발생할 수 있고, WiFi는 VR 스트리밍과 대역폭 경합이 생깁니다.

## 결론: 핵심 인사이트

이 프로젝트의 가장 큰 기술적 결정은 **SteamVR을 Linux에서 직접 돌릴 것인가, Windows에서 돌릴 것인가**입니다. SteamVR Linux가 베타이고 Pico 모션 트래커의 안정적 패스스루가 Virtual Desktop(Windows 전용)에서만 검증되어 있으므로, 듀얼 PC가 현시점 최적입니다. 다만 ALVR의 빠른 발전 속도를 고려하면, 6-12개월 내에 Linux 단일 PC 구성이 실용화될 가능성도 있습니다.

**UDCAP 글러브는 SteamVR 경유보다 직접 SDK(HandDriver UDP)가 명백히 우월**합니다. 120Hz에서 21개 관절 각도를 Linux에서 직접 수신하는 것이, SteamVR을 경유하여 5개 fingerCurl 값으로 축소되는 것보다 로봇 손의 정밀 제어에 적합합니다.

현재 학계의 휴머노이드 텔레오퍼레이션 트렌드는 카메라 기반(HumanPlus, AnyTeleop)이나 Apple Vision Pro(Bunny-VisionPro, Open-TeleVision) 방향이지만, SteamVR + 풀바디 트래커 + 글러브 조합은 **위치 추적 정밀도와 손가락 해상도에서 카메라 기반 방법을 크게 능가**하며, Apple Vision Pro 대비 **하체 트래킹과 전신 제어**에서 우위를 가집니다. `dex-retargeting` 라이브러리와 Isaac Lab의 `PinkIKController`를 활용하면, 커스텀 코드 양을 최소화하면서도 연구 수준의 전신 텔레오퍼레이션 시스템을 구축할 수 있습니다.
