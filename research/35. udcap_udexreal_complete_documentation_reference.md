> 출처: [UDexReal 공식 문서](https://udexreal.gitbook.io/udexreal-docs) (전 페이지 + llms-full.txt 추출)
> 목적: ust_fourier_260421 (Isaac Lab + Fourier GR1T2 + UDCAP gloves) 프로젝트에서 활용 가능한 UDexReal 의 모든 기능을 한 문서에 정리. 우리가 **이미 쓰고 있는 것**, **쓸 수 있는데 안 쓰는 것**, **무시해도 되는 것** 을 명확히 구분.

## 0. 한 줄 요약 (TL;DR for ust_fourier_260421)

> **UDexReal docs 의 ~80% 는 VR/게이밍/애니메이션용 (Plugin Unity/UE/Maya, Unity Interaction SDK, VRChat, MetaHuman) — 우리 로보틱스 워크플로우엔 무관. 우리가 즉각 활용 가능한 5가지: (1) Protobuf SDK (port 5555, binary, 5x 작은 packet), (2) Recording of Actions (FBX/BVH 데모 데이터셋), (3) Channel & Firmware (RF channel 6+ 간격 = crosstalk 방지), (4) Vibration API (port 8920, contact 햅틱 피드백), (5) HandDriver Web Deployment (B/S 아키텍처, 원격 모니터링). 추가 발견: UDCAP 글러브의 4 variants (Square 1-to-1 / Square 1-to-2 / Arcuate / IMU-based Arcuate) 중 우리가 쓰는 것이 어느 것인지에 따라 wired connection / channel 범위 / 펌웨어 업데이트 방법 모두 다름. 프로젝트 진행 전 사용자가 **자신이 보유한 글러브 variant 를 명확히 구분** 해야 한다.**

## 1. UDCAP 글러브 4가지 variant — 우리 프로젝트 관점 비교

[Packing List 페이지](https://udexreal.gitbook.io/udexreal-docs/hardware-instruction/packing-list) 기준:

| Variant | Receiver | 핵심 차이 | ust_fourier_260421 용도 |
|---|---|---|---|
| **Square Glove (1-to-1)** | 2 dongles (좌/우 각각) | Channel 1-99, 좌 default 6 / 우 default 15, **각 글러브당 1 USB port 필요** | △ 사용 가능 |
| **Square Glove (1-to-2)** | 1 dongle (양손 통합) | Channel 0-49, **wired Type-C 모드 지원 (HandDriver 2.2.1+)** , 1 USB port 만 | ✅ **권장 (lower latency 옵션)** |
| **Arcuate Glove** | 2 dongles | IMU 없음, Channel 1-99, **Web Deployment 미지원** | △ 가능 (단 wired/web 기능 X) |
| **IMU-Based Arcuate Glove** | 2 dongles | **IMU 추가 → 손목 쿼터니언 자체 추적** , 시작 시 평평히 두고 power-on 필요 | ✅ **권장 (IMU 데이터로 손목 회전 정확도 ↑)** |

### 1.1 사용자 액션 — 자신의 글러브 식별 방법

**전원 후 LED 색상 확인**:
- **Arcuate**: 빨간 LED (초기화) → 파란 LED 깜박임 (페어링 중) → 파란 LED 상시 (HandDriver 연결됨)
- **Square**: 초록 LED 상시 (HandDriver 연결됨), 충전 시 초록 LED 깜박임

**Receiver 외관**:
- 1-to-1: 좌/우 USB dongle 2개 (서로 다른 생김새)
- 1-to-2: 1개 USB dongle 만 (양손 통합)

**HandDriver UI 의 "Add Character" 화면**:
- 1-to-1: receiver dropdown 에서 좌/우 별도 선택
- 1-to-2: receiver type 먼저 선택 후 unit 선택

→ **사용자 측 권장 액션**: 시뮬레이션 시작 전 LED 색상 + USB dongle 개수 확인 후 docs 의 해당 variant 섹션을 우선 참조

### 2.1 우리 프로젝트가 활용 중인 옵션 vs 미활용 옵션

| 옵션 | 9.27 상태 | 활용 가능성 |
|---|---|---|
| Data Transmission Format | **VMC** | → Protobuf 전환 가능 (research/34 Phase E) |
| FPS | (사용자 측 설정 미확인) | **사용자 확인 필요 — 120 Hz 인지** |
| Multi-target | 사용 안 함 | △ 디버깅 시 다른 머신에 동시 송신 가능 |
| Recording of Actions | 사용 안 함 | ⭐ **데모 데이터셋 생성 (BC training 용)** 활용 가능 |
| Channel | default | 사용자 측 다른 무선기기 (Wi-Fi 6 GHz, 다른 글러브) 와 충돌 시 변경 권장 |
| IMU 토글 | 사용자 측 미확인 | IMU 글러브면 활성화 시 손목 회전 정확도 ↑ |
| Vibration | 사용 안 함 | ⭐ **contact event 햅틱 피드백** 활용 가능 (research/34 Phase G) |
| Web Deployment | 사용 안 함 | △ 원격 모니터링/공유 시 유용 |
| Linux deployment | 사용 안 함 | △ Linux Isaac Lab 환경 운영 시 |

## 3. 데이터 전송 프로토콜 — 3가지 + Vibration

### 3.1 비교 매트릭스

| 항목 | VMC (현재) | JSON (Euler) | JSON (Quaternion) | Protobuf | Vibration |
|---|---|---|---|---|---|
| 포트 (default) | 39539 (UDCAP 측) | 5555 | 5555 | 5555 | 8920 |
| 형식 | OSC text | UTF-8 JSON | UTF-8 JSON | binary | UTF-8 JSON |
| Packet 크기 (양손 30 bones) | ~3500-4000 B | ~1500-2000 B | ~1500-2000 B | **~700-900 B** | ~50-100 B |
| Joint 표현 | quat per bone | l0-l27 + r0-r27 (각도) | bones[0..14] (xyzw) | TeleopDataAngle/Quat protobuf | LeftHand/RightHand 진동 명령 |
| Schema | OSC `/VMC/Ext/Bone/Pos` | 위 l/r 프리픽스 | DeviceID + bones array | `handdriver_teleop.proto` | `{"ctrl": {"LeftHand": [vibrator,duration,amplitude]}}` |
| 설계 의도 | VR 아바타 | 일반용 | 일반용 | **로보틱스** | 햅틱 피드백 |
| 양손 통합 | ❌ (bone 별 packet) | ✅ (l/r 한 message) | ❌ (DeviceID 별) | ✅ (LeftHand+RightHand 한 message) | ✅ |
| 우리가 사용? | ✅ | ❌ | ❌ | ❌ | ❌ |

### 3.2 Protobuf 사용 시 권장 schema (TeleopDataQuat)

`handdriver_teleop.proto` (공식 SDK 가 정의):
```protobuf
message TeleopDataQuat {
  int64 TimeStamp = 1;
  int32 FrameIndex = 2;
  string RoleName = 3;
  HandData LeftHand = 4;
  HandData RightHand = 5;
}

message HandData {
  string serial = 1;
  int32 battery = 2;
  int32 calibration_state = 3;
  // joints[0..14] — 양손 각각 15 quat (proximal/intermediate/distal × 5 fingers)
  repeated Quaternion joints = 10;
  Quaternion imu = 11;        // IMU 글러브 만
  // 컨트롤러 입력
  float joyX = 20;
  float joyY = 21;
  bool aButton = 22;
  bool bButton = 23;
  bool joyButton = 24;
  bool menu = 25;
}

message Quaternion { float x; float y; float z; float w; }
```

### 3.3 Vibration JSON schema (port 8920)

```json
{
  "ctrl": {
    "LeftHand": [vibrator_idx, duration_sec, amplitude],
    "RightHand": [vibrator_idx, duration_sec, amplitude]
  }
}
```
- `vibrator_idx`: 0=none, 1=button vib (검지/엄지 사이), 2=joystick vib (손바닥), 3=both
- `duration_sec`: 0.04 - 2.5
- `amplitude`: 4 - 10
- LAN 내에서만 동작

### 4.1 Protobuf SDK Python 사용 예 (공식 reference)

```python
# 공식 udp_receiver.py 예제 (HandDriver_Cross_Python_Protobuf_src 패키지에서)
python udp_receiver.py --port 5555 --type quat
# 또는
python udp_receiver.py --port 5555 --type angle
```

수신 루프 골격:
```python
import socket
from handdriver_teleop_pb2 import TeleopDataQuat
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("0.0.0.0", 5555))
while True:
    data, addr = sock.recvfrom(8192)
    pkt = TeleopDataQuat()
    pkt.ParseFromString(data)
    print(pkt.LeftHand.joints[0])  # (x, y, z, w)
```

## 5. Linux 환경 구축 가이드 (잠재적 미래 옵션)

[HandDriver Linux docs](https://udexreal.gitbook.io/udexreal-docs/llms-full.txt):

### 5.1 호환성
- **OS**: Ubuntu 18 / 20 / 22 / 24 (AMD64 only — ARM64 미지원)
- **GPU 드라이버**: nouveau 비호환, NVIDIA proprietary 필요
- **OpenGL**: 제거 시 HandDriver 부팅 실패

### 5.2 설치 절차
```bash
# 1. brltty 충돌 해결 (Ubuntu 일부 배포판)
sudo apt remove brltty || sudo systemctl disable brltty.service

# 2. 실행 권한
sudo chmod +x HandDriver.x86_64

# 3. receiver 먼저 꽂은 후 실행 (순서 중요!)
sudo ./HandDriver.x86_64

# 4. /dev/ttyUSB* permission (필요 시)
sudo chmod 666 /dev/ttyUSB0    # 1-to-1 receiver
sudo chmod 666 /dev/ttyACM0    # 1-to-2 receiver

# 5. recognition 검증
lsusb | grep -i udexreal
sudo dmesg | tail -20
#   1-to-2: "UDEXREAL" + "ttyACM"
#   1-to-1: "ch341-uart converter now attached to ttyUSB"
```

### 5.3 우리 프로젝트 시나리오
- **현재**: Windows + Isaac Lab + UDCAP HandDriver 모두 같은 PC
- **장기**: Linux Isaac Lab 별도 머신 + Windows HandDriver 별도 머신 → Multi-target UDP 송신 가능
  - HandDriver 의 "Target IP" 에 Linux 머신 IP 추가
  - Linux Isaac Lab 의 VMC/Protobuf 수신기가 외부 UDP 수용
  - 추가 latency: 같은 LAN 내 ~1-3 ms (무시 가능)
- **이점**: Linux Isaac Lab 의 GPU 활용 + Windows 의 SteamVR/UDCAP 분리

### 5.4 HandDriver Web Deployment (B/S 아키텍처)
- 1-to-2 receiver 글러브 만 지원
- Linux: HandDriver 2.2.4+ 자동 deploy (Nginx + Backend)
- Default port: 8088 (HTTP) / 443 (HTTPS, SSL 별도 구성)
- Windows: `HDService.exe` 직접 실행
- 다중 client 동기화 (한 client 의 calibration 다른 client 들에게 자동 반영)
- **제약**: FBX/BVH 녹화 미지원, 펌웨어 업데이트 미지원, 엄지 root 조정 미지원
- **우리 활용**: SteamVR ↔ Isaac Lab 분리 시, 또는 외부 모니터링 대시보드

## 6. PICO MotionTracker 통합 — 손가락이 아니라 위치 트래킹용

[Glove & PICO MotionTracker Guide](https://udexreal.gitbook.io/udexreal-docs/gloves-in-vr-headsets/glove-and-pico-motiontracker-guide):

### 6.1 지원/요구사항
- **PICO 모델**: 4 Ultra Enterprise / 4 Enterprise / neo3 Enterprise (**Consumer 모델 미지원**)
- **OS**: PICO OS v5.12+
- **Body Tracker SW**: 2.0.1+
- **PICO Unity SDK**: 2.3.4 preview+
- **PICO UE SDK**: 2.3.0+

### 6.2 페어링 절차
1. PICO MotionTracker 를 "Object Tracking" 모드로 변경
2. 시스템 prompt 따라 연결 (첫 연결 = 좌수)
3. 벨크로로 글러브에 부착 (글러브 데이터 박스 위치)

### 6.3 우리 프로젝트 영향
- **PICO MotionTracker 는 손목/손의 6DoF 포지션 + 회전 만 제공** — 손가락 굽힘 데이터 아님
- 손가락 데이터는 여전히 UDCAP RF dongle → HandDriver → UDP 경로
- 우리가 SteamVR forearm tracker 로부터 받던 정보와 동일 종류
- 9.26 `--ignore_trackers` 처리는 PICO MotionTracker 도 같이 무시
- **사용자 PICO 4 Ultra (Consumer) 사용 시 미지원** → 시도 가치 없음

## 8. 데모 데이터 녹화 — Recording of Actions (Imitation Learning 용)

[Recording docs](https://udexreal.gitbook.io/udexreal-docs/llms-full.txt) 에서 추출:

### 8.1 핵심 사양
- 형식: **FBX** 또는 **BVH**
- 프레임 rate: 24 / 30 / 60 / 96 / 100 / 120 fps
- 본 범위: Hand-only / Full Body / Both
- 최대 1시간 (자동 종료)
- 다중 캐릭터 동시 녹화 (모든 "showed" 캐릭터)
- 파일명: `{YYYY_MM_DD_HH_MM_SS}_Device{N}_FPS{xx}_{Hand|Body}.{fbx|bvh}`

### 8.2 우리 프로젝트 활용 시나리오
- **현재**: ust_260502_win 의 4-layer test harness 가 HDF5 (Robomimic) 형식으로 녹화 중 (Pink IK 36D action 시계열)
- **추가 활용 가능**: HandDriver 의 FBX 녹화로 손가락 motion 만 별도 녹화 → BC-RNN training 의 finger-only 데이터셋 보강
  - 손목 트래커 / Pink IK 결과는 Isaac Lab HDF5 에 저장
  - 손가락 raw motion 은 HandDriver FBX 에서 추출 → 후처리로 결합
- **caveat**: FBX 의 hand bone 이 Fourier 11-joint 와 매핑 필요 (Sample Hand Model 의 bone 이름 대응)

### 8.3 BC-RNN training 데이터 multi-source
| Source | 형식 | Pros | Cons |
|---|---|---|---|
| Isaac Lab HDF5 (현재) | hdf5 (timestamped 36D action) | Pink IK 결과 그대로, env state 포함 | 실시간 quality 기록 X |
| HandDriver FBX | FBX (skeletal animation) | UDCAP 원본 데이터 | Fourier 매핑 추가 필요 |
| HandDriver BVH | BVH (joint angle 시계열) | 텍스트, 디버깅 용이 | FBX 와 동일 매핑 필요 |
| HandDriver CSV (Data Acquisition) | CSV | tabular 데이터 분석 용이 | 1-to-1 receiver, 캐릭터당 1 file |

→ **권장**: 본격 데이터셋 수집 시작 시 HandDriver CSV (raw 글러브 데이터) + Isaac Lab HDF5 (시뮬 결과) 병행 → 후처리로 retargeting accuracy 검증 가능

## 9. Channel & Firmware Management — 다중 글러브 / RF 간섭 대응

[Channel docs](https://udexreal.gitbook.io/udexreal-docs/llms-full.txt):

### 9.1 채널 spacing 권장
- **Square 1-to-1**: channel 1-99, 좌 default 6 / 우 default 15 → **간격 9** (안전)
- **Square 1-to-2**: channel 0-49 (좌/우 통합)
- **Arcuate**: channel 1-99
- **6+ 채널 간격 권장** (crosstalk 방지)
- 채널 변경 시 글러브를 **receiver 10cm 이내** 까지 가져가기

### 9.2 우리 프로젝트 시나리오
- **현재**: 단일 사용자, 단일 글러브 pair → channel 변경 거의 무관
- **잠재 문제**: 사용자가 다른 무선기기 (Wi-Fi 6 GHz, Bluetooth, 다른 글러브) 와 같은 2.4 GHz 대역 사용 시 crosstalk
  - 증상: HandDriver 에서 **action stuttering** 또는 disconnection
  - 해결: HandDriver UI → Channel → 6+ 다른 채널로 변경
- **다중 글러브 (8 pair) 사용 시**: 1-to-1 = 99 채널 / 6 spacing = 최대 16 pair, 1-to-2 = 50 채널 / 6 spacing = 최대 8 pair

### 9.3 Firmware Update 절차
- **Square 1-to-1**: USB-C wired 만 → 글러브 끄기 → Type-C 데이터 케이블 (핑크 손가락 측 포트) → HandDriver 의 update 실행 → "Latest Version" 표시 → 자동 재시작
- **Square 1-to-2**: 무선 가능 → HandDriver 에서 update 실행 (popup 닫으면 안 됨)
- **Arcuate**: 별도 절차 (docs 에 명시 없음)

→ **사용자 측 권장**: HandDriver 시작 시 "Update Available" 빨간 점 보이면 firmware 업데이트 실행. 최신 펌웨어가 latency / drift 개선 가능성.

## 10. Calibration 심화 — 영구 저장 / hot-reload / drift 대응

### 10.1 캘리브레이션 메커니즘
- **3-step**: 주먹 (3초) → 손가락 펴고 모음 (3초) → 손가락 최대 벌림 (3초)
- **Trigger**:
  - Square: 글러브 스위치 0.5초 누름
  - Arcuate: HandDriver SW 의 "Calibration" 버튼
  - 양쪽 다 HandDriver UI 의 단축키 가능 (1-3 키 조합)
- **권장 자세**: 손바닥 아래로, 손목 약간 아래 굽힘
- **재캘 빈도**: 시간당 1번 권장 (Calibration Reminder 옵션 60분 설정)

### 10.2 영구 저장 / 재시작 시
- 캘리브레이션 결과는 HandDriver 종료 후에도 보존
- 재시작 시 사용자가 "재캘 vs 기존 사용" 선택
- **drift**: 글러브 sensor 자연 drift 로 시간 경과 시 inaccuracy 증가 → 1시간마다 재캘 권장

### 10.3 우리 프로젝트 영향
- 현재 `vmc_rest_frames=60` (시뮬 측) 으로 추가 zero cal 수행 중 — HandDriver cal 과 별도 layer
- HandDriver cal 이 "open hand = quat identity" 보장 안 함 → 우리 mapper 의 `vmc_subtract_rest=True` 가 필수
- 사용자 hot-reload 키 (research/32 §8.1 후보) 추가 가능 → Isaac Sim 안 끄고 mapper.reset_vmc_rest()
- **장기 fix**: HandDriver 측 계측 결과를 SDK 로 받아서 자동 zero-cal 가능 (현재 미구현)

## 11. FAQ — 사용자가 겪을 수 있는 문제 + 해결

[FAQs page](https://udexreal.gitbook.io/udexreal-docs/faqs/faqs) 정리:

### 11.1 Hardware 문제

| 증상 | 해결 |
|---|---|
| 글러브 미인식 | 글러브 off → on, 채널 일치 확인, 1-to-2 면 채널 占有 적은 쪽 선택 |
| Receiver 미인식 (Windows) | Device Manager → Ports (COM & LPT) 확인, USB serial device 보이는지, 미설치 시 receiver driver 별도 설치 |
| USB 호환 문제 | USB 2.0 권장 (3.0 일부 컴퓨터에서 충돌), 데이터 연장 케이블 + 어댑터 사용 |
| HandDriver 2.1.8 이전 | PC 당 CH340 device 1개만 인식 |
| 데이터 박스 케이블 분리 | 금속면 아래로, 검정 테두리가 검정 버클 안에 완전 고정 |

### 11.2 Connection 문제

| 증상 | 해결 |
|---|---|
| 사용 중 disconnect | Channel crosstalk 가능, 6+ 간격 채널로 변경 (예: 31 vs 32 → 좌 6 / 우 15 같이) |
| Pairing 실패 | 1-to-2 receiver 글러브는 re-pair 가능, HandDriver UI 에서 다시 페어링 |
| 글러브 거리 | 2-3m 이내 권장, 최대 5m |

### 11.3 Performance / Latency 문제

| 증상 | 해결 |
|---|---|
| 동작 stuttering / delay | (1) channel crosstalk, (2) 거리 과다, (3) 컴퓨터 사양 부족 (Task Manager 모니터링) |
| 손모양 빨간 점 다수 | 글러브 size 사용자 손에 맞지 않을 수 있음 → 안감 글러브 (lining glove) 착용 |
| 빨간 점 (sensor 단위) | Sensor 고장 가능성 → 기술 지원 문의 |

### 11.4 Calibration 문제

| 증상 | 해결 |
|---|---|
| Calibration 결과 부정확 | 손바닥 아래로, 손목 약간 굽힘 자세 유지 |
| 기존 cal 사용 vs 새 cal | 매 sessions 시작 시 사용자 선택, drift 의심 시 새 cal |

### 11.5 Data Transmission 문제

| 증상 | 해결 |
|---|---|
| 외부 앱이 데이터 못 받음 | (1) Target IP 와 port 일치, (2) Character name 매칭, (3) 네트워크 안정성, (4) hand mapping 설정 |
| Multi-target 안 보냄 | HandDriver 2.2.2+ 부터 broadcast 미지원, "+" 버튼으로 unicast 다수 추가 |

### 11.6 우리 프로젝트 trouble-shooting checklist

ust_fourier_260421 의 사용자 보고 "lag" 증상이 보일 때 확인:
1. ✅ HandDriver UI 의 FPS = 120 Hz?
2. ✅ Channel crosstalk 없음? (6+ spacing, 다른 무선 기기 OFF)
3. ✅ 글러브-receiver 거리 < 2-3 m?
4. ✅ USB 2.0 port 사용? (USB 3.0 충돌 시 USB 2.0 hub 거쳐 연결)
5. ✅ Calibration 최근 1시간 이내 수행?
6. ✅ 글러브 안감 적절히 착용? (느슨하면 sensor 부정확)
7. ✅ Receiver Driver / HandDriver 최신 버전? (HandDriver 2.1.9 r1 / Udcap-Driver v0.1.3.3)
8. ✅ Task Manager 에서 HandDriver / python.exe CPU < 80% 확인?

## 14. 사용자 의사결정 가이드 — 다음 단계

### 14.1 사용자가 즉시 답해야 할 4 질문

1. **글러브 variant 가 무엇인가?**
   - Square 1-to-1 / Square 1-to-2 / Arcuate / IMU Arcuate 중 어느 것?
   - 답에 따라 wired connection / web deployment 가능성, 채널 범위 결정

2. **HandDriver 버전이 무엇인가?**
   - 2.2.2+ → JSON / Protobuf / VMC 모두 지원
   - 2.2.1 ↔ 2.1.7 → Euler / Quat / VMC mutually exclusive
   - 2.1.6 이전 → broadcast 가능 (legacy)
   - 답에 따라 Phase E (Protobuf) 가능성 결정

3. **HandDriver UI 의 FPS 가 몇 Hz 로 설정되어 있는가?**
   - 60 / 90 / 120 — 120 이어야 9.24 와 매칭
   - 답에 따라 9.23 EMA / 9.24 decimation 의 sub-sampling 비율 재계산

4. **PICO 모델이 Consumer 인가 Enterprise 인가?**
   - Consumer 4 Ultra → Android Service / MotionTracker 미지원
   - Enterprise 4 Ultra → 모두 지원 (단 우리 use case 와 무관)

### 14.2 9.27 이후 개선 path 우선순위

```
Phase E [Protobuf 전환]  ← 가장 효과 큼 (5-10 ms)
   ↓

   ↓
Phase G [Vibration API 통합]  ← perceived latency 단축
   ↓
[사용자 글러브 variant 확인]
   ↓ (square 1-to-2 인 경우)
Phase J [Wired Type-C 연결 시도]  ← RF latency ~1-2 ms 단축
   ↓
[모든 SW 적용 후에도 lag 잔존 시]
   ↓
Phase H [HW 교체 — Manus Quantum / 다른 글러브]  ← 큰 비용
```

## 16. 부록 — 발견한 docs 의 limitation / 정정

### 16.1 docs 가 누락한 정보 (사용자 측에서 직접 확인해야 함)

| 항목 | docs 상태 | 확인 방법 |
|---|---|---|
| End-to-end latency 측정 방법 | "< 10ms" 만 | 자체 측정 (research/34 §4.1) |
| IMU sample rate vs UDP rate | 명시 없음 | 60/90/120 Hz UDP rate 만 확정, IMU 내부 sample rate 불명 |
| Sub-driver / kernel-level access | 없음 | UDP 만 노출, 직접 receiver 통신 방법 미공개 |
| Wired 연결 시 latency 변화 | 명시 없음 | RF 제거로 1-2 ms 추정 (research/34 §3.4) |
| Glove sensor scan rate | 명시 없음 | docs 에 sensor-level spec 없음 |
| Protobuf .proto 파일 자체 download URL | Google Drive folder 만 (직접 link 불명) | Protobuf SDK 패키지 안에 포함 |

### 16.2 우리 memory.md / CLAUDE.md 정정 필요 사항

1. **9.23 / 9.24 의 "UDCAP 140 Hz" 가정 → "UDCAP 120 Hz"** (max 공식 spec)
2. **9.24 의 "1.17:1 sub-sampling" → "1:1 매칭"** (decimation=1, sim.dt=1/120)
3. **9.23 EMA 의 본래 정당화 약화 명시** — UDCAP 가 120 Hz, env.step 120 Hz 일 때 sub-sampling 거의 없음
4. **HandDriver UDP rate 가 사용자 측 설정에 의존** — UI 에서 60 Hz 설정 시 EMA/decimation 의미 다름
5. **Udcap-Driver vs HandDriver 구분** — GitHub 레포는 OpenVR 드라이버 (SteamVR 컨트롤러 에뮬), UI 앱은 별도 (Google Drive)
