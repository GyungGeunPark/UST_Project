# 37. SteamVR 직접 입력 vs VMC OSC — UDCAP 글러브 + 트래커 + 컨트롤러 통합 경로 권장 가이드

> 작성: 2026-05-06
> 사용자 보고: PICO 4 Ultra 의 PICO 네이티브 streaming 으로 SteamVR 진입 → 테스트 컨트롤러 화면에서 컨트롤러 + 모션 트래커 (SteamVR 표시 = "Vive Tracker") 모두 정상 동작 확인. 그동안 Virtual Desktop 으로만 모니터 화면 확인하던 상태에서는 못 보던 것. UDCAP 글러브 역시 동작하는데 우리가 못 본 것일 가능성.
> 배경: research/27 ~ 36 의 9.13 ~ 9.28 fix 시리즈가 모두 VMC OSC 경로 (port 39539) 로 UDCAP 손가락 데이터를 받아 ust_fourier_260421 의 retargeter 에 입력하는 구조 + research/34 가 Protobuf path C 도입 (Phase E) 을 추천.
> 핵심 질문: VMC 가 아닌 **SteamVR 입력 (OpenVR Action API + Skeletal Input 2.0)** 으로 모든 신호 (HMD + 컨트롤러 + 트래커 + UDCAP 글러브 손가락) 를 통합 수신하는 것이 가능한가? 가능하다면 그것이 더 나은 path 인가, 아니면 현재 VMC + research/34 의 Protobuf 방향 그대로 가야 하는가?

## 0. 한 줄 요약 (TL;DR)

> **결론 1 — 좋은 소식**: 우리 코드베이스는 **이미 SteamVR 직접 입력 경로를 완전히 구현해 두었다**. `ust_ws/ust_260418_win/teleop/vr_sampler.py` 의 `SteamVRSampler` 가 pyopenvr 로 (1) HMD pose, (2) Vive 트래커 / 모션 트래커 pose, (3) 컨트롤러 pose + 버튼 + axis, (4) **양손 31-bone Skeletal 데이터 (Skeletal Input 2.0)**, (5) 5-finger curl (Index emulator action) 까지 모두 sampling 한다. `gr1t2_retargeter.py::_resolve_hand_joints` 의 **6단계 우선순위 chain** 이 [DexPilot → Skeletal bones → Action curls → VMC OSC → trigger/grip → idle] 순으로 fallback 한다. 즉 **사용자가 PICO 네이티브 streaming 에서 본 모든 SteamVR 신호는 코드가 이미 받을 수 있다** — 다만 UDCAP 의 skeletal 채널이 우리 PC 에서 활성화되지 않아 항상 4번째 (VMC) 로 폴백되어 왔다.
>
> **결론 2 — 진짜 봐야 할 것**: 사용자의 새 관찰 (PICO 네이티브 → SteamVR 에서 트래커 정상 표시) 은 실제로 큰 의미가 있다. 그동안 Virtual Desktop 만 켜두고 모니터 모드로 디버깅 했기 때문에 SteamVR 의 트래커/컨트롤러 status 를 본인 눈으로 확인한 적이 거의 없었다. **PICO Connect 모드 + UDCAP 의 v0.1.8.1 (2026-03-12 release)** 조합에서는 UDCAP 의 Skeletal Input 2.0 도 활성될 가능성이 높다 (UDCAP 공식 docs: "perfectly supports VRChat's latest Skeletal Input 2.0"). 가장 먼저 해야 할 일은 **"SteamVR 직접 경로가 이미 켜져있는지 / Skeletal 채널이 활성인지"** 를 코드로 확인하는 것 — 이미 우리가 만들어 둔 `_probe_openvr_skeletal()` 진단으로 5분 안에 결정 가능.
>
> **결론 3 — 권장 절차 (Phase X)**:
> 1. **즉시 (5–15분)**: `python -X utf8 -m ust_ws.ust_fourier_260421.scripts.diagnose_udcap_dataflow` 실행 + teleop 시 standalone 으로 _probe_openvr_skeletal 결과 확인 (이미 device 시작 시 자동 출력). UDCAP 글러브 v0.1.8.1 driver 가 **Skeletal Input 2.0 활성** 이면 → `bActive=True` + `tracking_level≥1` (Partial 이상) 이 보일 것. 이 한 줄로 "VMC 계속 가야 하는지 / SteamVR direct 로 갈아탈 수 있는지" 가 결정된다.
> 2. **Skeletal 활성 확인 시 (Phase X1, 1–2시간)**: 현재 6단계 priority chain 의 첫 번째에 이미 위치한 Skeletal 경로가 자동으로 채택됨. 추가 코드 변경 0줄. 단, **`enable_skeletal=True`** 가 cfg default (이미 그렇게 됨) 이고 `--ignore_trackers` 같은 umbrella flag 가 끄지 않는지 한 번만 검증하면 끝. 그리고 VMC 의존성을 점진 제거 (`path_b_port=0` 으로 OSC listener 제거 → CPU/네트워크 부담 감소).
> 3. **Skeletal 비활성, finger curl 만 활성 시 (Phase X2, 1시간)**: priority chain 3번째 (action curls) 가 자동 채택. `bindings_udcap.json` 이 이미 `/input/finger/{thumb,index,middle,ring,pinky}` 5채널을 바인딩 — `Save Personal Binding` 만 SteamVR UI 에서 누르면 됨.
> 4. **둘 다 비활성 시 (Phase X3)**: 현재 VMC path 그대로 유지 + research/34 의 Phase E (Protobuf) 적용. UDCAP driver/glove 페어링/캘리브레이션 문제로 SteamVR layer 자체에 데이터가 안 가는 케이스 → research/34 §1.5 의 PICO MotionTracker Guide (Enterprise 모델만 지원) 문제는 별개.
>
> **결론 4 — 상황별 권장 final**:
> - **사용자가 SteamVR 직접 사용 가능 = True (highly likely 시나리오)**: VMC 는 **fallback 으로 demote**, primary 는 SteamVR Skeletal/Action API 로 이동. 이게 가장 latency 도 짧고 (parsing 단순화 ~1–3 ms 단축), 코드도 단순해지고, **research/34 의 Protobuf 작업 (Phase E) 은 보류** — Skeletal/Action API 가 이미 binary stream 이라 Protobuf 의 packet-크기 이점과 사실상 equivalent.
> - **SteamVR 직접 사용 불가 (skeletal + curl 모두 비활성)**: research/34 의 Phase E (Protobuf) 진행. 이 시나리오는 UDCAP driver/binding 자체 문제 — SteamVR layer 가 working 인지 별개로 검증.

## 1. 사용자의 새 관찰 — 의미 분석

### 1.1 그동안의 셋업 (Virtual Desktop 단독)

memory.md §10.27 ~ §10.34 와 사용자 보고에 따르면 그동안 verification flow 는:

1. PICO 4 Ultra 부팅 → Virtual Desktop 앱 실행
2. PC 측 Virtual Desktop Streamer + SteamVR 자동 시작
3. Isaac Sim 을 **monitor mode** (`--render_mode monitor`) 로 시작
4. 손가락 / 팔 움직임 검증은 PC 모니터로만 확인
5. SteamVR overlay 자체는 거의 보지 않음

**문제점**: SteamVR 의 "Test Controller" / "Devices" 화면을 한 번도 안 봤기 때문에, UDCAP 글러브의 skeletal 채널이 SteamVR 에서 **bActive=True** 인지 / 트래커가 어떤 serial 로 잡히는지 / Vive Tracker 로 표시되는지 모두 black-box.

### 1.3 Virtual Desktop vs PICO Connect 의 차이 (트래커 path)

| 트래커 경로 | Virtual Desktop | PICO Connect (네이티브) |
|---|---|---|

| **End-to-end latency** | ~30-60 ms (VD encode+RF+decode) | ~25-40 ms (PICO 공식 path) |

## 2. SteamVR 직접 입력 경로 — 이미 구현된 stack

### 2.1 SteamVRSampler (`ust_260418_win/teleop/vr_sampler.py`) 의 capability

`SteamVRSampler` 는 background thread 로 120 Hz 에서 다음을 sampling:

```python
snapshot = {
    "hmd":         {"pos": (3,), "quat": (4, wxyz)},
    "trackers":    {role: {"pos": (3,), "quat": (4, wxyz)}},   # tracker_binding.json serial → role
    "hands": {
        "left":  {"bones": (31, 7), "fingerCurls": (5,), "fingerSplays": (4,)},
        "right": …,
    },
    "controllers": {
        "left":  {"pose": ..., "buttons": {"trigger": float, "grip": float, "menu": bool}},
        "right": …,
    },
}
```

| 채널 | OpenVR API | 활성 조건 |
|---|---|---|
| HMD pose | `getDeviceToAbsoluteTrackingPose` (TrackingUniverseStanding) | HMD 켜짐 (항상) |
| 트래커 pose | 동일 (TrackedDeviceClass_GenericTracker) | tracker_binding.json 에 serial 등록 |
| 컨트롤러 pose | 동일 (TrackedDeviceClass_Controller) | 컨트롤러 페어링 + 트래킹 |
| **컨트롤러 axis (trigger/grip)** | `getControllerState` (legacy) + 우리 device 의 `_read_action_inputs` (action API) | 컨트롤러 binding 활성 |
| **31-bone hand skeleton** | `VRInput.getSkeletalBoneData(handle, Model_space, WithoutController_range)` | 글러브 driver 가 Skeletal Input 2.0 구현 + binding 활성 |
| **5-finger curl summary** | `VRInput.getSkeletalSummaryData` | 동일 (skeletal 활성) |
| **5-finger curl per-action** | `VRInput.getDigitalActionData / getAnalogActionData` for `/input/finger/*` | UDCAP-native binding (`controller_type=udcap`) 활성 |

### 2.2 Retargeter 의 6단계 우선순위 chain (`gr1t2_retargeter.py:756-870`)

```
1. DexPilot       → URDF + skeletal fingertips → 11-DoF/side optimizer
2. Skeletal bones → 31 bones → FourierHandMapper.map_hand_skeletal → 11-DoF/side
3. Action curls   → 5 per-finger floats (UDCAP 의 finger_thumb_left 등) → map_from_finger_curls
4. VMC OSC bones  → UDP 39539 → VMCHandReceiver → map_hand_vmc → 11-DoF/side  (현재 default)
5. Trigger/grip   → 2 binary signals → 미구현, idle
6. Idle / zero    → 모든 손가락 0
```

각 단계는 이전 단계의 데이터가 부재 (`None`) 일 때만 fall through. **사용자가 SteamVR 에서 컨트롤러/트래커 본 것은 1-3 단계의 사전 조건 (`SteamVRSampler` 가 OpenVR 와 통신 OK) 가 충족 됨을 의미**.

### 2.3 actions.json + bindings_udcap.json 의 design intent

`config/openvr_actions/actions.json:33-44`:
```json
{ "name": "/actions/teleop/in/skeleton_left",  "type": "skeleton",
  "skeleton": "/skeleton/hand/left",  "requirement": "optional" },
{ "name": "/actions/teleop/in/skeleton_right", "type": "skeleton",
  "skeleton": "/skeleton/hand/right", "requirement": "optional" },
```

`config/openvr_actions/bindings_udcap.json:30-40`:
```json
"skeleton": [
  { "output": "/actions/teleop/in/skeleton_left",
    "path":   "/user/hand/left/input/skeleton/left" },
  { "output": "/actions/teleop/in/skeleton_right",
    "path":   "/user/hand/right/input/skeleton/right" }
]
```

→ **UDCAP 의 native skeleton 출력에 대한 binding 이 이미 작성돼 있음**. SteamVR 의 binding resolver 가 device 의 controller_type (`"udcap"`) 와 매칭되는 binding 을 자동 적용.

### 2.4 우리가 이미 구축한 진단 도구

| 도구 | 위치 | 용도 |
|---|---|---|
| `_probe_openvr_skeletal()` | `gr1t2_udcap_device.py:762-828` | Device 시작 시 자동 호출 — `bActive` / `getSkeletalTrackingLevel` / `getBoneCount` 출력 |

## 3. 정량 비교 — VMC vs SteamVR Skeletal vs SteamVR Action curls

### 3.1 데이터 raw spec 비교

| 채널 | 데이터 양 (per frame) | 업데이트 rate | Latency (sensor → Python) | Priority chain 단계 |
|---|---|---|---|---|
| **OpenVR Skeletal Input 2.0** (1) | **31 bones × 7 (pos+quat) = 217 floats/hand × 2 hands = 434 floats** | 120 Hz | sensor → driver → SteamVR shared mem → vr_input call → Python = ~5-10 ms | 2 (skeletal) |
| **OpenVR Action curls** (2) | 5 floats/hand × 2 = 10 floats | 120 Hz | 동일 ~5-10 ms | 3 (finger_action) |
| **VMC OSC** (3) | 30 bones × 8 OSC args = ~3500-4000 byte text | UDCAP UI 설정 (default 120 Hz) | UDP loopback + OSC parse = ~2-4 ms | 4 (vmc) |
| **Protobuf SDK** (4, research/34 추천) | 양손 30 quats binary = ~700-900 byte | 120 Hz | UDP + binary parse = ~1-2 ms | 4 (대체) |

**핵심**:
- (1) Skeletal Input 2.0 은 우리 Python 코드의 OpenVR API call 만으로 **UDCAP driver 의 internal shared memory** 에 직접 access — **OSC 와 비교해 추가 packet serialize/deserialize 없음**
- (2) Action curls 는 (1) 의 압축형 — UDCAP driver 가 skeletal 미구현 시 polyfill 가능
- (3) VMC 는 추가 hop (UDP serialize → OSC parse) 발생, 가장 큰 overhead
- (4) Protobuf 는 (3) 의 binary 버전 — 그래도 (1)/(2) 의 OpenVR 직접 호출보단 hop 1개 더

### 3.2 Latency 누적 비교 (motion-to-Isaac action)

research/33 의 latency budget 을 path 별로 갱신:

| 단계 | VMC OSC (current) | OpenVR Skeletal | OpenVR Action curls |
|---|---|---|---|
| Glove sensor → 2.4G RF → UdcapDriver.exe | 5-10 ms | 5-10 ms | 5-10 ms |
| UdcapDriver → SteamVR driver (named pipe) | 1-2 ms | 1-2 ms | 1-2 ms |
| **SteamVR driver → broadcast 경로** | UdcapDriver UDP 송신 (VMC OSC) ~1 ms | OpenVR shared memory ~0.1-0.5 ms | OpenVR shared memory ~0.1-0.5 ms |
| **Python 수신 + parse** | pythonosc dispatch + dict 갱신 ~1-3 ms | pyopenvr `getSkeletalBoneData` 호출 ~1-2 ms | pyopenvr `getAnalogActionData` × 10 호출 ~1-2 ms |
| **Mapper 실행** | `map_hand_vmc` ~0.5 ms | `map_hand_skeletal` ~0.5 ms | `map_from_finger_curls` ~0.1 ms |
| **소계 (sensor → 22D action 도달)** | **8.5-16.5 ms** | **7.6-15 ms** | **7.2-14.5 ms** |
| **VMC vs Skeletal Δ** | — | **~1-2 ms 단축** | **~1-2 ms 단축** |

→ **순수 latency 단축 효과는 1-2 ms 수준, 절대값으론 작음**. 하지만:
- Python 처리 thread CPU 부담 감소 → 다른 부분 (env.step) headroom 증가
- Code path 단순화 → 디버깅 용이
- 하나의 OpenVR 세션에서 모든 데이터 (HMD, 트래커, 컨트롤러, 손가락) 일관 → race condition 감소

### 3.3 정성적 비교 — 추가 가치

| 항목 | VMC OSC | OpenVR Skeletal | 비고 |
|---|---|---|---|
| **Hand skeleton 전체 (31 bones)** | △ (UDCAP 의 30 bones) | ✓ (full SteamVR 표준) | DexPilot 에 31 bones 직접 사용 가능 |
| **Pose 동기화 (HMD + 트래커 + 글러브)** | ✗ (별도 채널) | ✓ (단일 OpenVR 세션) | 시간 동기화 보장 |
| **확장성 (Vive 글러브 / Manus / Quantum 등)** | ✗ (vendor-specific) | ✓ (OpenVR 표준) | 다른 글러브 도입 시 코드 변경 0 |
| **Calibration 통합** | ✗ (UDCAP 자체) | △ (OpenVR `getDominantHand` 등) | UDCAP 내부 cal 은 동일 적용 |
| **개발자 도구** | UDCAP UI + 우리 osc sniffer | SteamVR Settings (binding editor 등) | SteamVR 가 더 풍부 |
| **TLS / 보안** | UDP 평문 | OpenVR shared memory (process boundary) | localhost 환경에선 차이 미미 |
| **해당 driver 의 계속 지원** | UDCAP 만 | 표준 — 모든 SteamVR-compatible 글러브 | OpenVR 가 더 안정적 미래 |


기대 출력에서 **결정적 신호**:
1. **Section 3** "Loaded server driver udcap" + "Received named pipe data" count > 100 → UDCAP 글러브 데이터가 SteamVR 에 도달 중
2. **Section 4** VMC live test "0 packets" 또는 "WARN: bind UDP 39539 failed" → VMC 자체 비활성

**그리고** teleop 한 번 실행 시 device.start() 단계에서 자동 호출되는 `_probe_openvr_skeletal()` 의 출력:
```
[GR1T2FourierUDCAPDevice] --- OpenVR skeletal probe ---
  left: action_handle=0x...
    getSkeletalActionData: bActive=??? activeOrigin=0x???
    getSkeletalTrackingLevel=? (Estimated/Partial/Full)
    getBoneCount=31
```

**3 가지 분기**:

| 결과 | 의미 | 다음 path |
|---|---|---|
| `bActive=True, getBoneCount=31, tracking_level≥1` | **UDCAP 가 Skeletal Input 2.0 emit 중** | **Phase X1 (SteamVR Skeletal 으로 primary 전환)** |
| `bActive=False, named_pipe_data_count > 100` | UDCAP 가 finger curl action 만 emit | **Phase X2 (Action curls 로 전환, binding 검증)** |
| `bActive=False, named_pipe_data_count = 0` 또는 모든 channel 0 | UDCAP driver 가 SteamVR 와 통신 자체 실패 | **Phase X3 (research/34 Phase E Protobuf 진행)** |

### 5.3 Isaac Lab 본가의 OpenXRDevice 와 우리 SteamVRSampler 차이

(참고용 — 우리 path 변경 추천 아님)

| 측면 | Isaac Lab `OpenXRDevice` | 우리 `SteamVRSampler` |
|---|---|---|
| 기반 API | OpenXR (CloudXR runtime) | OpenVR (pyopenvr → SteamVR) |
| 트래킹 | OpenXR hand tracking (26 joints) | SteamVR Skeletal Input (31 bones) |
| 트래커 emulation | OpenXR action 으로 자동 매핑 | tracker_binding.json 으로 수동 매핑 |
| HMD | OpenXR pose | SteamVR pose |
| Hand glove 통합 | Apple Vision Pro / Quest 3 hand tracking 만 | Pinch-to-grip 외 분해, UDCAP/Manus 등 SteamVR 글러브 |
| CloudXR 의존 | ✓ (Docker runtime 필요) | ✗ (직접 SteamVR) |
| Isaac Lab 본가 통합 | DOC 화 됨 | 자체 모듈 |

→ Isaac Lab 본가 path 로 마이그레이션은 **CloudXR 인프라 + OpenXR runtime 재구성** 이 큰 작업. 우리 path 가 SteamVR 에 직접 access 하므로 추가 layer 없는 게 강점. 단, **Isaac Lab 본가가 OpenXR 표준화 트렌드** 라 미래 유지보수 측면에선 OpenXR 가 우세 (3-5년 시계). 지금은 OpenVR 우리 path 유지 권장.

### 5.4 PICO Connect vs Virtual Desktop — 미세 차이

| 측면 | Virtual Desktop | PICO Connect |
|---|---|---|
| **모션 트래커 → SteamVR (Vive Tracker emulation)** | "Emulate Vive Tracker" 옵션 ON 해야 (수동) | 자동 (Body Tracker 2.0.1+) |
| **컨트롤러 input forward** | "Forward controller input to SteamVR" 옵션 (default ON) | 자동 |
| **Encoder/streaming latency** | ~30-60 ms (사용자가 측정 안한 약 40 ms 추가 — research/33 §2.1) | ~25-40 ms |
| **AI body tracking jitter** | VD 측 AI 가 Pico 의 raw IMU 보강 → 가끔 phantom-tracker 발생 (research/29 / gotcha #18) | PICO 공식 Body Tracker → 일반적으로 더 안정 |
| **Wi-Fi 부하** | 6/6E 권장 | 동일 |
| **UDCAP 글러브 호환** | 이상 무 (USB 통신은 별개) | 동일 |
| **개발자 디버깅** | VD 디버그 메뉴 풍부 | Steam UI 직접 |

→ **사용자가 PICO Connect 모드로 전환했다면** Virtual Desktop 의 phantom-tracker 문제 (research/29 gotcha #18) 가 자동 해결될 가능성 — `--ignore_trackers` flag 가 더 이상 필수 아닐 수 있음. **Step 1 의 진단 후 hips tracker 가 정상 pose 보고하는지 별도 확인**.

## 10. 결론 — 사용자에게 전달할 한 줄

> **현재 코드는 SteamVR 의 모든 입력 (HMD + 트래커 + 컨트롤러 + 31-bone hand skeleton + 5-finger curl) 을 받을 수 있도록 이미 설계돼 있다. 다만 그동안 UDCAP 의 skeletal 채널이 inactive 한 상태로 가정하고 VMC OSC 를 default 로 써왔다. 사용자가 PICO 네이티브 streaming 에서 SteamVR 의 트래커/컨트롤러 정상 동작을 확인했으니, 한 번의 진단 실행 (`python -X utf8 -m ust_ws.ust_fourier_260421.scripts.diagnose_udcap_dataflow` + teleop 실행 시 자동 출력되는 `_probe_openvr_skeletal` 결과) 으로 "Skeletal 도 활성인지" 가 결정된다. 활성이면 Phase X1 (코드 변경 거의 0, primary 를 skeletal 로) — 비활성이면 Phase X2 (UDCAP-native binding + Save Personal Binding) — 둘 다 안 되면 Phase X3 (research/34 의 Protobuf 진행). UDCAP-Driver 가 v0.1.3 이하면 v0.1.8.1+ 로 업데이트만 해도 Skeletal Input 2.0 활성 가능성 ↑. VR streaming back 자체 latency (research/33 Cause #1, ~50 ms) 는 여전히 가장 큰 단일 contributor 이지만, SteamVR direct 전환은 추가 작업 없이 1-3 ms 단축 + 코드 단순화 + VMC 디버깅 surface 제거의 부수 효과가 있다.**
