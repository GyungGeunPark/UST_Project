## 0. 한 줄 요약 (TL;DR)

> **결론: 우리는 UDCAP 의 가장 우회적이고 latency 가 큰 데이터 경로 (VMC OSC) 만 쓰고 있었다. UDCAP 공식 SDK 는 (a) Protobuf 바이너리 + UDP port 5555 = VMC 보다 packet 작고 빠르고 schema 명확, (b) JSON-Quaternion / JSON-Euler 도 별도 옵션으로 제공, (c) 60/90/**120 Hz** 명시적 설정 가능 (지금까지 우리가 추정한 "140 Hz" 는 부정확 — 공식 max 는 120 Hz, Isaac Lab physics 와 1:1 매칭), (d) 별도 SDK 가 Google Drive 에 공개됨 (Windows + Linux + Python). Phase E 로 ust_fourier_260421 의 VMC fallback 경로를 Protobuf SDK 직접 통합으로 교체 시 packet 소형화 + parse 단순화로 OSC dispatch overhead ~1-3 ms 추가 단축 + 데이터 형식 명확성으로 디버깅 용이성 ↑. 단, UDCAP 의 RF 자체 latency (sensor → 2.4G dongle → HandDriver 처리 ~10 ms) 는 SDK 변경으로도 줄지 않으므로, **최대 추가 단축은 5-10 ms 수준**. lag 의 근본 원인이 여전히 풀리지 않는다면 RF/전송 layer 가 아닌 글러브 자체 (sensor/calibration) 문제 또는 사용자 perception (display refresh rate / VR streaming) 문제일 가능성이 높다. 9.27 까지 적용된 상태에서 잔존 lag 는 monitor mode 에서도 50-80 ms 추정 — 이는 (1) HandDriver 자체 ~10-20 ms + (2) UDP 전송 ~1 ms + (3) Python 처리 ~3-5 ms + (4) PhysX PD 응답 ~10-20 ms + (5) Render/Display ~16-30 ms 합산.**

## 1. UDexReal 공식 docs 에서 발견한 5가지 핵심 사실

### 1.1 HandDriver 가 지원하는 3가지 데이터 출력 프로토콜 — Protobuf, JSON, VMC

[Data Transmission docs](https://udexreal.gitbook.io/udexreal-docs/software-instruction/software-instruction/data-transmission):

| 프로토콜 | 형식 | Port (default) | 권장 용도 |
|---|---|---|---|
| **Protobuf** | binary (handdriver_teleop.proto) | **5555** (UDP) | **로보틱스 (권장)** |
| **JSON (Quaternion)** | text (UTF-8) | 5555 (UDP) | 다국어 환경, 디버깅 용이 |
| **JSON (Euler)** | text (UTF-8) | 5555 (UDP) | 실제 사람 손가락 데이터 직관적 표현 |
| **VMC** | OSC over UDP, bone quat 양자 stream | **사용자 설정 (UDCAP 기본 39539)** | VR 아바타 (VRChat / VTubing) — **현재 우리가 쓰는 것** |

> 공식 인용 (HandDriver 2.2.2+): `Three transmission formats — JSON, Protobuf, VMC — are mutually exclusive selections`. Earlier (2.1.7-2.2.1): `Euler/Quaternion/VMC mutually exclusive`.

**우리 상태 (9.27 시점)**:
- `path_b_port=39539` 으로 VMC OSC 수신 사용
- `pythonosc.ThreadingOSCUDPServer` 로 30 bones × 120 Hz = 3600 msgs/s 처리

**의의**:
- Protobuf 는 **VMC OSC 보다 binary serialize → packet 크기 ~5x 작음** (text "/VMC/Ext/Bone/Pos LeftIndexProximal 0.0 0.0 0.0 0.123 -0.456 0.789 0.876" vs binary `\x08\x01\x10...`)
- Protobuf schema 가 정의된 **`handdriver_teleop.proto`** → 파싱이 정형화 (quat → bend 변환 단계 명확)
- 정의된 메시지 타입: **`TeleopDataAngle`** (각 손가락 23 joint pitch/yaw/roll) 또는 **`TeleopDataQuat`** (각 손가락 15 joint quat)

### 1.2 HandDriver UDP 출력 rate 는 60 / 90 / **120 Hz** — 140 Hz 는 우리 잘못된 가정

[데이터 전송 페이지](https://udexreal.gitbook.io/udexreal-docs/software-instruction/software-instruction/data-transmission):
> `Frame Rates Supported: 120Hz, 90Hz, and 60Hz. The default FPS is 120Hz`

**memory.md / CLAUDE.md gotcha 수정 필요**:
- 9.23 EMA 의 "UDCAP 140 Hz / SteamVR 120 Hz" 가정 → **둘 다 120 Hz 로 동일** (HandDriver 가 120 Hz 로 송신)
- 9.24 decimation=1 (env.step 120 Hz) 와의 sub-sampling 비율 → **1.17:1 이 아니라 정확히 1:1**
- 즉, 9.23 EMA fix 는 이미 9.24 decimation 1 이후엔 **거의 무용지물** (사용자가 `--finger_lp_alpha 1.0` 으로 끈 것이 옳았음을 재확인)
- **사용자 주의: HandDriver UI 에서 FPS 가 120 Hz 로 설정돼있는지 확인** — 60 Hz 면 우리 코드에서 EMA / decimation 모두 의미 다름

### 1.3 글러브 → HandDriver 까지의 latency 는 **~10 ms** (공식 spec)

[UDCAP 공식 product 페이지](https://udexreal.com/products/udcap-vr-gloves):
> `2.4G connection with USB dongle, data transmission frequency 120Hz, latency < 10ms, range up to 10m`

[Robotics page](https://udexreal.gitbook.io/udexreal-docs/robotics/usage-for-udexreal-robotics-products):
> `End-to-End Latency: Approximately 20ms from hand motion onset to SDK invocation (excluding network delay)`

**해석 (latency budget breakdown)**:
| 단계 | 시간 | 출처 |
|---|---|---|
| Glove sensor → 2.4G RF → USB dongle (driver) | ~5–10 ms | UDCAP product spec |
| HandDriver 내부 처리 (calibration / quat 변환) | ~5–10 ms | "End-to-End ... 20ms ... excluding network" |
| UDP 송신 (5555 또는 39539) → Python 수신 | <1 ms (loopback) | OSC/UDP 표준 |
| Python parsing (pythonosc dispatch) | ~1–3 ms | 4200 msgs/s 시 lock contention |
| **소계 (sensor → Python action 도달)** | **~12–25 ms** | — |

→ 글러브 자체에서 **이미 12-25 ms latency** 발생.  Isaac Lab / PhysX / Render 추가 latency 와 합쳐 motion-to-photon ~50-100 ms.  **UDCAP 글러브 가속 자체에는 손이 거의 안 닿는 영역** (RF / 마이크로컨트롤러 펌웨어).

### 1.5 PICO MotionTracker Guide — 글러브 위치 트래킹용, 손가락 데이터 경로 변경 ❌

[PICO MotionTracker Guide](https://udexreal.gitbook.io/udexreal-docs/gloves-in-vr-headsets/glove-and-pico-motiontracker-guide):
- **지원 모델**: PICO 4 Ultra Enterprise / PICO 4 Enterprise / PICO neo3 Enterprise (**Consumer 모델은 미지원** — 사용자가 일반 Pico 4 Ultra 사용 중일 가능성 확인 필요)

- **연결 방법**: PICO MotionTracker 를 "Object Tracking" 모드로 변경 → 벨크로로 글러브에 부착 → 첫 번째 연결된 트래커가 자동으로 left hand 로 인식
- **제공하는 정보**: 글러브 손목/손 등의 **포지션 (XYZ) + 회전 (quat)** — 즉, 우리가 SteamVR Skeletal forearm tracker 로부터 받던 정보와 동일 종류
- **제공하지 않는 정보**: 손가락 굽힘/회전 — 이건 **계속 UDCAP RF dongle → HandDriver → UDP** 경로

**의의**:
- PICO MotionTracker 활성화는 **SteamVR forearm tracker 의 대안**일 뿐 (또는 보완책)
- 9.26 `--ignore_trackers` 가 forearm 트래커 무시 모드인데, MotionTracker 를 추가해도 같은 forearm 역할이라 차이 없음
- **사용자가 PICO Consumer 모델 (Enterprise 아님)** 이면 그래서 미지원 → 굳이 시도할 가치 없음

### 1.6 (보너스) Vibration API — 햅틱 피드백 (port 8920)

[Vibration API docs](https://udexreal.gitbook.io/udexreal-docs/glove-data-c++-python-sdk-for-robotics/vibration-api):
- Port: **8920** (UDP)
- 메시지: JSON `{"ctrl": {"LeftHand": [vibrator, duration, amplitude], "RightHand": [...]}}`
- 파라미터:
  - **Vibrators**: 0=none, 1=button vib, 2=joystick vib, 3=both
  - **Duration**: 0.04–2.5 sec
  - **Amplitude**: 4–10
- LAN 내에서만 동작

**의의**:
- 사용자가 시뮬레이션 contact 발생 시 손가락에 진동 → **proprioception 강화로 perceived latency ↓**
- "lag 가 느껴진다" 는 인지를 contact 피드백으로 보완하는 보조 채널
- ust_fourier_260421 에 통합 시: env contact sensor → vibrate

## 2. 9.27 까지 적용 후 잔존 latency 의 가능 원인 (재진단)

### 2.1 단계별 latency budget (9.27 적용 후)

| # | 단계 | 9.26 default | 9.27 적용 후 | research/34 추가 단축 가능 |
|---|---|---|---|---|
| 1 | Glove sensor → RF → HandDriver | 10–20 ms | 10–20 ms | ❌ HW 한계 (UDCAP 펌웨어 영역) |
| 2 | HandDriver 내부 처리 + UDP 송신 | 1–3 ms | 1–3 ms | ❌ HandDriver UI 영역 |
| 3 | Python OSC 수신 + parsing | 1–3 ms | 1–3 ms | ✅ Protobuf 로 0.5–1 ms 단축 |
| 4 | retargeter (mapper + EMA) | <1 ms | <1 ms | (이미 충분히 빠름) |
| 5 | Pink IK QP (arm 전용) | 5 ms (P99) | 5 ms | ❌ |
| 6 | PhysX articulation (PD) | 10–20 ms | 8–15 ms (vel_limit_sim 50 적용) | ❌ |
| 7 | env.step wall time | 6–8 ms | 4–6 ms (render_interval=2 적용) | (적용됨) |
| 8 | Render | 5–10 ms | 5–10 ms | ❌ |
| 9 | Display refresh | 8–17 ms (60 Hz monitor) | 8–17 ms | ❌ (모니터 주사율 한계) |
| 10 | Human visual perception | 10–20 ms | 10–20 ms | ❌ (생물학적 한계) |
| **합계** | **64–112 ms** | **52–87 ms** | **추가 5–10 ms 단축 가능** | |

→ **9.27 까지 적용된 상태의 monitor mode latency 추정 ~52-87 ms**.  사용자가 "실시간 트래킹 역부족" 으로 느끼는 임계치 (학술적 합의 50 ms) 와 매우 근접.  **남은 가장 큰 변수는 step 6 (PhysX) + step 9 (디스플레이 주사율)**.

### 2.2 Protobuf 도입의 정량 효과 (~3-8 ms 추가 단축)

VMC OSC vs Protobuf packet 비교:

| 항목 | VMC OSC | Protobuf |
|---|---|---|
| Packet size (양손 30 bones) | ~3500–4000 byte | ~700–900 byte |
| 1 packet parse 시간 (Python) | 0.5–1.5 ms (string parse) | 0.1–0.3 ms (binary parse) |
| 30 bones × 120 Hz = 3600 msg/s | 1.8–5.4 ms total/s | 0.36–1.08 ms total/s |
| **Python thread 점유율 (% of 1 core)** | **20-30%** | **3–5%** |

→ Python thread 점유율 감소로 main thread 의 IO/처리 지연 감소 → **Step 3, 4 합쳐 추가 1-3 ms 단축, P99 단축 ~5-10 ms**

**중요한 caveat**:
- Protobuf 는 packet 안에 **양손 데이터 한꺼번에** (single TeleopDataAngle/Quat) — VMC 의 30 bone × 30 packets 와 달리 1 packet/frame
- 즉, lock 경합도 자동 해소 (memory.md §10.31 의 EMA 도입 배경이었던 sub-sampling aliasing 문제 자체가 무관)

### 2.3 PhysX PD 응답이 여전히 가장 큰 단일 contributor (step 6)

stiffness=10000 + damping=100 + armature=0.001 → 시정수 ~10 ms.
9.27 의 velocity_limit_sim=50 / effort_limit_sim=200 적용으로 fast transient 시 PhysX rate-limiting 이 풀려도, **steady-state PD 응답 자체는 여전히 ~10-15 ms**.

추가 단축 옵션 (research/35 후보):
- Implicit actuator → **Joint Drive 직접 set** (PhysX articulation API): 미세하게 빠를 수 있음
- 일부 task 에서 finger 만 **kinematic 모드** (실시간 매칭이 우선이고 contact dynamics 는 무시): PhysX PD 우회, 즉시 set
- 단, kinematic 모드는 contact force 무시 → manipulation 시뮬엔 부적절

#### Step 3: ust_260418_win/teleop 에 Protobuf 수신기 추가
새 파일 `ust_ws/ust_260418_win/teleop/protobuf_receiver.py`:
```python
"""HandDriver Protobuf UDP receiver (Path C — replaces VMC Path B).

Reference: research/34 §3.1 / official docs:
  https://udexreal.gitbook.io/udexreal-docs/glove-data-c++-python-sdk-for-robotics/protobuf-c++-python-sdk-manual
"""
import socket
import threading
from typing import Dict, Optional, Tuple

# generated from handdriver_teleop.proto
from .gen.handdriver_teleop_pb2 import TeleopDataQuat   # type: ignore

class HandDriverProtobufReceiver:
    """Threaded UDP listener for Protobuf TeleopDataQuat (port 5555)."""
    def __init__(self, port: int = 5555, host: str = "0.0.0.0"):
        self.port = port
        self.host = host
        self._lock = threading.Lock()
        self._latest: Optional[TeleopDataQuat] = None
        self._sock = None
        self._thread = None
        self._running = False
        self._message_count = 0

    def start(self):
        self._sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        self._sock.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 1 << 20)
        self._sock.bind((self.host, self.port))
        self._sock.settimeout(0.1)
        self._thread = threading.Thread(target=self._loop, daemon=True)
        self._running = True
        self._thread.start()

    def _loop(self):
        while self._running:
            try:
                data, _ = self._sock.recvfrom(8192)
            except socket.timeout:
                continue
            pkt = TeleopDataQuat()
            try:
                pkt.ParseFromString(data)
            except Exception:
                continue
            with self._lock:
                self._latest = pkt
                self._message_count += 1

    def latest_bones_xyzw(self) -> Dict[str, Tuple[float, float, float, float]]:
        """VMC-compatible API for drop-in replacement of VMCHandReceiver.

        Maps Protobuf 15-quat-per-side joint fields to UDCAP's VMC bone naming
        so FourierHandMapper.map_hand_vmc() can be reused unchanged.
        """
        with self._lock:
            pkt = self._latest
        if pkt is None:
            return {}
        out: Dict[str, Tuple[float, float, float, float]] = {}
        # Map fields: pkt.LeftHand.joints[0..14] -> VMC bone names
        # ... (15 joint mapping per side)
        return out

    def stop(self):
        self._running = False
        if self._sock:
            self._sock.close()
            self._sock = None
```

### 3.3 Phase G [1-2일] — Vibration API 통합으로 perceived latency 단축

UDCAP Vibration API (port 8920) 를 사용하여 **Isaac Lab contact event → 글러브 진동** 피드백 제공.  실제 latency 가 줄지 않아도 사용자의 손가락 끝 proprioception 이 시각 피드백 결손을 보완.

#### Step 1: ust_ws 에 vibration sender 추가
`ust_ws/ust_260418_win/teleop/udcap_vibration.py`:
```python
import json, socket
class UDCAPVibrator:
    PORT = 8920
    def __init__(self, host: str = "127.0.0.1"):
        self._sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        self._addr = (host, self.PORT)
    def vibrate(self, side: str, duration: float = 0.05, amplitude: int = 6,
                vibrator: int = 1):
        """side: 'left'|'right', duration 0.04-2.5s, amplitude 4-10, vibrator 1|2|3."""
        key = "LeftHand" if side == "left" else "RightHand"
        msg = {"ctrl": {key: [vibrator, duration, amplitude]}}
        self._sock.sendto(json.dumps(msg).encode(), self._addr)
```

#### Step 2: env contact sensor → vibration 연결
GR1T2 USD 에 ContactSensor (fingertip prim) 가 이미 있으면:
```python
# run_teleop.py 의 main loop 안
contact_sensor = env.scene.sensors["fingertip_contacts"]
prev_contact = torch.zeros_like(contact_sensor.data.net_forces_w[0])
# while loop:
contact = (contact_sensor.data.net_forces_w[0].norm(dim=-1) > 0.5)
new_contact = contact & ~prev_contact   # rising edge
if new_contact[:5].any(): vibrator.vibrate("left", duration=0.05, amplitude=6)
if new_contact[5:].any(): vibrator.vibrate("right", duration=0.05, amplitude=6)
prev_contact = contact
```

**효과**:
- Contact 시 **즉시 햅틱** (UDP 5-10 ms one-way + 글러브 진동 즉발)
- 사용자가 "ah, 손가락이 닿았다" 인지 → 시각 피드백 lag 가 있어도 OK
- Pick-and-place 같은 manipulation 정확도 ↑

### 3.4 (참고) Phase H — UDCAP 글러브 자체 latency 단축 시도 (Won't help much)

UDCAP 공식 spec 에 따라 glove sensor → HandDriver 까지 ~10-20 ms 는 **하드웨어 한계**.  다음은 효과 미미:

| 시도 | 예상 효과 | 권장도 |
|---|---|---|
| 와이어드 USB-C 연결 (square glove only) | RF noise 제거, latency 변화 미미 (~1-2 ms) | ❌ 작업량 대비 효과 낮음 |
| HandDriver FPS 120 → ?? Hz (override) | docs 상 60/90/120 만 지원, 그 이상 불가 | ❌ 불가능 |
| RF channel 변경 | 다른 글러브와 간섭 시에만 | △ 다른 글러브 동시 사용 시 |
| 글러브 위치를 receiver 더 가까이 | 신호 강도 ↑, latency 변화 미미 | ❌ |
| Sensor calibration 자주 재수행 | drift 줄임, latency 변화 없음 | △ 정확도엔 도움 |

→ **사용자가 9.27 + Phase E + Phase F 까지 적용한 후에도 lag 잔존 시** → UDCAP 글러브 → HandDriver layer 가 한계.  추가 단축 = 글러브 교체 (Manus Quantum, StretchSense, Rokoko) 가 유일.
