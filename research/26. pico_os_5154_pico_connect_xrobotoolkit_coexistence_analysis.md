# Windows 네이티브 Isaac Lab + PICO Connect + XRoboToolkit 동시 실행 가능성 분석 (PICO OS 5.15.4)

> 작성일: 2026-04-10
> 선행 문서: `25. windows_isaac_lab_pico_connect_architecture_analysis.md`
> 전제 조건:
> - **PC 측**: Windows 11 네이티브 Isaac Sim / Isaac Lab (WSL2 불가 확정)
> - **헤드셋 측**: PICO 4 Ultra, **PICO OS 5.15.4** (PICO OS 6 현재 수급 불가)
> - **기존 실패 사례**: Ubuntu + CloudXR 6.0.1 Docker Runtime + XRoboToolkit App 동시 실행 불가
> - **목표**: 전신+손 트래킹(XRoboToolkit) + VR 뷰 스트리밍(PICO Connect) 동시성 확보

---

## 1. 결론 (TL;DR)

### 불가능. Windows로 이전해도 PICO OS 5.15.4에서는 근본적으로 두 앱을 "동시 실행"할 수 없습니다.

CloudXR 6.0.1 + XRoboToolkit 동시 실행이 실패했던 것은 **PC OS 문제가 아니라 헤드셋 OS의 구조적 제약**입니다. Windows 네이티브로 이전하고 PICO Connect를 사용하더라도 **동일한 벽에 부딪힙니다**.

| 조합 | PC OS | 헤드셋 앱 | 결과 |
|------|-------|----------|------|
| Ubuntu + CloudXR 6.0.1 Docker | Ubuntu | CloudXR.js + XRoboToolkit | ❌ (기존 실패) |
| Windows + CloudXR 6.0.1 Native | Windows 11 | CloudXR.js + XRoboToolkit | ❌ (동일한 원인) |
| **Windows + PICO Connect + XRoboToolkit** | **Windows 11** | **PICO Connect + XRoboToolkit** | **❌ (이 문서의 결론)** |
| Windows + PICO Connect 단독 | Windows 11 | PICO Connect | ✅ (트래킹 포기) |
| Windows + XRoboToolkit 단독 | Windows 11 | XRoboToolkit | ✅ (PICO Connect PCVR 포기) |

핵심 원인 3가지:

1. **PICO OS 5.15.4는 "2D 윈도우 멀티태스킹"만 지원.** Fully-immersive OpenXR VR 앱은 **동시에 하나만** 활성화될 수 있습니다. 두 앱 모두 fully-immersive VR 앱입니다.
2. **PICO Connect의 헤드셋 클라이언트와 XRoboToolkit Unity Client는 모두 PRIMARY OpenXR 세션을 독점**합니다. 한쪽이 활성화되면 다른 쪽은 세션 `xrSessionState = STOPPING → IDLE`로 밀려나 트래킹/렌더링이 끊깁니다.
3. **PICO OS 6의 "Spatial Multitasking (3D+2D Shared Space)" 이 바로 이 문제를 해결하려고 재설계된 기능**이지만, PICO OS 6은 현재 수급 불가 상태입니다.

## 2. 근본 원인 분석: 왜 OS만 바꾼다고 해결되지 않는가

### 2.1 "동시 실행"의 두 가지 의미

| 계층 | 의미 | Windows로 해결? |
|------|------|-----------------|
| **PC 측** | Isaac Sim + CloudXR/Pico Connect Server + XRoboToolkit-PC-Service 세 프로세스가 같은 Windows에서 실행 | ✅ 해결됨 (RTX PRO 6000, NVENC 무제한) |
| **헤드셋 측** | PICO Connect 클라이언트 앱 + XRoboToolkit APK 두 개의 fully-immersive VR 앱이 **같은 Android 세션**에서 동시에 활성화 | ❌ **PC OS 무관, 헤드셋 OS가 거부** |

기존 `25.md` 문서에서 Windows 이전을 고려했던 이유는 **PC 계층**의 문제 해결이 목표였습니다 (Isaac Sim이 WSL2에서 안 돌아감, Docker 의존성 제거 등). 그러나 **헤드셋 계층**의 동시 실행 문제는 PC를 바꾸는 것과 완전히 독립적인 문제입니다.

### 2.2 PICO OS 5.x 멀티태스킹의 실체

PICO OS 5.13.0에서 도입되고 5.14/5.15에서 유지되는 "파노라마 워크스페이스"(Panoramic Screen Workspace)는 겉보기에 멀티태스킹처럼 보이지만, 실제 구조는 다음과 같습니다:

```
┌─────────────────────────────────────────────────────┐
│ PICO OS 5.15.4 Home / Passthrough Environment       │  ← 이 위에서만
│                                                      │     "멀티태스킹" 가능
│  [2D App 1]  [2D App 2]  [Browser]  [System Panel]  │
│     ^           ^             ^           ^          │
│     └───── 모두 Android 2D 윈도우 (flat) ──────┘    │
│                                                      │
│  ✘ Fully-immersive VR 앱은 여기에 윈도우로 배치     │
│    될 수 없음                                        │
└─────────────────────────────────────────────────────┘
                      │
                      │ 사용자가 VR 앱 실행 → 전환
                      ▼
┌─────────────────────────────────────────────────────┐
│ Fully-Immersive VR Session (OpenXR PRIMARY)         │
│                                                      │
│  한 번에 ONE 앱만 세션 점유:                         │
│    - PICO Connect 클라이언트  OR                     │
│    - XRoboToolkit Unity Client  OR                   │
│    - CloudXR.js (브라우저 WebXR)  OR                 │
│    - 기타 VR 게임/앱                                 │
│                                                      │
│  이 모드로 들어가면 Panoramic Workspace 는           │
│  suspended 상태                                      │
└─────────────────────────────────────────────────────┘
```

**핵심**: PICO OS 5.x의 멀티태스킹은 "2D Android 윈도우 + 배경 홈 환경" 조합 전용입니다. 두 개의 immersive VR 앱이 공존할 수 있는 구조가 아닙니다 ([UploadVR, Pico 4 Ultra OS 5.13.0](https://www.uploadvr.com/pico-4-ultra-os-5-13-0-free-window-positioning/), [Mixed-News](https://mixed-news.com/en/pico-os-update-5-13-0-u/)).

PICO OS 6의 공식 세일즈 포인트가 **"게이밍 중에도 비디오 챗/웹브라우징 창을 띄울 수 있다"** 인 이유가 바로 이것입니다 — 5.x에서는 그조차 제한적이며, **두 immersive VR 앱 동시성은 6에서도 "Shared Space"라는 신규 개념으로만 가능**합니다 ([PICO OS 6 Announcement](https://www.picoxr.com/global/about/newsroom/os6)).

### 2.3 OpenXR 세션 라이프사이클이 강제하는 제약

PICO의 OpenXR 런타임은 Android 포그라운드 앱에만 `xrBeginSession()`/`xrWaitFrame()` 콜을 허용합니다. Android 액티비티가 `onPause()`를 받는 순간 OpenXR 세션은 다음 상태 전이를 따릅니다:

```
XR_SESSION_STATE_FOCUSED
       │ (앱이 background로 밀림)
       ▼
XR_SESSION_STATE_VISIBLE
       │
       ▼
XR_SESSION_STATE_SYNCHRONIZED
       │
       ▼
XR_SESSION_STATE_STOPPING  ← 이 시점부터 pose 데이터 스트림 중단
       │
       ▼
XR_SESSION_STATE_IDLE
```

이 때문에 "XRoboToolkit을 백그라운드로 돌려놓고 PICO Connect를 띄운다" 같은 전략이 성립하지 않습니다 — 백그라운드로 밀리는 순간 XRoboToolkit-Unity-Client는 head/controller/hand/body 포즈 데이터를 더 이상 샘플링할 수 없고, PC Service로 전송할 데이터가 끊깁니다.

> XRoboToolkit Unity Client는 **PICO Integration SDK 3.1.2 기반 Unity 2022.3.16f1 네이티브 VR 앱**으로, Android Manifest의 `category`가 `com.oculus.intent.category.VR` (PICO에서 동일하게 처리) 이며 PRIMARY immersive session을 요구합니다 ([XRoboToolkit-Unity-Client README](https://github.com/XR-Robotics/XRoboToolkit-Unity-Client)).

### 2.4 PICO Connect 클라이언트의 정체

PICO Connect는 단순한 "스트리밍 뷰어"가 아니라 **그 자체가 fully-immersive PICO native VR 앱**입니다:

| 항목 | 값 |
|------|-----|
| 앱 타입 | Fully-immersive OpenXR native (PICO Store 배포) |
| HMD 점유 | PRIMARY_IMMERSIVE_STEREO 세션 독점 |
| PC 측 OpenXR 런타임 | `PicoStreamingXR` (VDXR fork, Windows 레지스트리 등록) |
| 실행 중 헤드셋 상태 | PICO Home 환경 pause, 다른 immersive 앱 실행 불가 |
| 종료 방법 | PICO Connect 세션을 명시적으로 끊어야 Home 복귀 |

ED Forums의 CloudXR/PicoStreamingXR 비교 논의에서 확인된 바로는, PicoStreamingXR이 Virtual Desktop의 VDXR 코드베이스(2023년 버전) fork이며 Windows 레지스트리의 `ActiveRuntime`을 자기 자신으로 덮어씁니다 ([DCS Forum: Pico Connect built-in experimental OpenXR runtime](https://forum.dcs.world/topic/372463-pico-headsets-pico-connect-built-in-experimental-openxr-runtime/)).

즉 **PICO Connect를 띄우는 순간 헤드셋은 단일 immersive 세션을 PICO Connect에 할당하며, 그 안에서 스트리밍되는 PCVR 콘텐츠가 재생**됩니다. 병렬로 XRoboToolkit Unity Client가 실행될 여지가 구조적으로 없습니다.

## 3. CloudXR 6.0.1 + XRoboToolkit 실패 사례 재해석

기존 실패를 이 프레임으로 다시 보면, 원인이 명확해집니다:

| 실패 요인 | PC 측 (Ubuntu) | 헤드셋 측 (PICO OS 5.x) |
|-----------|---------------|-------------------------|
| 네트워크/IPC | 해결 가능 (Docker Runtime, IPC_IGNORE_VERSION=1) | - |
| 런타임 버전 매치 | 해결 가능 (Kit 바인딩 교체) | - |
| **Immersive session 독점** | - | **두 앱 동시 점유 불가** ← 이것이 진짜 원인 |

즉, CloudXR 6.0.1 + XRoboToolkit 조합의 실패는 "CloudXR의 PC측 설정 문제"가 아니라 **"두 개의 fully-immersive VR 앱을 PICO OS 5.x에 동시 올릴 수 없다는 구조 제약"** 이 본질이었습니다. PICO Connect로 CloudXR을 교체해도 본질은 같습니다 — CloudXR.js 브라우저 WebXR 세션도, PICO Connect 스트리밍 세션도, 모두 하나의 PRIMARY immersive OpenXR 슬롯을 요구하기 때문입니다.

## 4. Windows + PICO Connect + XRoboToolkit 경로를 그래도 시도한다면

학습적으로라도 아키텍처를 고민해볼 가치는 있으니, 이론상 구성을 정리합니다. 모두 **헤드셋 측 제약**에 걸립니다.

### 시나리오 A: PICO Connect 포그라운드, XRoboToolkit "백그라운드 서비스"

```
[Windows PC]
  Isaac Sim → SteamVR → PICO Connect Server (PCVR 스트리밍)
  XRoboToolkit-PC-Service (WiFi TCP/UDP listener, 13579 등)

[PICO 4 Ultra]
  PICO Connect App  ← immersive foreground (PCVR 영상 수신)
  XRoboToolkit APK  ← 이론상 background Android service?
```

**문제점**: XRoboToolkit은 Unity VR 앱이며 포즈 데이터는 OpenXR 세션에서 샘플링됩니다. 앱이 `onPause()` 되면 OpenXR 세션이 `STOPPING → IDLE`로 빠져 포즈 이벤트가 중단됩니다. 순수 Android `Service` 컴포넌트로 분리해 백그라운드에서 트래킹 SDK를 직접 호출하는 방법은 XRoboToolkit-Unity-Client가 지원하지 않으며, PICO OpenXR SDK 역시 포그라운드 앱에만 head/controller/hand/body pose를 배포합니다 ([PICO OpenXR SDK](https://sdk.picovr.com/docs/OpenXRMobileSDKv2/en/chapter_four.html)).

**결과**: ❌ 백그라운드 XRoboToolkit에서 데이터가 흐르지 않음.

### 시나리오 B: XRoboToolkit 포그라운드, PICO Connect "백그라운드"

PICO Connect 역시 foreground immersive 앱이므로, 동일한 이유로 **백그라운드로 밀리는 순간 PCVR 스트리밍이 중단**됩니다.

**결과**: ❌ PICO Connect PCVR 뷰가 끊김.

### 시나리오 C: 빠른 컨텍스트 스위치 (교대 운영)

조작자가 1초 간격으로 두 앱을 전환하는 방식. PICO OS 5.x의 앱 콜드 스타트가 2~5초 걸리고, 매 전환 시 OpenXR 세션 재생성(xrCreateSession)과 PICO Connect 재연결이 발생합니다.

**결과**: ❌ 텔레오퍼레이션 용도 불가 (레이턴시/끊김).

### 시나리오 D: PICO Connect 안에서 "가상 데스크톱"으로 XRoboToolkit UI를 띄우기

PICO Connect가 Windows 데스크톱을 미러링하는 모드를 이용해, Windows에서 실행 중인 Isaac Lab 창과 XRoboToolkit-PC-Service 로그를 모니터 창으로 보는 방식.

**문제점**: 이 시나리오에서 **트래킹 데이터의 출처가 없습니다**. PICO Connect는 head+controller pose만 SteamVR 스택을 통해 PC로 전달하고, XRoboToolkit이 필요로 하는 **motion tracker (발목/허리)** 와 **풀바디 pose** 는 전달하지 않습니다. 이것이 애초에 XRoboToolkit APK가 별도로 필요한 이유입니다.

**결과**: ❌ 풀바디/모션트래커 데이터 확보 불가.

### 시나리오 E: 2대의 헤드셋 분업

PICO 4 Ultra 1대: XRoboToolkit APK 실행 (조작자가 착용)
PICO 4 Ultra 2대: PICO Connect로 VR 뷰 스트리밍 (조작자가 착용?)

**문제점**: 조작자가 헤드셋 두 개를 동시에 착용할 수 없습니다.

**결과**: ❌ 현실성 없음.

## 5. 실제로 가능한 경로 (우선순위 순)

### 경로 1: XRoboToolkit 단독 모드 + 내장 비디오 스트리밍 ⭐ (권장)

XRoboToolkit-Unity-Client는 **자체 스테레오 비디오 스트리밍 파이프라인**을 가지고 있습니다. PC Service 쪽에서 로봇 카메라(예: ZED Mini, RealSense, 또는 Isaac Sim 렌더 출력)를 H.264/H.265로 인코딩해서 UDP로 헤드셋에 전송하면, Unity Client 안에서 스테레오 뷰로 표시됩니다 ([XRoboToolkit arXiv](https://arxiv.org/html/2508.00097v1)).

```
[Windows 11 PC (RTX PRO 6000)]
  Isaac Sim 5.1.0 (네이티브)
    └─ G1 Kitchen Sorting env
         ├─ 좌/우 카메라 렌더 → H.264 NVENC 인코딩
         │    → UDP → PICO (XRoboToolkit 내장 디코더)
         └─ 조작 루프 (pose 수신 ← XRoboToolkit-PC-Service)

[PICO 4 Ultra, OS 5.15.4]
  XRoboToolkit Unity Client (immersive foreground)
    ├─ 수신: Isaac Sim 카메라 H.264 → 스테레오 뷰 표시
    └─ 송신: head+controller+hand+body+tracker pose (90Hz) → PC
```

**장점**:
- PICO Connect 불필요, SteamVR 불필요
- 단일 immersive 세션으로 PICO OS 5.x 제약 우회
- Ubuntu → Windows 이전도 선택사항 (Isaac Sim 네이티브는 Windows/Linux 모두 지원)
- XRoboToolkit 설계 의도 그대로 사용 → 문서/커뮤니티 지원 풍부

**단점**:
- Isaac Sim 카메라 출력을 XRoboToolkit 비디오 프로토콜에 맞춰 인코딩하는 어댑터 레이어 필요
  - XRoboToolkit은 `OrinVideoSender` 같은 Jetson용 샘플 송신기를 제공 → Windows/Linux 포팅 가능
  - 또는 Isaac Sim의 `CameraCfg` 출력을 FFmpeg/NVENC로 UDP 전송하는 브리지 작성
- PICO Connect 생태계의 SteamVR 타이틀은 포기

**작업량 추정**:
| 단계 | 설명 | 예상 소요 |
|------|------|----------|
| 1 | Isaac Sim Camera → NVENC H.264 인코더 브리지 | 2-3일 |
| 2 | XRoboToolkit 비디오 프로토콜 확인 (13579 포트, 포맷) | 1일 |
| 3 | Windows (또는 Ubuntu 유지) PC Service 빌드 | 0.5일 |
| 4 | PICO에 XRoboToolkit APK 설치 + 네트워크 페어링 | 0.5일 |
| 5 | 엔드투엔드 통합 테스트 | 1-2일 |

### 경로 2: 모니터 뷰 + XRoboToolkit 트래킹 (현재 검증 완료된 방식) ⭐⭐

이미 `ust_260220`에서 검증된 **방안3 (모니터 뷰)** 방식의 Windows 버전입니다.

```
[Windows 11 PC]
  Isaac Sim (GUI 창, 물리 모니터에 렌더)
    └─ G1 Kitchen Sorting env
         └─ pose 수신 ← XRoboToolkit-PC-Service

[외부 모니터]
  조작자가 직접 바라봄 (Isaac Sim Viewport)

[PICO 4 Ultra, OS 5.15.4]
  XRoboToolkit Unity Client (immersive foreground, 패스스루 또는 최소 UI)
    └─ 송신: head+controller+hand+body+tracker pose → PC
```

**장점**:
- **이미 구현/검증 완료** (프로젝트 기존 파이프라인 재활용)
- PICO 화면은 trivial 표시만 하면 되므로 렌더 부하 최소
- VR 멀미 감소 (모니터로 볼 때)
- Windows 이전 없이 Ubuntu에서도 그대로 동작

**단점**:
- 조작자가 HMD + 모니터를 교대로 봐야 함 (몰입감 ↓)
- 정밀 조작 시 시선 전환 비용

### 경로 3: PICO Connect 단독 모드 (트래킹 포기)

PCVR 스트리밍은 고품질로 확보되지만, 모션 트래커/풀바디는 포기합니다.

- Isaac Sim OpenXR Kit 확장을 PicoStreamingXR 런타임에 연결
- head + 2 controller + (옵션) PICO 내장 hand tracking 까지만 확보
- G1 전신 텔레오퍼레이션 목적에는 부족

### 경로 4: PICO OS 6 수급 시까지 대기

PICO OS 6의 "Spatial Multitasking / Shared Space" 가 두 immersive 앱의 공존을 목표로 설계되었으므로, 업데이트 수급 가능 시 경로 재평가. 현재 수급 불가이므로 차선책 아님.

   │    │          │

   │    │          │    │

   │    │          │    │
   │    │          │    └─ No  → ★ 경로 2 (모니터 뷰, 현재 검증됨)
   │    │          │

   │    │
   │    └─ No → head+controller만 OK → PICO Connect 단독 (경로 3)
   │
   └─ Windows 이전 자체는 경로 1/2 와 독립적인 결정 (Isaac Sim WSL2 이슈 해소 목적)

## 7. Windows 이전 재평가

25번 문서는 "Windows 네이티브 Isaac Sim + CloudXR + XRoboToolkit" 구성을 검토했습니다. 본 분석 결과에 따라 **Windows 이전의 의사결정 기준을 재조정**할 필요가 있습니다:

| 원래 Windows 이전 근거 (25번 문서) | 재평가 (본 문서) |
|-------------------------------------|------------------|
| "CloudXR + XRT 동시 실행이 Windows에서 될 수도 있다" | ❌ PC OS 문제 아님, 헤드셋 OS 제약이 본질 |
| "PICO Connect를 네이티브로 쓸 수 있다" | ⚠️ 쓸 수는 있으나 XRT와 공존 불가 |
| "Isaac Sim Docker WSL2 미지원 회피" | ✅ 여전히 유효 (Windows 이전의 **유일한 실질적 이득**) |
| "RTX PRO 6000 NVENC 세션 확장" | ✅ 유효하지만, 경로 1/2는 세션 1개만 필요 |

**결론**: Windows 이전의 편익은 "Isaac Sim Docker 탈출" 한 가지로 축소됩니다. 풀바디 트래킹 + VR 뷰 동시성 확보가 주 목표라면 Windows 이전은 **해결책이 아니며**, 경로 1 (XRT 내장 비디오) 또는 경로 2 (모니터 뷰) 로 진행해야 합니다. 두 경로 모두 Ubuntu/Windows 무관하게 동작합니다.
