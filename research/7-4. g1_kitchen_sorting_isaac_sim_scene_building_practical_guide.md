## 2. Nucleus 에셋 시스템 딥다이브

### 2.1 경로 해석 원리

Isaac Lab의 에셋 경로는 Python 상수로 시작한다:

```python
# source/isaaclab/isaaclab/utils/assets.py (lines 26-36)
NUCLEUS_ASSET_ROOT_DIR = carb.settings.get_settings().get("/persistent/isaac/asset_root/cloud")
NVIDIA_NUCLEUS_DIR = f"{NUCLEUS_ASSET_ROOT_DIR}/NVIDIA"
ISAAC_NUCLEUS_DIR = f"{NUCLEUS_ASSET_ROOT_DIR}/Isaac"
ISAACLAB_NUCLEUS_DIR = f"{ISAAC_NUCLEUS_DIR}/IsaacLab"
```

`/persistent/isaac/asset_root/cloud`의 실제 값은 Kit 설정 파일에서 결정된다:

```toml
# apps/isaaclab.python.kit
persistent.isaac.asset_root.cloud = "https://omniverse-content-production.s3-us-west-2.amazonaws.com/Assets/Isaac/5.1"
```

따라서 경로 변환 체인은:

```
코드에서 쓰는 경로:
  {ISAACLAB_NUCLEUS_DIR}/Mimic/pick_place_task/pick_place_assets/sorting_bin_blue.usd

실제 해석 결과:
  https://omniverse-content-production.s3-us-west-2.amazonaws.com/Assets/Isaac/5.1/Isaac/IsaacLab/Mimic/pick_place_task/pick_place_assets/sorting_bin_blue.usd
```

**핵심 포인트**: Nucleus는 로컬 서버가 아니라 **AWS S3 CDN**이다. 인터넷 연결이 필요하며, 에셋은 HTTP(S) GET으로 다운로드된다.

### 2.2 다운로드 메커니즘

에셋 파일의 존재 여부와 다운로드는 `assets.py`의 세 함수가 담당한다:

```python
def check_file_path(path: str) -> Literal[0, 1, 2]:
    """
    Returns:
        1 — 로컬 파일 존재 (os.path.isfile)
        2 — Nucleus 서버에 존재 (omni.client.stat)
        0 — 어디에도 없음
    """
```

```python
def retrieve_file_path(path: str, download_dir=None, force_download=True) -> str:
    """
    - status 1 (로컬): os.path.abspath(path) 그대로 반환
    - status 2 (Nucleus): omni.client.copy()로 다운로드 → 로컬 경로 반환
    - status 0: FileNotFoundError 발생

    download_dir 기본값: tempfile.gettempdir() (예: /tmp)
    force_download=True: 캐시된 파일이 있어도 항상 재다운로드
    """
```

```python
def check_usd_path_with_timeout(usd_path: str, timeout=300, log_interval=30) -> bool:
    """
    비동기 체크. 서버 응답 대기 중 30초마다 경고 로그.
    300초(5분) 타임아웃. USD 스폰 전 서버 무응답 감지용.
    """
```

**실전 의미**:
- Nucleus 에셋을 처음 사용하면 S3에서 다운로드 → `/tmp/`에 캐싱
- `force_download=True`이므로 매번 실행 시 재다운로드 (개발 중 에셋 변경 반영)
- S3 서버 불안정 시 5분 타임아웃 후 실패 → 오프라인 환경에서는 **프리미티브 기반 워크플로우** 필요

### 2.5 프리미티브 전략: Nucleus 없이 작동하는 워크플로우

`kitchen_sorting_env_cfg.py`가 프리미티브를 선택한 이유:

1. **Nucleus 의존성 제거**: S3 다운로드 실패 시에도 환경 동작
2. **정확한 치수 제어**: Cube의 `size` 파라미터로 mm 단위 크기 지정
3. **물리 속성 완전 제어**: Mass, Friction, Collision 근사 방식을 코드에서 직접 지정
4. **환경 복제 효율**: 단순 프리미티브는 GridCloner에서 빠르게 복제
5. **시맨틱 태그 통합**: 코드에서 생성 시 `semantic_tags` 파라미터로 일괄 설정

단점: 시각적 사실성이 떨어짐. 프로토타이핑 후 Nucleus USD로 교체 가능.

## 3. USD Reference vs Payload — 에셋 추가의 내부 메커니즘

### 3.1 Reference란

Isaac Sim의 Content Browser에서 에셋을 스테이지로 드래그앤드롭하면 내부적으로 **USD Reference**가 생성된다. 코드로 표현하면:

```python
# source/isaaclab/isaaclab/sim/spawners/from_files/from_files.py (line 277)
prim_utils.create_prim(
    prim_path,
    usd_path=usd_path,        # ← 이 경로가 Reference로 추가됨
    translation=translation,
    orientation=orientation,
    scale=cfg.scale,
)
```

`prim_utils.create_prim()`은 내부적으로 USD의 `references.AddReference(usd_path)` API를 호출한다. 결과:

```
/World/SortingBinBlue  (Xform)
    ├── references: ["sorting_bin_blue.usd"]   ← 원본 USD를 참조
    ├── xformOp:translate = (x, y, z)          ← 로컬 transform
    └── (원본 USD의 모든 자식 프림이 합성되어 보임)
```

**핵심**: Reference는 **복사가 아니라 참조**다. 원본 USD 파일의 내용이 현재 스테이지에 합성(composition)되어 보이지만, 실제로 데이터가 복제되지는 않는다. 원본 파일이 변경되면 참조하는 모든 곳에 반영된다.

### 3.2 Reference vs Payload 비교

| 속성 | Reference | Payload |
|------|-----------|---------|
| **로딩** | 항상 로드 | 선택적 로드 (Unload 가능) |
| **용도** | 일반 에셋 추가 | 대규모 환경의 부분 로딩 |
| **GUI 접근** | 기본 드래그앤드롭 | 우클릭 > Add Payload |
| **USD 계층** | `references` 목록에 추가 | `payloads` 목록에 추가 |
| **Isaac Lab에서** | `UsdFileCfg`의 기본 방식 | 거의 사용하지 않음 |

Isaac Lab 환경에서는 GridCloner가 전체 환경을 복제하므로 Payload의 선택적 로딩 장점이 없다. **Reference가 표준**.

### 3.3 Transform 합성

에셋을 Reference로 추가한 후 위치를 조정하면 두 레벨의 Transform이 합성된다:

```
최종 위치 = 부모 Xform Transform × Reference 내부 Transform
```

**예시**: `sorting_bin_blue.usd` 내부에 `defaultPrim`의 원점이 바닥 중앙에 있는 경우

```
/World/BinKitchen
    xformOp:translate = (-0.28, 0.82, 0.80)   ← 부모 Transform (GUI에서 설정)
    └── (Reference 내부)
        defaultPrim 원점 = (0, 0, 0)           ← 에셋 내부 원점
        └── mesh들의 상대 위치                  ← 에셋 구조
```

최종 위치: `(-0.28, 0.82, 0.80) + (0, 0, 0) = (-0.28, 0.82, 0.80)`

**함정**: 일부 에셋은 내부 원점이 중앙이 아니라 모서리에 있다. 이 경우 GUI에서 설정한 좌표와 실제 시각적 위치가 다르다. 항상 **Viewport에서 시각적 위치를 확인**해야 한다.

### 3.4 물리 속성 상속과 Override

Reference로 추가한 에셋에 이미 RigidBodyAPI, CollisionAPI가 있는 경우:

- GUI에서 `+ Add > Physics > Rigid Body`를 하면 **Override**가 생성된다
- Override는 원본 속성 위에 덮어쓰며, 제거하면 원본 값으로 돌아간다
- Isaac Lab 코드에서는 `schemas.modify_*` 함수가 이 역할을 한다:

```python
# from_files.py — USD 에셋의 기존 속성을 override
schemas.modify_rigid_body_properties(prim_path, cfg.rigid_props)
schemas.modify_collision_properties(prim_path, cfg.collision_props)
schemas.modify_mass_properties(prim_path, cfg.mass_props)
```

반면 프리미티브 생성 시에는 속성이 없으므로 `define_*`를 사용:

```python
# shapes.py — 새로 생성하는 프리미티브에 속성 추가
schemas.define_rigid_body_properties(prim_path, cfg.rigid_props)
schemas.define_collision_properties(prim_path, cfg.collision_props)
schemas.define_mass_properties(prim_path, cfg.mass_props)
```

### 3.5 defaultPrim

USD 파일의 `defaultPrim`은 Reference로 추가될 때 **진입점**이 되는 프림이다.

- `defaultPrim`이 설정되지 않으면 Reference 추가 시 에러 또는 빈 프림
- GUI에서 설정: Stage 패널에서 프림 우클릭 > `Set as Default Prim`
- 코드에서 설정: `stage.SetDefaultPrim(prim)`
- **관례**: `/World` Xform을 defaultPrim으로 설정

```python
# USD 파일 헤더 (.usda 형식으로 확인)
#usda 1.0
(
    defaultPrim = "World"
    metersPerUnit = 1
    upAxis = "Z"
)
```

## 4. Scale의 진실 — 프리미티브 크기 설정

### 4.1 Cube 기본 size 2.0 문제

**가장 흔한 혼동 원인**: USD의 `UsdGeomCube`는 `size` 속성 하나만 갖는다. 이 `size`는 한 변의 길이이며, 기본값은 `2.0` (즉 -1 ~ +1 범위의 정육면체).

GUI에서 Create > Mesh > Cube를 생성하면:
- `size = 2.0` (한 변 2m)
- Scale `(1, 1, 1)` → 실제 크기 `2m × 2m × 2m`

따라서 **원하는 크기의 Cube를 만들려면**:

```
GUI Scale = 원하는 치수(m) / size
         = 원하는 치수(m) / 2.0
```

**예시**: 테이블 (0.9m × 0.6m × 0.75m)

```
Scale X = 0.9 / 2.0 = 0.45
Scale Y = 0.6 / 2.0 = 0.30
Scale Z = 0.75 / 2.0 = 0.375
```

### 4.2 코드에서의 Scale 처리 (shapes.py)

Isaac Lab의 `spawn_cuboid()` 함수는 다른 방식으로 처리한다:

```python
# source/isaaclab/isaaclab/sim/spawners/shapes/shapes.py (lines 97-102)
size = min(cfg.size)                        # 최소 치수를 USD size로 사용
scale = [dim / size for dim in cfg.size]    # 나머지를 비율로 환산
attributes = {"size": size}
_spawn_geom_from_prim_type(prim_path, cfg, "Cube", attributes, translation, orientation, scale)
```

**예시**: `CuboidCfg(size=(0.9, 0.6, 0.75))`

```
size = min(0.9, 0.6, 0.75) = 0.6         → USD Cube size = 0.6
scale = [0.9/0.6, 0.6/0.6, 0.75/0.6]
      = [1.5, 1.0, 1.25]                  → xformOp:scale
실제 크기 = 0.6 × [1.5, 1.0, 1.25] = [0.9, 0.6, 0.75] ✓
```

**GUI와 코드의 차이**:
- GUI: size=2.0 (고정), Scale로 크기 조절
- 코드: size=최소 치수, Scale은 비율만 조절
- 결과는 동일하지만 USD 파일의 수치가 다르다

### 4.3 Cylinder와 Sphere

Cylinder와 Sphere는 Cube와 다르게 **직접 치수 속성**을 갖는다:

```python
# Cylinder: radius + height 직접 지정 → Scale 불필요
spawn_cylinder(cfg=CylinderCfg(radius=0.04, height=0.08))
# → UsdGeomCylinder: radius=0.04, height=0.08, axis="Z"

# Sphere: radius 직접 지정 → Scale 불필요
spawn_sphere(cfg=SphereCfg(radius=0.04))
# → UsdGeomSphere: radius=0.04
```

GUI에서 Create > Mesh > Cylinder를 생성한 후:
- Property 패널 > Raw USD Properties > `radius`, `height` 직접 편집 가능
- 또는 Scale로 조절 (단, 비균등 Scale은 Collision 근사에 영향)

### 4.4 metersPerUnit 불일치

일부 외부 에셋이 cm 단위(`metersPerUnit = 0.01`)로 제작된 경우:

```
에셋 내부: 75cm 높이 테이블 → height = 75 (cm 단위)
현재 스테이지: metersPerUnit = 1.0 (m 단위)
→ 75m 높이의 거대한 테이블이 생성됨!
```

**진단**: Property 패널에서 에셋의 Layer Properties > `metersPerUnit` 확인

**해결**: 에셋을 Reference로 추가한 후 Scale을 `0.01`로 설정:
```
Scale = 에셋의 metersPerUnit / 스테이지의 metersPerUnit
      = 0.01 / 1.0 = 0.01
```

Isaac Lab의 Kit 설정에서 기본 단위가 미터로 설정되어 있으므로 (`simulation.defaultMetersPerUnit = 1.0`), 표준 Isaac Lab 에셋은 이 문제가 없다.

### 4.5 실전 검증 방법

크기가 올바른지 확인하는 가장 확실한 방법:

1. 해당 프림을 선택
2. Translate을 `(0, 0, 0)`으로 설정 (원점에 배치)
3. Viewport에서 Front View (숫자키 `1`) 또는 Right View (숫자키 `3`) 전환
4. Ground Plane 격자 눈금과 비교 (격자 1칸 = 1m)
5. 원하는 크기인지 시각적으로 확인 후 원래 위치로 복원

## 5. Scene Composition 패턴

### 5.1 단일 파일 vs 분할 파일

**패턴 A: 단일 USD 파일** — 배경 + 물체 모두를 하나의 USD에 포함

```
kitchen_scene.usd
├── /World
│   ├── /Table, /Bins (정적)
│   └── /Mug, /Plate, /Can... (동적)
```

- 장점: Isaac Sim GUI에서 전체 씬을 한눈에 확인 가능
- 단점: Isaac Lab의 개별 물체 제어(Domain Randomization, Reset) 불가

**패턴 B: 하이브리드 (배경 USD + 코드 물체)** ← **권장, 현재 env_cfg.py가 사용하는 패턴**

```
kitchen_background.usd          ← GUI에서 구축
├── /World
│   ├── /PhysicsScene
│   ├── /GroundPlane, /Lights
│   └── /Table, /Bins (정적 배경)

kitchen_sorting_env_cfg.py      ← 코드에서 정의
├── scene.table = AssetBaseCfg(usd_path="kitchen_background.usd")   # 배경 로드
├── scene.mug = RigidObjectCfg(spawn=CylinderCfg(...))              # 개별 물체
├── scene.plate = RigidObjectCfg(spawn=CylinderCfg(...))
└── ...
```

- 장점: 배경은 시각적으로 편집, 물체는 코드에서 완전 제어
- 장점: Domain Randomization, 초기 위치 랜덤화, 물체 상태 리셋이 자유로움
- 단점: 배경과 물체의 물리적 상호작용(충돌)은 양쪽 모두 Collision이 올바르게 설정되어야 함

**패턴 C: 전부 코드** ← **현재 env_cfg.py의 실제 구현**

```
kitchen_sorting_env_cfg.py
├── scene.table = AssetBaseCfg(spawn=CuboidCfg(size=(0.9, 0.6, 0.75), ...))
├── scene.bin_kitchen = AssetBaseCfg(spawn=CuboidCfg(...))
├── scene.mug = RigidObjectCfg(spawn=CylinderCfg(...))
└── ...
```

- 장점: 외부 파일 의존성 없음, 완전 재현 가능
- 단점: 시각적 사실성 최저, GUI에서 레이아웃 조정 불편

### 5.2 배경 USD 구축 8단계 요약

| 단계 | 작업 | GUI 조작 | 결과 |
|------|------|----------|------|
| 1 | 새 Stage | File > New | 빈 스테이지 |

@configclass
class KitchenSceneCfg(InteractiveSceneCfg):
    # 배경 USD — 전체 환경에 한 번 로드
    background = AssetBaseCfg(
        prim_path="{ENV_REGEX_NS}/Background",

### 5.5 저장 포맷

| 포맷 | 확장자 | 특징 | 용도 |
|------|--------|------|------|
| USD ASCII | `.usda` | 사람이 읽을 수 있는 텍스트 | 개발/디버깅 |
| USD Crate | `.usdc` | 바이너리, 빠른 로딩 | 배포/성능 |
| USD (자동) | `.usd` | 저장 시 Crate로 저장됨 | **권장 — 일반 사용** |

- 개발 중에는 `.usda`로 저장하여 텍스트 에디터로 내용 확인
- 최종 배포 시 `.usd` (자동으로 Crate 바이너리)
- **주의**: `.usd`와 `.usdc`는 동일한 바이너리 포맷이지만, `.usd`는 향후 포맷 변경에 유연함

## 6. 물리 속성의 내부 동작

### 6.1 Rigid Body

`UsdPhysics.RigidBodyAPI`를 프림에 적용하면 해당 프림이 물리 시뮬레이션의 대상이 된다.

```python
# 코드에서의 적용 (schemas.py 내부)
UsdPhysics.RigidBodyAPI.Apply(prim)
```

GUI에서의 적용: 프림 선택 > `+ Add > Physics > Rigid Body`

**주요 속성**:

| 속성 | 기본값 | 의미 |
|------|--------|------|
| `physics:rigidBodyEnabled` | True | 물리 시뮬레이션 참여 여부 |
| `physics:kinematicEnabled` | False | True면 외부 힘 무시, Transform만 변경 가능 |
| `physxRigidBody:solverPositionIterationCount` | 4 | Solver 반복 횟수 (높을수록 정확, 느림) |
| `physxRigidBody:maxAngularVelocity` | 100 | 최대 각속도 (rad/s) |

**Kinematic vs Dynamic**:

| 모드 | 중력 | 충돌 반응 | 외부 힘 | 용도 |
|------|------|----------|---------|------|
| Dynamic (`kinematic=False`) | 영향 받음 | 밀려남 | 적용됨 | 물체, 로봇 |
| Kinematic (`kinematic=True`) | 무시 | 밀리지 않음 | 무시 | 테이블, 정리함 (배경 고정물) |

`kitchen_sorting_env_cfg.py`에서:
- Table, Bins → `kinematic_enabled=True` (배경에 고정, 물체가 위에 올라감)
- Mug, Can, Apple 등 → `kinematic_enabled` 미설정 (기본 False, 동적)
- 동적 물체의 solver 반복: `solver_position_iteration_count=16` (기본 4의 4배, 안정적 접촉)

### 6.2 Collision

`UsdPhysics.CollisionAPI`를 프림에 적용하면 충돌 감지가 활성화된다.

**Collision 없는 Rigid Body**: 물리 시뮬레이션에 참여하지만 다른 물체를 통과한다 (유령 상태).

**Mesh Approximation** (충돌 형상 근사):

| 근사 방식 | 정확도 | 성능 | 용도 |
|----------|--------|------|------|
| `convexHull` | 중간 | 빠름 | 일반 물체 (기본) |
| `convexDecomposition` | 높음 | 느림 | 오목한 형상 (그릇, 컵) |
| `meshSimplification` | 높음 | 느림 | 복잡한 메시 |
| `none` (triangle mesh) | 최고 | 가장 느림 | 정밀 충돌 필요 시 |
| `boundingCube` / `boundingSphere` | 낮음 | 가장 빠름 | 대략적 충돌 |

프리미티브(Cube, Cylinder, Sphere)는 기본 형상 자체가 정확한 충돌 형상이므로 근사가 불필요하다 — 이것이 프리미티브 기반 접근의 또 다른 장점이다.

### 6.3 Mass

`UsdPhysics.MassAPI`를 적용하여 질량을 설정한다.

```python
# env_cfg.py에서의 패턴
mass_props=MassPropertiesCfg(mass=0.25)  # Mug: 250g
```

| 속성 | 의미 | 비고 |
|------|------|------|
| `physics:mass` | 질량 (kg) | 0이면 밀도에서 자동 계산 |
| `physics:density` | 밀도 (kg/m³) | mass가 설정되면 무시됨 |
| `physics:centerOfMass` | 무게 중심 (로컬 좌표) | 미설정 시 형상에서 자동 계산 |
| `physics:diagonalInertia` | 관성 텐서 대각 성분 | 미설정 시 형상+질량에서 자동 계산 |

**Kinematic 물체는 Mass가 불필요**: 외부 힘과 중력이 적용되지 않으므로 질량이 의미 없다. `kitchen_sorting_env_cfg.py`에서 Table과 Bins에는 `mass_props`가 설정되지 않았다.

### 6.4 Physics Material

전역 물리 재질과 개별 바인딩:

```python
# env_cfg.py — 전역 물리 재질 (SimulationCfg)
physics_material=RigidBodyMaterialCfg(
    static_friction=0.7,
    dynamic_friction=0.5,
    restitution=0.1,
)
```

| 속성 | 의미 | env_cfg.py 값 |
|------|------|--------------|
| `static_friction` | 정지 마찰 계수 | 0.7 |
| `dynamic_friction` | 운동 마찰 계수 | 0.5 |
| `restitution` | 반발 계수 (0=완전 비탄성, 1=완전 탄성) | 0.1 |

**전역 vs 개별**:
- 전역: `SimulationCfg.physics_material`로 설정 → 모든 Collision에 기본 적용
- 개별: 특정 프림에 `PhysicsMaterialAPI`를 바인딩 → 전역 설정 override
- GUI: 프림 선택 > `+ Add > Physics > Physics Material` > 바인딩

### 6.5 UsdPhysics vs PhysxSchema

| 네임스페이스 | 출처 | 역할 | 예시 |
|-------------|------|------|------|
| `UsdPhysics` | Pixar USD 표준 | 기본 물리 API (호환성 보장) | `RigidBodyAPI`, `CollisionAPI`, `MassAPI` |
| `PhysxSchema` | NVIDIA 확장 | PhysX 전용 고급 기능 | `PhysxRigidBodyAPI` (solver iterations), `PhysxCollisionAPI` |

**실전 규칙**:
- 기본 물리 설정은 `UsdPhysics` API 사용
- 고급 설정(solver iterations, GPU 관련)은 `PhysxSchema` API 사용
- GUI의 `+ Add > Physics` 메뉴는 양쪽 모두 자동 적용

## 8. 실전 워크플로우 — 주방 배경 USD 구축

이 섹션은 Isaac Sim GUI를 열고 배경 USD를 구축하는 전체 과정을 시간 순서대로 안내한다. 각 단계에서 "왜 이렇게 하는가"를 함께 설명한다.

### 8.1 사전 준비 (~5분)

**Isaac Sim 실행**:
```bash
./isaaclab.sh -s
```

실행 후 확인 사항:
1. **Console 패널 열기**: Window > Console (오류 확인용)
2. **Viewport 확인**: Z-up, 격자 눈금 보이는지 확인
3. **단위 확인**: Edit > Preferences > Stage > Default Meters Per Unit = `1.0`

Kit 설정에서 이미 보장되는 항목 (`isaaclab.python.kit`):
```toml
app.stage.upAxis = "Z"
simulation.defaultMetersPerUnit = 1.0
app.primCreation.DefaultXformOpOrder = "xformOp:translate, xformOp:orient, xformOp:scale"
app.primCreation.DefaultXformOpPrecision = "Double"
```

### 8.4 테이블 생성 (~10분)

**1) Cube 생성**:
- `/World` 선택 > Create > Mesh > Cube
- 이름: `Table`

**2) 크기 설정** — 핵심: Scale 계산

`env_cfg.py` 기준 테이블 크기: `0.9m × 0.6m × 0.75m`

GUI에서 Cube의 기본 size = `2.0`이므로:

```

Scale Y = 0.6 / 2.0 = 0.30
Scale Z = 0.75 / 2.0 = 0.375
```

Property 패널에서:
```

xformOp:scale = (0.45, 0.30, 0.375)
```

**왜 Translate Z가 0.375인가**: Cube의 원점은 중심에 있다. 테이블 높이 0.75m의 중심은 0.375m. 바닥에 놓으려면 Z = half_height.

**왜 Kinematic인가**: 테이블은 물리 시뮬레이션에서 움직이면 안 된다. Kinematic으로 설정하면 중력과 충돌 반응이 무시되지만, 다른 물체가 테이블 위에 놓일 수 있도록 Collision은 동작한다.

**4) Collision 설정**:
- Table 선택 > `+ Add > Physics > Collider`
- Collision Approximation: `Box` (Cube이므로 정확한 형상)

**5) 재질 설정**:
- Table 선택 > Property > Material > `+ Create > OmniPBR`
- Albedo > Color = `(0.6, 0.4, 0.2)` — 나무색

## 10. Isaac Lab 코드에서 배경 USD 로드

### 10.1 UsdFileCfg 패턴

배경 USD를 Isaac Lab 환경에 로드하는 코드:

```python
@configclass
class KitchenSortingSceneCfg(InteractiveSceneCfg):
    """배경 USD + 동적 물체 코드의 하이브리드 Scene"""

    # 배경 USD (테이블 + 정리함 + 조명 + 바닥)
    background = AssetBaseCfg(
        prim_path="{ENV_REGEX_NS}/Background",
        spawn=UsdFileCfg(
            usd_path=os.path.join(
                os.path.dirname(__file__), "assets", "kitchen_background.usd"
            ),
        ),
    )

    # 동적 물체 — 개별 RigidObjectCfg
    mug = RigidObjectCfg(
        prim_path="{ENV_REGEX_NS}/Mug",
        spawn=CylinderCfg(
            radius=0.04,
            height=0.08,
            rigid_props=RigidBodyPropertiesCfg(
                solver_position_iteration_count=16,
                max_angular_velocity=1000.0,
            ),
            mass_props=MassPropertiesCfg(mass=0.25),
            collision_props=CollisionPropertiesCfg(),
            visual_material=PreviewSurfaceCfg(diffuse_color=(0.7, 0.5, 0.3)),
            semantic_tags=[("class", "mug"), ("category", "kitchen")],
        ),
        init_state=RigidObjectCfg.InitialStateCfg(pos=(0.15, 0.55, 0.79)),
    )
    # ... 나머지 7개 물체
```

### 10.2 `{ENV_REGEX_NS}` 패턴과 GridCloner

`{ENV_REGEX_NS}`는 Isaac Lab의 `InteractiveScene`이 GridCloner로 환경을 복제할 때 치환되는 패턴이다:

```
prim_path="{ENV_REGEX_NS}/Background"

→ 실제 생성되는 프림 경로:
   /World/envs/env_0/Background
   /World/envs/env_1/Background
   /World/envs/env_2/Background
   ...
```

GridCloner 동작 순서:
1. `env_0`에 모든 에셋 생성 (원본)
2. `env_0`의 전체 프림 트리를 복제하여 `env_1`, `env_2`, ... 생성
3. 복제 시 물리 속성은 유지되며, Transform은 `env_spacing`에 따라 오프셋

`env_spacing = 3.0`이면 각 환경이 3m 간격으로 배치된다.

### 10.3 배경 USD의 PhysicsScene 충돌 문제

**주의**: 배경 USD에 PhysicsScene이 포함되어 있고, Isaac Lab의 `SimulationCfg`도 PhysicsScene을 생성하면 **충돌**할 수 있다.

해결 방법:
- **방법 A**: 배경 USD에서 PhysicsScene 제거 (Isaac Lab이 관리)
- **방법 B**: 배경 USD의 PhysicsScene을 유지하되, `SimulationCfg`에서 중복 생성 방지
- **권장**: 방법 A — 배경 USD에는 시각 요소(테이블, 조명)와 Ground Plane만 포함

## 11. 실전 함정 모음

### 함정 1: Scale vs Size 혼동

**증상**: 0.9m 너비 테이블을 만들려고 Scale X = 0.9로 설정했더니 1.8m가 됨

**원인**: GUI Cube의 기본 `size = 2.0`. Scale은 `size`에 곱해지므로 `2.0 × 0.9 = 1.8m`

**해결**: Scale = 원하는 치수 / 2.0 = 0.9 / 2.0 = **0.45**

**검증**: 프림 선택 후 Property > Raw USD Properties > `extent` 확인. `extent`는 bounding box의 실제 크기를 표시한다.

### 함정 2: Pivot Point 불일치

**증상**: Nucleus에서 가져온 에셋의 위치가 예상과 다름

**원인**: 에셋의 원점(pivot)이 중앙이 아니라 바닥 또는 모서리에 있는 경우

**진단**: 에셋 선택 > Translate = `(0, 0, 0)` > Viewport에서 원점 기준 위치 확인

**해결**: 에셋을 빈 Xform의 자식으로 넣고, Xform의 Translate로 최종 위치 조절. 또는 에셋 내부 Transform을 수정.

### 함정 3: apiSchemas Override (SdfTokenListOp 빈 override)

**증상**: USD에서 `RigidBodyAPI`가 적용되어 있어야 하는 프림이 물리 시뮬레이션에 참여하지 않음. `GetAppliedSchemas()`가 빈 리스트 반환.

**원인**: 부모 USD에서 해당 프림의 `apiSchemas` 정보가 빈 `SdfTokenListOp()`로 override되어 있음. 이는 "빈 리스트로 덮어쓰기"를 의미하며, Reference로 가져온 하위 USD의 모든 API 스키마를 무력화한다.

**진단**:
```python
# Script Editor에서 확인
from pxr import Usd
stage = omni.usd.get_context().get_stage()
prim = stage.GetPrimAtPath("/World/SomePrim")
print(prim.GetPrimStack())  # 어떤 레이어에서 apiSchemas가 설정되었는지 확인
```

**해결**:
```python
# 빈 override 제거
prim_spec = layer.GetPrimAtPath("/World/SomePrim")
prim_spec.ClearInfo("apiSchemas")  # override 제거 → 하위 USD 값 복원
```

**UST 프로젝트 사례**: 그리퍼 joints, Livox bodies, RealSense bodies에서 발견. `ust_project1_fixed.usd`에서 참조하는 arm physics USD의 `PhysxMimicJointAPI:transY`가 이 문제로 무력화되었다.

### 함정 4: Visual Mesh가 RigidBody의 sibling인 경우

**증상**: 물리 시뮬레이션 시 메시가 제자리에 멈춰 있고 RigidBody만 이동

**원인**: Visual mesh가 RigidBody 프림의 **형제(sibling)**로 존재. RigidBody가 움직여도 sibling은 따라가지 않음.

```
/World/SomeThing
├── base (RigidBody)        ← 물리로 이동
└── visual_mesh (Mesh)      ← 제자리에 멈춤! (sibling이므로)
```

**해결**: Visual mesh를 RigidBody의 **자식(child)**으로 이동:

```
/World/SomeThing
└── base (RigidBody)
    └── visual_mesh (Mesh)  ← 부모를 따라 이동 ✓
```

USD에서 reparent:
```python
from pxr import Sdf
# Sdf.CopySpec + 원본 삭제 패턴
Sdf.CopySpec(layer, "/World/SomeThing/visual_mesh",
             layer, "/World/SomeThing/base/visual_mesh")
layer.RemoveRootPrim(layer.GetPrimAtPath("/World/SomeThing/visual_mesh"))
```

### 함정 5: user.config.json Override

**증상**: `.kit` 파일에서 설정한 값이 적용되지 않음

**원인**: Kit는 영구 설정을 `user.config.json`에 저장한다. 이 파일의 `persistent.*` 설정이 `.kit` 파일의 동일 경로 설정보다 **우선**한다.

**진단**:
```bash
# user.config.json 위치 확인
find ~/.local/share -name "user.config.json" 2>/dev/null
# 또는 Kit 로그에서 "user.config" 검색
```

**해결**: `user.config.json`에서 해당 설정을 삭제하거나 올바른 값으로 수정.

**UST 프로젝트 사례**: CloudXR 설정에서 `user.config.json`의 `xr.system.openxr.runtime: "custom"`이 `.kit` 파일의 `"system"` 설정을 override하여 OpenXR 런타임 로드 실패.

### 함정 6: Physics Material 미적용

**증상**: 물체가 테이블 위에서 미끄러지거나 비현실적으로 튕김

**원인**: Collision은 있지만 Physics Material (마찰/반발)이 설정되지 않음. 기본 마찰 계수 = 0.

**해결**:
- 전역: `SimulationCfg`에서 `physics_material` 설정 (모든 Collision에 적용)
- 개별: 프림에 `PhysicsMaterialAPI` 추가 + 바인딩
- **권장**: 전역 설정이 충분하면 개별 설정 불필요

`env_cfg.py` 전역 설정:
```python
physics_material=RigidBodyMaterialCfg(
    static_friction=0.7,   # 정지 마찰
    dynamic_friction=0.5,  # 운동 마찰
    restitution=0.1,       # 반발 (낮을수록 덜 튕김)
)
```

### 함정 7: Nucleus 경로 이식성

**증상**: 로컬에서 작동하던 USD가 다른 머신에서 에셋 로드 실패

**원인**: USD 내부 Reference 경로가 `omniverse://localhost/...` (Nucleus 서버 의존) 또는 절대 로컬 경로

    # Xform (루트 프림)

    # Geometry
    geom_path = f"{path}/geometry/mesh"
    if obj["type"] == "Cylinder":
        geom = UsdGeom.Cylinder.Define(stage, geom_path)
        geom.GetRadiusAttr().Set(obj["radius"])
        geom.GetHeightAttr().Set(obj["height"])
        geom.GetAxisAttr().Set("Z")
    elif obj["type"] == "Sphere":
        geom = UsdGeom.Sphere.Define(stage, geom_path)
        geom.GetRadiusAttr().Set(obj["radius"])

### 12.3 시맨틱 태그 일괄 추가 스크립트

```python
import omni.usd
from pxr import Usd, Sdf

stage = omni.usd.get_context().get_stage()

semantic_map = {
    "/World/BinKitchen": [("class", "bin_kitchen")],
    "/World/BinFood": [("class", "bin_food")],
    "/World/BinMisc": [("class", "bin_misc")],
    "/World/Mug": [("class", "mug"), ("category", "kitchen")],
    "/World/Plate": [("class", "plate"), ("category", "kitchen")],
    "/World/Bowl": [("class", "bowl"), ("category", "kitchen")],
    "/World/Can": [("class", "can"), ("category", "food")],
    "/World/Bottle": [("class", "bottle"), ("category", "food")],
    "/World/Apple": [("class", "apple"), ("category", "food")],
    "/World/Sponge": [("class", "sponge"), ("category", "misc")],
    "/World/TeddyBear": [("class", "teddy_bear"), ("category", "misc")],
}

for prim_path, tags in semantic_map.items():
    prim = stage.GetPrimAtPath(prim_path)
    if not prim.IsValid():
        print(f"WARNING: {prim_path} not found!")
        continue
    for i, (sem_type, sem_data) in enumerate(tags):
        api_name = f"Semantics_{sem_type}_{sem_data}" if i > 0 else "Semantics"
        prim.ApplyAPI(f"SemanticsAPI:{api_name}" if ":" not in api_name else api_name)
        prim.GetAttribute(f"semantic:{api_name}:params:semanticType").Set(sem_type)
        prim.GetAttribute(f"semantic:{api_name}:params:semanticData").Set(sem_data)
    print(f"Tagged {prim_path}: {tags}")

print("Done! Semantic tags applied.")
```

> **주의**: 위 시맨틱 스크립트는 Isaac Lab의 `define_semantic_properties()` 함수 구현에 따라 API 적용 방식이 다를 수 있다. Script Editor에서 테스트 후 결과를 확인해야 한다.
