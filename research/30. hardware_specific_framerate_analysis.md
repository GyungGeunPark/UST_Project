# 30. RTX PRO 6000 Blackwell + 7950X3D + 128GB DDR5 환경에서 옵션 1 최적 frame rate 분석

> 작성: 2026-05-03 (§29 보고서를 받은 후 사용자가 본인 PC 스펙 공개하며 정량 답변 요청)
> 목적: 사용자 specific 하드웨어에서 env step rate를 어디까지 올릴 수 있는가 — 그리고 더 올려도 의미 없는 한계점은 어디인가

---

## 0. Executive Summary — 한 줄 답

> **120 Hz env step (decimation=1, sim.dt=1/120)이 사용자 PC에서 실용적 최대.** 그 이상은 input pipeline (UDCAP 140 Hz / SteamVR 120 Hz / Pico 90 Hz) 한계로 의미가 사라지고, Pink IK QP budget(8.33 ms)이 빠듯해진다. 사용자 GPU(RTX PRO 6000 Blackwell)와 CPU(7950X3D)는 120 Hz까지 큰 여유가 있지만 input pipeline ceiling 때문에 240 Hz로 가도 개선이 없다.

**한 순간에 알 수 있는 표:**

| env step | sub-sample 대 UDCAP 140Hz | Pink IK budget | HW 여유 (RTX PRO 6000 + 7950X3D) | 실용성 | 권장 |
|---|---|---|---|---|---|
| 20 Hz (현재) | 7.0 : 1 | 50 ms (86% 여유) | 매우 큼 | jagged 잔존 | 9.23 EMA만 |
| 60 Hz (decimation=2) | 2.3 : 1 | 16.7 ms (58% 여유) | 매우 큼 | 부드러움 ↑ | **1차 시도** |
| **120 Hz (decimation=1) ★** | **1.17 : 1** | **8.33 ms (16% 여유)** | **충분** | **거의 매칭** | **✓ 권장 최대** |
| 240 Hz (sim.dt=1/240, dec=1) | 0.58 : 1 (over-sample) | 4.17 ms (-68% 부족) | 위험 | UDCAP 한계 초과로 효과 없음 | ✗ 비추 |
| 60 Hz + physics 240 Hz (dec=4, dt=1/240) | 2.3 : 1 | 16.7 ms | physics 정밀도 ↑ | finger grip 안정성 ↑ | 옵션 |

## 1. 사용자 PC 스펙 분석

| 부품 | 모델 | 우리 task에서 의미 |
|---|---|---|
| GPU | **NVIDIA RTX PRO 6000 (Blackwell)** | 96 GB VRAM, sm_120, 데스크톱급 최고 — PhysX/Render는 무한대 가까운 여유 |
| CPU | **AMD Ryzen 9 7950X3D** | 16C/32T, boost 5.7 GHz, **128 MB L3 with 3D V-Cache** — single-thread cache-heavy 작업에 최적 |
| RAM | **DDR5 128 GB** | 메모리 bandwidth 한계 X, large dataset cache 가능 |

### 1.1 RTX PRO 6000 Blackwell — 단일 env에서 거의 무한 GPU 여유
- 1 env physics step 비용: 보통 ~0.1~0.5 ms (54 joints 휴머노이드 + 22 finger joints)
- 1 env render: 우리 KitchenSorting / RobotOnly 정도면 ~0.5~1.5 ms
- 96 GB VRAM은 우리 use case 5% 미만 사용
- **결론**: GPU는 frame rate ceiling이 아님

### 1.2 알려진 호환성 이슈 — RTX PRO 6000 Blackwell + Isaac Lab
검색 결과 다수의 사용자가 다음 이슈를 보고:
- **PhysX GPU pipeline fallback to CPU** ([Discussion #3612](https://github.com/isaac-sim/IsaacLab/discussions/3612)) — 드라이버 R570/R580 호환성 문제
- **PhysX Internal CUDA error 719** ([Issue #4668](https://github.com/isaac-sim/IsaacLab/issues/4668)) — RL training 중 200~1000 step 후 무작위 발생
- **Abnormally low FPS on dual RTX PRO 6000** ([IsaacSim Issue #578](https://github.com/isaac-sim/IsaacSim/issues/578)) — 일부 scene 24 fps, 0.15 fps 보고

> **확인 필수**: 사용자 환경에서는 9.22 lock-cleanup 이후 Isaac Lab이 정상 부팅되고 있으므로 (이전 세션 로그 `Simulation App Startup Complete` 확인), GPU PhysX가 정상 작동 중일 가능성이 높음. 그러나 우려되면 `print(physx_view.is_using_gpu_pipeline())` 또는 sim startup log에서 `"GPU solver pipeline failed, switching to software"` 워닝 검색.
> 만약 GPU PhysX → CPU fallback 상태라면, 7950X3D 단일 코어가 PhysX와 Pink IK 둘 다 처리 → step rate 한계가 60 Hz까지로 하향됨.

### 1.3 7950X3D — Pink IK CPU work에 최적 매치
- **Pink IK = single-thread numpy/scipy + Pinocchio C++ + osqp QP solver**
- 7950X3D의 **3D V-Cache (96 MB extra L3)**는 분기/cache-heavy 코드에 매우 효과적
  - Pinocchio FK는 sequential traversal — V-Cache가 임팩트 큼
  - osqp warm-start QP는 작은 인스턴스의 반복 수렴 — V-Cache hit ratio ↑
- 단일 코어 5.7 GHz boost — 5 ms QP가 1~2 ms로 떨어질 가능성
- Multi-thread 32T는 VR sampler / VMC receiver / Isaac Sim 다른 thread에 분산

> **추정 Pink IK time on 7950X3D**: 3~5 ms (cold) → **1~2 ms (warm-start)**. QP가 캐시 hit하면 V-Cache 효과로 더 짧아짐.

### 1.4 DDR5 128 GB — 우리 task엔 과잉
- 1 env Isaac Sim은 ~10 GB VRAM, ~5 GB RAM
- 128 GB는 long-horizon recording (1시간 30 fps stereo camera = 100 GB) 등 dataset 용도에서 의미

## 2. Input Pipeline Ceiling — env step rate를 올려도 의미 없는 지점

핵심 깨달음: **env step rate를 input rate보다 더 높게 올려도, 같은 패킷을 여러 번 읽는 것일 뿐**. 정보가 추가되지 않는다.

### 2.1 각 input source의 hard ceiling

| Source | 측정/명세 frame rate | 우리 시스템에서의 hard ceiling |
|---|---|---|
| **UDCAP VMC broadcast** | 사용자 보고 ~140 Hz | **140 Hz** — UDCAP driver가 더 높이 못 보냄 |
| **SteamVR Sampler thread** | rate_hz=120 (default in vr_sampler.py) | **120 Hz** — pyopenvr 한계 + thread sleep |
| **Pico 4 Ultra HMD display** | 명세 90 Hz | **90 Hz** — HMD 자체 refresh rate |
| **Virtual Desktop streaming** | 90 Hz lock (Pico display 호환) | **90 Hz** — VD가 HMD에 lock |
| **Vive forearm trackers** | 명세 1000 Hz raw, OpenVR ~250 Hz | 250 Hz — 그러나 우리 sampler가 120 Hz로 down-sample |
| **HMD pose** | 90 Hz (VD streaming bound) | 90 Hz |

**Effective input rate (모든 source 합쳤을 때 가장 빠른 갱신 주기)**: 
- 손가락: 140 Hz (UDCAP VMC)
- 팔/손목: 120 Hz (SteamVR Sampler) 또는 250 Hz raw (Vive direct)
- 머리/HMD: 90 Hz

### 2.2 env step 120 Hz vs 240 Hz 비교

| | env step 120 Hz | env step 240 Hz |
|---|---|---|
| 손가락 (UDCAP 140 Hz) | sub-sample 1.17:1 — 거의 1:1 | over-sample 0.58:1 — **같은 패킷 두 번 읽음** |
| 팔 (SteamVR 120 Hz) | sub-sample 1.0:1 — 정확 매칭 | over-sample 0.5:1 — 같은 데이터 두 번 |
| 머리 (HMD 90 Hz) | over-sample 0.75:1 (괜찮음, HMD는 부드러운 motion이라 OK) | over-sample 0.375:1 (의미 없음) |
| **새로운 정보 비율** | **거의 100%** | **~50%** |

→ **240 Hz는 input 한계 때문에 정보가 추가되지 않음**. CPU/GPU 부담만 2배.

### 2.3 9.23 EMA가 input pipeline 한계를 더 강조함
- VMC packet jitter ±20 Hz (140 Hz 명목, 실제 120~160 Hz 범위)
- env step 120 Hz면 매번 packet 갱신이 보장되지만, 240 Hz면 절반은 stale 데이터
- EMA가 stale 데이터에 weight를 줘서 "유사 lag"를 만들 수 있음 — 240 Hz에서 EMA alpha를 매우 높여야(거의 1.0) 정상 동작 → EMA 효과 사라짐

## 3. Pink IK QP Budget 정량 분석 (7950X3D 기준)

### 3.1 Pink IK의 한 step 비용 분해
([pink_ik.py:190 compute()](source/isaaclab/isaaclab/controllers/pink_ik/pink_ik.py:190) 기준)

| 단계 | 작업 | 7950X3D + 3D V-Cache 기준 추정 |
|---|---|---|
| 1. Joint reordering (Isaac Lab → Pink) | numpy index | 0.05 ms |
| 2. Pinocchio FK (54 joints) | C++ in-cache | 0.3~0.5 ms |
| 3. Frame Task Jacobian × 2 (left/right palm) | C++ | 0.5~1.0 ms |
| 4. Null-Space Posture Task | C++ | 0.2~0.4 ms |
| 5. QP build | numpy/scipy sparse | 0.5~1.0 ms |
| 6. **osqp solve** (cold) | C OSQP | 2.0~5.0 ms |
| 6'. **osqp solve** (warm-start, sequential calls) | C OSQP | **0.5~1.5 ms** ★ |
| 7. Reorder back + tensor copy | numpy | 0.1 ms |
| **Total cold-start** | | **3.6~7.0 ms** |
| **Total warm-start** | | **1.6~3.5 ms** ★ |

OSQP는 sequential MPC-style 호출에서 warm-start가 핵심. Pink IK는 매 step 비슷한 QP를 풀므로 warm-start가 자동 활성.

### 3.2 env step rate vs Pink IK 안전 margin
| env step | budget | warm-start avg (2.5ms) | margin | warm-start P99 (5ms) | margin |
|---|---|---|---|---|---|
| 60 Hz | 16.7 ms | 2.5 ms | 85% | 5 ms | 70% — 매우 안전 |
| 120 Hz | 8.33 ms | 2.5 ms | 70% | 5 ms | 40% — 안전 |
| 240 Hz | 4.17 ms | 2.5 ms | 40% | 5 ms | -20% — **위험** |

### 3.3 결론
- **120 Hz env step에서 Pink IK는 P99 안전 zone**
- **240 Hz는 P99 worst case 위반 가능성 ↑**
- **60 Hz는 매우 안전**

### 3.4 비상 안전망 — Pink IK divergence 시
[pink_ik.py:227 (compute())](source/isaaclab/isaaclab/controllers/pink_ik/pink_ik.py:227)에 fail-safe 존재:
> "If the IK solver fails, returns the current joint positions unchanged to maintain stability."

→ 일시적 budget violation 시 robot freeze (새 명령 무시), 다음 step에서 정상화. catastrophic failure 아님. 그러나 **빈번한 violation은 visual lag로 나타남**.

## 4. Render Pipeline 분석

### 4.1 우리 환경 (`render_interval=1`)
- 매 sim_step 마다 render 호출 → physics 120 Hz면 render 120 Hz
- Render는 GPU bound, 단일 env면 RTX PRO 6000으로 ~1 ms

### 4.2 env step rate 변경 시 render 영향
- decimation=1, sim.dt=1/120: physics 120 Hz × render 120 Hz = render 120 Hz, **OK**
- decimation=2, sim.dt=1/240: physics 240 Hz × render 240 Hz = render 240 Hz, **GPU 부담 ↑**
  - 이 경우 `render_interval=2`로 설정해 render 120 Hz로 cap 추천

### 4.3 VR streaming
- Virtual Desktop은 HMD 90 Hz lock
- env render 120 Hz여도 VD가 90 Hz로 frame skip → effective 90 Hz
- env render 60 Hz면 VD가 frame을 보간/duplicate → 시각적으로 부드러움 ↓ (VD bound)

> **권장 render rate: 120 Hz** (= env step 120 Hz). 90 Hz HMD에 1.33배 over-sample로 부드러움 보장.

## 5. 사용자 PC 정확한 sweet spot 분석

### 5.1 후보 변형 종합

| 변형 | env step | physics | render | sub-sample | Pink IK margin (P99) | GPU/CPU 부담 | 추천도 |
|---|---|---|---|---|---|---|---|
| A 현재 | 20 Hz | 120 Hz | 120 Hz | 7.0:1 | 90% | 매우 낮음 | 9.23 EMA만 적용 |
| B 보수 | 60 Hz | 120 Hz | 120 Hz | 2.3:1 | 70% | 낮음 | 1차 시도 |
| **C 균형** ★ | **120 Hz** | **120 Hz** | **120 Hz** | **1.17:1** | **40%** | **중간** | **★ 권장 최대** |
| D 정밀 contact | 120 Hz | 240 Hz | 120 Hz (render_interval=2) | 1.17:1 | 40% | 중-높 | finger grip 정확도 추가 시 |
| E 비실용 | 240 Hz | 240 Hz | 240 Hz | 0.58:1 | -20% | 높음 | ✗ 효과 없음 |

### 5.2 변형 C가 ★ 권장 최대인 4가지 이유

**1. Input pipeline 한계와 일치**
- UDCAP 140 Hz / SteamVR 120 Hz와 거의 1:1 매칭
- 240 Hz로 가면 같은 packet 두 번 읽기 — 정보 0% 추가

**2. Pink IK QP budget P99 안전**
- 7950X3D + 3D V-Cache로 warm-start QP 평균 1~2.5 ms, P99 5 ms
- 8.33 ms budget에서 P99 40% 여유 → 안정적

**3. RTX PRO 6000 GPU 여유**
- 단일 env physics + render 합쳐도 5 ms 미만
- GPU 사용률 20% 미만 예상 (96 GB VRAM은 99% 비사용)

**4. 9.23 EMA fix와 자연스럽게 결합**
- 120 Hz step에서 alpha=0.4 → time constant ~17 ms (현재 20 Hz의 ~98 ms 대비)
- 결과: 더 responsive하고 동시에 부드러움. alpha=0.2 또는 0.3 추천

### 5.3 변형 D — finger grip 안정성 우선 시 옵션
**physics 240 Hz의 의미:**
- Articulation contact resolution이 매 4.17 ms 마다 수행
- 손가락이 물체를 잡을 때 micro-slip / penetration 감소
- 그러나 dexterous task에서 PhysX는 1/120에서 이미 충분히 안정적이라는 다수 사례

**언제 D를 선택할까?**
- variant C에서 실제로 손가락이 잡고 있는 물체를 떨어뜨리는 등의 grip jitter 보고된다면
- 또는 물체 reorientation task에서 contact phase가 빠르게 바뀐다면

### 6.2 EMA alpha 재계산
| 현재 alpha @ 20 Hz | time constant | 동등한 alpha @ 120 Hz |
|---|---|---|
| 0.4 | 98 ms | **0.07** (매우 강한 smoothing) |
| 0.6 | 54 ms | **0.13** |
| 0.2 | 227 ms | **0.03** (사실상 정지) |

→ 120 Hz로 올리면 alpha를 0.07 정도로 낮춰야 현재의 부드러움을 유지. 그러나 그러면 EMA가 거의 정지 — 사실상 input 자체가 부드러우므로 EMA를 약하게.

**실제 권장**:
- 120 Hz로 올린 후 **alpha=0.4 그대로 시도** — time constant 17 ms로 lag이 거의 없는 부드러움
- 또는 **alpha=0.6** (10 ms time constant) — 더 responsive
- alpha=0.07로 낮출 필요는 없음 — 120 Hz의 input이 이미 부드럽기 때문

## 7. 변형 C 이상으로 가지 않는 이유 — 7가지 논리

1. **UDCAP 140 Hz가 손가락 input의 ceiling** — 이 이상 갈 수 없음 (UDCAP driver 한계)
2. **SteamVR Sampler 120 Hz가 wrist input의 ceiling** — vr_sampler.py rate_hz default
3. **Pico 4 Ultra HMD 90 Hz가 head input의 ceiling** — 디스플레이 refresh rate 한계
4. **Virtual Desktop 90 Hz lock** — HMD에 lock되어 있어 그 이상 못 받음
5. **Pink IK QP P99 5 ms** — 4.17 ms (240 Hz) budget 위반 가능성 ↑
6. **9.23 EMA의 의미가 사라짐** — over-sampling 환경에서 EMA는 사실상 비활성
7. **GPU/CPU 부담만 2배 증가** — 정보 0% 추가, 부담 100% 증가

## 8. 결론

### 8.1 권장 사항
> **변형 C — `decimation=1, sim.dt=1/120`로 env step 120 Hz**가 사용자 PC에서 옵션 1의 실용적 최대값.

### 8.2 권장 작업 순서
1. ✅ 9.23 EMA fix 라이브 검증 (이미 적용)
2. ⏳ **변형 B 시작** — `decimation=2`로 env step 60 Hz (sub-sample 2.3:1)
3. ⏳ 결과 만족스럽고 GPU PhysX 정상 작동 확인되면 **변형 C** — `decimation=1`로 120 Hz
4. ⏳ 결과 비교 후 최종 default 결정 (60 Hz vs 120 Hz)
5. ⏳ EMA alpha 재튜닝 (60 Hz → 0.4, 120 Hz → 0.4 또는 0.6)
6. ⏸️ 변형 D (`sim.dt=1/240`)는 finger grip 안정성 이슈가 있을 때만 추가 검토

### 8.3 한 단계씩 가는 이유
- **변형 B → C 점진 확장**이 가장 안전
- 60 Hz에서 만족스러우면 120 Hz로 올릴 필요 없음 (불필요한 risk + 부담)
- RTX PRO 6000 Blackwell의 PhysX CPU fallback 이슈가 의심되면 60 Hz가 안전 zone
- 60 Hz에서 jagged가 잔존하면 120 Hz로 올려 ceiling 도달

### 8.4 240 Hz 이상은 안 가는 이유 — 명확한 한 줄
> **UDCAP 140 Hz가 hard ceiling이라 240 Hz로 가면 절반의 step은 같은 packet을 두 번 읽는 것에 불과**. 정보 0% 추가, 부담 100% 추가.

### 8.5 sweet spot 요약
| 우선 순위 | 시나리오 | 권장 변형 |
|---|---|---|
| 정보 매칭 + 안정성 | UDCAP 140 Hz와 거의 1:1 매칭 + GPU 여유 | **변형 C (120 Hz)** ★ |
| 안전성 + 점진 | 일단 안전하게 1차 시도 | **변형 B (60 Hz)** |
| Finger grip 정확도 | physics가 더 정확해야 contact 안정 | **변형 D (env 120Hz, physics 240Hz)** |
| GPU PhysX CPU fallback 의심 | 7950X3D 단일 코어가 PhysX 처리 | 변형 B 유지 |

## 9. 추가 고려 — Blackwell GPU PhysX 이슈 (사용자 환경)

GitHub에서 다수 보고된 issue들:
| 이슈 | 영향 | 우리 환경 점검 |
|---|---|---|
| [Discussion #3612](https://github.com/isaac-sim/IsaacLab/discussions/3612) — PhysX GPU pipeline fallback | 단일 env에서 7950X3D가 CPU PhysX 처리 → step rate ↑ 시 부담 ↑ | sim startup 로그에 "GPU solver pipeline failed" 검색 |
| [Issue #4668](https://github.com/isaac-sim/IsaacLab/issues/4668) — PhysX Internal CUDA error 719 | RL training 200~1000 step 후 무작위 crash | teleop 사용 case는 직접 영향 적음 (training 아님) |
| [IsaacSim Issue #578](https://github.com/isaac-sim/IsaacSim/issues/578) — Abnormally low FPS on Blackwell | 일부 scene 24 fps 또는 0.15 fps | 사용자 9.22 시점 부팅 정상 — 영향 없는 듯 |

> **사용자 9.22 라이브 teleop이 정상 동작 (`Simulation App Startup Complete` 확인) — GPU PhysX 정상 작동 가능성 높음**. 그러나 변형 C (120 Hz) 시도 전에 sim 부팅 로그 한번 더 점검 추천.

확인 명령:
```powershell
python -X utf8 -m ust_ws.ust_fourier_260421.scripts.run_teleop --env_variant robot_only --teleop_device pico_udcap 2>&1 | Select-String -Pattern "GPU solver|switching to software|GPU pipeline|fallback"
```
출력 없으면 GPU PhysX 정상.
