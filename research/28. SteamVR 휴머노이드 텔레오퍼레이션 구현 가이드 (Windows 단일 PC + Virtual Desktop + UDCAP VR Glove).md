# SteamVR 휴머노이드 텔레오퍼레이션 구현 가이드 v2 — Windows 11 단일 PC 구성

> **문서 27의 후속 심화 가이드.** 27번 문서가 "듀얼 PC(Windows SteamVR + Linux Isaac Lab)"를 권장했지만, 본 구현에서는 **Windows 11 네이티브 단일 PC** 환경으로 결정되었다. 이에 따라 아키텍처, 데이터 브리지, Isaac Lab Device 구현을 **Windows 단일 PC 기준으로 전면 재작성**한다.

> **결정된 사항 (사용자 확정)**
> 1. **Pico 4 Ultra + Virtual Desktop (Windows 전용) + Enhanced Forearm 모드** (허리 + 양 발목 + 양 팔뚝 = 5트래커)

**Windows 11 단일 PC가 가능해진 핵심 이유:**
- Isaac Lab은 Windows에서 `pip install isaacsim[all] isaaclab`으로 공식 설치 가능 (2.x부터). 3.0-beta에서도 Windows 지원 예정.
- **Isaac Lab의 OpenXR 런타임은 교체 가능** — Windows에서 SteamVR이 활성 OpenXR 런타임이면 Isaac Lab의 `OpenXRDevice`/OpenXR 의존 코드는 CloudXR 없이도 동일 PC에서 Pico 트래킹을 활용할 수 있다.

## 1. Virtual Desktop + Pico 4 Ultra + 5 트래커 Enhanced Forearm 상세 구성

### 1.1 Virtual Desktop의 Vive Tracker 에뮬레이션 메커니즘

Virtual Desktop(유료 $25, Windows 전용)은 Quest/Pico 헤드셋의 자체 바디 트래킹 데이터를 **SteamVR driver로 주입**하여, 실제 HTC Vive Tracker가 붙은 것처럼 SteamVR에 인식시킨다. Pico 4 Ultra + Pico Motion Tracker(2.4GHz 독자 프로토콜) 5개 구성 시:

```
Pico Motion Tracker × 5 ──2.4GHz──▶ Pico 4 Ultra 헤드셋
                                        │
                                        │ (헤드셋 내부 AI가 24관절 스켈레톤으로 융합)
                                        ▼
                              Virtual Desktop Client (APK)
                                        │
                                  ── Wi-Fi 6/6E ──▶ Windows PC
                                        │
                              Virtual Desktop Streamer
                                        │
                          ┌─────────────┴─────────────┐
                          ▼                           ▼
                   SteamVR OpenVR API        SteamVR OpenXR 런타임
                   (HMD + 5 Vive Tracker      (HMD pose, hand tracking)
                    에뮬레이션)
```

**VD Streamer 설정 (필수):**
- `Streaming` 탭 → `Forward trackers to SteamVR` **ON**
- 또는 구버전 레이블: `Emulate Vive Trackers` **ON**
- Pico OS 5.14 이상 (Enhanced Forearm 모드 필요)
- 헤드셋에서 Pico 트래킹 설정 → Enhanced Forearm 선택 (waist + 2 ankle + 2 forearm)

### 1.2 5 트래커 역할 바인딩

SteamVR에 에뮬레이션된 5개 트래커는 각각 고유 시리얼(`LHR-xxxxxxxx` 포맷)을 가진다. SteamVR의 `Manage Vive Trackers` UI에서 역할을 지정하되, **프로그래밍 시에는 시리얼 기반 매핑을 병행**해야 한다 (SteamVR role assignment는 설정 파일 분실 시 리셋됨).

```json
// tracker_binding.json (프로젝트 루트에 두고 device init 시 로드)
{
  "trackers": {
    "LHR-3CD1A9DA": { "role": "waist",         "steamvr_role": "TrackerRole_Waist" },
    "LHR-25865D81": { "role": "left_ankle",    "steamvr_role": "TrackerRole_LeftFoot" },
    "LHR-4359D2B6": { "role": "right_ankle",   "steamvr_role": "TrackerRole_RightFoot" },
    "LHR-AABBCCDD": { "role": "left_forearm",  "steamvr_role": "TrackerRole_LeftElbow" },
    "LHR-EEFF0011": { "role": "right_forearm", "steamvr_role": "TrackerRole_RightElbow" }
  },
  "hmd": "auto"
}
```

> ⚠️ VD가 에뮬레이션하는 트래커의 시리얼은 Pico 트래커 실물 시리얼이 아니라 **VD가 가상 생성한 LHR- 포맷**이다. 시리얼을 확인하려면 최초 연결 후 `pyopenvr`로 enumerate 후 기록한다.

**팔뚝 트래커(forearm)의 역할:** UDCAP VR Glove는 **절대 위치 추적이 없다**. 따라서 양 손목의 6DoF 포즈는 Enhanced Forearm의 **forearm 트래커**에서 가져오고, 팔꿈치-손목 offset(~0.10 ~ 0.15m)을 상수로 적용하여 손목 포즈를 복원한다. (상세 수식은 §5.2)

### 1.3 성능/지연 예상 수치

| 구간 | 지연 | 비고 |
|------|------|------|
| Pico tracker → 헤드셋 | ~5 ms | 2.4GHz 독자 링크 |
| 헤드셋 AI 융합 | ~10-15 ms | 24관절 IK 추론 |
| Wi-Fi 6 왕복 | ~5-10 ms | QoS 설정 및 AP 품질에 따라 변동 |
| VD streamer → SteamVR | ~1-2 ms | IPC |
| SteamVR → pyopenvr | ~1 ms | OpenVR API |
| **총 엔드-투-엔드** | **~22-35 ms** | |

**관건은 Wi-Fi 안정성**이다. 유선 이더넷으로 Windows PC를 AP 바로 옆에 두고, Wi-Fi 6E 전용 채널(6GHz)을 Pico에 단독 할당하는 것이 권장된다.

## 2. UDCAP VR Glove 연결 — 주 경로와 부 경로

### 2.1 제품 확인: UDCAP **VR Glove** vs **Data Glove**

사용자 장비는 **UDCAP VR Glove** 라인업 ($699). 이는 게임/VRChat 용도로 설계된 소비자용 버전으로, 주 출력이 **SteamVR Skeletal Input (Valve Index 컨트롤러 에뮬레이션)**이다. Linux 네이티브 HandDriver + UDP/Protobuf는 **Data Glove($1,799)** 전용 기능이므로 VR Glove에서는 사용 불가. 그러나 VR Glove도 **VMC/OSC broadcast 기능**을 UDCAP Driver에서 제공하므로, 이를 활용한 보조 경로가 가능하다.

| 출력 채널 | VR Glove ($699) | Data Glove ($1,799) |
|----------|----------------|---------------------|
| SteamVR Skeletal Input 2.0 | ✅ 주 기능 | ✅ |
| SteamVR Index 컨트롤러 에뮬레이션 | ✅ | ✅ |
| VMC broadcast (UDP/OSC) | ✅ General Settings → VMC Broadcast | ✅ |
| OSC broadcast (UDP) | ✅ 동일 메뉴 | ✅ |
| HandDriver UDP (JSON/Protobuf 21DOF) | ❌ | ✅ |
| Linux 네이티브 드라이버 | ❌ (Windows only) | ✅ |
| C++/Python SDK | ❌ | ✅ |

### 2.2 공통 하드웨어 파이프라인

```
UDCAP VR Glove (L + R) ──2.4GHz──▶ USB 동글 ──▶ Windows PC
                                                   │
                                                   ▼
                                           UDCAP Driver (GUI 앱)
                                                   │
                          ┌────────────────────────┼────────────────────────┐
                          ▼                         ▼                         ▼
                   SteamVR Driver         VMC Broadcast            OSC Broadcast
                   (Add-on 등록)           UDP:39539 (기본)         UDP:port (사용자 지정)
                   21관절 → Index          /VMC/Ext/Bone/Pos        임의 OSC 주소
                   fingerCurls + Skeletal
```

- 손당 12개 플렉스 센서 → 손당 **21 관절 각도** 출력 (15 finger joints × 일부는 다축)
- 120 Hz 샘플링, < 10 ms 센서 지연
- **UDCAP Driver의 SteamVR 드라이버는 Add-on으로 SteamVR에 설치**되며, Skeletal Input 2.0 (VRChat 호환) 규격을 따른다.

### 2.3 주 경로 (Path A): UDCAP Driver → SteamVR Skeletal Input → pyopenvr

이 경로는 VR Glove의 정식 경로이며, SteamVR 내부에서 모든 추적 데이터(HMD + 5트래커 + 양손)를 동일한 시간축과 좌표계로 제공받을 수 있다는 **막대한 장점**이 있다.

#### 2.3.1 SteamVR Skeletal Input 2.0 데이터 구조

OpenVR의 `IVRInput::GetSkeletalBoneData()`는 31개 뼈 변환(root, wrist, thumb0-3, index0-4, middle0-4, ring0-4, pinky0-4, aux)을 `VRBoneTransform_t` (pos + quaternion) 배열로 반환한다. 또한 `IVRInput::GetSkeletalSummaryData()`는 5개 손가락의 **fingerCurls[0..4]** (0..1 정규화) 및 **fingerSplays[0..3]** 값을 요약으로 제공한다.

**pyopenvr에서 Skeletal Input 읽기 패턴:**

```python
# Windows 11 native, Python 3.11, openvr 1.26.*+
import openvr

vr_system = openvr.init(openvr.VRApplication_Other)
vr_input  = openvr.VRInput()

# 1) 액션 매니페스트 JSON 로드 (프로젝트에 actions.json 준비 필요)
vr_input.setActionManifestPath(os.path.abspath("openvr_actions/actions.json"))

# 2) 양손 Skeletal 액션 핸들
h_skel_l = vr_input.getActionHandle("/actions/teleop/in/skeleton_left")
h_skel_r = vr_input.getActionHandle("/actions/teleop/in/skeleton_right")
h_set    = vr_input.getActionSetHandle("/actions/teleop")

# 3) 매 프레임
vr_input.updateActionState([openvr.VRActiveActionSet_t(
    ulActionSet=h_set, ulRestrictedToDevice=openvr.k_ulInvalidInputValueHandle)])

# 31개 뼈 변환 (parent-space reference pose 포함)
bones_l = vr_input.getSkeletalBoneData(
    h_skel_l,
    openvr.VRSkeletalTransformSpace_Parent,
    openvr.VRSkeletalMotionRange_WithController)

# 요약 (fingerCurls 5, fingerSplays 4)
summary_l = vr_input.getSkeletalSummaryData(
    h_skel_l,
    openvr.VRSummaryType_FromAnimation)
curls_l = list(summary_l.flFingerCurl)   # [thumb, index, middle, ring, pinky]
splays_l = list(summary_l.flFingerSplay)
```

`actions.json` 최소 예시 (전체는 Valve 공식 샘플 참조):

```json
{
  "action_sets": [{ "name": "/actions/teleop", "usage": "single" }],
  "actions": [
    {"name":"/actions/teleop/in/skeleton_left",  "type":"skeleton", "skeleton":"/skeleton/hand/left",  "requirement":"optional"},
    {"name":"/actions/teleop/in/skeleton_right", "type":"skeleton", "skeleton":"/skeleton/hand/right", "requirement":"optional"}
  ],
  "default_bindings": [],
  "localization": [{"language_tag":"en_us","/actions/teleop":"UST Teleop"}]
}
```

> 💡 **VRChat Skeletal Input 2.0 호환**: UDCAP Driver는 VRChat 호환 Skeletal Input 2.0을 주장하므로 31 bone full skeleton이 정상적으로 채워진다. `VRSkeletalMotionRange_WithoutController` 모드를 사용하면 "컨트롤러를 쥐지 않은" 자연스러운 포즈가 나오며, 로봇 손 리타게팅에는 이 모드가 더 적합하다.

#### 2.3.2 21 관절각 vs 31 본 — 로봇 손 리타게팅 관점

SteamVR Skeletal은 31 bone 변환을 제공하지만, UDCAP 하드웨어의 네이티브 출력인 **21 관절각**과는 약간 다르다. `dex-retargeting` 라이브러리(DexPilot 기반, Inspire Hand/Shadow Hand/Allegro 지원)는 **손가락 끝점 위치 5점(fingertips) + 손목 기준 방향 벡터**만을 입력으로 쓰므로, 31 bone 중 각 손가락의 tip bone(3,7,12,17,22 인덱스) 5개만 추출하면 충분하다. 정밀도 관점에서 21DOF 직접 접근이 Data Glove 경로보다 이론상 우월하지만, VR Glove의 SteamVR 경로에서도 **DexPilot 입력 스펙에 필요한 정보는 전부 얻을 수 있다**.

### 2.4 부 경로 (Path B): UDCAP Driver → VMC Broadcast → Python UDP 수신

VMC 프로토콜(Virtual Motion Capture Protocol)은 Unity humanoid bone을 OSC over UDP로 브로드캐스트하는 일본 VTuber 생태계 표준. UDCAP Driver의 **General Settings → Data Transmission Format → VMC Broadcast** 를 활성화하면 손 본들이 VMC 규격으로 송신된다.

**VMC 핵심 OSC 주소:**

| 주소 | 페이로드 | 내용 |
|------|---------|------|
| `/VMC/Ext/OK` | `int` | 상태 (0/1) |
| `/VMC/Ext/T` | `float` | 타임스탬프 (초) |
| `/VMC/Ext/Root/Pos` | `str, 7×float` | 루트 pos(3)+quat(4) |
| `/VMC/Ext/Bone/Pos` | `str name, 7×float` | **본 이름** + pos+quat |

`name`은 Unity `HumanBodyBones` enum 명 — 손가락은 `LeftThumbProximal`, `LeftIndexDistal` 등. pos는 parent-relative이며 단위는 미터.

**Python 수신기 (python-osc):**

```python
# pip install python-osc
from pythonosc import dispatcher, osc_server
import threading, numpy as np

BONE_ORDER_L = [  # HumanBodyBones 명명 규약
    "LeftThumbProximal","LeftThumbIntermediate","LeftThumbDistal",
    "LeftIndexProximal","LeftIndexIntermediate","LeftIndexDistal",
    "LeftMiddleProximal","LeftMiddleIntermediate","LeftMiddleDistal",
    "LeftRingProximal","LeftRingIntermediate","LeftRingDistal",
    "LeftLittleProximal","LeftLittleIntermediate","LeftLittleDistal",
]

class VMCHandReceiver:
    def __init__(self, port=39539):
        self.bones = {}
        d = dispatcher.Dispatcher()
        d.map("/VMC/Ext/Bone/Pos", self._on_bone)
        self.server = osc_server.ThreadingOSCUDPServer(("0.0.0.0", port), d)
        threading.Thread(target=self.server.serve_forever, daemon=True).start()

    def _on_bone(self, _addr, name, px, py, pz, qx, qy, qz, qw):
        self.bones[name] = (np.array([px,py,pz]), np.array([qx,qy,qz,qw]))

    def left_hand_joint_positions(self):
        return np.stack([self.bones[b][0] for b in BONE_ORDER_L if b in self.bones])
```

**이 경로의 쓸모:**
1. SteamVR Add-on 로딩 실패 등 장애 시 폴백
2. Isaac Lab 프로세스에서 **OpenVR 세션 점유 없이** 손 데이터만 수신 (OpenVR 세션 충돌 회피 디버깅용)
3. 비 VR 워크플로(예: 글러브만 끼고 데스크톱 아바타 드라이빙)

### 2.5 직접 SDK → ROS2 경로 — VR Glove에서는 **불가능**

27번 문서가 강력 권장했던 **Data Glove의 HandDriver → UDP Protobuf 21DOF → ROS2** 경로는 **VR Glove 하드웨어/펌웨어에서는 지원되지 않는다**. VR Glove에서 제공되는 비-SteamVR 출력은 VMC/OSC 뿐이며, 이는 Unity humanoid bone 규격을 따르므로 raw 플렉스 센서 값이나 21 관절각 원시값이 아니다.

또한 본 프로젝트는 **Windows 11 단일 PC**이고 Windows에는 네이티브 ROS 2 Jazzy가 공식 지원되지 않는다 (Windows 10만 지원). 따라서 ROS 2 기반 IPC 자체가 Windows 환경에서는 부적합하다. **ZMQ나 loopback UDP** 같은 경량 IPC로 대체한다 (§4 참조).

### 2.6 결론: 구현 우선순위

```
[1순위] Path A: SteamVR Skeletal Input (OpenVR)
        └─ pyopenvr로 HMD + 5 Tracker + Skeletal Hands 한 번에 획득
        └─ 시간 동기화 보장, 좌표계 단일, 구현 단순

[2순위] Path B: VMC Broadcast (OSC/UDP) — 폴백/보조 로깅
        └─ SteamVR 세션 문제 격리용

[불가] Data Glove 전용 HandDriver UDP 경로 — 하드웨어 미지원
```

### 3.3 OpenXR 런타임 설정 (선택)

Isaac Lab의 `OpenXRDevice`나 Pinocchio pose viewer 등이 OpenXR을 사용하는 경우, **Windows의 활성 OpenXR 런타임을 "SteamVR"로 지정**해야 Pico/SteamVR 에코시스템과 일관성이 유지된다.

- SteamVR → 설정 → 개발자 → "SteamVR을 현재 OpenXR 런타임으로 설정"
- 또는 레지스트리 `HKLM\Software\Khronos\OpenXR\1\ActiveRuntime = C:\Program Files (x86)\Steam\steamapps\common\SteamVR\steamxr_win64.json`

## 4. 데이터 파이프라인: pyopenvr → (in-process) → Isaac Lab Device

단일 Windows PC에서는 네트워크 홉이 불필요하다. 두 가지 권장 구성 중 선택:

### 4.1 구성 A — 동일 프로세스 (권장)

Isaac Lab 스크립트(`run_teleop.py`) 내부에 **VR 샘플러 스레드**를 띄우고, 메인 Isaac Lab 메인 스텝이 매 프레임 최신 스냅샷을 읽는다. 가장 지연이 낮고 동기화 이슈가 적다.

```python
# vr_sampler.py — Isaac Lab 프로세스 내부 스레드
import threading, time, numpy as np, openvr

class SteamVRSampler:
    def __init__(self, tracker_serials: dict, hand_action_handles: dict,
                 rate_hz: float = 120.0):
        self.vr = openvr.init(openvr.VRApplication_Other)
        self.input = openvr.VRInput()
        self.input.setActionManifestPath(os.path.abspath("openvr_actions/actions.json"))
        self.h_set = self.input.getActionSetHandle("/actions/teleop")
        self.h_sk  = {k: self.input.getActionHandle(v) for k,v in hand_action_handles.items()}
        self.tracker_serials = tracker_serials  # {"waist": "LHR-...", ...}

        self.latest = {"hmd": None, "trackers": {}, "hands": {}}
        self._lock = threading.Lock()
        self._stop = False
        self._dt = 1.0 / rate_hz
        threading.Thread(target=self._loop, daemon=True).start()

    def _loop(self):
        while not self._stop:
            t0 = time.perf_counter()
            poses = self.vr.getDeviceToAbsoluteTrackingPose(
                openvr.TrackingUniverseStanding, 0,
                openvr.k_unMaxTrackedDeviceCount)

            snap = {"trackers": {}, "hands": {}, "hmd": None}
            # 디바이스 → 시리얼 매핑
            sn2idx = {}
            for i in range(openvr.k_unMaxTrackedDeviceCount):
                cls = self.vr.getTrackedDeviceClass(i)
                if cls == openvr.TrackedDeviceClass_Invalid: continue
                sn = self.vr.getStringTrackedDeviceProperty(i, openvr.Prop_SerialNumber_String)
                sn2idx[sn] = (i, cls)

            # HMD
            for sn,(i,cls) in sn2idx.items():
                if cls == openvr.TrackedDeviceClass_HMD and poses[i].bPoseIsValid:
                    snap["hmd"] = _mat_to_pq(poses[i].mDeviceToAbsoluteTracking); break

            # 5 트래커
            for role, sn in self.tracker_serials.items():
                if sn in sn2idx:
                    i,_ = sn2idx[sn]
                    if poses[i].bPoseIsValid:
                        snap["trackers"][role] = _mat_to_pq(poses[i].mDeviceToAbsoluteTracking)

            # 양손 Skeletal + 요약
            self.input.updateActionState([openvr.VRActiveActionSet_t(
                ulActionSet=self.h_set,
                ulRestrictedToDevice=openvr.k_ulInvalidInputValueHandle)])
            for side, h in self.h_sk.items():
                bones = self.input.getSkeletalBoneData(
                    h, openvr.VRSkeletalTransformSpace_Model,
                    openvr.VRSkeletalMotionRange_WithoutController)
                summary = self.input.getSkeletalSummaryData(
                    h, openvr.VRSummaryType_FromAnimation)
                snap["hands"][side] = {
                    "bones": np.array([(b.position.v[0], b.position.v[1], b.position.v[2],
                                        b.orientation.x, b.orientation.y,
                                        b.orientation.z, b.orientation.w)
                                       for b in bones], dtype=np.float32),
                    "fingerCurls":  np.array(list(summary.flFingerCurl), dtype=np.float32),
                    "fingerSplays": np.array(list(summary.flFingerSplay), dtype=np.float32),
                }

            with self._lock:
                self.latest = snap

            # rate 유지
            dt = time.perf_counter() - t0
            if dt < self._dt: time.sleep(self._dt - dt)

    def snapshot(self):
        with self._lock:
            return dict(self.latest)  # shallow copy; numpy는 공유
```

`_mat_to_pq`는 34 매트릭스에서 pos(3)+quat(4)를 추출하는 유틸 (문서 27의 `extract_pose` 참조).

### 4.2 구성 B — 별도 프로세스 + ZMQ/UDP (선택)

Python GIL 혹은 충돌 분리를 원할 때. `vr_bridge.py`가 120Hz로 ZMQ PUB를 내보내고, Isaac Lab이 SUB로 읽는다. localhost loopback 지연은 0.1-0.3 ms이므로 A와 거의 구분 안 됨. 구현/디버깅 오버헤드를 고려하면 A 권장.

## 5. Isaac Lab 커스텀 DeviceBase 구현

### 5.1 클래스 설계

`isaaclab.devices.ManusVive`가 Manus 글러브 + Vive tracker 6개 조합을 `DeviceBase`로 래핑하는 정확한 전례다. 이를 참조해 다음 클래스를 만든다:

```
PicoUDCAPDevice(DeviceBase)
├── cfg: PicoUDCAPDeviceCfg
├── sampler: SteamVRSampler  (§4.1)
├── retargeter chain:
│   ├── PinkIKRetargeter       → 팔+허리 → 로봇 upper-body joint targets
│   ├── DexHandRetargeter(L)   → 좌손 5 fingertip pos → 로봇 손 joint targets
│   ├── DexHandRetargeter(R)   → 우손 동일
│   └── LowerBodyRetargeter    → waist+ankles → 하체 제어 (standing / RL policy)
└── advance() → dict["upper_body", "left_hand", "right_hand", "lower_body"]
```

### 5.2 손목 포즈 복원 (팔뚝 트래커 → 손목 6DoF)

UDCAP VR Glove는 위치 추적이 없으므로 SteamVR Skeletal의 wrist 본 위치는 **절대 위치가 아닌** Index 컨트롤러 에뮬레이션 기준 원점(손목 근처 임의 상수)이다. 로봇 팔 IK에 사용할 **월드 좌표계 손목 포즈**를 얻으려면 **forearm 트래커 포즈 + 팔꿈치-손목 오프셋**으로 합성한다.

```python
def forearm_to_wrist(T_forearm_world, forearm_to_wrist_offset=np.array([0.12, 0.0, 0.0])):
    """Forearm 트래커(팔꿈치-전완 중간에 부착) → 손목 6DoF 월드 포즈.
    offset은 팔뚝 트래커 로컬 +X 방향으로 손목까지 거리 (사용자 팔 길이에 따라 캘리브레이션)."""
    R = quat_to_rotmat(T_forearm_world["quat"])
    wrist_pos  = T_forearm_world["pos"] + R @ forearm_to_wrist_offset
    wrist_quat = T_forearm_world["quat"]   # 손목 회전은 글러브에서 나온 상대회전과 합성
    return {"pos": wrist_pos, "quat": wrist_quat}
```

캘리브레이션 시 사용자가 "손목을 forearm 트래커 중앙에" 자세를 취하게 한 후 실측. 평균 offset 0.10-0.15 m.

### 5.3 좌표계 변환: SteamVR (Y-up) → Isaac Lab (Z-up)

```python
def svr_to_isaaclab(pos, quat_wxyz):
    # SteamVR: +Y up, -Z forward  →  Isaac Lab(ROS REP-103): +Z up, +X forward
    # ROS_X = -SVR_Z, ROS_Y = -SVR_X, ROS_Z = SVR_Y
    sx, sy, sz = pos
    p = np.array([-sz, -sx, sy], dtype=np.float32)
    R_svr2il = np.array([[0,0,-1],[-1,0,0],[0,1,0]], dtype=np.float32)
    from scipy.spatial.transform import Rotation as R
    q = quat_wxyz; r_dev = R.from_quat([q[1],q[2],q[3],q[0]])
    r_frame = R.from_matrix(R_svr2il)
    r_out = r_frame * r_dev * r_frame.inv()
    return p, r_out.as_quat()  # (xyzw)
```

### 5.5 DeviceBase 스켈레톤

```python
# isaaclab_tasks/ust_260220/devices/pico_udcap_device.py
from dataclasses import dataclass, field
from isaaclab.devices import DeviceCfg, DeviceBase
import torch, numpy as np
from .vr_sampler import SteamVRSampler

@dataclass
class PicoUDCAPDeviceCfg(DeviceCfg):
    tracker_binding_json: str = "tracker_binding.json"
    actions_json:         str = "openvr_actions/actions.json"
    forearm_wrist_offset: tuple = (0.12, 0.0, 0.0)
    upper_ik_cfg: "PinkIKControllerCfg" = None
    left_hand_retarget_yaml:  str = "inspire_left_dexpilot.yml"
    right_hand_retarget_yaml: str = "inspire_right_dexpilot.yml"

class PicoUDCAPDevice(DeviceBase):
    def __init__(self, cfg: PicoUDCAPDeviceCfg):
        super().__init__()
        self.cfg = cfg
        # 바인딩 로드
        with open(cfg.tracker_binding_json) as f:
            self._bind = json.load(f)["trackers"]
        self._serial_map = {v["role"]: sn for sn, v in self._bind.items()}
        # 샘플러 (VR 프로세스 내부 스레드)
        self.sampler = SteamVRSampler(
            tracker_serials=self._serial_map,
            hand_action_handles={"left":"/actions/teleop/in/skeleton_left",
                                 "right":"/actions/teleop/in/skeleton_right"},
        )
        # 리타게터 연쇄 인스턴스 생성 (PinkIK, dex-retargeting)
        self._upper_ik = _build_pink_ik(cfg.upper_ik_cfg)
        self._lhand    = _build_dex(cfg.left_hand_retarget_yaml)
        self._rhand    = _build_dex(cfg.right_hand_retarget_yaml)
        self._zero()

    def reset(self):
        self._zero()

    def add_callback(self, key, func):  # 베이스 클래스 시그니처 충족
        pass

    def advance(self):
        snap = self.sampler.snapshot()

        # 1) 손목 포즈 복원
        wrist_L = forearm_to_wrist(snap["trackers"]["left_forearm"],
                                   np.asarray(self.cfg.forearm_wrist_offset))
        wrist_R = forearm_to_wrist(snap["trackers"]["right_forearm"],
                                   np.asarray(self.cfg.forearm_wrist_offset))

        # 2) SVR→Isaac 좌표계
        wrist_L_il = _apply_svr2il(wrist_L)
        wrist_R_il = _apply_svr2il(wrist_R)
        waist_il   = _apply_svr2il(snap["trackers"]["waist"])
        lank_il    = _apply_svr2il(snap["trackers"]["left_ankle"])
        rank_il    = _apply_svr2il(snap["trackers"]["right_ankle"])

        # 3) 상체 IK
        upper_q = self._upper_ik.solve(wrist_L_il, wrist_R_il,
                                       head=snap.get("hmd"))

        # 4) 손 리타게팅 (fingertips at wrist frame)
        tips_L = _extract_fingertips(snap["hands"]["left"]["bones"])
        tips_R = _extract_fingertips(snap["hands"]["right"]["bones"])
        hand_q_L = self._lhand.retarget(tips_L)
        hand_q_R = self._rhand.retarget(tips_R)

        # 5) 하체 커맨드 (RL policy 또는 standing; 여기서는 raw pose만 전달)
        lower_cmd = {"waist": waist_il, "left_ankle": lank_il, "right_ankle": rank_il}

        return {
            "upper_body": torch.from_numpy(upper_q).float(),
            "left_hand":  torch.from_numpy(hand_q_L).float(),
            "right_hand": torch.from_numpy(hand_q_R).float(),
            "lower_body": lower_cmd,
        }
```

## 8. 알려진 함정 / 팁

### 8.1 SteamVR/VD
- **`requireHmd: false`** (`steamvr.vrsettings`): HMD 없이 디버깅하고 싶을 때. VD는 HMD 에뮬레이션을 이미 제공하므로 평상시에는 불필요.
- **VD의 "Forward Trackers to SteamVR" 옵션이 기본 OFF** — 반드시 켜야 5 트래커 emuation 됨.
- **Pico OS 5.14+ 필수**: Enhanced Forearm은 5.14에서 추가됨. 5.13 이하에서는 waist+ankle 3개만 가능.
- **트래커 역할 자동 지정 실패** 잦음: SteamVR UI에서 "Identify" → 신체 부위 수동 지정. 프로그램적으로는 시리얼 매핑이 안정적.
- **Wi-Fi 간섭**: UDCAP 글러브 2.4GHz와 Pico Wi-Fi 채널이 겹치면 스트리밍/트래킹 양쪽이 불안정. Pico를 **5GHz 또는 6GHz** 단독 AP에 붙이고, 글러브 동글은 PC 뒷면이 아닌 **앞면 USB에 익스텐더로 책상 위**로 올리기.

### 8.2 UDCAP VR Glove
- UDCAP Driver SteamVR Add-on 순서 주의: **SteamVR 실행 전 UDCAP Driver를 먼저 기동**해야 Add-on이 정상 로드. Startup order는 UDCAP Driver 설정에서 "Auto-start with SteamVR" 켜는 것이 편함.
- Skeletal Input 2.0은 VRChat 용도로 최적화되어 "with controller" vs "without controller" 모드에서 뼈 위치가 다르다. **로봇 손 리타게팅은 `Without Controller` 모드**가 더 자연스럽다.
- UDCAP Driver가 Valve Index 컨트롤러를 에뮬레이션하므로, **SteamVR의 left/right controller 슬롯에 UDCAP가 들어간다**. 실제 Pico 컨트롤러가 연결되어 있으면 충돌 → **Pico 컨트롤러는 페어링 해제**.
- VMC Broadcast 포트 기본값 39539, 충돌 시 General Settings에서 변경.

### 8.3 Isaac Lab / Windows
- `Se3Keyboard`는 `omni.appwindow` GUI를 요구 → **headless 금지**. VR teleop 전용으로는 헤드리스 OK(키보드 fallback 없다면).
- Long Path 지원 반드시 켤 것 (경로 >260자 흔함).
- `pip install isaacsim[all]` 후 최초 실행 시 **수 GB 다운로드**가 일어남 → 충분한 디스크와 안정적 인터넷 필요.
- CUDA 12.8 PyTorch 2.7.0 이외 버전은 **Isaac Sim 5.x에서 crash** (CUDA 13 PyTorch 비호환 확인됨).
- Windows에서 pyopenvr + Isaac Sim이 같은 프로세스에서 OpenVR 세션을 공유하려 하면 충돌 가능 → **Isaac Sim은 `VRApplication_Other`로 초기화하는 우리 샘플러만 OpenVR에 붙고, Isaac Sim 자체는 OpenXR을 선택적으로 사용** (또는 전혀 안 씀).
- Isaac Lab `OpenXRDevice`를 굳이 쓸 필요 없다 — 본 가이드의 `PicoUDCAPDevice`가 더 직접적.

### 8.4 리타게팅
- **PinkIK URDF 요구사항**: 작업 대상 링크(손목)에 고유한 link 이름이 있어야 함. G1 Inspire-FTP URDF에는 이미 `left_wrist_yaw_link`, `right_wrist_yaw_link`가 있음.
- **dex-retargeting Inspire Hand YAML**: fingertip link 이름이 실제 손끝 말단에 위치해야 DexPilot 최적화가 안정. G1 Inspire FTP URDF는 이 요구를 만족.
- **캘리브레이션 없는 리타게팅은 거의 항상 실패**: 사용자 어깨/팔 길이와 로봇의 팔 길이 비율이 1:1이 아니므로, 최초 몇 초간 T-pose 유지 → 스케일 팩터 학습.

## 10. 미해결 이슈 / 추가 조사 필요

1. **UDCAP Driver의 VMC Broadcast 실제 송신 본 수**: VR Glove는 손 본만 송신하는지 / 몸 전체 humanoid bones를 송신하는지 공식 문서 불명. 실장 후 확인 필요.
2. **SteamVR Skeletal Input 2.0의 실시간 수신 주기**: VRChat 런타임은 90 Hz 이지만 `updateActionState` 호출 측은 Python에서 얼마나 자주 호출해야 최신 프레임을 놓치지 않는지 경험적 측정 필요 (120-144 Hz 권장).
3. **Isaac Sim 5.x + SteamVR 동일 PC에서 GPU 점유 경합**: 렌더러 두 개(SteamVR compositor + Isaac Sim RTX)가 동일 GPU를 쓰므로 프레임 타임 스파이크 가능. RTX PRO 6000 96GB면 메모리는 문제 없으나, async render 설정 튜닝 필요.
4. **Isaac Lab 3.0-beta Windows 빌드 출시 시점**: 본 가이드는 2.3.x 기준으로 작성. 3.0가 Windows pip wheel을 정식 제공하면 재검증 필요.

## 부록 A — VR 시각 피드백(Isaac Lab 뷰포트를 VR HMD에서 볼 수 있는가?) 심층 분석

### A.1 질문 정리

"SteamVR(OpenVR + OpenXR 런타임)에 Pico 4 Ultra가 연결된 상태에서, Isaac Lab/Isaac Sim의 시뮬레이션 뷰포트를 **스테레오 렌더링하여 VR HMD 안에서 볼 수 있는가?**"

- **입력 방향(트래커/글러브 → Isaac Lab)** 은 pyopenvr만으로 완전히 해결됨 (§4–5).
- **출력 방향(Isaac Lab 뷰포트 → HMD 디스플레이)** 은 별도의 "XR 렌더러/컴포지터"가 필요하며, 이는 현재 Isaac Sim 5.x의 정책 변화가 직접 영향을 준다.

결론을 먼저 말하면: **"가능하지만 2025-2026 현재로서는 최상의 경로는 CloudXR이며, 순수 SteamVR 네이티브 경로는 Isaac Sim 5.0에서 공식 UI가 빠진 상태이고 회귀 버그가 존재**한다. 완전한 네이티브 스테레오 렌더링을 원한다면 (1) CloudXR을 쓰거나 (2) Isaac Sim 4.5 기반으로 `omni.kit.xr.profile.vr` 우회 실행, (3) 비(非) 스테레오 모니터 뷰를 SteamVR 데스크탑 오버레이로 띄우는 타협안을 선택해야 한다.

### A.2 Isaac Sim의 XR 렌더 파이프라인 기초

Isaac Sim은 Omniverse Kit의 `omni.kit.xr.core` 확장을 통해 XR을 지원한다. 이 코어는 **플러그인 기반으로 런타임을 교체**한다:

| 플러그인 | 지원 런타임 | Isaac Sim 4.x 상태 | Isaac Sim 5.0+ 상태 |
|---------|------------|-------------------|---------------------|
| `omni.kit.xr.system.steamvr` | OpenVR/SteamVR 직결 | ✅ 기본 선택 가능 | ⚠️ **VR 탭 드롭다운에서 제거됨** (IsaacSim#33) |
| `omni.kit.xr.system.openxr` | 시스템 활성 OpenXR 런타임 | ✅ | ✅ (Quest 2/3 테스트됨) |
| `omni.kit.xr.system.cloudxr` | NVIDIA CloudXR | ✅ | ✅ **Isaac Lab 공식 기본** |

Kit 106.4 → 106.5 전환(Isaac Sim 4.5 → 5.0 구간) 시 **기본 VR 시스템이 SteamVR → CloudXR로 변경**되었다. NVIDIA 개발자 포럼은 이를 "deprecation"이라고 명시적으로 밝히지는 않았지만, UI 드롭다운에서 SteamVR 옵션이 **제거**되었고, 정식 Isaac Lab teleoperation 문서는 **CloudXR만** 언급한다.

뷰포트를 VR로 보내는 실제 메커니즘은 동일하다: `XRCore`가 씬을 양 눈용으로 2회 렌더하고 컴포지터가 둘을 OpenVR/OpenXR 스왑체인에 제출한다. 그러나 **어떤 시스템 플러그인이 스왑체인을 받을 자격이 있는가**가 버전에 따라 달라진다.

### A.3 경로별 가능성 분석

#### Path-1 — CloudXR (공식/권장, Isaac Lab 2.3+/3.0)
```
Isaac Lab @ Windows 11
   │ stereo render
   ▼
CloudXR Runtime (Docker 권장, Windows에서는 WSL2 or 별 머신)
   │ WebRTC (H.265/AV1 encode)
   ▼
Pico 4 Ultra — CloudXR.js (Quest Browser) 또는 CloudXR APK
```
- 현재 Isaac Lab의 **공식 단일 지원 경로**.
- Pico 4 Ultra, Quest 3가 Early Access로 공식 지원.
- 장점: 최신 Isaac Lab 버전과 동기, Isaac Lab AR 앵커(`XrCfg`) 기능 사용 가능, HMD 트래킹이 Isaac Lab 내부로 들어옴 → Pick-Place-GR1T2 같은 공식 예제 곧바로 동작.
- 단점: **CloudXR Runtime은 Linux 컨테이너**가 주 배포 형태. Windows 11 단일 PC 환경에서는 WSL2 + Docker Desktop을 추가로 돌려야 한다. 본 프로젝트의 ust_260207에서 CloudXR 6.0.1-webrtc 이미지를 이미 사용 중이므로 재활용 가능.
- 현실 이슈: **SteamVR과 동시 실행은 설계상 요구되지 않음**. CloudXR은 독자 런타임이고, Pico 트래킹 데이터는 CloudXR 앱 내부에서 OpenXR hand tracking으로 들어오지 Virtual Desktop을 거치지 않는다. → **본 가이드의 "SteamVR + VD + 트래커" 입력 경로와 상충**.

#### Path-2 — SteamVR Native (Isaac Sim 4.5까지는 가능, 5.0에서 회귀)
```
Isaac Lab (Sim 4.5) @ Windows 11
   │ stereo render via omni.kit.xr.profile.vr + omni.kit.xr.system.steamvr
   ▼
SteamVR Compositor
   ▼
Virtual Desktop Streamer → Pico 4 Ultra
```
- Isaac Sim 4.2까지는 SteamVR 스트리밍이 정상 동작했다는 보고. 4.5에서 **standalone python 스크립트에서 화면이 검게** 나오는 회귀 발생(포럼 327719). GUI에서 직접 Isaac Sim을 실행하면 동작하나 standalone은 깨짐.
- Isaac Sim 5.0에서는 VR 탭에 **SteamVR 항목 자체가 누락**(IsaacSim#33). `omni.kit.xr.system.steamvr` 확장은 설치되어 있으나 UI에서 선택 불가 → 스크립트로 `xr_core.request_enable_profile("vr")` 강제 호출 후 시스템을 수동 선택해야 하는 실험적 경로.
- **본 프로젝트 용도에는 큰 이점**: SteamVR 내에서 입력(트래커/글러브)도 이미 받고 있으므로, 같은 SteamVR 세션이 출력까지 담당하면 파이프라인이 가장 짧다.
- **리스크**: Isaac Sim 5.x로 올라가면 SteamVR 렌더링 회귀가 재현될 가능성이 크다. Isaac Sim 4.5 고정 사용은 CUDA/Py 스택 비호환으로 이어질 수 있음.

#### Path-3 — System OpenXR via Virtual Desktop's VDXR (실험적)
```
Isaac Lab @ Windows 11
   │ omni.kit.xr.system.openxr → VDXR runtime (Virtual Desktop 고유 OpenXR)
   ▼
VD Streamer → Pico 4 Ultra
```
- Virtual Desktop은 자체 OpenXR 런타임(**VDXR**)을 제공하여 SteamVR을 거치지 않고 OpenXR 앱을 스트리밍. Options → "Use Virtual Desktop OpenXR runtime" 체크.
- Windows의 활성 OpenXR 런타임을 VDXR로 설정하면 Isaac Sim의 `omni.kit.xr.system.openxr`가 이를 대상으로 제출할 수 있다 (이론상).
- **치명적 문제**: VDXR를 활성 런타임으로 바꾸면 **SteamVR이 비활성**화되므로, SteamVR에 의존하는 **Vive Tracker 에뮬레이션(5 트래커)과 UDCAP Skeletal Input 경로가 모두 끊긴다**. VDXR은 OpenXR 표준 hand tracking만 제공하며 Vive Tracker 에뮬레이션 API가 없다.
- 즉 Path-3은 **입력 경로를 포기해야** 성립하므로, 본 프로젝트에서는 **채택 불가**.

#### Path-4 — 타협안: SteamVR Desktop Theater / 오버레이로 모노 뷰포트만
```
Isaac Lab → Windows 데스크탑 창 (모노, 일반 뷰포트)
   │
   ▼
SteamVR Desktop 기능 또는 Desktop+ 오버레이 또는 OVR Toolkit
   │ (SteamVR 환경 내 2D 화면으로 배치)
   ▼
Virtual Desktop → Pico 4 Ultra
```
- 스테레오 몰입 렌더링은 포기하고, Isaac Sim 윈도를 **VR 공간 안의 2D 스크린**으로 띄운다.
- **Desktop+** (Steam store, 무료), **OVR Toolkit**(유료), **OpenVRDesktopDisplayPortal**(OSS) 등 여러 도구가 임의 윈도를 SteamVR 오버레이로 부착.
- Virtual Desktop의 "데스크탑 모드"는 이미 전체 모니터를 VR에서 띄워주므로 추가 도구 없이도 작동.
- **단점**: 깊이감/몰입감 없음. 로봇 팔의 깊이/거리 판단이 필요한 dexterous 조작에는 불충분.
- **장점**: 구현 난이도 0. SteamVR 세션은 입력 전용으로 그대로 유지되고, 출력은 Virtual Desktop의 데스크탑 미러링이 알아서 처리. 본 프로젝트에서 **Week 1-2 초기 검증용**으로 즉시 사용 가능.

#### Path-5 — Dual Runtime (하이브리드, 복잡)
```
Isaac Lab @ Windows 11
  ├─ 입력: pyopenvr → SteamVR (VD + 트래커 + UDCAP Skeletal)
  └─ 출력: omni.kit.xr.system.cloudxr → CloudXR Runtime → Pico 4 Ultra CloudXR 앱
```
- **입력은 SteamVR, 출력은 CloudXR**로 분리. 같은 PC 위에서 두 VR 스택이 동시 실행.
- Pico 헤드셋은 "Virtual Desktop 앱" 또는 "CloudXR 앱" 둘 중 하나만 실행 가능 → **한 세션에서 둘을 동시에 받을 수 없다**.
- 해결책: Pico 헤드셋은 CloudXR 앱만 실행하여 스테레오 수신. 트래커는 **CloudXR이 자체 OpenXR body tracking / hand tracking 으로 수신**하고, UDCAP 글러브는 별도 2.4GHz USB 동글로 PC에 직결되므로 SteamVR 없이도 UDCAP Driver가 독립 동작할 수 있음.
- 단, 이 경우 **"5 Pico Motion Tracker의 Vive Tracker 에뮬레이션"** 은 Virtual Desktop의 기능이므로 **쓸 수 없게 된다**. CloudXR 앱이 5 트래커를 OpenXR 확장으로 읽어오는지는 별도 확인 필요 (CloudXR 6.0.1-webrtc + Pico 4 Ultra 조합에서 OpenXR `XR_FB_body_tracking` 또는 Pico 고유 body tracking 확장 지원 여부).
- **실현성: 중간**. CloudXR이 Pico 5 tracker 데이터를 Isaac Lab으로 올려준다는 공식 문서는 아직 약하다 (Early Access 단계).

### A.5 본 프로젝트 권장 전략 (단계적)

#### 단계 1 (즉시, Week 1-2) — **Path-4 Desktop Theater**
- Virtual Desktop "데스크탑 모드"로 Isaac Sim 모니터 창을 VR 내에서 확인.
- 입력 경로(VD + 5 트래커 + UDCAP Skeletal)를 먼저 완전히 검증. 시각 피드백은 2D로도 초기 개발에 충분.
- 지연/동기화/좌표 변환을 가장 적은 변수로 확립.

#### 단계 2 (Week 3-4, 선택) — **Path-2 실험적 적용**
- Isaac Sim 4.5 기반으로 `omni.kit.xr.system.steamvr` 활성화 시도.
- standalone 스크립트의 블랙 스크린 이슈가 있으면 Isaac Sim 셀렉터 UI 경로로 실행.
- 동작 시 스테레오 몰입 렌더 확보. 단, Isaac Sim 5.x 업그레이드 시점에 재평가 필요.

#### 단계 3 (중장기) — **Path-1 CloudXR 이관**
- 프로젝트가 성숙하고 Isaac Lab 3.0 Windows 정식 지원이 나오면 CloudXR 경로로 이동.
- 이때 **입력 경로를 재설계**해야 한다: (a) Pico 5 트래커를 CloudXR OpenXR body tracking으로 수신, (b) UDCAP 글러브는 SteamVR 불필요한 별도 OSC/VMC 경로(§2.4)로 전환.
- Isaac Lab 공식 GR1T2/G1 teleop 파이프라인과 100% 호환되는 최종 상태.

### A.6 실무적 결론

- **"SteamVR로 연결만 되면 HMD 안에서 Isaac Lab 뷰포트가 자동으로 보이는가?"** → **자동으로 보이지는 않는다.** Isaac Sim 내부에서 "VR profile 활성화 + SteamVR 시스템 플러그인 선택 + Start VR" 세 단계가 필요하며, 5.0에서 UI가 빠져 있어 스크립트 우회가 필요하다.
- 본 프로젝트의 **실전 첫 시연**은 Virtual Desktop의 데스크탑 모드로 모니터 뷰를 VR 공간에 띄우는 방식(Path-4)으로 시작하는 것이 **시간 대비 효과 최대**다. 이 상태에서 데이터 수집/리타게팅/IK 튜닝을 전부 끝낼 수 있다.
- 스테레오 몰입 렌더가 **정말로 필요**해지는 시점(예: dexterous pick-place 정밀 작업)이 오면, 그때 Path-2 (Isaac Sim 4.5 SteamVR 실험) 또는 Path-1 (CloudXR 이관)을 별도 서브 프로젝트로 추진한다.
- 본 가이드의 §3-5 코드와 아키텍처는 **입력 경로만 책임**지며, 시각 피드백 경로는 별개 레이어이므로 위 전략 중 어느 것을 골라도 입력 코드 변경이 거의 필요 없다는 점이 설계상 장점이다.
