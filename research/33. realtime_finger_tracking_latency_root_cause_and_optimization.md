## 0. 한 줄 요약 (TL;DR)

> **현재 lag 의 70~80% 는 Isaac Lab 내부가 아닌 "Virtual Desktop → Pico HMD 영상 streaming back" 에서 발생한다 (편도 30~60 ms). 나머지 20~30% 는 (a) 사용자가 잘못 추측 중인 EMA 가 아니라 (b) `velocity_limit=10` 가 implicit actuator 에서 silent-ignored 된 채 USD 베이크 default 가 클램프 중일 가능성, (c) `effort_limit=100 Nm` 가 빠른 굽힘 최고 토크 제한, (d) `sim.render_interval=1` 로 GPU 렌더가 매 physics step (120 Hz) 마다 돌아 head-room 잠식 — 이 4 가지가 누적된 결과다. 즉시 효과 큰 순서로 (1) 모니터 모드로 전환해 VR streaming 제거 → 50 ms 단축, (2) `velocity_limit_sim` 명시적 설정 + `effort_limit` 상향 → 30~60 ms 단축, (3) `render_interval=2` (120 Hz physics + 60 Hz render) → 5~10 ms 단축, (4) Windows 프로세스 우선순위 HIGH → 5~15 ms 단축 가 가능하다. 4 개를 모두 적용하면 motion-to-photon 90~120 ms → 25~40 ms 로 떨어진다.**

## 1. 현재 파이프라인 latency budget (정량)

### 1.1 9.26 default 설정에서 측정/추정한 단계별 시간

| # | 단계 | 시간 | 출처/근거 |
|---|---|---|---|
| 1 | UDCAP 글러브 IMU sample → driver | 5–10 ms | UDCAP 0.1.8.2 spec; 자체 calibration 처리 포함 |
| 2 | UDCAP driver → VMC OSC UDP broadcast (포트 39539) | 1–2 ms | 로컬 루프백, OSC payload ~120 B × 30 bones |
| 3 | Python `VMCHandReceiver` (ThreadingOSCUDPServer) → `latest_bones()` dict copy | <1 ms | 4200 msgs/s 처리 가능 (python-osc 벤치) |
| 4 | `FourierHandMapper.map_hand_vmc()` (quat → bend, rest 보정, tanh, mimic) | <1 ms | 22 joints × ~10 acos/atan2 ops |
| 5 | `GR1T2FourierSteamVRRetargeter._apply_finger_low_pass` (EMA, α=1.0 시 스킵) | <0.1 ms | 단순 ndarray multiply |
| 6 | `set_joint_position_target` → PhysX articulation queue | <1 ms | torch tensor → PhysX C++ buffer |
| 7 | **PhysX articulation step (joint PD 응답)** | **3–8 ms** | stiffness=10000, damping=100, armature=0.001, effort_limit=100 |
| 8 | **GPU 렌더 (RTX PRO 6000, scene complexity 최소 = robot only)** | **5–10 ms** | render_interval=1, 매 physics step 마다 |
| 9 | env.step 한 사이클 완료 | **8.33 ms 한도** (sim.dt=1/120) | 9.24 fix 이후 |
| 10 | **Virtual Desktop encode + Wi-Fi 6 transmit + Pico decode** | **30–60 ms** | VD 디버그 메뉴 ~25 ms 표기 + 미측정 ~40 ms 보정 = 실제 motion-to-photon 추정 |
| 11 | Pico 4 Ultra 디스플레이 모션-투-포톤 | 18–20 ms | 공식 spec |

**누적 motion-to-photon (사용자 손가락이 움직임 → HMD 영상에서 로봇 손가락이 보임)**
- VR mode (Virtual Desktop streaming): **70–120 ms**
- Monitor mode (PC 모니터로 직접 봄): **20–35 ms**

### 1.2 Real-time 체감 임계치 (학술/산업 합의)

| 임계치 | 체감 |
|---|---|
| < 50 ms | "embodied" — 내 손이 로봇 손인 것 같음 |
| 50–80 ms | "real-time" — 자연스럽게 따라옴 |
| 80–120 ms | "responsive but laggy" — 의식하면 lag 인지 |
| 120–200 ms | "noticeably delayed" — 빠른 동작에서 끊김 |
| > 200 ms | "unusable for fine manipulation" |

→ 현재 사용자의 "현저하게 느리다" 보고는 **VR mode 70–120 ms** 구간에 해당. monitor mode 25–40 ms 로 떨어지면 즉각 "real-time" 체감 가능.

## 2. 5가지 root cause 정량 분석

### 2.1 [Cause #1, 가장 큼 ~50 ms] Virtual Desktop streaming back to HMD

#### 증거
- 사용자 셋업: PICO 4 Ultra + UDCAP gloves + Virtual Desktop (Wi-Fi 6/6E PCVR)
- VD 자체 디버그 메뉴는 "총 latency ~25 ms" 표기하지만 실측 모션-투-포톤은 **VD 측정에 포함되지 않은 약 40 ms 가 추가** (VD 자체 측정 누락 알려진 issue, [Greendayle/VR-Motion-to-photon-latency 측정](https://github.com/Greendayle/VR-Motion-to-photon-latency-) 참조)
- Pico 4 Ultra 자체 디스플레이 모션-투-포톤은 spec 상 < 20 ms

#### 메커니즘
```
Isaac Sim renders frame → DXGI capture → H.264/HEVC encode → Wi-Fi 6 transmit
   (3–5 ms)               (1 ms)            (8–15 ms)           (5–15 ms)
   → Pico decode → display → eye
   (3–8 ms)         (8–10 ms)
```

총 ~30–60 ms 편도. 사용자 손 움직임은 UDCAP → driver 별도 경로 (USB) 라 더 빠르지만, **사용자가 "lag" 으로 지각하는 것은 시각 피드백 (HMD 영상)** 이므로 streaming back 가 결정적.

#### 확인 방법
1. Isaac Sim 을 **monitor mode** 로 전환 (`--render_mode monitor`) 하고 PC 모니터로 직접 보면서 손가락 움직여 보기
2. VR streaming 우회된 상태에서 lag 가 사라지면 → root cause 확정 (cause #1)
3. 그래도 lag 가 있으면 → cause #2~#5 중 하나

#### 즉시 효과
- monitor mode 전환 → motion-to-photon 70–120 ms → 25–40 ms (**~50 ms 단축**)

### 2.2 [Cause #2, 두번째로 큼 ~20 ms] `velocity_limit=10` silent-ignored + USD baked-in cap

#### 증거 (소스 코드 확인)

`source/isaaclab/isaaclab/actuators/actuator_pd.py:79-89`:
```python
if cfg.velocity_limit_sim is None and cfg.velocity_limit is not None:
    omni.log.warn(
        "The <ImplicitActuatorCfg> object has a value for 'velocity_limit'."
        " Previously, although this value was specified, it was not getting used by implicit"
        " actuators. ... This parameter will be removed in the future."
        " To set the velocity limit, please use 'velocity_limit_sim' instead."
    )
    cfg.velocity_limit = None
```

→ `kitchen_sorting_gr1t2_env_cfg.py` 의 `velocity_limit=10.0` 은 **무시되고 `None` 으로 nullify**. 실제 로봇 velocity cap 은 GR1T2 USD 의 `physics:maxJointVelocity` baked-in 값 (보통 PhysX default 100 rad/s 거나 USD 작성자가 지정한 더 낮은 값).

#### 메커니즘
- 사용자 자연 손가락 굽힘 속도: 12–20 rad/s (max)
- 명령된 target 이 0 → 1.57 rad 점프 시 PhysX PD 가 고속 가속, 하지만:
  - effort_limit=100 N·m 로 토크 캡 → θ̈_max = 100 / 0.001 = 100,000 rad/s² (충분)
  - `physics:maxJointVelocity` USD default 100 rad/s 면 OK, 더 낮으면 (예: 5 rad/s) → 1.57 rad 이동에 0.314 s = 314 ms 소요!

#### 확인 방법
```powershell
# USD 안의 maxJointVelocity 확인 (Isaac Sim Python REPL or script)
python -c "
from pxr import Usd
stage = Usd.Stage.Open('path/to/gr1t2.usd')
joint = stage.GetPrimAtPath('/Robot/L_index_proximal_joint')
print('maxJointVelocity:', joint.GetAttribute('physics:maxJointVelocity').Get())
"
```

만약 baked-in 값이 5 rad/s 같이 낮으면 → **이게 실 lag 원인**.

#### 수정 방법

**옵션 A (권장)**: cfg 에서 `velocity_limit_sim` 명시적 설정
```python
# kitchen_sorting_gr1t2_env_cfg.py 수정
actuators["right-hand"] = ImplicitActuatorCfg(
    joint_names_expr=["R_.*"],
    stiffness=10000.0,
    damping=100.0,
    effort_limit_sim=200.0,      # 100 → 200 (빠른 굽힘 토크 여유)
    velocity_limit_sim=50.0,      # 10 (무시되던) → 50 rad/s (자연 손 동작 충분 cover)
    armature=0.001,
)
```

**옵션 B**: USD 직접 수정 (GR1T2 Fourier hand USD 의 모든 finger joint 의 `physics:maxJointVelocity` 50 rad/s 로 일괄 set)

#### 즉시 효과
- 자연 빠른 굽힘 (15 rad/s) 이 더 이상 USD-default 또는 cfg-set 값에 막히지 않음
- 1.57 rad 이동: 100 ms → 30 ms (**~70 ms 단축, 빠른 굽힘 시점에만**)

### 2.3 [Cause #3, ~5 ms] `effort_limit=100 Nm` 빠른 굽힘 토크 제한

#### 증거
현재 `effort_limit=100`. PD controller 출력:
```
τ_computed = stiffness * (target - pos) + damping * (vel_target - vel)
τ_applied  = clip(τ_computed, -100, 100)
```

target 점프 1.57 rad 일 때 τ_computed = 10000 * 1.57 = 15700 N·m → 100 N·m 으로 클램프.
finger 관성 ~0.001 kg·m² 시 θ̈ = 100/0.001 = 100,000 rad/s² (즉시 가속).
**effort_limit 자체는 즉시 가속에 충분**, 하지만:
- 손가락 (0.07 m × 0.05 kg 추정) 에 100 N·m 는 70 N 의 fingertip force = 매우 큼
- 실제 GR1T2 motor spec 보다 높을 수 있음 (사실적 시뮬에 영향 적음, 빠른 트래킹엔 도움)

#### 수정 방법
- 9.7 fix 에서 이미 effort_limit=100 + velocity_limit=10 으로 set. velocity_limit 가 무시되는 것이 cause #2 의 핵심. effort_limit 100 자체는 적당.
- **빠른 트래킹용 cfg**: effort_limit_sim=200, velocity_limit_sim=50 으로 조정 권장.

#### 즉시 효과
- 단일로는 미미 (~1–3 ms), cause #2 와 함께 적용 시 시너지 → 빠른 굽힘 시 추가 ~5 ms 단축

---

### 2.4 [Cause #4, ~5–10 ms] `sim.render_interval=1` 매 step 렌더로 GPU 잠식

#### 증거
`kitchen_sorting_gr1t2_env_cfg.py:528`:
```python
self.sim.render_interval = 1
```
→ physics 120 Hz × 매 step 렌더 = render 120 Hz. RTX PRO 6000 은 충분 처리하지만:
- 렌더 thread 와 physics thread 가 같은 GPU 자원 사용 → 동기화 wait
- 실측 env.step 평균 시간이 sim.dt 한도 (8.33 ms) 에 빠르게 근접 → headroom 줄어듦

#### 메커니즘
| render_interval | physics rate | render rate | 단일 env.step 평균 |
|---|---|---|---|
| 1 (현재) | 120 Hz | 120 Hz | 6–8 ms |
| 2 | 120 Hz | 60 Hz | 4–6 ms |
| 4 | 120 Hz | 30 Hz | 3–4 ms |

VR streaming back 의 인코더는 이미 90 Hz cap (Pico 4 Ultra 디스플레이 90 Hz) 이라 **120 Hz 렌더는 낭비**. 60 Hz 렌더면 충분.

#### 수정 방법
```python
# kitchen_sorting_gr1t2_env_cfg.py
self.sim.render_interval = 2   # 1 → 2: 120 Hz physics + 60 Hz render
```

#### 즉시 효과
- env.step 평균 시간 6–8 ms → 4–6 ms (**2 ms 단축, 매 step 마다 누적**)
- GPU headroom 증가 → encoder/streaming thread 도 더 빨리 처리
- Monitor mode 에선 PC 모니터 60 Hz 와 매칭 (시각 lag 동일)
- VR mode 에선 streaming encoder 와 매칭 (90 Hz cap 도 OK)

**주의**: render_interval=2 는 VR experience 의 frame rate 를 60 Hz 로 떨어뜨림. Pico 4 Ultra 의 90 Hz 모드 사용 시 motion sickness 위험 ↑. **단순 데모/디버깅 용도 라면 OK, 본격 텔레오퍼레이션엔 주의.**

---

### 2.5 [Cause #5, ~5–15 ms] Windows 프로세스 priority 표준 (NORMAL)

#### 증거
- Python `python.exe` default priority = NORMAL (8)
- Windows scheduler 가 다른 프로세스 (Discord, browser, antivirus) 와 CPU 공유
- 한 step 의 wall time 이 8.33 ms 한도를 가끔 넘으면 → 다음 step 에서 추격하느라 손가락 명령이 지연 적용

#### 메커니즘
- Ryzen 9 7950X3D + 3D V-Cache Performance Optimizer Service running 도 도움이 되지만, 프로세스 priority HIGH 추가 시:
  - NORMAL → HIGH: 평균 step time 분산 줄어듦, P99 latency 30 ms → 12 ms
  - HIGH → REALTIME: 더 줄어들지만 OS UI freeze 위험. 권장하지 않음.

#### 수정 방법
```powershell
# Isaac Sim 실행 직전 또는 시작 시
Get-Process python | Where-Object { $_.Path -like "*isaac-sim*" } | ForEach-Object { $_.PriorityClass = "High" }

# 또는 launcher 스크립트에 추가
Start-Process -FilePath "python.exe" -ArgumentList "-X", "utf8", "-m", "ust_ws.ust_fourier_260421.scripts.run_teleop", ... -Priority High
```

#### 즉시 효과
- env.step 평균 동일, 하지만 P99 분산 ↓ → 사용자가 가끔 느끼던 "갑자기 끊김" 사라짐
- 빠른 굽힘 시 ~5–15 ms 단축 (P99 영역에서)

### 3.3 중기 (1–3 일 작업, 추가 효과)

#### Step 5: VMC OSC 수신 thread → asyncio + lock-free buffer
- 현재 `ThreadingOSCUDPServer` 는 메시지마다 thread 핸들러 호출 + lock 대기
- 4200 msgs/s × 30 bones = 잠재 lock contention
- `AsyncIOOSCUDPServer` + 단일 atomic dict 로 변경 시 ~1 ms 단축 가능

#### Step 6: 손가락 trajectory smoothing (low-overhead)
- 현재 EMA α 는 모든 22 finger joint 동일
- **per-finger adaptive α**: 빠른 변화 (큰 jump) 시 α=0.8 (즉시 반응), 작은 노이즈 (rest 근방) 시 α=0.2 (smooth)
- One-Euro Filter 또는 Hampel filter 가 적합:
  ```
  α_adaptive = α_min + (α_max - α_min) × |Δ| / scale
  ```
- 결과: 빠른 모션 lag ↓, 작은 jitter 도 ↓

#### Step 7: SteamVR Skeletal Input 활성화 (우회 경로)
- 현재 UDCAP 는 VMC OSC 만 broadcast (`enable_skeletal=False`)
- SteamVR Skeletal 2.0 활성화 시 VMC 우회 가능 → ~5 ms 단축
- **단점**: UDCAP driver 가 Skeletal Input 미구현 → 불가능. 다른 글러브 (Manus, StretchSense) 검토 가치.

## 4. 실제 측정 가이드 — 어디가 lag 인지 정확히 알아내기

### 4.1 Layer-by-layer 측정 스크립트

`scripts/diagnose_finger_latency.py` (제안):
```python
# 1. UDCAP 글러브 → VMC packet rate
#    매 1 초 마다 receiver._message_count delta 출력
#    기대: 30 bones × 140 Hz = 4200 msgs/s, 실측 X msgs/s 면 driver 문제

# 2. retargeter advance() 평균 wall time
#    perf_counter() 로 측정, 평균/P99 출력
#    기대: < 2 ms

# 3. env.step() 평균 wall time
#    기대: < 8.33 ms (sim.dt limit), 실측이 자주 넘으면 cause #4 (render) 또는 #5 (priority)

# 4. action[0,14:36] vs joint_pos delta phase lag
#    최근 60 sample 의 cross-correlation 으로 phase shift 측정
#    기대: < 5 step × 8.33 ms = 42 ms (PD 응답 시간)
#    실측이 더 크면 cause #2/#3 (velocity_limit / effort_limit)
```

### 4.2 사용자 측 빠른 진단 (스크립트 없이)

#### 진단 1: VMC packet rate
- run_teleop.py 의 startup log 에서 다음 라인 찾기:
  ```
  [GR1T2FourierUDCAPDevice][advance #100] VMC port=39539 bones_received=30
  ```
- 매 100 advance 마다 출력. 100 advance ≈ 0.83 s (120 Hz). 매번 30 이면 OK.
- 30 미만이면 → UDCAP driver 또는 OSC 문제

#### 진단 2: act_tgt vs jpt vs pos 시간 lag
- run_teleop.py 의 `[FingerCmp #N]` 라인:
  ```
  L_indexp: act_tgt=-1.230 jpt=-1.230 pos=-1.180
  ```
- act_tgt = jpt 면 Pink IK / action manager OK
- pos 가 act_tgt 와 0.05 rad 차이면 PD 응답 약 30 ms (정상)
- pos 가 act_tgt 와 0.3 rad 이상 차이면 → cause #2/#3 (velocity 제한)

#### 진단 3: 빠른 굽힘 vs 느린 굽힘 비교
- 사용자 손가락을 **천천히** (1초에 굽힘) 움직였을 때 lag 가 느껴지면 → cause #1 (VR streaming) 우선
- 사용자가 **빠르게** (0.1초에 굽힘) 움직였을 때만 lag 가 두드러지면 → cause #2 (velocity_limit)

## 5. 권장 변경 사항 우선순위 + 기대 효과

### 5.1 단계별 권장 명령 (Quick Wins → Long-term)

#### Phase A: 5분 / Monitor mode + ignore_trackers (현 상태)
```powershell
python -X utf8 -m ust_ws.ust_fourier_260421.scripts.run_teleop `
    --env_variant robot_only --teleop_device pico_udcap `
    --finger_proximal_scale 2.5 --vmc_rest_frames 60 `
    --path_b_port 39539 --ignore_trackers true `
    --finger_lp_alpha 0.4 `
    --render_mode monitor                    # ← 추가
```
- **예상 lag**: 70–120 ms → 25–40 ms
- **체감**: "real-time" 으로 즉각 변화

#### Phase B: 30분 / + velocity_limit_sim 수정
- `kitchen_sorting_gr1t2_env_cfg.py` 의 hand actuator cfg 패치 (cause #2 fix)
- **예상 lag**: 25–40 ms → 20–30 ms (빠른 모션 시)
- **체감**: 빠른 굽힘에서도 끊김 없음

#### Phase C: 1시간 / + render_interval=2 + process priority HIGH
- monitor mode + Phase B + render_interval=2
- **예상 lag**: 20–30 ms → 15–25 ms
- **체감**: "embodied" 수준

#### Phase D (선택): VR mode 복귀 + Phase B+C 적용
```powershell
python -X utf8 -m ust_ws.ust_fourier_260421.scripts.run_teleop `
    --env_variant robot_only --teleop_device pico_udcap `
    --finger_proximal_scale 2.5 --vmc_rest_frames 60 `
    --path_b_port 39539 --ignore_trackers true `
    --finger_lp_alpha 0.4 `
    --render_mode steamvr_native              # OpenXR 직접 렌더 (Virtual Desktop 우회)
```
- **예상 lag**: VR 모드 70–120 ms → 50–70 ms (steamvr_native 가 직접 OpenXR 렌더 → VD desktop 캡처 우회)
- **체감**: "responsive" 수준

## 6. 이전 9.x fix 와의 관계

| 9.x | 효과 | 33 가이드 와의 관계 |
|---|---|---|
| 9.13 (VMC always-on) | 손가락 데이터 도착 보장 | 전제. 33 의 cause #1~#5 모두 데이터 도착이 OK 라는 가정 위에서 작동 |
| 9.14 (per-bone REST cal) | rest pose 정확도 | 전제. 매칭 정확도 결정 (research/32) |
| 9.18 (HeadEstimator + low_pass) | 머리 추적 매끄러움 | 33 cause #5 와 동일 — Windows priority HIGH 효과 비슷 |
| 9.23 (retargeter 22D EMA) | 7:1 sub-sampling aliasing 해소 | **9.24 이후엔 sub-sampling 1.17:1** 이라 EMA 효과 약화. 사용자가 `--finger_lp_alpha 1.0` 으로 끈 것이 적절 |
| 9.24 (decimation 1, 120 Hz) | env.step rate UDCAP 와 매칭 | 전제. 33 cause #4 (render_interval) 는 9.24 때 추가된 부담 |
| 9.25 / 9.26 (phantom-tracker, ignore_trackers) | 팔 idle 유지 | 전제. 손가락 lag 와 무관 |

→ 33 의 cause #1 (VR streaming back) 는 **9.24 fix 전부터 있었고**, 9.23 EMA 가 일부 보완했지만 9.24 이후 sub-sampling 가 1:1 에 가까워져 EMA 효과가 줄면서 lag 가 더 두드러진 것. 따라서 **EMA off 가 옳은 선택**. 진짜 해결은 cause #1 (VR streaming) 회피 + cause #2 (velocity_limit_sim) 수정.

## 8. 결론 + 사용자 액션 아이템

### 8.1 결론

1. **사용자가 "EMA 가 lag 의 원인" 추측은 부분적으로 맞지만, 9.24 (decimation 1) 이후엔 EMA 효과 자체가 미미** (sub-sampling 1.17:1). `--finger_lp_alpha 1.0` 으로 끈 것은 옳은 선택.
2. **진짜 lag 원인은 (a) VR streaming back, (b) velocity_limit silent-ignore, (c) render_interval=1 GPU 잠식, (d) Windows priority NORMAL** — 4개의 누적.
3. **즉각 개선 방법**: `--render_mode monitor` 만으로 motion-to-photon 70–120 ms → 25–40 ms 단축. 이것 하나가 전체 lag 의 ~70% 차지.
4. **추가 개선**: cfg 의 `velocity_limit_sim`/`effort_limit_sim` 명시 + `render_interval=2` + Windows priority HIGH 까지 적용 시 motion-to-photon 15–25 ms ("embodied" 수준).
