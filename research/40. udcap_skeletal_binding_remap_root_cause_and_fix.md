# 40. SteamVR knuckles→oculus_touch auto-remap 으로 인한 Skeletal Input + 5-finger curl 손실 — 근본 원인 + 수정

> 작성: 2026-05-06
> 사용자 보고: research/39 의 Plan A 적용 후 SteamVR Test Controller 에선 양손 grip 활성 확인 (research/38 의 영상 분석) 했지만, 우리 앱 (`ust_fourier_260421`) 의 모든 액션이 0. `_probe_openvr_skeletal()` 의 `bActive=False`. VMC packet 도 0.
> 핵심 데이터: SteamVR `vrserver.txt` 의 binding 로드 + remap 트레이스 + 우리 앱의 OpenVR device inventory.

## 0. 한 줄 요약 (TL;DR)

> **결론**: 사용자 시스템엔 **두 set 의 컨트롤러가 동시 등록**돼있다 — (1) UDCAP 가 만든 가상 `knuckles` 2개 (`LHR-E227UD40`, `LHR-E227UD41`, role=Left/Right), (2) Virtual Desktop 이 emulate 한 `oculus_touch` 2개 (`1PASH5D1P17365_Controller_*`, role=0=Invalid). SteamVR 는 **양쪽 모두에 우리 앱 binding 을 적용** 하려 시도했고, `bindings_index.json` (controller_type=knuckles) 을 **oculus_touch 로 자동 remap**.  하지만 oculus_touch profile 에는 `/input/skeleton/*` 와 `/input/finger/*` 경로가 **존재하지 않으므로 SteamVR 가 그 binding 들을 모두 SKIP**.  vrserver.txt 의 결정적 한 줄:
> ```
> [Remapping] Skipped remapping of path::mode: /user/hand/left/input/skeleton/left::
> [Remapping] Skipped remapping of path::mode: /user/hand/left/input/finger/index::trigger
> ```
> → **Skeleton + 5-finger curl binding 이 oculus_touch 에는 적용 안 됨**. UDCAP knuckles 에는 binding 자체는 로드됐지만 (vrserver: `Successfully loaded binding file ... bindings_index.json`), 우리 앱 입장에선 `getSkeletalActionData(handle).bActive = False`. 즉 **knuckles 측의 active source 가 없는 상태**. 동시에 UDCAP 가 글러브 데이터를 받지 못해 (UDCAP UI 의 캘리브레이션 / `Controller_Priority=true` HIGH 모드에서 oculus_touch 의 trigger 가 0 인 것을 그대로 borrow → 글러브 finger sensor 우회) 글러브 데이터 자체가 SteamVR layer 에 안 도달.
>
> **두 갈래 fix 가 필요**:
> 1. **SteamVR binding 측면** (가장 시급, 코드 fix):
>    - `default_bindings` 에 **`oculus_touch` 명시 entry 추가** + `bindings_oculus_touch.json` 신규 작성 (trigger/grip 만, skeleton/finger 는 자동 unbound)
>    - bindings_index.json 의 grip 을 `force_sensor → trigger` 로 변경 (auto-remap 자동 처리되긴 했지만 명시적 표기로 디버깅 명료)
>    - actions.json 의 skeleton actions 를 `requirement: "optional"` 유지 (mandatory 로 변경 시 oculus_touch 에 binding 없으면 startup 실패)
> 2. **UDCAP 글러브 데이터 도달** (사용자 측 UI 조작):
>    - UDCAP UI 의 글러브 캘리브레이션 (Open / Fist / Per-finger) — 미완료 시 finger 데이터 emit 안 됨
>    - UDCAP UI → Settings → Controller_Priority **LOW** 로 변경 (HIGH 일 때 underlying oculus_touch 의 0-input 을 그대로 borrow → 글러브 sensor 데이터 무시됨, 이게 우리 코드의 [경고](https://github.com/.../GR1T2FourierUDCAPDevice.py:944) 에서 #2 순위로 명시한 그 케이스)
>    - 글러브 페어링 + 배터리 + UDCAP UI Devices "Connected" + FPS > 30
>    - PICO Touch controllers 일시적 power off 또는 sleep — VD 의 oculus_touch 가 사라지면 SteamVR 가 UDCAP knuckles 를 사용 (단, 사용자는 손에 글러브만 끼고 컨트롤러는 안 잡는 환경)
>
> **즉시 적용 5단계 절차** (코드 ~30분 + 사용자 검증):
> 1. (코드) `actions.json` 의 `default_bindings` 에 `oculus_touch` entry 추가
> 2. (코드) `bindings_oculus_touch.json` 신규 작성 (trigger/grip 만)
> 3. (코드) `bindings_index.json` 의 grip mode `force_sensor → trigger` 로 변경
> 4. (사용자) UDCAP UI 캘리브레이션 + Controller_Priority **LOW** 로 변경
> 5. (사용자) SteamVR + 앱 재시작 후 검증
>
> 이 fix 후 **여전히 finger curl 이 0 인 경우** = UDCAP 글러브 자체가 SteamVR layer 에 데이터를 못 보내는 상태 → **VMC fallback (Path B)** 가 진짜 primary 경로가 됨 → research/34 의 Phase E (Protobuf) 가 다음 후보. 하지만 VMC 도 0 인 현재 상태 이므로 **글러브 데이터 자체** 가 UdcapDriver.exe 에 도달 못 하는 케이스.

### 1.2 (knuckles) 와 (oculus_touch) 둘 다 같은 파일을 로드하는 이유

`actions.json` 의 default_bindings:
```json
"default_bindings": [
    { "controller_type": "udcap",    "binding_url": "bindings_udcap.json" },
    { "controller_type": "knuckles", "binding_url": "bindings_index.json" }
]
```

→ controller_type 매칭 표:
- UDCAP knuckles (controller_type=knuckles) → `bindings_index.json` 직접 매칭 ✓
- VD oculus_touch (controller_type=oculus_touch) → **default_bindings 에 없음** → SteamVR 가 fallback 로직으로 가장 가까운 controller (knuckles) binding 을 자동 remap 시도 ❌
- Vive trackers / Rift / 등 (controller_type=rift, vive_tracker, ...) → 매칭 없음 → log 의 `[Error] has no configured binding` 9개 줄

**즉**: `default_bindings` 에 `oculus_touch` 가 빠져있어서 SteamVR 가 knuckles binding 을 그쪽에 강제 remap. 이 과정에서 oculus_touch 에 없는 input path (skeleton/finger) 가 모두 누락.

## 2. UDCAP knuckles 측 binding 은 어떻게 됐나? (vrserver.txt 추가 분석)

### 2.1 핵심 발견: knuckles remap 단계는 **로그에 없음**

vrserver.txt 의 트레이스에서 `Beginning remapping from controller type: knuckles to controller type: oculus_touch` 는 보였지만 **knuckles 측에 대한 binding 적용 완료 메시지는 없음**.

가능한 해석:
- (a) knuckles 는 `bindings_index.json` 의 controller_type 과 직접 일치 → remap 불필요 → 정상 binding 적용. 단, **로그에 명시적 "Successfully bound to knuckles" 메시지가 없음**
- (b) knuckles 측 binding 이 어떤 이유로 활성화 안 됨

우리 앱의 `_probe_openvr_skeletal()` 결과:
```
left: action_handle=0x1000718000000414
    getSkeletalActionData: bActive=False activeOrigin=0x0
    getSkeletalTrackingLevel FAILED: ValueError: invalid literal for int() with base 10: b'\x01\x00\x00\x00'
    getBoneCount=31
```

`getSkeletalTrackingLevel` 의 raw bytes `b'\x01\x00\x00\x00'` = **little-endian uint32 = 1 = "Partial"** ← pyopenvr 의 int() 변환이 실패한 거지, **실제 SteamVR 는 tracking_level=1 (Partial)** 로 응답함.

→ **이는 SteamVR 가 skeletal action 을 "어떤 device 에 binding 시킨 상태"** 라는 의미. 단, `bActive=False` + `activeOrigin=0x0` 이라 **현재 active source 가 없음**.

### 2.2 결정적 모순 (2.1 의 결과를 어떻게 해석할까)

`tracking_level=1 (Partial)` + `bActive=False` 의 조합은 SteamVR 의 binding 시스템에서 다음을 의미:
- SteamVR 는 binding 정의를 알고 있음 (그래서 tracking_level 응답 가능)
- 하지만 현재 어떤 active controller 도 그 binding 에 데이터를 흘리지 않음 (그래서 bActive=False)

해석:
- UDCAP knuckles 컨트롤러는 등록돼 있고 binding 도 알고 있지만,
- **UDCAP 가 그 컨트롤러에 skeletal data 를 emit 하지 않거나 (UDCAP 의 SteamVR-side driver_UDCAP 가 CreateSkeletonComponent 를 호출 안 함),**
- 또는 **컨트롤러 active 상태가 아닌 (idle / glove 와 paired 안 된)** 상태

UDCAP UI 에서 글러브가 "Connected" 라도 calibration 미완료 시 **finger sensor 데이터를 ignore 하면서 skeletal/finger 채널을 활성화 안 하는** 보호 동작 가능성이 있다 (UDCAP-Driver 가 v0.1.8.x 에서 도입한 안전 기능).

## 3. 사용자 영상 (research 38 분석) 과 본 로그의 모순 해소

영상에서 SteamVR Test Controller 화면이 양손 grip pull 시 정상 활성:
- 컨트롤러 visualizer: knuckles 모양 (LHR-E227UD40 으로 표시)
- Grip Pull bar: 채워짐 ✓
- Trigger Pull bar: 채워짐 ✓

본 로그에서 우리 앱이 받는 값:
- left: trigger=0.000 grip=0.000 finger_curls=[모두 0]
- right: 동일

### 3.1 모순의 정체

**SteamVR Test Controller 와 우리 앱은 다른 API 경로를 사용**:

| 경로 | API | 데이터 source |
|---|---|---|
| SteamVR Test Controller | Legacy `IVRSystem::getControllerState()` | UDCAP 가 emit 하는 raw axis state (controller_priority HIGH 모드 시 underlying oculus_touch 의 axis 를 borrow) |
| 우리 앱 | OpenVR Action Manifest API (`getDigitalActionData`, `getAnalogActionData`) | 우리가 정의한 `/actions/teleop/in/*` actions, controller_type 기반 binding 거쳐 도달 |

**즉, Test Controller 는 컨트롤러의 raw state 를 직접 읽지만, 우리 앱은 binding layer 를 거친다**.

영상에서 본 grip 활성은:
- 사용자가 PICO Touch 컨트롤러 (실물) 의 grip button 을 누름
- VD 가 oculus_touch 채널로 SteamVR 에 emit
- UDCAP 가 underlying controller 의 grip 을 borrow 해서 자기 LHR-E227UD40 의 raw state 에 set
- Test Controller 가 LHR-E227UD40 의 raw state 를 표시 → bar 채움
- **하지만 binding layer 거치지 않으므로 우리 앱에는 도달 안 함**

본 로그의 0:
- 우리 앱이 action API 로 `/actions/teleop/in/grip_left` 쿼리
- knuckles binding 의 grip 매핑은 `force_sensor` mode 로 정의
- 하지만 LHR-E227UD40 (UDCAP knuckles) 의 grip 은 **raw axis 만 있고 force_sensor channel 없음** (UDCAP_profile.json 에 force 채널 없음)
- 또는 oculus_touch 로 remap 된 binding 이 활성이지만, 사용자가 PICO Touch 를 잡고 있긴 한데 grip 만 누르지 trigger 는 안 누른 상태에서 logged → trigger=0 + grip=0 모두 0 으로 보임 (영상 시점과 로그 시점이 다름)

### 3.2 결과 해석

영상 시점: 사용자가 grip 누름 → Test Controller raw state 활성, UDCAP 가 underlying 으로 borrow.
본 로그 시점: 사용자가 손을 idle 또는 binding 적용 안 된 상태에서 grip 누름 → 우리 앱 0.

또 한 가지 가능성: 본 로그는 사용자가 grip 을 안 누른 상태로 30초 idle. 그러면 모두 0 인 게 정상. **사용자는 본 명령 실행 시 grip 을 안 눌렀을 가능성**.

→ 검증 방법: 본 명령 다시 실행하면서 30초간 양손 grip 을 누르고 release 반복. log 에서 `act_tgt > 0` 인 frame 이 있는지 확인.

## 4. UDCAP 측 데이터 흐름 진단 (VMC 와 finger curl 둘 다 0)

### 4.1 VMC packet=0 의 의미

`[GR1T2FourierUDCAPDevice][advance #100] VMC port=39539 bones_received=0 (waiting for first packet)`

UDCAP UI 의 `UdcapDriver.dll.config` 는:
```xml
<add key="VMC_State" value="True" />
<add key="VMC_PORT" value="39539" />
```

→ VMC 송신 활성. 하지만 우리 listener 가 packet 0 → **UDCAP 가 글러브 데이터를 받지 못해서 VMC 송신 자체를 안 하는 상태**.

### 4.2 가능한 원인 (우선순위 순)

| # | 원인 | 진단 |
|---|---|---|
| 1 | 글러브 캘리브레이션 미완료 | UDCAP UI 의 글러브 아이콘 → "Calibrated" 또는 "Calibration: F1" 라벨 확인 |
| 2 | 글러브 페어링 / 배터리 / FPS | UDCAP UI → Devices : 양 글러브 "Connected" + FPS > 30 + 배터리 OK |
| 3 | Controller_Priority HIGH 모드 + underlying oculus_touch 의 0-input | UDCAP UI → Settings → Controller Priority = LOW 로 변경 |
| 4 | UdcapDriver.exe 가 글러브 데이터를 못 받지만 SteamVR 와는 통신 OK | `python -X utf8 -m ust_ws.ust_fourier_260421.scripts.diagnose_udcap_dataflow` 실행 — Section 3 (vrserver.txt named pipe data count) 가 0 또는 매우 낮으면 글러브 → driver 단계 실패 |
| 5 | 글러브 RF dongle 이 USB 에 연결 안 됨 | UdcapDriver UI → Devices 에서 "USB dongle: Not detected" 표시 |

### 4.3 우리 앱이 이미 분석해둔 진단 가이드 (로그 발췌)

```
[GR1T2FourierUDCAPDevice] WARNING -- no SteamVR Input action

  VMC fallback: ENABLED but receiving NO packets on UDP 39539

    1. *** UDCAP NOT CALIBRATED ***

    3. Glove not actually connected -- UDCAP UI > Devices should

    4. UDCAP's VMC broadcast disabled or on a different port.  ...
```

→ 우리 코드의 진단 로직과 본 분석이 일치. **사용자 측에서 UDCAP UI 를 직접 확인** 해야 #1-5 중 어떤 게 원인인지 결정.

## 5. 코드 수정 — `bindings_oculus_touch.json` 추가 + `actions.json` `default_bindings` 확장

### 5.1 변경 1: `actions.json` 의 `default_bindings` 에 oculus_touch entry 추가

**Before** (현재):
```json
"default_bindings": [
    { "controller_type": "udcap",    "binding_url": "bindings_udcap.json" },
    { "controller_type": "knuckles", "binding_url": "bindings_index.json" }
]
```

**After** (수정):
```json
"default_bindings": [
    { "controller_type": "udcap",        "binding_url": "bindings_udcap.json" },
    { "controller_type": "knuckles",     "binding_url": "bindings_index.json" },
    { "controller_type": "oculus_touch", "binding_url": "bindings_oculus_touch.json" }
]
```

## 6. 사용자 측 조치 — UDCAP 글러브 데이터 도달

### 6.1 UDCAP UI 캘리브레이션 (가장 중요)

1. UdcapDriver.exe 가 떠있는지 확인 (시스템 트레이 아이콘)
2. 트레이 아이콘 우클릭 → "Open UDCAP" (또는 UI 자동 활성)
3. **Devices** 화면 :
   - 양 글러브 "Connected" 표시 ✓
   - FPS > 30 (보통 120 표시) ✓
   - 배터리 > 20% ✓
4. **Calibration** 화면 (또는 F1 단축키):
   - "Not Calibrated / Please Calibration" 표시되면 calibration 시퀀스 실행
   - Step 1: 양손 펴고 30 도 정도 손 들기 → "OPEN" 버튼 클릭
   - Step 2: 양손 주먹 쥐기 → "FIST" 버튼 클릭
   - Step 3: 손가락 하나씩 따로 굽혀가며 per-finger calibration
   - 완료 후 "Calibrated" 라벨 확인

### 6.2 Controller Priority 변경 (HIGH → LOW)

**우리가 이전 research/38, 39 에서 HIGH 권장한 게 잘못이었던 케이스**.  HIGH 모드의 동작:
- UDCAP 가 underlying physical controller (oculus_touch from VD) 의 axis state 를 borrow
- 그러면 사용자가 PICO Touch 의 trigger/grip 누르는 것은 받지만,
- 글러브의 sensor 데이터는 무시됨 (oculus_touch 의 axis 가 raw state 를 점유)

**LOW 모드의 동작**:
- UDCAP 가 글러브 sensor 데이터를 native 로 emit
- physical controller 의 axis state 는 무시 (또는 추가 layer 로만)

→ 사용자가 UDCAP 글러브의 finger sensor 를 진짜로 사용하려면 **LOW 모드** 가 맞음.

조치:
1. UDCAP UI → Settings → General (또는 Controller)
2. **Controller Priority: HIGH → LOW**
3. SteamVR + UdcapDriver 재시작

이 변경 후:
- VMC packet 이 도달 (UdcapDriver 가 finger sensor 데이터를 받아 UDP 39539 로 송신)
- 우리 앱의 path B fallback (VMC) 활성화
- 또는 UDCAP knuckles 의 skeleton/finger curl action 도 활성화 가능

### 6.3 (선택) PICO Touch 일시적 power off

여전히 underlying oculus_touch 가 글러브 input 을 mask 한다면, PICO Touch 컨트롤러 배터리 분리 또는 sleep:
- 컨트롤러를 30초 정도 가만히 두면 sleep mode (LED off)
- 그러면 SteamVR 의 oculus_touch device 가 사라짐
- UDCAP knuckles 만 active controller 로 남음
- 글러브 sensor 데이터가 그대로 SteamVR layer 에 도달

단점: 사용자가 trigger / button 도 눌러야 한다면 컨트롤러를 다시 깨워야 함.

### 6.4 (대안) gripper subproject 사용 (research/36)

만약 UDCAP 글러브 자체가 동작 안 하는 환경이라면:
- `ust_260504_win` (PICO Touch + 2-finger gripper) 로 전환
- 22-DoF Fourier hand 대신 단순 gripper
- 5-finger glove 데이터 불필요
- 즉시 동작 가능 (이미 research/36 에서 구현)
