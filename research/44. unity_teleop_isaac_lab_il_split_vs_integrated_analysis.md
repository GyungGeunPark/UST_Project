## 0. Executive Summary (1 분 요약)

| 결론 | 핵심 근거 |
|---|---|
| **사용자의 통증 대부분은 "Isaac Lab 시뮬레이션 자체"가 아닌 "VR I/O + USD 빌드 + Pink IK 특이사항"에 있다.** Unity로 옮긴다고 자동으로 해결되지 않는다. | memory.md 9개 세션 분석: 9개 issue 중 7개는 Isaac Sim USD 빌드 / SteamVR IPC / Pink IK 특이 버그 — Unity로 옮겨도 같은 문제는 다른 형태로 재발하거나 새로운 형태가 등장한다. |

| **장기적으로 "텔레오퍼레이션 인프라 분리" 자체는 가치 있는 방향성이지만, Unity가 아닌 "ROS2 hand_retarget abstraction" (Open TeleDex 패턴) 이 더 합리적.** | Unity는 게임 엔진 우선, robotics는 보조 카테고리 (URDF Importer는 단순 팔 위주, 휴머노이드 전용 모듈 없음). ROS2 추상화는 시뮬-실기 통합이 자연스러움. |

**한 줄 결론**: **Unity로 옮기지 말 것**. 9개 세션의 GR1T2+Robotiq+Pink IK+PICO Connect 인프라는 이미 산업 표준에 근접한 수준이다. 현재 통증은 마지막 통합 단계(SteamVR 안정성, USD 빌드 회귀 방지)에서 발생하는 것이며, Unity로 옮기면 sunk cost + sim-to-sim gap + 자산 중복 부담이 더 크다. 대신 **Newton 백엔드 활성화 → CloudXR 마이그레이션 → LeRobot v3 export 추가** 순으로 점진 개선하라.

## 1. 현재 상황 정확한 진단 (memory.md 9개 세션 통계 분석)

### 1.1 9개 세션의 issue를 카테고리로 분류

[ust_hm_grip/memory.md](../ust_hm_grip/memory.md) 를 카테고리별로 집계:

| 카테고리 | Issue 개수 | 비율 | Unity로 옮기면 해결되는가? |
|---|---|---|---|
| **VR I/O 파이프라인** (SteamVR IPC, PICO Connect, controller binding, OpenVR 초기화) | 3 | 33% | **부분적 ✓** — Unity XR Plug-in Manager + OpenXR plugin이 더 매끈하나, PICO Connect + 외부 mocap glove 의존성은 그대로 남음 |

| **UX/플랫폼 문제** (HIGH-priority UI freeze, PowerShell buffering) | 2 | 22% | **회피 ✓** — Unity Editor는 자체 main thread를 가지며 Windows process priority와 무관. 그러나 Unity Editor freeze는 다른 원인으로 발생 가능 (script reload, scene load) |

**총평**: Unity로 옮기면 **44% (USD 빌드)** + **22% (Pink IK)** + **22% (UX)** = 88%의 통증이 회피 가능. 그러나 **11% (closed-loop physics)** 는 회피 못하고, 동시에 **새로운 통증** (Unity ↔ Isaac Lab 데이터 변환, sim-to-sim gap, 자산 중복) 이 추가됨.

### 1.2 통증의 시간적 분포

memory.md를 시간순으로 보면:

- **2026-05-10 (Pink IK + IPC + UI freeze)**: 1 세션에서 5개 issue 동시 해결 → **시스템 통합 phase**
- **2026-05-13 (1st~3rd session)**: USD 빌드 / 시각 / 회전 / mount → **USD asset phase**
- **2026-05-13 (4th~8th session)**: instancing leak, mesh strip, drive 재적용 → **USD edge case phase**
- **2026-05-13 (9th session)**: closed-loop PD 발산 → **physics phase**

**관찰**: 통증의 80%가 **2일 안에 압축적으로 해결됨**. 9세션 동안 진전 속도가 매우 빠름. 이는 인프라가 거의 완성 상태에 도달했음을 의미하며, **Unity로 갈아탈 적절한 타이밍이 아님** (sunk cost를 폐기하기엔 진척도가 너무 높음).

### 1.3 향후 예상되는 통증 (즉, 사용자가 Unity로 도망가고 싶은 이유)

memory.md TODO 섹션 + claude.md "함정" 표를 보면 **아직 남은 검증**:

- [ ] GUI 시각 최종 확인 (palm-down 자세)
- [ ] XR 모드 텔레오퍼레이션 end-to-end
- [ ] TCP offset 캘리브레이션
- [ ] 실제 grasping 검증 (contact force, drop)
- [ ] PD gain 튜닝 (object drop 시 effort 증가)

이 5개 항목 중 **Unity로 옮기면 해결될 것** vs **Unity로 옮겨도 동일**:

| TODO | Unity에서 더 쉬운가? |
|---|---|
| GUI 시각 최종 확인 | ✓ Unity Editor scene view가 Isaac Sim보다 가볍고 빠름 |
| XR 모드 end-to-end | ✓ OpenXR plugin이 SteamVR custom path보다 매끈 |

**결론**: 남은 5개 TODO 중 2개는 Unity 유리, 1개는 동일, 2개는 Unity 불리. 마이그레이션 ROI가 명확하지 않다.

## 2. "Unity VR teleop + Isaac Lab IL" 분리 아키텍처 상세 분석

### 2.1 아키텍처 다이어그램

```
[사용자가 제안한 아키텍처]
사용자 (PICO 4 Ultra HMD + 컨트롤러)
  ↓
Unity XR Plug-in Manager + OpenXR Plug-in
  ↓ XR Controllers → Hand pose (6-DoF) + trigger/grip
Unity Animation Rigging / Final IK / VRIK
  ↓ Humanoid (Mecanim Avatar) IK target → 51 joint angles
Unity Articulation Body (PhysX 4.0)
  ↓ joint state @ Time.fixedDeltaTime (0.02s = 50 Hz)
Unity 측 데이터 export (custom JSON / CSV / HDF5)
  ↓ episode_XXXX.json
[변환 레이어 — 새로 구축 필요]
  ↓ Unity coord → Isaac Lab coord, Unity joint order → Isaac order
Isaac Lab Mimic / LeRobot 학습
  ↓ BC-RNN / Diffusion Policy / ACT
실기 GR1T2 또는 Isaac Lab evaluation
```

### 2.2 Unity 측에서 구현해야 할 것 (1차 추정)

| 컴포넌트 | 구현 난이도 | 기존 자산 활용도 | 예상 작업량 |
|---|---|---|---|
| **PICO 4 Ultra OpenXR 연결** | ★★ 쉬움 | Unity OpenXR Plug-in (공식) | 1-2일 |
| **GR1T2 URDF → Unity Avatar** | ★★★★ 어려움 | URDF Importer (Unity-Technologies) — **휴머노이드 Avatar 자동 변환 없음** | 5-7일 (수동 bone mapping + Avatar 설정) |
| **Robotiq 2F-85 ArticulationBody** | ★★★★★ 매우 어려움 | URDF에서 mimic 미지원 → 수동 PhysX joint motor 작성 | 7-10일 (4-bar linkage 안정화 = 9th session 의 문제 재현) |
| **Final IK + Avatar 휴머노이드 retargeting** | ★★★ 중간 | Final IK 에셋 (Asset Store $90) — VRIK 컴포넌트 사용 | 3-5일 (51-DoF GR1T2에 맞게 bone 설정) |
| **Wrist pose → arm IK target** | ★★ 쉬움 | VRIK가 head/hand target 자동 처리 | 1일 |
| **Grip/trigger → Robotiq close 명령** | ★★ 쉬움 | InputAction 시스템 | 1일 |
| **데이터 export (joint state @ 50 Hz)** | ★★★ 중간 | 수동 직렬화 코드 작성 | 2-3일 |
| **Unity coord → Isaac Lab coord 변환** | ★★★★ 어려움 | 좌표계 + joint convention 통일 필요 | 3-5일 |
| **Isaac Lab 측 import + replay** | ★★★ 중간 | 신규 import 스크립트 + Mimic compatibility 검증 | 3-5일 |

**총 예상 작업량**: 26-39일 (즉 **약 1-2개월**). 이는 현재 9개 세션 (≒ 2-3일) 의 거의 10배 작업량.

### 2.3 분리 아키텍처의 본질적 위험 — Sim-to-Sim Gap

[28번 리서치 §7](28.%20cross_simulator_teleop_data_pipeline_research.md) 에서 이미 다룬 핵심 위험:

> **수집 시뮬 (Unity PhysX 4.0)** 에서 사람이 텔레오퍼레이션으로 만든 trajectory가, **학습 시뮬 (Isaac Lab PhysX 5.x / Newton)** 에서 그대로 reproduce 되지 않을 가능성.

원인:
1. **Contact dynamics 차이**: Unity PhysX 4.0 Articulation은 Featherstone reduced-coordinate를 쓰지만 contact solver (PGS) 가 Isaac Sim의 TGS / Newton보다 덜 정확.
2. **Joint friction 모델 차이**: Unity는 단순 damping, Isaac Lab은 ImplicitActuatorCfg에 stiffness/damping/effort_limit 별도.
3. **Robotiq 4-bar linkage 표현 차이**: Unity는 mimic constraint 미지원 → joint motor + script 수동 sync 필요. Isaac Sim 5.1은 PhysxMimicJointAPI (known issue 있지만 hardware-accelerated).
4. **Action timing**: Unity Time.fixedDeltaTime 50 Hz vs Isaac Lab decimation 후 20 Hz — 데이터 sampling rate 불일치.

**결과**: 사용자가 Unity에서 "성공" 시범을 만들어도, Isaac Lab에서 imitation learning policy가 학습 후 평가에서 실패할 가능성. 이를 검증하려면 **양쪽 시뮬에서 동일 trajectory를 replay하는 sim-to-sim validation pipeline** 을 별도로 구축해야 함 — 추가 2-3주.

### 2.4 분리 아키텍처가 합리적인 경우 vs 비합리적인 경우

[28번 리서치 §9](28.%20cross_simulator_teleop_data_pipeline_research.md) 의 의사결정 기준 재인용:

#### 합리적인 경우 ✓
- 한쪽 시뮬의 throughput이 critical bottleneck (예: MuJoCo Warp는 PhysX 대비 313x 빠름)
- 수집할 데이터가 매우 많고 (수천 episode) sim throughput이 시간을 지배
- 다양한 robot/scene을 빠르게 prototyping해야 할 때

#### 비합리적인 경우 ✗
- 학습-수집 sim의 **물리 충실도 차이** 가 정책 정확도에 직접 영향
- 자산 변환 부담이 학습 가속분보다 클 때
- 한 시뮬에 이미 SOTA가 검증된 task

**우리 케이스 평가**:
- 수집 데이터양: 1-10 episode (사용자 본인 손으로 작성하는 텔레오퍼레이션) → throughput이 critical 아님
- 물리 충실도: Robotiq 4-bar linkage가 contact-rich → 분리 시 sim-to-sim gap 매우 큼
- 이미 Isaac Lab에서 GR1T2 + Robotiq 인프라가 9세션 만에 거의 완성
- → **분리 비합리적**

## 3. Unity가 정말 더 성숙한 영역인가? 객관적 비교

### 3.1 Unity의 robotics ecosystem 현황

Unity는 **게임 엔진 우선, robotics는 부차적**. [Unity Robotics Hub](https://github.com/Unity-Technologies/Unity-Robotics-Hub) 의 자산을 보면:

| 기능 | Unity Robotics Hub | 휴머노이드 적용 가능성 |
|---|---|---|
| URDF Importer | ✓ (Niryo One, UR5 등 단순 팔 위주) | △ — 휴머노이드 Avatar 자동 변환 없음 |
| ROS-TCP-Connector | ✓ (ROS1/ROS2 메시지 송수신) | △ — ROS2 인프라 필요 |
| ROS2 Foxy/Galactic 통합 | ✓ | △ |
| Articulation Body | ✓ (PhysX 4.0) | △ — Isaac Sim 5.x보다 features 적음 |
| Humanoid Mecanim Avatar | ✓ | ✓ (게임 캐릭터 기준, 로봇용 아님) |
| Pick & Place 튜토리얼 | ✓ | × (단순 팔만) |
| **휴머노이드 전용 모듈** | **✗ 없음** | - |

**중요한 점**: Unity Robotics Hub의 모든 공식 튜토리얼은 **단순 로봇 팔 (Niryo, UR)** 이며, **휴머노이드 + 다관절 그리퍼** 전용 reference가 없다. Unity에서 GR1T2 + Robotiq 2F-85를 구현하려면 처음부터 직접 작성해야 함.

### 3.2 Unity의 휴머노이드 VR teleop 사례

WebSearch 결과:

- **[Final IK / VRIK](https://assetstore.unity.com/packages/tools/animation/final-ik-14290)**: Asset Store 유료 ($90). VR 게임 캐릭터에 VRIK 적용 사례 많음 (Dead and Buried 2 등). 그러나 **로봇 articulation**이 아닌 **게임 캐릭터 (rigged mesh)** 용 — robot joint torque 제어와 직결 안 됨.
- **[leggedrobotics/unity_ros_teleoperation](https://github.com/leggedrobotics/unity_ros_teleoperation)**: Unity OpenXR → ROS2 일반 인터페이스. **휴머노이드 전용 아니며 단순 OpenXR 통신만**.
- **[Unity-Technologies/articulations-robot-demo](https://github.com/Unity-Technologies/articulations-robot-demo)**: Robotiq Hand-E (단일 prismatic 그리퍼) + UR5. **2F-85 (4-bar linkage) 가 아님**.

**대조적으로 Isaac Lab은**:
- [GR1T2 retargeter 공식 모듈](https://github.com/isaac-sim/IsaacLab) (`isaaclab.devices.openxr.retargeters.humanoid.fourier.gr1t2_retargeter`)
- [PickPlace-GR1T2-WaistEnabled 등 4개 내장 태스크](https://docs.isaacsim.omniverse.nvidia.com/)
- DexPilot YAML (Fourier 6-DoF hand 전용 retargeting)
- Manus Vive / OpenXR 통합 env_cfg
- Pink IK + NullSpacePostureTask (Isaac Lab 2.3 신규)
- [Newton physics integration](https://isaac-sim.github.io/IsaacLab/main/source/experimental-features/newton-physics-integration/index.html) 베타

**결론**: 휴머노이드 + 정밀 손가락 + VR teleop은 **Isaac Lab이 절대적으로 우세한 분야**. Unity는 단순 산업 팔까지만 성숙. 이미 [30번 리서치](30.%20humanoid_robot_teleop_alternatives_for_isaac_lab_ko.md) 에서 "GR1T2 + Fourier 6-DoF hand가 2026-04 시점 유일한 Ready 풀스택" 이라고 결론.

### 3.3 Unity Articulation Body vs Isaac Sim PhysX 5.x

| 기능 | Unity Articulation Body (PhysX 4.0) | Isaac Sim PhysX 5.x |
|---|---|---|
| Featherstone reduced coord | ✓ | ✓ |
| TGS contact solver | ✓ | ✓ |
| Mimic joint constraint | **✗ 미지원** (수동 script sync) | ✓ (PhysxMimicJointAPI, 5.1 known issue 있지만 H/W 가속) |
| Articulated soft body | ✗ | ✓ (5.x deformable) |
| Newton backend | ✗ | ✓ (Isaac Lab 3.0 beta) |
| GPU 가속 시뮬 | 부분 | ✓ (PhysX GPU) |
| 다중 인스턴스 (RL 환경) | △ (한 씬 안에 여러 prefab) | ✓ (cloned environments, GridCloner) |
| MotorAPI 세밀 제어 | 기본만 (stiffness/damping) | ImplicitActuator / ExplicitActuator 풍부 |

**Robotiq 2F-85 같은 4-bar linkage는 Unity에서 어떻게?**:
- Unity는 mimic 미지원 → 매 FixedUpdate 에서 script로 follower joint 의 target position을 lead 의 angle × gear ratio 로 수동 설정.
- 그러나 **9th session 에서 발견한 closed-loop linkage 의 PD 솔버 발산** 은 Unity에서도 동일하게 발생. Unity의 articulation body 는 Isaac Lab 같은 advanced damping 옵션이 적어 더 어려울 가능성 큼.

**결론**: Unity로 옮기면 USD 빌드 통증은 회피하지만, **closed-loop physics는 더 어려워짐**.

## 6. 옵션 B (Unity 분리) 가 합리적이 되려면? — Steel-man 분석

사용자의 제안을 무조건 부정하지 않고, **어떤 조건 하에서 합리적이 되는지** 검토:

### 6.1 합리적이 되는 조건들

1. **사용자 본인이 Unity 개발 경험이 풍부하고 Isaac Sim 경험이 적을 때**
   - 현실: memory.md를 보면 사용자는 Isaac Lab을 9세션 동안 깊이 다뤄왔음 → 학습 곡선 부담이 Unity 쪽이 큼

2. **Unity 측에 이미 휴머노이드 + 다관절 그리퍼 reference가 있을 때**
   - 현실: Unity Robotics Hub에 휴머노이드 전용 모듈 없음. Unitree-Robotics 같은 robot vendor도 Unity는 보조 → 처음부터 구축

3. **데이터 수집 throughput이 critical bottleneck일 때**
   - 현실: 사용자는 본인 손으로 텔레오퍼레이션 → 1 episode = 30초~5분, throughput 무관

4. **Unity의 시각화 / 디버깅 UI가 결정적으로 우월할 때**
   - 현실: Unity Scene View는 가벼움 ✓. 그러나 Isaac Sim도 5.1에서 viewport 개선 + Newton 통합 시 더 빨라질 예정

5. **VR 사용자 경험 (haptic, comfort) 이 Unity에서 훨씬 좋을 때**
   - 현실: PICO 4 Ultra 자체의 OpenXR 지원이 어디서나 동일. Unity가 VR 게임 측면에서 성숙하지만 robotics teleop 에선 동일 OpenXR API

### 6.2 종합 평가

5개 조건 중 0개가 명확히 만족. **사용자의 제안은 "직관적으로 매력적"이지만 객관적 근거가 부족**.

### 6.3 만약 사용자가 정말 Unity로 가야 한다면?

극단적 시나리오 — Unity 도입이 필수라면:

1. **GR1T2 포기, 단순한 휴머노이드 (또는 단순 팔 + 손) 로 prototype 부터**
   - 예: UR5 + Robotiq 2F-85 (Unity의 articulations-robot-demo 차용)
   - 휴머노이드 전신은 일단 보류

2. **VR teleop 검증 후 Isaac Lab으로 자산 마이그레이션**
   - Unity scene + robot 정의를 URDF로 export
   - Isaac Lab에서 URDF importer 사용 (현재와 동일 경로)

3. **Sim-to-sim validation pipeline 구축**
   - 동일 trajectory를 Unity / Isaac Lab 양쪽에서 replay
   - joint angle / contact force / TCP world position 비교
   - 발산이 크면 정책 학습 불가

이 시나리오의 총 작업량: **2-3개월 추가**. 현재 9개 세션 완료 단계에서 reset 비용이 매우 큼.

   ```csharp
   }
   ```
3. 4-bar linkage closed-loop 안정성 검증 — **9th session의 PD 발산 문제 재발 예상**, Unity에선 lead-only PD가 ImplicitActuator 같은 추상화 없어 직접 PhysX joint motor 설정 필요

### A.3 Phase 3 — VR teleop wiring (1주)

1. XR Origin + XR Hands + XR Controllers 설정
2. VRIK avatar에 head/hand IK target 연결
3. PICO 컨트롤러 grip/trigger → InputAction → Robotiq close 명령
4. Controller pose → arm IK target (Unity 좌표계)

### A.4 Phase 4 — 데이터 export pipeline (1-2주)

1. 매 FixedUpdate 에서 robot state 직렬화:
   ```csharp
   public class TeleopRecorder : MonoBehaviour {
       public List<FrameData> frames = new();
       void FixedUpdate() {
           frames.Add(new FrameData {
               timestamp = Time.fixedTime,
               jointPositions = robot.GetJointPositions(),
               jointVelocities = robot.GetJointVelocities(),
               leftHandPose = leftController.transform,
               rightHandPose = rightController.transform,
               leftGrip = leftController.gripValue,
               rightGrip = rightController.gripValue,
           });
       }
   }
   ```
2. Unity 좌표계 (left-handed) → Isaac Lab (right-handed) 변환
3. JSON / HDF5 / Parquet export
4. Isaac Lab 측 import 스크립트 작성

### A.5 Phase 5 — Sim-to-sim validation (1-2주)

1. 동일 trajectory를 Unity와 Isaac Lab 양쪽에서 replay
2. Joint angle, TCP world position, contact force 비교
3. RMS error < 5% 이내면 imitation learning 가능, 그 이상이면 도메인 갭 fine-tuning 필요

### A.6 총 예상 작업량: **5-8주**

대비 옵션 A (Status Quo) 의 잔여 작업량: **1-2주**.

**ROI 비교**: Unity 경로는 옵션 A 대비 **3-5x 더 많은 작업** + sim-to-sim gap risk + 자산 중복 부담.
