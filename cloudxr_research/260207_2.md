# 로봇 시뮬레이터 심층 비교 분석: Isaac Sim/Lab 중심의 기술 아키텍처와 성능 평가

**RTX Pro 6000 GPU 환경에서 모바일 매니퓰레이터 + VR 원격조작 + 모방 학습 + ROS2 통합을 위한 최적 시뮬레이터를 선정하려면, 단일 "최고" 솔루션은 존재하지 않으며 워크플로우 단계별로 시뮬레이터를 조합하는 전략이 가장 현실적이다.** Isaac Sim + Isaac Lab은 GPU 병렬 학습, 포토리얼리스틱 렌더링, ROS2 네이티브 통합에서 가장 균형 잡힌 선택이지만, 모방 학습 프레임워크(ACT, Diffusion Policy) 생태계는 MuJoCo + LeRobot/Robomimic 조합이 압도적이다. ManiSkill3는 GPU 메모리 효율성에서 Isaac Lab을 **2~3배** 앞서며, Genesis는 멀티피직스 시뮬레이션에서 독보적이나 아직 초기 단계다. 사용자의 RTX Pro 6000(48GB VRAM)은 Isaac Lab에서 **4,096~16,384개** 병렬 환경을 동시 실행할 수 있는 충분한 자원을 제공한다.

## 제1부: Isaac Sim + Isaac Lab 대비 시뮬레이터 상세 비교

### 1. 물리 시뮬레이션 성능과 GPU 병렬화 역량

Isaac Sim + Isaac Lab의 핵심 강점은 **PhysX 5 GPU 가속 물리 엔진**과 Direct-GPU API를 통한 제로카피(zero-copy) CUDA 텐서 접근이다. 단일 RTX 4090에서 상태 기반(state-based) 시뮬레이션 시 약 **700,000 steps/s**(Ant 태스크, 4,096 환경), 8×RTX Pro 6000 분산 학습에서 최대 **200만 steps/s**에 도달한다. 그러나 이 수치는 렌더링을 포함하지 않은 것이며, RTX 레이트레이싱 카메라를 활성화하면 성능이 크게 하락한다.

| 시뮬레이터 | 물리 엔진 | 상태 기반 FPS (단일 GPU) | GPU 병렬 환경 수 | GPU 메모리 (4,096 envs) | 렌더링 포함 FPS |
|:---|:---|:---|:---|:---|:---|
| **Isaac Sim + Isaac Lab** | PhysX 5 (TGS) | ~700K (Ant) | 4,096~16,384 | ~6.1GB (로코모션) | ~20K~60K/GPU (RTX) |
| **MuJoCo MJX** | 볼록 최적화 (JAX) | ~950K (A100, 8,192 envs) | 4,096~8,192 | JAX 관리 | Madrona 배치 렌더러 |
| **MuJoCo Warp** | MuJoCo-Warp (CUDA) | MJX 대비 **70~100×** | 수천 개 | nconmax 의존 | 개발 중 |
| **ManiSkill3** | PhysX 5 (SAPIEN) | ~200K+ | 128~수천 | **3.5GB** (128 envs) | **30K+ FPS** (래스터) |
| **Genesis** | 자체 솔버 (Taichi) | 43M (단순 씬)* | 수천 개 | Taichi 관리 | ~10× 실시간 |
| **OmniGibson** | PhysX 5 (Omniverse) | 서브 실시간 | 제한적 병렬 | 높음 (RTX 의존) | <10 FPS (Flatcache 미사용) |
| **Robosuite** | MuJoCo (CPU) | 수백 FPS | 불가 (CPU 단일) | 최소 | CPU 렌더링 |
| **Gazebo** | DART/ODE/Bullet (CPU) | 6~10× 실시간 | 불가 | CPU 의존 | OGRE2 |
| **CoppeliaSim** | MuJoCo/ODE/Bullet/Vortex (CPU) | Gazebo 대비 낮은 CPU 사용 | 불가 | CPU 의존 | OpenGL 2.1 |
| **Webots** | ODE 포크 (CPU) | 양호한 실시간 | 불가 | CPU 의존 | OpenGL 3.3 |

> *Genesis의 43M FPS 수치는 **자가 충돌이 비활성화된 단일 Franka 암 + 평면** 최소 씬에서의 상태 전용 시뮬레이션 값이다. UC San Diego 연구팀의 독립 분석(2024.12)에서 실제 매니퓰레이션 태스크(FrankaPickCube)에서는 ManiSkill/SAPIEN 대비 **3~10배 느린** 것으로 확인되었다.

**GPU 메모리 효율성**은 ManiSkill3가 두드러진다. 동일 Cartpole 태스크에서 128개 병렬 환경 기준 ManiSkill3는 **3.5GB**, Isaac Lab은 **14.1GB**를 사용하여 약 **4배** 차이가 난다. 이는 SAPIEN의 경량 Vulkan 래스터라이제이션과 Isaac Sim의 RTX 레이트레이싱 렌더링 파이프라인 차이에서 비롯된다. RTX Pro 6000의 48GB VRAM에서 Isaac Lab은 대규모 로코모션 태스크(4,096 envs)에 약 6.1GB, 카메라 기반 태스크(1,024 envs)에 약 16.7GB를 사용하므로 충분한 여유가 있다.

**렌더링 성능**에서는 단일 환경 기준 MuJoCo의 네이티브 OpenGL 렌더러가 **2,263 RGB FPS**(RTX 4090)로 가장 빠르며, Isaac Sim의 레이트레이싱은 **182 FPS**로 가장 느리지만 **시각적 품질은 최고 수준**이다. SAPIEN(ManiSkill3)는 래스터라이제이션으로 **1,176 FPS**를 달성하며 속도와 품질의 균형을 제공한다.

### 2. 구축 난이도와 학습 곡선의 현실적 비교

시뮬레이터 선택에서 가장 과소평가되는 요소가 **설치 복잡도와 디버깅 용이성**이다. Isaac Sim + Isaac Lab은 가장 강력한 기능을 제공하지만, 초기 진입 장벽도 가장 높다.

**Isaac Sim의 설치**는 2025년 오픈소스화 이후 크게 개선되었으며, `pip install "isaacsim[all,extscache]==5.1.0"` 명령으로 설치 가능하다. 그러나 첫 실행 시 셰이더 컴파일에 **수 분~10분**이 소요되고, 이후에도 **10~30초**의 시작 시간이 필요하다. Ubuntu 22.04가 주 지원 플랫폼이며, 24.04는 GCC/G++ 11이 필요한 제한적 지원 상태다. Docker 컨테이너(`nvcr.io/nvidia/isaac-lab:2.3.0`)가 가장 안정적인 설치 경로다.

**의존성 관리** 측면에서 MuJoCo가 가장 단순하다. 핵심 라이브러리가 `pip` 패키지에 포함되어 별도 바이너리 설치가 불필요하며, 렌더링도 EGL(헤드리스) 또는 OSMesa(소프트웨어)로 GPU 없이 작동한다. 반면 Isaac Sim은 NVIDIA RTX GPU(최소 RTX 2070, 권장 RTX 4090/Pro 6000), CUDA 12.4+, 특정 Ubuntu 버전 등 **가장 엄격한 하드웨어 요구사항**을 갖는다. ManiSkill3는 Vulkan 드라이버 의존성으로 인해 Docker/클러스터 환경에서 설정 문제가 발생할 수 있다.

**커스텀 로봇 모델 통합**에서 Isaac Sim은 URDF, MJCF, OnShape, CAD 포맷 모두를 USD로 변환하는 내장 임포터를 제공하여 **가장 폭넓은 포맷 지원**을 보인다. MuJoCo는 URDF 직접 로딩을 지원하지만 MJCF가 네이티브이므로 복잡한 로봇 모델은 MJCF로 변환해야 최적 성능을 얻을 수 있다.

## 제2부: 각 시뮬레이터의 내부 구조와 원리

### 4. 물리 엔진 아키텍처의 근본적 차이

로봇 시뮬레이션의 물리 정확도와 성능은 **접촉 역학(contact dynamics) 솔버의 수학적 정형화**에 의해 결정된다. 주요 시뮬레이터들은 크게 세 가지 접근법을 사용한다.

**MuJoCo의 볼록 최적화 접근법 (Convex Optimization)**

MuJoCo는 대부분의 물리 엔진이 사용하는 LCP(Linear Complementarity Problem)를 의도적으로 피한다. 마찰이 있는 접촉의 LCP 정형화는 **NP-hard** 문제이므로, MuJoCo는 엄격한 상보성(complementarity) 제약을 제거하고 접촉 해상도를 **볼록 최적화 문제**로 축소했다. 접촉 임펄스는 비관통(non-penetration)과 마찰 원뿔(friction cone) 제약 하에서 접촉 공간의 운동 에너지를 최소화한다.

세 가지 솔버 알고리즘이 제공된다:
- **Newton** (기본값, v1.50+): 해석적 2차 도함수를 사용하는 정확한 Newton 법, Hessian의 Cholesky 분해와 정확한 라인 서치. RL 워크로드에서 종종 **1회 반복**만으로 수렴
- **CG (Conjugate Gradient)**: Polak-Ribière-Plus 공식의 비선형 켤레 기울기법
- **PGS (Projected Gauss-Seidel)**: 쌍대 정형화(dual formulation)로 작동, 다른 엔진에서 가장 흔한 알고리즘

시간 적분은 **4가지 방법**을 지원한다: 반암시적 오일러(Semi-implicit Euler), `implicitfast`(권장, 속도 의존력에 대한 암시적 적분), `implicit`(완전 암시적), RK4(4차 Runge-Kutta). `implicitfast`가 안정성-성능 절충의 최적점이다.

**PhysX 5의 TGS 솔버 (Isaac Sim, ManiSkill3, OmniGibson)**

PhysX 5는 **Temporal Gauss-Seidel(TGS)** 비선형 반복 솔버를 기본 사용한다(solver_type=1). PGS도 제공되지만 TGS가 강력히 권장된다. 기본 위치 반복(position iteration) 4회, 속도 반복(velocity iteration) 1회. Featherstone 기반 아티큘레이션 솔버로 다관절 로봇을 처리하며, 미믹 조인트, 폐루프 기구학 체인, 필터링된 접촉 리포팅을 지원한다. 시간 적분은 **반암시적 오일러(symplectic Euler)**를 사용한다.

접촉 파라미터는 세밀하게 설정 가능하다: 접촉 오프셋(기본 0.02m), 정지 오프셋(0.01m), 바운스 임계 속도(0.2 m/s), 마찰 오프셋 임계값(0.04m). 순응적(spring-damper) 접촉 역학도 지원된다. 마찰/반발 결합 모드는 average < min < multiply < max 우선순위를 따른다.

**Genesis의 멀티피직스 통합 (Taichi 기반)**

Genesis는 **6가지 독립 솔버**를 하나의 프레임워크에 통합한 독특한 아키텍처를 갖는다:

```
┌──────────────────────────────────────────────────────┐
│                Genesis 통합 물리 프레임워크              │
├─────────────┬──────────┬──────────┬─────────────────┤
│  강체 솔버   │  MPM     │  SPH     │  FEM            │
│ (Rigid Body) │(Material │(Smoothed │(Finite Element  │
│              │ Point    │ Particle │ Method)         │
│              │ Method)  │ Hydro.)  │                 │
├─────────────┼──────────┼──────────┼─────────────────┤
│  PBD        │ Stable   │ 솔버 간  │ Taichi GPU 컴파일│
│(Position-   │ Fluid    │ 양방향   │ → CUDA 커널     │
│ Based Dyn.) │ (연기)   │ 커플링   │                 │
└─────────────┴──────────┴──────────┴─────────────────┘
```

**MPM**은 모래, 점토, 변형체, 근육 시뮬레이션에, **SPH**는 유체, **FEM**은 탄성/변형 재료, **PBD**는 천과 연체, **Stable Fluid**는 연기/가스에 사용된다. 이 솔버들은 **양방향 커플링**으로 연결되어 로봇 팔이 물을 통과하며 변형체를 잡는 등의 다중 재료 상호작용을 단일 씬에서 시뮬레이션할 수 있다. Taichi가 Python 코드를 **GPU 커널로 JIT 컴파일**하여 CUDA, AMD, Apple Metal, CPU 백엔드를 지원한다.

**전통적 시뮬레이터의 물리 엔진**

| 시뮬레이터 | 물리 엔진 | 솔버 유형 | 접촉 모델 | 시간 적분 |
|:---|:---|:---|:---|:---|
| **Gazebo** | DART(기본)/ODE/Bullet/Simbody | DART: 일반화 좌표, LCP | 다양 (엔진별) | 반암시적 오일러 |
| **CoppeliaSim** | MuJoCo/ODE/Bullet/Vortex/Newton (5종) | 엔진별 상이 | 엔진별 상이 | 엔진별 상이 |
| **Webots** | ODE 포크 (단일) | PGS/Dantzig | 다면체 마찰 원뿔 근사 | 반암시적 오일러 |

CoppeliaSim은 **5개 물리 엔진을 런타임에 드롭다운으로 전환**할 수 있는 유일한 시뮬레이터로, 동일 씬에서 엔진 간 동작 차이를 즉시 비교할 수 있다. Webots는 ODE 단일 엔진만 사용하지만 **48ms 시간 스텝까지 유효한 결과**를 산출하여 다른 시뮬레이터(MuJoCo: 3ms, Gazebo: 1ms)보다 넓은 시간 스텝 허용 범위를 보인다.

### 5. 렌더링 파이프라인의 기술적 스펙트럼

렌더링 파이프라인은 **래스터라이제이션(rasterization)**과 **레이트레이싱(ray tracing)** 두 축으로 나뉘며, 속도와 시각적 품질 간의 근본적 트레이드오프를 결정한다.

**Isaac Sim의 RTX 렌더링 파이프라인**은 NVIDIA OptiX 기반 하드웨어 가속 레이트레이싱을 사용하며, 실시간 경로 추적(path tracing), 반사, 굴절, 전역 조명(global illumination), MDL(Material Definition Language) 기반 물리 기반 재질을 지원한다. 병렬 환경 렌더링에는 **타일드 렌더링(tiled rendering)** 기법을 사용하여 다수의 카메라를 GPU 프레임버퍼의 공간 타일로 배치하고 단일 렌더 패스로 처리한다. DLSS(AI 업스케일링), DLAA, FXAA, TAA 안티앨리어싱과 DLSS Frame Generation을 지원한다. RL 태스크에서는 RTX 대신 물리 기반 레이캐스팅을 사용하는 **RayCasterCamera**가 단일 GPU에서 더 빠른 대안이 된다.

**MuJoCo의 네이티브 렌더러**는 **고정 함수 OpenGL 1.5**(호환성 프로파일)를 기반으로 C로 작성되었다. 현대적 셰이더를 사용하지 않지만, 모든 리소스를 GPU에 선행 업로드하여 드라이버 내부의 최적화된 셰이더를 활용하므로 **효율성은 현대 렌더러에 필적**한다. 두 단계로 분리된 파이프라인이 특징적이다: 추상 시각화(`mjv_` 접두사, 그래픽 독립)와 OpenGL 렌더링(`mjr_` 접두사). MuJoCo Playground의 **Madrona 배치 렌더러**는 CUDA 레이트레이서로 배치 비전 기반 정책 학습을 단일 GPU에서 가능하게 한다.

|:---|:---|:---|:---|:---|:---|
| **Isaac Sim** | Omniverse RTX | OptiX/RTX | ✅ 네이티브 HW 가속 | ✅ MDL | ✅ 타일드 렌더링 |

| **Genesis** | LuisaRender + 래스터 | 커스텀 DSL | ✅ LuisaRender | ✅ | 제한적 |
| **OmniGibson** | Omniverse RTX (상속) | OptiX/RTX | ✅ | ✅ MDL | Isaac Sim 수준 |

### 6. 소프트웨어 아키텍처 설계 패턴

각 시뮬레이터의 소프트웨어 아키텍처는 확장성, 유지보수성, 성능 특성을 근본적으로 결정한다.

**Isaac Sim + Isaac Lab의 레이어 구조**

```
┌─────────────────────────────────────────────┐
│           사용자 태스크/환경 정의              │
├─────────────────────────────────────────────┤
│  Isaac Lab (ManagerBased / Direct 워크플로우)  │
│  ┌──────────┬──────────┬──────────┐         │
│  │Observation│ Action   │ Reward   │ ...     │
│  │ Manager  │ Manager  │ Manager  │         │
│  └──────────┴──────────┴──────────┘         │
├─────────────────────────────────────────────┤
│  Tensor API Views (ArticulationView, etc.)  │
│  → Direct-GPU CUDA 텐서 (제로카피)           │
├─────────────────────────────────────────────┤
│  Isaac Sim (Omniverse Kit Extension)        │
│  ┌─────────────┬────────────┬──────────┐    │
│  │ PhysX 5 GPU │ RTX 렌더러 │ USD Stage│    │
│  │ (또는 Newton)│ (OptiX)   │ (Fabric) │    │
│  └─────────────┴────────────┴──────────┘    │
├─────────────────────────────────────────────┤
│  Omniverse Kit SDK + OpenUSD Runtime        │
└─────────────────────────────────────────────┘
```

**ManagerBased 워크플로우**는 환경을 ObservationManager, ActionManager, RewardManager, TerminationManager, CurriculumManager, CommandManager, EventManager로 분해한다. 각 매니저는 `@configclass` 데코레이터를 사용한 설정 클래스로 정의되며, 서로 다른 팀원이 독립적으로 작업할 수 있다. 오버헤드는 Direct 워크플로우 대비 **5% 미만**이다.

**Direct 워크플로우**는 모든 기능을 단일 클래스(`DirectRLEnv` 또는 `DirectMARLEnv`)에 구현하는 방식으로, JIT 트레이싱 최적화가 가능하고 초기 프로토타이핑에 적합하다. 다중 에이전트 RL은 **PettingZoo Parallel API** 기반의 `DirectMARLEnv`로 지원된다.

**USD(Universal Scene Description) 활용 방식**: 모든 씬 요소가 USD "프림(prim)"으로 표현되며, USDPhysics 스키마가 강체, 충돌, 조인트, 재질의 표준 기술을 확장한다. PhysX 특화 파라미터는 PhysxSchema로, MuJoCo 특화 파라미터는 MjcPhysics(Google DeepMind과 공동 개발 중)로 추가된다. Flatcache/Fabric 인터페이스를 활성화하면 USD 읽기/쓰기 연산을 우회하여 오버헤드를 감소시킬 수 있다. Fabric이 없으면 OmniGibson처럼 대규모 씬에서 프레임레이트가 **10 FPS 이하**로 떨어진다.

**PhysX와 Newton의 관계**: 이 둘은 **완전히 별개의 물리 엔진**이다. Newton은 2025년 GTC에서 NVIDIA, Google DeepMind, Disney Research가 공동 발표한 **오픈소스, GPU 가속, 미분 가능** 물리 엔진으로, NVIDIA Warp 기반이며 MuJoCo-Warp를 핵심 백엔드로 사용한다. Newton은 PhysX를 **대체하지 않으며** 공존한다. Isaac Lab 3.0(Isaac Sim 6.0 호환)에서 추상 기본 인터페이스(`Articulation`, `ContactSensor`)를 통해 두 엔진을 모두 플러그인 방식으로 지원할 예정이다. Newton에서 학습된 정책이 PhysX로 전이되어 **Unitree G1 실제 로봇**에 성공적으로 배포된 사례가 검증되었다.

**MuJoCo MJX의 JAX 병렬화**: MuJoCo의 시뮬레이션 알고리즘을 **JAX/XLA 프리미티브로 완전히 재구현**한 것으로, 래퍼가 아니다. `jax.vmap`으로 단일 디바이스에서 벡터화 배치 시뮬레이션, `jax.pmap`으로 멀티디바이스 병렬화를 수행한다. XLA 최적화(연산 퓨전, 상수 전파, 데드코드 제거, JIT 컴파일)를 자동으로 적용하며, JAX의 자동 미분(`vjp`/`jvp`)을 통해 **종단간 미분 가능** 시뮬레이션을 제공한다. NVIDIA GPU, AMD GPU, Apple Silicon, Google TPU에서 작동한다.

**ManiSkill3의 GPU 병렬화 구현**: 모든 병렬 환경을 **단일 PhysX 씬 내의 서브씬(sub-scene)**으로 배치하는 접근법을 사용한다. SAPIEN이 GPU 버퍼 할당과 서로 다른 DOF를 가진 아티큘레이션의 패딩을 관리한다. `Actor`, `Articulation`, `Link`, `Pose` 래퍼가 원시 GPU 버퍼 위에 배치 뷰를 제공하며, `.merge()` 함수로 서브씬 간 객체 뷰를 재구성할 수 있다. 이 **이질적 시뮬레이션(heterogeneous simulation)** 설계가 ManiSkill3의 핵심 혁신으로, 각 병렬 환경이 완전히 다른 씬, 객체, DOF를 가질 수 있다.

**Gazebo의 ECS 아키텍처**: 새로운 Gazebo(Harmonic/Ionic/Jetty)는 **Entity Component System**을 사용한다. 엔티티(Entity)가 씬 객체를 나타내고, 컴포넌트(Component)가 속성을 보유하며, 시스템(System)이 플러그인으로 동작한다. Entity Component Manager(ECM)가 쿼리와 업데이트를 관리한다. 물리, 렌더링, 센서가 모두 독립 시스템으로 구현되어 모듈 교체가 자유롭다. 클라이언트-서버 분리 구조에서 Gazebo Transport(ZeroMQ + Protobuf)로 통신한다.

### 7. GPU 병렬화 구현 방식의 기술적 차이

GPU 병렬화 방식은 시뮬레이터의 성능 특성을 결정하는 가장 중요한 아키텍처 결정이다.

| 시뮬레이터 | GPU 병렬화 기술 | 데이터 관리 | 미분 가능성 |
|:---|:---|:---|:---|
| **Isaac Lab (PhysX)** | PhysX 5 Direct-GPU API → CUDA 텐서 | Replication API로 프로토타입 복제 | ❌ |
| **Isaac Lab (Newton)** | NVIDIA Warp → CUDA 커널 | Warp 텐서 | ✅ (Warp 기반) |
| **MuJoCo MJX** | JAX/XLA → `jax.vmap`/`jax.pmap` | JAX DeviceArray | ✅ (JAX autodiff) |
| **MuJoCo Warp** | NVIDIA Warp → CUDA 커널 | Warp 텐서 | 검토 중 |
| **ManiSkill3** | PhysX 5 단일 씬 서브씬 분할 | SAPIEN GPU 버퍼 + 패딩 | ❌ |
| **Genesis** | Taichi → GPU 커널 JIT 컴파일 | Taichi 필드 | ✅ (부분적: MPM, Tool) |
| **Gazebo/CoppeliaSim/Webots** | ❌ CPU 전용 | CPU 메모리 | ❌ |

Isaac Lab의 PhysX 5는 **Direct-GPU API**를 통해 시뮬레이션 상태와 제어 데이터를 GPU 메모리에서 직접 읽고 쓸 수 있는 CUDA 텐서를 발행한다. 이는 CPU-GPU 데이터 전송 병목을 완전히 제거한다. 환경 복제는 **Replication API**로 프로토타입 환경을 수천 개의 병렬 인스턴스로 효율적으로 복제한다. Newton은 NVIDIA Warp를 기반으로 하여 CUDA 가속 시뮬레이션과 **미분 가능 물리**를 동시에 제공한다. MuJoCo-Warp 솔버는 CPU MuJoCo 대비 인간형 로봇 시뮬레이션에서 **70배**, 인핸드 매니퓰레이션에서 **100배** 속도 향상을 달성했다.

### 8. 커뮤니티 생태계와 산업 채택 현황

시뮬레이터의 장기적 생존력은 학술 인용, GitHub 활동성, 산업 채택에 의해 결정된다.

MuJoCo가 학술 인용 **4,884회**, GitHub 스타 **~11,900개**로 연구 커뮤니티에서 압도적 위치를 차지한다. 2021년 무료화, 2022년 오픈소스화 이후 RL/IL 연구의 사실상 표준이 되었다. **MuJoCo Menagerie**는 UR5e, Franka, Unitree, Shadow Hand 등 고품질 로봇 모델 컬렉션을 제공한다.

Gazebo는 학술 인용 **3,949회**로 ROS 생태계에서 16년간 **사실상 표준 시뮬레이터** 역할을 해왔다. DARPA Robotics Challenge, NASA Space Robotics Challenge 등 주요 로봇 대회에서 사용되었다. 다만 Intrinsic의 Open Robotics 상업 부문 인수(2022) 이후 개발 속도에 대한 우려가 존재하며, OSRF가 오픈소스 프로젝트를 계속 관리한다.

Isaac Sim + Isaac Lab은 GitHub 스타 **~5,400개**(Isaac Lab)로 급성장 중이며, NVIDIA의 GR00T 로봇 파운데이션 모델 플랫폼의 핵심 프레임워크다. Foxconn, BMW 등 제조업 파트너십을 통해 산업 채택이 확대되고 있다. 2025년 오픈소스화는 커뮤니티 성장의 전환점이 되었다.

## 결론: 연구 파이프라인에 맞춘 전략적 선택

이 비교 분석에서 도출되는 핵심 인사이트는 **단일 시뮬레이터로 모든 요구사항을 충족하는 것이 불가능하다**는 점이다. 모바일 매니퓰레이터 + VR 원격조작 + 모방 학습 + ROS2의 교차점에서 각 시뮬레이터의 강점이 서로 다른 파이프라인 단계에 위치한다.

**데이터 수집(VR 원격조작)** 단계에서는 Isaac Sim의 CloudXR + Meta Quest 3S 조합이 가장 직접적인 경로이며, Open-Teach + MuJoCo 기반 시뮬레이션(LIBERO)이 더 성숙한 대안이다. **모방 학습(ACT/Diffusion Policy)** 단계에서는 Robosuite + Robomimic 또는 LeRobot + MuJoCo가 알고리즘 다양성과 검증된 파이프라인 면에서 우세하지만, Isaac Lab Arena를 통해 Isaac Lab 환경에서도 LeRobot 정책을 학습할 수 있다. **대규모 GPU 병렬 학습**에서는 Isaac Lab(PhysX/Newton)과 ManiSkill3가 최적이며, RTX Pro 6000의 48GB VRAM을 최대한 활용할 수 있다. **실제 로봇 배포(ROS2)** 단계에서는 Gazebo가 여전히 가장 안전한 선택이며, Isaac Sim의 ROS2 브리지도 실용적 수준에 도달했다.

향후 주목할 기술 동향은 **Newton 물리 엔진의 성숙**(PhysX와 MuJoCo의 장점을 결합한 미분 가능 GPU 물리), **LeRobot 생태계의 확장**(시뮬레이터 독립적 모방 학습 표준화), 그리고 **Genesis의 멀티피직스 역량이 매니퓰레이션 성능 검증을 통과하는지** 여부다. RTX Pro 6000 사용자에게 **가장 미래 지향적인 선택은 Isaac Lab + Newton**이며, **가장 즉시 생산적인 선택은 MuJoCo + LeRobot + Gazebo 스택**이다.
