## 1. 시스템 전체 구성 이해

### 1.1 아키텍처 개요

│  ┌─────────────────────────────┐    ┌─────────────────────────────────┐    │
│  │  ① CloudXR Runtime Docker   │    │  ② Isaac Lab (Isaac Sim 5.1)    │    │
│  │     (컨테이너 또는 독립)      │    │     (컨테이너 또는 로컬)         │    │
│  │                             │    │                                 │    │
│  │  역할:                       │    │  역할:                          │    │
│  │  - VR 영상 스트리밍 서버     │◄──►│  - 물리 시뮬레이션 (PhysX)      │    │
│  │  - 핸드 트래킹 데이터 중계   │    │  - 로봇 렌더링/제어             │    │

│                 │                                                           │
│       ┌─────────┴─────────┐                                                │

                    │

         │                     │

         │  - 핸드 트래킹 입력  │
         │  - 스테레오 영상 표시 │

### 1.2 핵심 통신 메커니즘

| 구간 | 프로토콜 | 설명 |
|------|---------|------|
| CloudXR Runtime ↔ Isaac Lab | **유닉스 도메인 소켓** (IPC) | 같은 서버 내 프로세스 간 통신. `/openxr/run/ipc_cloudxr` 소켓 파일 사용 |
| CloudXR Runtime ↔ Quest 3S | **TCP/UDP** 네트워크 | TCP 48010 (시그널링), UDP 47998~48012 (비디오/오디오 스트리밍) |
| Isaac Lab → CloudXR Runtime | **OpenXR API** | Isaac Sim이 OpenXR 앱으로서 렌더링된 프레임을 CloudXR에 전달 |
| Quest 3S → CloudXR Runtime | **핸드 트래킹 데이터** | 손 관절 26개의 7D 포즈 (위치 3D + 쿼터니언 4D) |

## 2. openxr 폴더의 역할과 구조

### 2.1 왜 openxr 폴더를 생성하는가?

`openxr` 폴더는 **CloudXR Runtime과 Isaac Lab 사이의 유일한 통신 채널**입니다.

OpenXR 표준에서는 **OpenXR Runtime(서버)**과 **OpenXR Application(클라이언트)**이 분리되어 있습니다:

```
OpenXR Application (Isaac Lab/Isaac Sim)
    │
    │ "이 런타임 어디 있어?" → XR_RUNTIME_JSON 환경변수로 알려줌
    │ "이 런타임과 어떻게 통신해?" → XDG_RUNTIME_DIR에 있는 IPC 소켓으로
    ▼
OpenXR Runtime (CloudXR Runtime Docker)
    │
    │ 런타임이 시작되면서 /openxr 폴더에 다음을 생성:
    │   1. IPC 소켓 파일 (프로세스 간 통신용)
    │   2. OpenXR 매니페스트 JSON (런타임 위치 정보)
    │
```

**즉, `openxr` 폴더를 만드는 이유**:
1. CloudXR Runtime Docker 컨테이너가 **소켓 파일과 설정 파일을 생성할 장소**가 필요함
2. Isaac Lab이 **같은 파일을 읽어서 CloudXR Runtime을 찾을 수 있도록** 공유 마운트 포인트가 필요함
3. Docker 컨테이너끼리는 파일시스템이 분리되어 있으므로 **공유 볼륨**이 반드시 필요함

### 2.2 openxr 폴더 내부 구조

CloudXR Runtime Docker 컨테이너가 시작되면, 빈 `openxr` 폴더 안에 다음 파일들이 **자동 생성**됩니다:

```
openxr/                              ← 사용자가 빈 폴더로 생성
├── run/                             ← CloudXR Runtime이 자동 생성
│   └── ipc_cloudxr                  ← ★ 유닉스 도메인 소켓 파일
│                                       (Isaac Lab ↔ CloudXR IPC 통신)
└── share/                           ← CloudXR Runtime이 자동 생성
    └── openxr/
        └── 1/
            └── openxr_cloudxr.json  ← ★ OpenXR 런타임 매니페스트
```

#### `ipc_cloudxr` (유닉스 도메인 소켓)

- **타입**: 유닉스 도메인 소켓 파일 (`srwx------` 형태)
- **목적**: Isaac Lab(OpenXR 앱)과 CloudXR Runtime(OpenXR 런타임) 간 로컬 IPC 통신
- **동작**: CloudXR Runtime은 Monado 기반 OpenXR 런타임으로, 이 소켓을 통해 렌더링 프레임 전달, 트래킹 데이터 수신 등을 처리
- **헬스체크**: Docker Compose에서 `test -S /openxr/run/ipc_cloudxr`로 이 소켓 파일 존재 여부를 확인하여 런타임 준비 상태를 판단

#### `openxr_cloudxr.json` (OpenXR 런타임 매니페스트)

- **형식**: OpenXR 표준 런타임 매니페스트 JSON (Khronos Group 사양)
- **내용 예시**:
  ```json
  {
      "file_format_version": "1.0.0",
      "runtime": {
          "name": "NVIDIA CloudXR Runtime",
          "library_path": "/path/to/libopenxr_cloudxr.so"
      }
  }
  ```
- **목적**: Isaac Lab의 OpenXR 로더가 이 파일을 읽고, `library_path`에 지정된 CloudXR 런타임 라이브러리를 로드
- **환경변수 연결**: `XR_RUNTIME_JSON` 환경변수가 이 파일의 절대 경로를 가리킴

### 2.3 환경변수와 openxr 폴더의 매핑

| 환경변수 | 값 | 매핑 대상 |
|---------|-----|----------|
| `XDG_RUNTIME_DIR` | `/openxr/run` (Docker) 또는 `$(pwd)/openxr/run` (로컬) | IPC 소켓이 있는 디렉토리 |
| `XR_RUNTIME_JSON` | `/openxr/share/openxr/1/openxr_cloudxr.json` | OpenXR 런타임 매니페스트 파일 |

## 3. 실행 순서 총정리

### 3.1 핵심 원칙: CloudXR Runtime을 반드시 먼저 시작

```
순서 1: CloudXR Runtime Docker 컨테이너 시작
  → openxr 폴더에 소켓/JSON 생성됨
  → VR 클라이언트 연결 대기 상태

순서 2: Isaac Lab/Isaac Sim 시작 (XR 모드)
  → openxr 폴더의 JSON을 읽어 CloudXR 런타임 로드
  → IPC 소켓으로 CloudXR Runtime에 연결
  → 시뮬레이션 렌더링 프레임을 CloudXR에 전달

순서 3: VR 헤드셋에서 클라이언트 앱 실행
  → TCP 48010으로 서버에 연결
  → UDP로 스테레오 영상 수신
  → 핸드 트래킹 데이터를 서버로 전송
```

**왜 이 순서인가?**
- Isaac Lab이 시작할 때 OpenXR API를 초기화하는데, 이때 `XR_RUNTIME_JSON`이 가리키는 파일이 **이미 존재해야** 합니다
- CloudXR Runtime이 `ipc_cloudxr` 소켓을 생성해야 Isaac Lab이 **연결할 수 있습니다**
- 순서가 바뀌면 `XR_ERROR_INSTANCE_LOST` 또는 런타임 초기화 실패가 발생합니다

### 3.2 두 가지 실행 방법

| 방법 | 설명 | 난이도 |
|------|------|-------|
| **Option 1: Docker Compose (권장)** | CloudXR + Isaac Lab 컨테이너를 Docker Compose로 함께 관리 | 쉬움 |
| **Option 2: 수동 설정** | CloudXR Docker + Isaac Lab 로컬 실행을 별도로 구성 | 중간 |

## 5. Step 2: CloudXR Runtime Docker 설정 및 실행

### 5.1 Option 1: Docker Compose 방식 (권장)

Isaac Lab에서 제공하는 Docker Compose 파일을 사용하면 CloudXR Runtime과 Isaac Lab 컨테이너를 함께 관리할 수 있습니다.

```bash
cd /workspace/isaaclab

# CloudXR Runtime + Isaac Lab 컨테이너 시작
./docker/container.py start \
    --files docker-compose.cloudxr-runtime.patch.yaml \
    --env-file .env.cloudxr-runtime
```

**Docker Compose가 하는 일**:
1. `openxr-volume`이라는 **Docker 공유 볼륨**을 자동 생성
2. `nvcr.io/nvidia/cloudxr-runtime:5.0.1` 이미지로 CloudXR 컨테이너 시작
3. CloudXR가 `openxr-volume` 안에 IPC 소켓 + JSON 매니페스트 자동 생성
4. Isaac Lab 컨테이너가 `depends_on`으로 CloudXR 이후에 시작
5. Isaac Lab 컨테이너에 `XDG_RUNTIME_DIR`, `XR_RUNTIME_JSON` 환경변수 자동 설정

**Docker Compose 파일 구조** (`docker-compose.cloudxr-runtime.patch.yaml`):

```yaml
services:
  cloudxr-runtime:
    image: nvcr.io/nvidia/cloudxr-runtime:5.0.1
    ports:
      - "48010:48010/tcp"      # 시그널링
      - "47998:47998/udp"      # 미디어 스트리밍
      - "47999:47999/udp"
      - "48000:48000/udp"
      - "48005:48005/udp"
      - "48008:48008/udp"
      - "48012:48012/udp"
    healthcheck:
      test: ["CMD", "test", "-S", "/openxr/run/ipc_cloudxr"]  # 소켓 존재 확인
    volumes:
      - openxr-volume:/openxr:rw    # ★ 공유 볼륨

  isaac-lab-base:
    environment:
      - XDG_RUNTIME_DIR=/openxr/run                              # ★ IPC 소켓 경로
      - XR_RUNTIME_JSON=/openxr/share/openxr/1/openxr_cloudxr.json  # ★ 런타임 매니페스트
    volumes:
      - openxr-volume:/openxr:rw    # ★ 같은 공유 볼륨
    depends_on:
      - cloudxr-runtime             # ★ CloudXR가 먼저 시작

volumes:
  openxr-volume:                    # Docker 관리 볼륨
```

Isaac Lab 컨테이너 진입:

```bash
./docker/container.py enter base
```

### 5.2 Option 2: 수동 설정 방식

Isaac Lab을 **로컬에서 직접 실행**하고, CloudXR Runtime만 Docker로 실행하는 경우입니다.

#### Step 2-1: openxr 공유 디렉토리 생성

```bash
cd /workspace/isaaclab

# ★ 빈 openxr 폴더 생성 (CloudXR가 내부 파일을 자동 생성함)
mkdir -p $(pwd)/openxr
```

**이 시점에서 openxr 폴더는 비어 있습니다. CloudXR Runtime이 시작되면서 자동으로 내부 파일을 생성합니다.**

#### Step 2-2: CloudXR Runtime Docker 컨테이너 실행

```bash
# CloudXR Runtime 시작 (백그라운드에서 계속 실행됨)
docker run -it --rm --name cloudxr-runtime \
    --user $(id -u):$(id -g) \
    --gpus=all \
    -e "ACCEPT_EULA=Y" \
    --mount type=bind,src=$(pwd)/openxr,dst=/openxr \
    -p 48010:48010 \
    -p 47998:47998/udp \
    -p 47999:47999/udp \
    -p 48000:48000/udp \
    -p 48005:48005/udp \
    -p 48008:48008/udp \
    -p 48012:48012/udp \
    nvcr.io/nvidia/cloudxr-runtime:5.0.1
```

**명령어 해석**:

| 옵션 | 설명 |
|------|------|
| `--rm` | 컨테이너 종료 시 자동 삭제 |
| `--user $(id -u):$(id -g)` | 호스트 사용자 권한으로 실행 (소켓 파일 접근 권한) |
| `--gpus=all` | GPU 전체 사용 (그래픽 인코딩에 GPU 필요) |
| `-e "ACCEPT_EULA=Y"` | NVIDIA 라이선스 동의 |
| `--mount type=bind,src=$(pwd)/openxr,dst=/openxr` | **★ 호스트의 openxr 폴더를 컨테이너의 /openxr에 마운트** |
| `-p 48010:48010` | TCP 시그널링 포트 매핑 |
| `-p 47998-48012/udp` | UDP 미디어 스트리밍 포트 매핑 |

#### Step 2-3: 소켓 파일 생성 확인

```bash
# 새 터미널에서 확인
ls -la $(pwd)/openxr/run/
# 출력 예: srwxrwxrwx 1 user user 0 ... ipc_cloudxr

ls -la $(pwd)/openxr/share/openxr/1/
# 출력 예: -rw-r--r-- 1 user user ... openxr_cloudxr.json

# 소켓 파일 존재 여부 테스트
test -S $(pwd)/openxr/run/ipc_cloudxr && echo "OK: Socket exists" || echo "ERROR: Socket not found"
```

## 10. 자주 묻는 질문 (FAQ)

### Q1: openxr 폴더를 수동으로 만들어야 하나요? 안에 무엇을 넣어야 하나요?

**A**: `mkdir -p openxr` 로 **빈 폴더**만 만들면 됩니다. 내부 파일(`ipc_cloudxr` 소켓, `openxr_cloudxr.json`)은 CloudXR Runtime Docker 컨테이너가 시작될 때 **자동으로 생성**합니다. 사용자가 직접 파일을 넣을 필요가 없습니다.

Docker Compose를 사용하면 `openxr-volume`이라는 Docker 볼륨이 자동 생성되므로 폴더를 수동으로 만들 필요도 없습니다.

### Q2: CloudXR Runtime Docker를 먼저 실행하고, 그 다음 Isaac Sim을 실행하는 건가요?

**A**: 네, 맞습니다. **반드시 CloudXR Runtime이 먼저 실행**되어야 합니다.

- Docker Compose에서는 `depends_on: cloudxr-runtime`으로 순서가 자동 보장됩니다
- 수동 설정에서는 터미널 1에서 CloudXR를 먼저 시작하고, 터미널 2에서 Isaac Lab을 시작합니다
- CloudXR Runtime이 `ipc_cloudxr` 소켓을 생성해야 Isaac Lab이 연결할 수 있습니다

### Q3: CloudXR 없이 텔레오퍼레이션을 테스트할 수 있나요?

**A**: 네, 키보드나 SpaceMouse를 사용하면 CloudXR 없이 테스트할 수 있습니다:

```bash
# 키보드 제어 (VR 불필요)
./isaaclab.sh -p scripts/run_teleop.py --teleop_device keyboard

# SpaceMouse 제어 (VR 불필요)
./isaaclab.sh -p scripts/run_teleop.py --teleop_device spacemouse
```

### Q4: GPU가 여러 개인 경우 어떻게 하나요?

**A**: `NV_GPU_INDEX` 환경변수로 CloudXR가 사용할 GPU를 지정합니다:

```bash
export NV_GPU_INDEX=0  # 첫 번째 GPU 사용
```

CloudXR Runtime과 Isaac Lab이 **같은 GPU**를 사용해야 합니다.

### Q5: Quest 3S 대신 Apple Vision Pro를 사용해야 하나요?

**A**: NVIDIA와 Isaac Lab 팀이 **Apple Vision Pro를 공식 권장**합니다. Quest 3S를 사용하려면 CloudXR APK를 직접 빌드해야 하고, CloudXR 6.0+의 CloudXR.js 브라우저 방식은 아직 Early Access입니다. Apple Vision Pro는 공식 클라이언트 앱(`isaac-xr-teleop-sample-client-apple`)이 제공됩니다.

### Q6: Isaac Sim UI에서 AR Panel의 "Start AR"은 언제 누르나요?

**A**: Isaac Sim이 시작된 후, CloudXR Runtime이 이미 실행 중인 상태에서 누릅니다. `--teleop_device handtracking` 플래그를 사용하면 **자동으로 XR이 활성화**되므로 수동으로 Start AR을 누를 필요 없이 스크립트가 처리합니다.

## 11. 트러블슈팅

### 11.1 연결 문제

| 증상 | 원인 | 해결 |
|------|------|------|
| `XR_ERROR_INSTANCE_LOST` | CloudXR Runtime이 실행되지 않음 | Runtime Docker 재시작 |
| 검은 화면 (영상 없음) | GPU 인덱스 불일치 | `export NV_GPU_INDEX=0` |
| 48010 포트 연결 실패 | 방화벽 차단 | `sudo ufw allow 48010/tcp` |
| 높은 지연/끊김 | WiFi 환경 불량 | 5GHz WiFi 6 사용, 전용 라우터 |
| VR에서 손이 인식 안됨 | 핸드 트래킹 비활성화 | Quest 설정에서 핸드 트래킹 활성화 |

### 11.2 Docker 관련

```bash
# CloudXR 컨테이너 상태 확인
docker ps | grep cloudxr

# 컨테이너 로그 확인
docker logs cloudxr-runtime

# 소켓 파일 확인
ls -la openxr/run/ipc_cloudxr

# 컨테이너 강제 정리 (이전 실행이 남아있을 때)
docker stop cloudxr-runtime
docker rm cloudxr-runtime

# 전체 정리
docker system prune -f
```

### 11.3 연결 테스트

```bash
# TCP 시그널링 포트 테스트 (VR 클라이언트가 연결하는 포트)
nc -vz <서버IP> 48010
# 성공: "Connection to <ip> port 48010 [tcp/*] succeeded!"

# Isaac Lab에서 CloudXR 연결 테스트
# (소켓 파일 존재 확인)
test -S $XDG_RUNTIME_DIR/ipc_cloudxr && echo "CloudXR IPC OK" || echo "CloudXR IPC FAIL"
```

### 11.4 무시해도 되는 경고

- `XR_ERROR_VALIDATION_FAILURE: xrWaitFrame` - AR 모드 중지 시 레이스 컨디션
- `TF_PYTHON_EXCEPTION` - AR 진입/종료 시 발생
- `Invalid version string` - 구버전 USD 셰이더 호환성 경고
