## 문제 1: Docker 컨테이너 간 파일 권한 문제

### 현재 상황 분석

현재 `start_cloudxr_runtime.sh`에는 `--user "$(id -u):$(id -g)"` 옵션이 있습니다 (라인 74).
이 스크립트를 호스트의 `ubuntu` 사용자로 실행하면 CloudXR가 UID 1000(ubuntu)으로 파일을 생성합니다.

Isaac Lab 컨테이너는 **root (UID=0)**으로 실행되므로:
- 읽기: **가능** (644 퍼미션으로 누구나 읽기 가능)
- IPC 소켓 연결: **가능** (755 퍼미션)
- 쓰기: **불가** (소유자만 쓰기 가능)

**결론: 파일 권한 자체는 현재 큰 문제가 아닙니다.** 읽기 권한은 충분합니다.

### 그러나 완전한 권한을 주고 싶다면

CloudXR Runtime을 `--privileged` 또는 root 권한으로 실행하는 방법이 있습니다:

#### 방법 A: `--privileged` 플래그 (모든 권한 부여)

```bash
docker run -it --rm \
    --name ust-cloudxr-runtime \
    --privileged \
    --gpus=all \
    -e "ACCEPT_EULA=Y" \
    --mount "type=bind,src=/workspace/isaaclab/ust_ws/openxr,dst=/openxr" \
    -p 48010:48010 \
    -p 47998:47998/udp -p 47999:47999/udp -p 48000:48000/udp \
    -p 48005:48005/udp -p 48008:48008/udp -p 48012:48012/udp \
    nvcr.io/nvidia/cloudxr-runtime:5.0.1
```

`--privileged` 효과:
- 컨테이너에 호스트의 모든 디바이스 접근 권한 부여
- 모든 Linux capability 활성화
- seccomp, AppArmor 프로필 비활성화
- GPU 직접 접근 가능

#### 방법 B: root 사용자로 실행 (--user 제거)

`start_cloudxr_runtime.sh`의 `--user "$(id -u):$(id -g)"` 줄을 제거하면
CloudXR가 root(UID=0)로 실행되어 생성 파일도 root 소유가 됩니다.

```bash
docker run -it --rm \
    --name ust-cloudxr-runtime \
    --gpus=all \
    -e "ACCEPT_EULA=Y" \
    --mount "type=bind,src=/workspace/isaaclab/ust_ws/openxr,dst=/openxr" \
    -p 48010:48010 \
    -p 47998:47998/udp -p 47999:47999/udp -p 48000:48000/udp \
    -p 48005:48005/udp -p 48008:48008/udp -p 48012:48012/udp \
    nvcr.io/nvidia/cloudxr-runtime:5.0.1
```

#### 방법 C: 공유 폴더 권한을 777로 설정

```bash
# 호스트에서 실행
chmod -R 777 /workspace/isaaclab/ust_ws/openxr/
```

이렇게 하면 어떤 UID로 실행하든 모든 읽기/쓰기/실행 가능합니다.

#### 방법 D: Docker Compose에서 설정 (권장)

Docker Compose 파일에서 `user: "0:0"`을 추가하면 root로 실행됩니다:

```yaml
services:
  cloudxr-runtime:
    image: nvcr.io/nvidia/cloudxr-runtime:5.0.1
    user: "0:0"        # ← root로 실행
    privileged: true    # ← 모든 권한 부여 (선택)
    # ... 나머지 설정
```

### ★ 그러나 진짜 문제는 권한이 아닙니다

현재 에러의 실제 원인은 **파일 권한**이 아니라 다음 두 가지입니다:

1. **Isaac Lab 컨테이너에 `/openxr`가 마운트되지 않음**
2. **`XR_RUNTIME_JSON` 환경변수가 설정되지 않음**

## ★★★ 진짜 문제: Isaac Lab 컨테이너 실행 방식

### 핵심 진단

현재 Isaac Lab 컨테이너 내부에서 확인한 결과:

```
mount | grep openxr  →  결과 없음 (마운트 안 됨)
echo $XR_RUNTIME_JSON  →  빈 값
echo $XDG_RUNTIME_DIR  →  빈 값
ls /openxr/  →  /openxr not mounted in this container
```

**즉, Isaac Lab 컨테이너가 Docker Compose(`docker-compose.cloudxr-ust.patch.yaml`)를 통해 시작되지 않았습니다.**

Docker Compose를 사용하면 `isaac-lab-base` 서비스에서 자동으로:
- `/openxr` 볼륨 마운트
- `XDG_RUNTIME_DIR=/openxr/run` 설정
- `XR_RUNTIME_JSON=/openxr/share/openxr/1/openxr_cloudxr.json` 설정

이 모든 것이 빠져 있으므로, Isaac Lab 컨테이너가 **CloudXR patch 없이 시작된 것**입니다.

### 해결 방법 A: Docker Compose로 재시작 (★ 권장)

호스트에서 Isaac Lab + CloudXR를 함께 시작합니다:

```bash
# 호스트 터미널에서 실행 (Isaac Lab 컨테이너 밖)
cd /workspace/isaaclab

# 기존 컨테이너 중지 (필요 시)
./docker/container.py stop

# CloudXR + Isaac Lab 동시 시작
./docker/container.py start \
    --files ust_ws/260207_ust/docker-compose.cloudxr-ust.patch.yaml \
    --env-file docker/.env.cloudxr-runtime

# Isaac Lab 컨테이너 진입
./docker/container.py enter base
```

이렇게 하면:
- CloudXR Runtime이 먼저 시작 (healthcheck로 IPC 소켓 확인)
- Isaac Lab 컨테이너에 `/openxr` 자동 마운트
- 환경변수 자동 설정
- `depends_on: service_healthy`로 순서 보장

### 해결 방법 B: 현재 컨테이너에서 수동 설정 (임시)

이미 실행 중인 Isaac Lab 컨테이너에서 환경변수만 설정하는 방법입니다.

**단, `/openxr`가 마운트되지 않았으므로 호스트 경로로 직접 참조해야 합니다.**

현재 `./ust_ws/openxr`가 `/workspace/isaaclab/ust_ws/openxr`로 보이므로:

```bash
# Isaac Lab 컨테이너 내부에서 실행
export XDG_RUNTIME_DIR=/workspace/isaaclab/ust_ws/openxr/run
export XR_RUNTIME_JSON=/workspace/isaaclab/ust_ws/openxr/share/openxr/1/openxr_cloudxr.json
export NV_GPU_INDEX=0
export NV_PACER_FIXED_TIME_STEP_MS=11

# 또는 setup 스크립트 사용
source /workspace/isaaclab/ust_ws/260207_ust/setup_cloudxr_env.sh
```

**주의:** 이 방법은 `/openxr` 컨테이너 내부 경로가 아닌 호스트 바인드 마운트 경로를 사용합니다.
`ust_ws`가 이미 Isaac Lab 컨테이너에 마운트되어 있다면 작동합니다.

### 해결 방법 C: 실행 중인 컨테이너에 볼륨 추가 (불가)

Docker는 실행 중인 컨테이너에 새 볼륨을 추가할 수 없습니다.
컨테이너를 재시작해야 하므로, **방법 A가 가장 확실합니다.**

## 문제 2: Meta Quest 3S 클라이언트 앱이 로딩 후 바로 대기 화면으로 전환

### 증상

Quest 3S에서 CloudXR 클라이언트 앱 실행 → 로딩 화면 → 바로 메인(홈) 대기 화면으로 돌아감

### 원인 분석

이 증상은 CloudXR 클라이언트가 **서버에 연결하지 못했거나, 연결 후 세션이 즉시 종료**된 것을 의미합니다.

가능한 원인은 다음과 같습니다:

#### 원인 A: CloudXR Runtime Docker가 실행 중이지 않음 (가장 유력)

현재 확인 결과, Docker 접근이 불가하여 CloudXR 컨테이너 상태를 확인할 수 없었습니다.
서버에 CloudXR Runtime이 실행 중이지 않으면, Quest 클라이언트는 연결 실패 후 즉시 종료됩니다.

**확인 방법 (호스트 터미널에서):**
```bash
docker ps | grep cloudxr

# 결과가 없으면 CloudXR 미실행 → 시작 필요
```

#### 원인 B: 서버 IP 주소가 잘못됨

Quest 클라이언트에 입력한 서버 IP가 틀리면 연결 타임아웃 후 종료됩니다.

**확인 방법:**
```bash
# 서버의 IP 확인
hostname -I | awk '{print $1}'

# Quest에서 입력할 IP는 위 결과와 동일해야 함
# ★ 주의: Docker 컨테이너 내부 IP가 아닌 호스트의 외부 IP를 사용해야 함
```

#### 원인 C: 네트워크 문제 (방화벽/포트 차단)

TCP 48010 포트가 차단되어 있으면 Quest가 연결할 수 없습니다.

**확인 방법 (호스트에서):**
```bash
# TCP 48010이 리스닝 중인지 확인
ss -tlnp | grep 48010

# 방화벽 상태 확인
sudo ufw status

# 필요 시 포트 개방
sudo ufw allow 48010/tcp
sudo ufw allow 47998:48012/udp
```

#### 원인 D: Quest와 서버가 다른 네트워크 서브넷

Quest 3S와 서버가 같은 로컬 네트워크에 있어야 합니다.

**확인 방법:**
- 서버 IP: `192.168.1.xxx` 이면
- Quest IP도: `192.168.1.yyy` 이어야 함 (같은 서브넷)
- Quest Settings > Wi-Fi > 연결된 네트워크 > IP 주소 확인

#### 원인 E: CloudXR APK 버전 불일치

CloudXR SDK 버전과 Runtime 버전이 일치해야 합니다.
- Runtime: 5.0.1 (`nvcr.io/nvidia/cloudxr-runtime:5.0.1`)
- APK도: 5.0.1 SDK로 빌드해야 함

**확인 방법:**
- APK 빌드에 사용한 SDK 버전 확인
- SDK 4.x APK로 Runtime 5.x에 연결 불가

#### 원인 F: Quest 클라이언트 서버 IP 설정 방법

CloudXR Quest 앱은 여러 방식으로 서버 IP를 설정합니다:

**방법 1: 앱 내 직접 입력**
- CloudXR 앱 실행 시 서버 IP 입력 화면이 나타남
- 서버의 호스트 IP를 정확히 입력

**방법 2: `launch-options.txt` 파일 사용**
```bash
# Quest의 내부 저장소에 설정 파일 생성 (adb 사용)
adb shell mkdir -p /sdcard/CloudXR/
adb push launch-options.txt /sdcard/CloudXR/

# launch-options.txt 내용:
# -s <서버IP>
# 예: -s 192.168.1.100
```

**방법 3: adb 명령으로 직접 실행**
```bash
adb shell am start -n com.nvidia.cloudxr.ovr/.MainActivity \
    -e "cmd" "-s <서버IP>"
```

    │

    │
    ├── 미리스닝 → Docker 포트 매핑 확인
    │
    ▼

    │
    ▼
[Step 4] Quest CloudXR 앱에서 서버 IP 입력
    │
    ├── 대기화면 복귀 → 로그 확인 (Step 5)
    │
    ▼

### Quest 3S 로그 확인 (adb)

```bash
# Quest 3S를 USB로 연결하고 adb 로그 확인
adb logcat | grep -i cloudxr

# 주요 로그 패턴:
# "Connection refused"     → 서버 미실행 또는 포트 차단
# "Connection timed out"   → IP 오류 또는 네트워크 불통
# "Version mismatch"       → SDK 버전 불일치
# "Session created"        → 연결 성공 (이 후 문제는 서버 측)
```

## ★ 종합 해결 순서 (Step-by-Step)

아래 순서대로 따라가면 두 문제 모두 해결됩니다.

### Step 1: 호스트에서 CloudXR + Isaac Lab Docker Compose 실행

현재 문제의 근본 원인: Isaac Lab 컨테이너에 `/openxr` 볼륨이 마운트 되지 않았고, CloudXR 관련 환경변수가 없음

```bash
# ★ 호스트 터미널에서 실행 (Docker 컨테이너 밖에서)

cd /workspace/isaaclab

# 1. openxr 공유 폴더 권한 설정 (모든 컨테이너에서 접근 가능하도록)
chmod -R 777 ./ust_ws/openxr/

# 2. 기존 컨테이너가 있으면 중지
./docker/container.py stop 2>/dev/null || true

# 3. CloudXR Runtime + Isaac Lab 동시 시작
./docker/container.py start \
    --files ust_ws/260207_ust/docker-compose.cloudxr-ust.patch.yaml \
    --env-file docker/.env.cloudxr-runtime
```

### Step 2: CloudXR Runtime 정상 시작 확인

```bash
# 호스트에서 확인
docker ps | grep cloudxr

# 기대 결과:
# ust-cloudxr-runtime  nvcr.io/nvidia/cloudxr-runtime:5.0.1  Up X seconds (healthy)
#                                                              ^^^^^^^^^^^^^^^^
#                                                              healthy가 보여야 함

# healthy가 아니면 로그 확인
docker logs ust-cloudxr-runtime 2>&1 | tail -20

# IPC 소켓 생성 확인
test -S ./ust_ws/openxr/run/ipc_cloudxr && echo "✓ 소켓 OK" || echo "✗ 소켓 없음"
```

### Step 3: Isaac Lab 컨테이너 진입 및 환경 확인

```bash
# Isaac Lab 컨테이너 진입
./docker/container.py enter base

# 컨테이너 내부에서 확인
echo "XR_RUNTIME_JSON = $XR_RUNTIME_JSON"
echo "XDG_RUNTIME_DIR = $XDG_RUNTIME_DIR"

# 기대 결과:
# XR_RUNTIME_JSON = /openxr/share/openxr/1/openxr_cloudxr.json
# XDG_RUNTIME_DIR = /openxr/run

# /openxr 마운트 확인
ls -la /openxr/
# lib/  run/  share/  가 보여야 함

# IPC 소켓 확인
test -S /openxr/run/ipc_cloudxr && echo "✓ 소켓 접근 가능" || echo "✗ 소켓 접근 불가"

# 매니페스트 확인
cat /openxr/share/openxr/1/openxr_cloudxr.json
```

### Step 4: 서버 IP 확인 (Quest에서 연결할 주소)

```bash
# 호스트의 외부 IP 확인 (Docker 내부 IP가 아님!)
hostname -I | awk '{print $1}'

# 예: 192.168.1.100
# 이 IP를 Quest 3S에서 입력해야 함
```

### Step 5: TCP/UDP 포트 확인

```bash
# 호스트에서 포트 리스닝 확인
ss -tlnp | grep 48010       # TCP 시그널링
ss -ulnp | grep 47998       # UDP 미디어

# 둘 다 LISTEN 상태여야 함
# 안 보이면 Docker 포트 매핑 문제 → docker-compose 파일 확인

# 방화벽 확인 및 개방
sudo ufw status
sudo ufw allow 48010/tcp
sudo ufw allow 47998:48012/udp
```

1. Quest 3S 전원 켜기

## 만약 Docker Compose 방식을 사용하지 않는 경우 (수동 설정)

현재 Isaac Lab 컨테이너가 이미 실행 중이고 재시작하고 싶지 않다면:

### 수동 방법: CloudXR를 별도로 실행 + Isaac Lab에서 환경변수 설정

**터미널 1 (호스트):** CloudXR Runtime 시작

```bash
cd /workspace/isaaclab

# openxr 폴더 권한 설정
chmod -R 777 ./ust_ws/openxr/

# CloudXR Runtime 시작 (--privileged로 모든 권한 부여)
docker run -it --rm \
    --name ust-cloudxr-runtime \
    --privileged \
    --gpus=all \
    -e "ACCEPT_EULA=Y" \
    --mount "type=bind,src=$(pwd)/ust_ws/openxr,dst=/openxr" \
    -p 48010:48010/tcp \
    -p 47998:47998/udp -p 47999:47999/udp -p 48000:48000/udp \
    -p 48005:48005/udp -p 48008:48008/udp -p 48012:48012/udp \
    nvcr.io/nvidia/cloudxr-runtime:5.0.1
```

**터미널 2 (Isaac Lab 컨테이너 내부):** 환경변수 설정

```bash
# ★ 핵심: ust_ws/openxr이 이미 /workspace/isaaclab/ust_ws/openxr 로 보이므로
# 호스트 경로를 직접 사용

export XDG_RUNTIME_DIR=/workspace/isaaclab/ust_ws/openxr/run
export XR_RUNTIME_JSON=/workspace/isaaclab/ust_ws/openxr/share/openxr/1/openxr_cloudxr.json
export NV_GPU_INDEX=0
export NV_PACER_FIXED_TIME_STEP_MS=11

# 또는 간단히:
source /workspace/isaaclab/ust_ws/260207_ust/setup_cloudxr_env.sh

# 확인
echo "XR_RUNTIME_JSON = $XR_RUNTIME_JSON"
cat $XR_RUNTIME_JSON

# Isaac Lab 실행
./isaaclab.sh -p scripts/environments/teleoperation/teleop_se3_agent.py \
    --task Isaac-PickPlace-GR1T2-Abs-v0 \
    --teleop_device handtracking
```

## 부록 A: Docker 권한 옵션 비교표

| 옵션 | 효과 | 보안 수준 | 사용 시기 |
|---|---|---|---|
| `--user root` (기본) | root로 실행, 파일 root 소유 | 보통 | 일반 사용 |
| `--user $(id -u):$(id -g)` | 호스트 사용자로 실행 | 높음 | 호스트 파일 권한 유지 |
| `--privileged` | 모든 Linux capability + 디바이스 접근 | 낮음 | GPU/디바이스 직접 접근 필요 시 |
| `--cap-add=ALL` | 모든 Linux capability | 낮음 | privileged 대안 |
| `chmod 777` 공유 폴더 | 누구나 읽기/쓰기 가능 | 낮음 | 개발 환경 빠른 해결 |

### CloudXR Runtime에 추천하는 옵션 조합

```bash
docker run -it --rm \
    --name ust-cloudxr-runtime \
    --privileged \          # 모든 디바이스 접근 (GPU 포함)
    --gpus=all \            # NVIDIA GPU 접근
    --network=host \        # 호스트 네트워크 직접 사용 (포트 매핑 불필요)
    -e "ACCEPT_EULA=Y" \
    --mount "type=bind,src=$(pwd)/ust_ws/openxr,dst=/openxr" \
    nvcr.io/nvidia/cloudxr-runtime:5.0.1
```

> `--network=host` 를 사용하면 `-p` 포트 매핑이 불필요하며, Quest에서 호스트 IP로 직접 연결 가능합니다.
> 이는 Docker 네트워크 NAT 문제도 해결합니다.

## 부록 B: Quest 3S "로딩 후 대기화면 전환" 문제 체크리스트

| # | 확인 항목 | 확인 방법 | 정상 |
|---|---|---|---|
| 1 | CloudXR Runtime 실행 중 | `docker ps \| grep cloudxr` | `Up (healthy)` |
| 2 | TCP 48010 리스닝 | `ss -tlnp \| grep 48010` | LISTEN 표시 |
| 3 | 서버 IP 정확 | `hostname -I` | Quest에 입력한 IP와 동일 |
| 4 | 같은 네트워크 | Quest/서버 IP 비교 | 같은 서브넷 |
| 5 | 방화벽 개방 | `sudo ufw status` | 48010/tcp, 47998-48012/udp 허용 |
| 6 | SDK 버전 일치 | APK 빌드 버전 확인 | APK 5.x = Runtime 5.x |
| 7 | WiFi 5GHz | Quest WiFi 설정 | 5GHz 밴드 연결 |
| 8 | adb 로그 | `adb logcat \| grep cloudxr` | 에러 메시지 확인 |
| 9 | 서버 로그 | `docker logs cloudxr-runtime` | "Client connected" 확인 |

### 가장 흔한 원인 TOP 3

1. **CloudXR Runtime이 실행 중이지 않음** → Docker 시작
2. **서버 IP가 Docker 내부 IP** → 호스트의 외부 IP 사용
3. **방화벽이 TCP 48010 차단** → `ufw allow 48010/tcp`

## 부록 C: 전체 연결 점검 원스탑 스크립트

호스트 터미널에서 아래 스크립트를 실행하면 전체 시스템 상태를 한 번에 진단합니다:

```bash
#!/bin/bash
echo "=========================================="
echo "  VR 텔레오퍼레이션 전체 시스템 진단"
echo "  $(date)"
echo "=========================================="
echo ""

# 1. CloudXR Runtime Docker
echo "[1] CloudXR Runtime Docker"
CXR=$(docker ps --filter "name=cloudxr" --format "{{.Names}}: {{.Status}}" 2>/dev/null)
if [ -n "$CXR" ]; then
    echo "  ✓ $CXR"
else
    echo "  ✗ CloudXR 컨테이너 미실행 ← 시작 필요!"
fi
echo ""

# 2. Isaac Lab Docker
echo "[2] Isaac Lab Docker"
ISAAC=$(docker ps --filter "ancestor=nvcr.io/nvidia/isaac-sim" --format "{{.Names}}: {{.Status}}" 2>/dev/null)
if [ -z "$ISAAC" ]; then
    ISAAC=$(docker ps --filter "name=isaac" --format "{{.Names}}: {{.Status}}" 2>/dev/null)
fi
if [ -n "$ISAAC" ]; then
    echo "  ✓ $ISAAC"
else
    echo "  ? Isaac Lab 컨테이너 확인 필요"
fi
echo ""

# 3. OpenXR 파일
echo "[3] OpenXR 공유 파일"
OPENXR_BASE="./ust_ws/openxr"
test -S "${OPENXR_BASE}/run/ipc_cloudxr" && echo "  IPC 소켓:     ✓" || echo "  IPC 소켓:     ✗"
test -f "${OPENXR_BASE}/share/openxr/1/openxr_cloudxr.json" && echo "  매니페스트:    ✓" || echo "  매니페스트:    ✗"
test -f "${OPENXR_BASE}/lib/libopenxr_cloudxr.so" && echo "  라이브러리:    ✓" || echo "  라이브러리:    ✗"
test -f "${OPENXR_BASE}/run/runtime_started" && echo "  런타임 시작:   ✓" || echo "  런타임 시작:   ✗"
echo ""

# 4. 파일 권한
echo "[4] 파일 권한"
ls -la "${OPENXR_BASE}/run/ipc_cloudxr" 2>/dev/null | awk '{print "  소켓 권한: "$1" 소유자: "$3":"$4}'
ls -la "${OPENXR_BASE}/share/openxr/1/openxr_cloudxr.json" 2>/dev/null | awk '{print "  JSON 권한: "$1" 소유자: "$3":"$4}'
echo ""

# 5. 네트워크
echo "[5] 네트워크"
echo "  서버 IP: $(hostname -I | awk '{print $1}')"
ss -tlnp 2>/dev/null | grep 48010 > /dev/null && echo "  TCP 48010:    ✓ 리스닝" || echo "  TCP 48010:    ✗ 미리스닝"
ss -ulnp 2>/dev/null | grep 47998 > /dev/null && echo "  UDP 47998:    ✓ 리스닝" || echo "  UDP 47998:    ✗ 미리스닝"
echo ""

# 6. GPU
echo "[6] GPU"
nvidia-smi --query-gpu=name,memory.used,memory.total --format=csv,noheader 2>/dev/null || echo "  nvidia-smi 실행 실패"
echo ""

# 7. Isaac Lab 컨테이너 내부 환경변수 확인
echo "[7] Isaac Lab 환경변수 (컨테이너 내부)"
ISAAC_CONTAINER=$(docker ps --filter "name=isaac" --format "{{.Names}}" 2>/dev/null | head -1)
if [ -n "$ISAAC_CONTAINER" ]; then
    XR_JSON=$(docker exec "$ISAAC_CONTAINER" printenv XR_RUNTIME_JSON 2>/dev/null)
    XDG_DIR=$(docker exec "$ISAAC_CONTAINER" printenv XDG_RUNTIME_DIR 2>/dev/null)
    echo "  XR_RUNTIME_JSON = ${XR_JSON:-(미설정 ✗)}"
    echo "  XDG_RUNTIME_DIR = ${XDG_DIR:-(미설정 ✗)}"

    # /openxr 마운트 확인
    docker exec "$ISAAC_CONTAINER" test -d /openxr 2>/dev/null && \
        echo "  /openxr 마운트:  ✓" || echo "  /openxr 마운트:  ✗ ← Docker Compose로 재시작 필요!"
else
    echo "  Isaac Lab 컨테이너를 찾을 수 없음"
fi
echo ""

echo "=========================================="
echo ""
echo "[해결 순서]"
echo "  1. CloudXR Runtime 미실행 → 시작"
echo "  2. /openxr 미마운트 → Docker Compose로 재시작"
echo "  3. 환경변수 미설정 → source setup_cloudxr_env.sh"
echo "  4. 포트 미리스닝 → 방화벽 확인"
echo "  5. Quest 연결 실패 → 서버 IP + 네트워크 확인"
echo ""
```
